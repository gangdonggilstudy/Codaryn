# Codaryn 아키텍처

상태: 2026-11-12 Codex가 검토해 채택한 구현 전 설계다. 제품 코드는 아직 없다.
표기: **[확정]** 사용자 확정 요구, **[선택]** Codex가 채택한 설계 선택과 규칙, **[미정]** 결정 전 항목. 근거와 미정 목록은 [decisions.md](decisions.md)에 있다.

## 1. 목표와 설계 원칙

- [확정] 코딩 외에 문서 작성, 자료 분석, 파일 정리도 수행하는 범용 로컬 작업 에이전트다. CLI부터 만들고 Anthropic API를 먼저 연결한다. 코딩과 자기 소스 개발이 첫 작업 유형이다.
- [선택] 구현 언어는 TypeScript다. 공통 엔진은 Git 저장소나 코드 테스트를 전제로 삼지 않는다.
- [선택] 단일 프로세스 안의 로컬 모듈로 시작한다. 서버, 메시지 큐, 데몬, 플러그인 런타임, 다중 에이전트는 두지 않는다.
- [선택] 엔진은 하나다. CLI, GUI, IDE는 같은 엔진을 호출하는 어댑터이며 작업 논리를 갖지 않는다.
- [선택] 테스트 통과는 "해당 검증기가 확인한 범위에서 통과"만 뜻한다. 보안이나 정확성 전체를 보장한다고 표현하지 않는다.

## 2. 모듈 경계

| 모듈 | 책임 | 알지 못해야 하는 것 |
| --- | --- | --- |
| adapter (cli, 후속 gui·ide) | 입력 해석, 진행 표시, 확인 질문, 취소 신호 전달 | 모델 형식, 도구 구현 |
| engine | 작업 상태 기계, 모델↔도구 반복, 한도 집행 | 코딩 전용 개념(Git, 테스트 러너) |
| model | 제공자 중립 요청/응답과 Anthropic 구현 | 파일 시스템, 정책 |
| tools | 도구 등록과 실행, 표시 등급·요구 권한·복원 허용 필드 선언 | 모델 제공자 |
| policy | 도구 호출 허용/확인/거부 판정 | 모델 출력의 의도 해석 |
| privacy | 전송·기록 전 치환, 제한된 로컬 복원, 대응표 보관 | 작업 유형 |
| verify | 검증기 실행과 결과 기록 | 수정 방법 |
| store | 가림본 실행 기록(journal), 산출물 색인, 분리된 원문 복구 스냅샷 | 모델 제공자 |
| workflows/* | 작업 유형별 도구·검증기·프롬프트 묶음 | 다른 워크플로 내부 |

의존 방향은 adapter → engine → (model, tools, policy, privacy, verify, store)이다. workflows는 엔진에 등록되는 설정 묶음이고 엔진이 워크플로를 가져다 쓰지 워크플로가 엔진을 바꾸지 않는다.

## 3. 공통 계약

다섯 계약은 모든 작업 유형이 공유한다. 필드는 설계 수준이며 타입 정의는 단계 1에서 확정한다.

| 계약 | 핵심 내용 |
| --- | --- |
| Task | 목표, 워크플로 종류, 작업 공간(허용 루트 디렉터리), 입력 자료, 한도(반복·토큰·시간), 사용할 검증기, 정책 프로필 |
| Tool | 이름, 입력 스키마, 표시 등급, 요구 권한 목록, 복원 허용 필드, 멱등 여부, 실행기, 시간 제한 |
| Artifact | 종류(파일 변경·새 문서·보고서·패치), 위치, 내용 해시, 생성한 실행 ID |
| Verifier | 검사 대상, 방법, 결과(pass / fail / inconclusive), 근거, **검사하지 않는 범위** |
| Policy | 권한별 규칙(경로, 명령, 네트워크, 파괴적 동작)과 판정(허용·확인·거부), 한도 |

표시 등급 [선택]: `read`, `write-local`, `exec`, `external`은 사용자에게 보여 주고 기록을 분류하기 위한 이름이다. 허용 판단의 근거가 아니다. 허용 여부는 호출마다 아래 권한을 각각 검사해 정한다.

| 권한 | 검사 대상 |
| --- | --- |
| 경로 | 실효 경로(심볼릭 링크 해석 후)가 허용 루트 안인지, 읽기인지 쓰기인지, 보호 경로인지 |
| 명령 | 실행 파일과 인자가 허용 목록에 맞는지, 작업 디렉터리와 환경 변수 |
| 네트워크 | 도구가 외부로 연결하거나 발송하는지 |
| 파괴적 동작 | 삭제, 덮어쓰기, 대량 이동처럼 되돌리기 어려운지 |

하나의 호출이 여러 권한을 요구할 수 있고 하나라도 거부되면 실행하지 않는다. 도구의 등급과 요구 권한은 코드에 고정하며 모델이나 인자로 낮출 수 없다.

Verifier 종류는 작업마다 다르다.

| 작업 유형 | 검증 예 | Git 필요 |
| --- | --- | --- |
| 코드 수정 | 지정한 테스트 명령의 종료 코드와 출력 | 아니오(있으면 활용) |
| 문서 작성 | 필수 절 존재, 링크 대상 존재, 길이·형식 규칙 | 아니오 |
| 파일 정리 | 실행 전 계획(이동 목록) 확인, 실행 후 파일 수·해시 대조 | 아니오 |
| 자료 분석 | 입력 행 수와 집계 재계산 대조, 사람 확인 | 아니오 |

자동 검증이 불가능한 작업은 `inconclusive`와 사람 확인 요청으로 끝낼 수 있어야 한다. 검증기 없는 작업을 "성공"으로 표시하지 않고 "검증 없음"으로 표시한다.

## 4. 실행 흐름

1. adapter가 Task를 만들고 engine이 작업 공간 잠금을 얻은 뒤 실행 기록을 연다.
2. engine이 문맥을 구성하고 privacy가 치환한 뒤 model에 보낸다.
3. 모델이 도구 호출을 요청하면 치환 토큰이 든 인자 그대로 policy가 1차 판정한다: 스키마와 구조, 목적지, 요구 권한.
4. 통과한 호출에 한해 privacy가 그 도구에 선언된 복원 허용 필드만, 허용된 목적에 대해서만 복원한다.
5. policy가 복원된 실효 인자(실제 경로, 실제 명령)를 다시 검사한다. 통과한 호출만 tools가 실행한다.
6. 도구 결과는 privacy가 먼저 치환한다. 가림본만 기록하고 가림본만 모델에 돌려준다.
7. 모델이 완료를 선언하면 verify가 Task에 지정된 검증기를 실행한다. 검증기 출력도 6과 같이 치환 후 기록한다.
8. 실패하면 근거를 문맥에 넣어 2로 돌아간다(단계 2부터. 단계 1은 `failed`로 끝난다). 한도를 넘으면 중단한다.

실행 기록과 모델 문맥에는 평문 도구 결과가 들어가지 않는다. 3~5 중 어디서든 거부되면 복원된 값을 버리고 거부 사유만 가림본으로 기록한다.

상태: `created → running → verifying → done | failed | needs-input | cancelled | budget-exhausted`. 모델의 "완료" 선언은 상태를 `done`으로 만들지 못한다. `done`은 검증기 결과로만 정해진다.

## 5. Anthropic 모델 어댑터

- [확정] 첫 제공자는 Anthropic이다. [선택] 실제 호출에는 로컬 `ANTHROPIC_API_KEY`와 `CODARYN_MODEL`로 명시한 모델을 쓴다. 모의 모델을 쓰는 오프라인 실행에는 둘 다 필요 없다.
- [선택] model 모듈은 `요청(메시지, 도구 정의, 설정) → 응답(내용 블록, 종료 사유, 사용량)` 인터페이스 하나만 노출한다. 엔진은 Anthropic 형식을 직접 다루지 않는다. 두 번째 제공자는 실제로 필요해질 때 추가하며 지금 추상화를 넓히지 않는다.
- [선택] 공식 TypeScript SDK로 Messages API를 호출하고, 반복 루프는 엔진이 직접 소유한다. 치환·정책·기록을 매 호출 사이에 끼워야 하기 때문이다. SDK의 tool runner 사용 여부는 단계 1에서 다시 판단한다.
- [선택] 도구는 클라이언트 도구로 정의해 로컬에서 실행한다. Anthropic 서버에서 실행되는 서버 도구는 초기 범위에서 쓰지 않는다. 로컬 치환·정책 경계를 거치지 않기 때문이다.
- [미정] 모델 ID와 기본 모델. 설정에 모델이 없으면 실행을 거부하고 임의의 기본값을 넣지 않는다.
- 구독 계정은 API 자격증명이 아니다. API 키가 없으면 호출하지 않고 설정 방법만 안내한다.
- 어댑터는 키 파일을 읽지 않고, 키를 로그·기록·자식 프로세스 환경에 넘기지 않는다.

외부 사실의 출처는 [decisions.md](decisions.md) 4절에 링크했다. 실제 API 호출로 확인한 것은 없다.

## 6. 네 가지 경계

**문맥.** 모델에 가는 내용은 사용자 입력과 도구가 허용 루트 안에서 읽은 것뿐이다. 파일·출력 크기 상한을 두고 잘린 경우 잘렸다고 표시한다. 문서와 도구 출력은 자료이며 지시가 아니다. 프로젝트 문서나 모델 출력이 권한을 넓힐 수 없다 [선택]. 긴 대화의 요약·압축 방식은 [미정].

**변경.** 모든 쓰기는 도구를 거친다. 실행 기록에는 변경 집합(경로, 전후 해시)만 남긴다. 되돌리기에 필요한 변경 전 원문은 실행 기록과 다른 보호 저장소(원문 복구 스냅샷)에 둔다. 이 저장소는 되돌리기 명령만 읽고, 모델 문맥·로그·Git에 들어가지 않으며, 보관 기간과 삭제 규칙을 따로 갖는다. 접근 정책의 세부는 privacy.md에서 정한다. Git은 코딩 워크플로가 있을 때 추가로 쓰는 수단이다. 네트워크·파괴적 동작은 되돌릴 수 없는 것으로 기록한다.

**민감정보.** [확정] API 전송 전 가역 치환, 로컬 복원. 아래 순서 규칙은 [선택]이며 세부는 privacy.md 담당자가 정한다.
- 치환은 privacy 게이트 한 곳에서 한다. 모델로 가는 내용과 기록으로 가는 내용이 모두 이 게이트를 지난다. 우회 경로를 만들지 않는다.
- 대응표는 로컬에만 있고 기록, Git, 로그, 모델 문맥에 들어가지 않는다.
- 복원은 무조건이 아니다. 순서는 구조·목적지·권한 확인 → 허용된 목적과 필드만 복원 → 실효 인자 재검증 → 실행이다(4절 3~5).
- 로컬 도구라는 이유만으로 복원하지 않는다. 특히 명령 문자열과 경로에 든 토큰은 자동 복원 대상이 아니다. 도구가 그 필드를 복원 허용으로 선언했고 정책이 그 목적을 허용한 경우에만 복원한다. 실행에 실제 값이 필요한 필드에 미해결 토큰이 남으면 호출을 거부한다. 가림 토큰을 기록하거나 화면에 표시하는 것은 실행과 구분한다.
- 복원 대상은 이번 실행이 발급했고 변형되지 않은 토큰뿐이다. 문자열 전체의 무조건 복원은 금지한다.
- 탐지는 완전하지 않다. 놓친 값이 전송·기록될 수 있다는 한계를 문서와 출력에 숨기지 않는다. 보호 수준은 [미정].

**도구 실행.** Git worktree는 변경 분리 수단이며 OS 경계가 아니다. 파일 접근도 네트워크도 막지 않는다. 초기 방어는 실효 경로 검사, 명령 허용 목록, 고정 작업 디렉터리, 시간 제한, 환경 변수 선별 전달이다. 이것은 실수 방지 수준이며 악의적 코드 실행을 막는다고 주장하지 않는다. OS 격리가 없는 단계에서 정책이 하는 일은 "네트워크를 쓰는 도구를 제공하지 않음"까지다. 허용된 명령이 띄운 프로세스의 네트워크 사용은 막지 못하므로 이를 네트워크 차단이라고 표시하지 않는다. OS 수준 격리는 [미정].

## 7. 자기 수정: 실행본, 후보, 보호된 검증기

[확정] 검증된 CLI가 별도 후보 작업 디렉터리에서 자기 소스를 개발한다. [선택] 이를 위해 아래 세 가지를 분리한다.

| 역할 | 위치 | 누가 바꾸는가 |
| --- | --- | --- |
| 실행본 | 채택된 커밋에서 빌드한 CLI. 후보 디렉터리 밖에 있음 | Codex의 채택 결정 뒤에만 교체 |
| 후보 | 별도 worktree와 브랜치 | 실행본이 작업으로서 수정 |
| 보호된 검증기 | 후보의 허용 루트 밖. 기준 테스트·검증 설정·정책 | 관리자만. 후보 작업은 읽기 전용 |

규칙 [선택]:
- 실행본은 후보 worktree만 허용 루트로 받는다. 자기 설치 위치, 검증기, 정책 파일에는 쓸 수 없다.
- 검증은 실행본(또는 관리자)이 시작한다. 후보 코드가 자기 합격을 판정하지 않는다.
- 검증 시작 전에 보호 대상의 해시를 기준값과 비교한다. 다르면 검증 자체를 무효로 한다.
- 후보가 추가한 테스트는 참고 자료다. 합격 판정은 보호된 기준 검증으로 한다.
- 자동 교체는 없다. 채택은 Codex가 검증 결과, 변경 내용, 사용자 변경과의 충돌을 보고 결정한다.
- 재시도·시간·토큰 한도를 넘으면 후보를 그대로 두고 보고한다.

후보 worktree는 OS 경계가 아니다. 위 쓰기 제한은 도구 정책으로만 집행되고, 후보 테스트는 후보 코드를 실행하므로 6절의 실행 경계 한계가 그대로 적용된다. 해시 확인은 이 한계를 보완하는 사후 탐지 수단이다.

## 8. 재시작, 중복, 충돌, 취소

- **기록.** 실행마다 로컬 상태 디렉터리에 추가 전용 기록을 남긴다(단계 시작, 도구 호출과 결과, 검증 결과). 기록되는 것은 치환된 가림본뿐이며 원문, 대응표, 키는 넣지 않는다.
- **재시작.** 자동 이어 하기는 초기 범위가 아니다. 중단된 실행은 기록으로 무엇이 끝났는지 보여 주고, 사용자가 되돌리거나 새 실행을 시작한다. 결과를 모르는 호출은 이렇게 처리한다: 읽기는 다시 실행, 로컬 쓰기는 해시로 적용 여부 확인, 명령 실행·네트워크·파괴적 동작은 자동 재실행하지 않고 `needs-input`.
- **중복.** 작업 공간마다 잠금 파일(프로세스 ID, 실행 ID)을 둔다. 같은 공간의 두 번째 실행은 거부한다. 죽은 프로세스의 잠금은 확인 후 회수한다. 같은 요청의 재제출은 새 실행이며 이전 실행과 자동 병합하지 않는다.
- **충돌.** 쓰기 직전에 파일 해시를 읽을 때의 해시와 비교한다. 다르면 쓰지 않고 다시 읽은 뒤 모델에 알린다. 사용자 변경을 덮어쓰지 않는다.
- **취소.** 취소 신호가 오면 모델 요청을 끊고, 실행 중인 자식 프로세스에 종료를 요청한 뒤 시간 내에 끝나지 않으면 강제 종료한다. 상태는 `cancelled`. 이미 적용된 변경은 유지하고 목록과 되돌리기 명령을 제시한다. 자동 롤백은 하지 않는다 [선택].

## 9. 범위 비판과 첫 CLI

현재 요구는 한 번에 만들기에 넓다. 다음 지점이 특히 위험하다.

- **범용 계약의 조기 고정.** 코딩 하나만 보고 Task·Verifier를 일반화하면 틀린 추상화가 굳는다. 반대로 워크플로를 여러 개 동시에 만들면 끝나지 않는다. 절충안으로 단계 1~2에 코딩 워크플로와 아주 작은 문서 작업 하나만 두어 계약에 Git·테스트 가정이 새지 않는지 확인한다.
- **민감정보 치환.** 코드에서의 가역 치환은 식별자·문자열·경로를 깨뜨리기 쉽고 탐지 누락도 피할 수 없다. 단계 1에서는 게이트 위치와 인터페이스만 고정하고 좁은 규칙(명시 등록 값, 키 형태 패턴)으로 시작해야 한다.
- **자기 수정.** 실행본·후보·검증기 분리 없이 시작하면 검증기를 고쳐 통과하는 경로가 열린다. 단계 2가 다른 저장소에서 안정되기 전에는 시작하지 않는다.
- **재시작 복구.** 완전한 이어 하기는 분산 시스템 수준의 문제를 끌어온다. 기록과 수동 재개로 충분하다.
- **GUI·IDE.** 어댑터 경계만 지키고 설계는 하지 않는다. 지금 GUI 형태를 가정하면 엔진 API가 그쪽으로 휜다.
- **보안 주장.** 초기 방어는 경로 검사와 허용 목록뿐이다. 이를 샌드박스나 네트워크 차단이라고 부르지 않는다.

현실적인 첫 CLI(단계 1) 범위:

- 명령 하나: 작업 디렉터리와 목표 문장을 받아 한 번 실행하고 끝난다. 대화형 세션, 설정 UI 없음.
- 도구 네 개: 파일 읽기, 목록/검색, 파일 쓰기(전체 또는 부분 교체), 허용 목록 명령 실행.
- 검증기 두 종류: 명령 종료 코드, 파일 존재·내용 규칙.
- 정책: 허용 루트 하나 안의 읽기·쓰기, 허용 목록 명령만 실행, 네트워크를 쓰는 도구는 제공하지 않음, 삭제 등 파괴적 동작은 거부. OS 격리는 없다.
- 치환 게이트: 자리와 인터페이스, 좁은 규칙. 결과 치환 후 기록, 인자의 선택적 복원과 재검증 순서 포함.
- 가림본 실행 기록, 작업 공간 잠금, 쓰기 전 해시 확인, 취소 처리.
- 검증 실패 시 결과를 보고하고 끝난다. 실패를 반영한 자동 재수정은 단계 2다.
- 모의 모델로 키 없이 전 과정을 실행할 수 있어야 한다. 실제 호출은 별도 하위 단계다.
- 제외: 병렬 도구 실행, 하위 에이전트, MCP·확장, 웹 접근, 자동 재개, 문맥 압축, 여러 제공자, 자기 수정.
