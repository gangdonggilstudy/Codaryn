### 읽는 법

- **상태**의 뜻
  - `병합됨(해시)`: 그 main 병합 커밋에 들어갔다고 원천이 말한다.
  - `결정됨·구현 전`: 결정만 있고 구현이 없다고 원천이 말한다.
  - `대체됨(→ id)`: 뒤의 결정이 내용을 바꿨다.
  - `알려진 한계로 둠`: 고치지 않기로 하고 한계로 기록했다.
  - `상태 미확인`: 원천에서 확인하지 못했다. 추측하지 않았다.
- **상태의 근거**: pm-status.md의 체크포인트 요약과 main 병합 커밋의 제목이다. 일부 항목은 worktree의 Git 기록에서 "그 결정 번호를 적은 커밋이 어느 병합 커밋에 들어 있는지"를 확인해 보탰다. 그런 곳은 커밋 해시를 함께 적었다. 코드를 읽어 동작을 대조하지는 않았다.

- **용어**: DR은 설계 검토 뒤 결정, N은 사용성 결정, Q는 사용자에게 물은 질문, CP는 체크포인트, G는 작업 지침이다. R-숫자(예: R-25)는 검토 보고의 번호다. "가림"은 비밀 값을 출력·기록·모델 요청에서 다른 표기로 바꾸는 것이다. "앱 계층"은 CLI와 GUI가 함께 쓰는 모듈 `src/app`이다. "작업 종류"는 워크플로(workflow) 정의다.

**지금 유효한 내용**: 변경 보기(`changes`, GUI의 변경 화면)는 다시 가린 비교만 보여 준다. 파일의 글은 "지금 등록된 비밀로 다시 가린 결과가 실행 때의 가린 표기와 같고, 파일이 실행이 남긴 그대로일 때"만 보인다. 아니면 경로와 상태만 보인다. ## 6. 키 거부와 비밀 가림

여기서 "키 거부"는 목표 문장, task 파일, 설정 파일에 API 키가 들어 있으면 실행을 시작하지 않는 것이다(이전 결정 S-6, S-8). "가림"은 실행 중 출력·기록·모델 요청에서 등록된 비밀 값을 가리는 것이다.

사슬: OpenAI 거부 모양 DR-32 (a) → **DR-33**. Anthropic 거부 모양 **DR-36 (c)** ⇢ **DR-40** ⇢ **DR-42 (a)(b)** → **DR-43 (c)**(DR-42 (a)의 비교 조건을 좁힘) ⇢ DR-45(남은 것은 한계). 유효한 것은 머리말 사슬 표와 같다: DR-36 (c)의 좁힌 모양에 DR-40, DR-42 (a)(b)를 더하고, 비교 조건은 DR-43 (c)의 것이다.

**지금 유효한 내용**
- 주 방어는 환경에 등록된 키 값과의 대조다. 키 모양 검사는 보조다. OpenAI 키의 접두사와 길이는 공식 문서에 없는 관행이므로 키를 검증하는 데 쓰지 않는다(DR-33, 사실 확인 C-3).
- 넓은 키 모양은 출력 가림에만 쓴다. 실행 거부에는 좁힌 모양을 쓴다.
- 등록된 값과의 대조는 구분 문자와 보이지 않는 문자를 뺀 글에서도 하고, "키 같은 값"이면 글자와 숫자만 남긴 글에서도 한다.
- 모양을 다시 볼 때는 보이지 않는 문자와 줄바꿈만 빼고 보이는 공백은 남긴다.

### 사용자의 상시 지시와 PM의 적용

원문은 pm-status.md "사용자 상시 지시 (2026-11-12)" 절(30절)과 "사용자 지시 (CP-12, 2026-11-12)" 절이다. 사용자의 말과 PM의 적용을 나눠 적는다.

**사용자의 말(상시 지시, 인용문 한 문장)**
- "GUI 등 최종 모든 설계를 중간에 멈추지 말고 내 지시가 없으면 끝까지 연속 진행하고 있어."

**PM의 적용(pm-status 30절, "PM은 이를 다음과 같이 적용한다")**
- roadmap의 남은 단계(단계 3 마무리, 단계 4 범용 작업 확장, 단계 5 GUI·IDE)를 사용자의 추가 지시 없이 차례로 설계·구현·검증한다. 미정 항목은 PM이 정하고 근거를 작업 지시서에 남긴다.
- 그대로 지키는 한계: PM과 작업자는 실제 Anthropic API를 호출하지 않고 키 파일을 읽지 않는다. 과금이 걸린 선택(세션 사용 한도 창 등)과 force push, 이력 재작성은 하지 않는다. `docs/pm-control.json`이 active가 아니면 멈춘다.
- 실제 API 검증이 필요한 완료 판단(1b, 단계 2·3의 실 API 기준)은 "미수행"으로 적고 다음 단계의 오프라인 작업을 계속한다.

**같은 날의 추가 지시(pm-status 30절이 사용자의 추가 지시로 옮겨 적은 것)**
- 편의성을 확보하게 설계한다. 설계 전문가를 다시 붙여 사용성 개선을 협의하고 추가 설계한다. UX 설계도 진행하고 모두 문서화한다. 문서화 없이 진행된 부분은 다 문서화한다. 모델명을 외워 치지 않도록 모델 목록을 불러와 고를 수 있게 한다.

**사용자 지시 (CP-12) 절에 적힌 것(PM이 옮겨 적은 사용자 지시)**
- 개발 목표는 최종 설계까지 모두 구현하는 것이다.
- 작업자는 작업 지침 교육을 받고 시작한다.
- 새 지침은 PM이 바로 더하지 않고 후보로 모아 사용자가 확인한 뒤 더한다.
- 사용자 판단이 필요한 질문은 PM이 먼저 받아 모으고, 사용자가 알려 달라고 하면 하나씩 정리한다.
- Codex는 사용 한도가 적어 검증 작업만 맡긴다.
- 커밋과 push는 적절한 단위로 하고, 작성자는 지정된 한 사람이다.
- 제품 방향: GUI를 지원한다. Codex도 지원한다. (Codex의 뜻은 그때 "PM의 이해"로 적혔고 Q-9의 답으로 확정됐다.)
