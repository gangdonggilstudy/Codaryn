# Codaryn 설계 결정

상태: 설계 단계 기록이다. 코드가 없으므로 어떤 결정도 구현이나 실행으로 검증되지 않았다.
사용자가 제품 방향을 정하고 Codex가 기술 판단을 맡는다. 2절의 선택은 2026-11-12 Codex가 문서 검토와 수정 반영 후 채택했다. 미정 항목은 해당 구현 단계 전에 별도로 결정한다.

## 1. 사용자 확정 사항

| ID | 내용 |
| --- | --- |
| U-1 | 범용 작업 에이전트다. 코딩 외에 문서 작성, 자료 분석, 파일 정리 등을 다룬다. |
| U-2 | CLI를 먼저 개발한다. GUI와 VS Code 개발 기능 연동은 후속이다. |
| U-3 | Anthropic API를 먼저 연결한다. |
| U-4 | 자기 코딩: 초기 CLI가 코드 수정 → 테스트 → 실패 피드백 → 재수정을 수행하고, 이후 별도 후보 작업 디렉터리에서 자기 소스를 개발한다. |
| U-5 | API 전송 전에 민감정보를 가역 치환하고 로컬에서 복원한다. |
| U-6 | 역할 분담: 최종 기술 판단과 관리는 Codex가, 코딩·긴 문서·대량 분석은 Claude가 맡는다. |
| U-7 | 커밋과 push의 작성자는 `gangdonggil <gangdonggilstudy@gmail.com>`이다. |
| U-8 | 커밋 메시지에 Git trailer를 넣지 않는다(Co-authored-by, Signed-off-by 등과 자동 귀속 문구 포함. `--signoff`, `--trailer` 사용 금지). |
| U-9 | 커밋은 논리적 변경 단위로 나누고, push는 Codex 검토 뒤에 한다. 작업 담당자는 직접 push하지 않는다. |
| U-10 | 필요한 문서를 docs 디렉터리에 보관하고 Claude에 개발 지침과 전문 페르소나를 사전 전달한다. 작업 충돌을 줄이기 위해 작업별 Git worktree를 분리한다. |
| U-11 | 유닛 테스트를 구현 효율을 높이는 방향으로 설계하고 구현과 함께 진행한다. |

## 2. 관리자 설계 선택과 규칙

| ID | 선택 | 근거 | 버린 대안 |
| --- | --- | --- | --- |
| M-1 | 구현 언어는 TypeScript. 단일 패키지, 단일 프로세스 | CLI와 후속 VS Code 연동이 같은 언어를 쓴다. 초기 규모에 모노레포·서비스 분리는 비용만 든다 | 다른 언어, 엔진 서버 + 클라이언트 |
| M-2 | 엔진은 하나, CLI·GUI·IDE는 어댑터 | 작업 논리가 인터페이스마다 갈라지는 것을 막는다 | 인터페이스별 구현 |
| M-3 | Task·Tool·Artifact·Verifier·Policy 공통 계약, 코딩은 첫 워크플로 | U-1과 U-4를 함께 만족한다 | 코딩 전용 엔진을 나중에 일반화 |
| M-4 | 엔진은 Git을 요구하지 않는다. 변경 추적은 자체 원본 보관과 해시 | 문서·파일 작업은 저장소 밖에서 일어난다 | 모든 작업 공간에 Git 초기화 |
| M-5 | 반복 루프는 엔진이 소유한다 | 치환·정책·기록을 매 호출 사이에 넣어야 한다 | SDK tool runner에 루프 위임(단계 1에서 재검토) |
| M-6 | 도구는 로컬 실행 클라이언트 도구만 쓴다 | 서버 실행 도구는 로컬 치환·정책 경계를 거치지 않는다 | 서버 도구(웹 검색 등) 초기 도입 |
| M-7 | read·write-local·exec·external은 표시용 등급. 허용 판단은 경로·명령·네트워크·파괴적 동작 권한을 호출마다 따로 검사 | 등급 하나로는 "허용 루트 안 삭제"와 "루트 밖 읽기"를 구분하지 못한다 | 등급만으로 허용·거부 |
| M-8 | 단계별 격리: 단계 1~2 경로 검사·허용 목록, 단계 3 후보 worktree + 외부 검증기. worktree는 OS 경계가 아니며 OS 격리 없는 단계를 네트워크 차단이나 샌드박스로 표시하지 않는다 | 필요한 시점에 필요한 만큼만 만들고, 없는 보호를 있다고 하지 않는다 | 처음부터 OS 샌드박스 |
| M-9 | 권한은 사용자 설정과 CLI 인자로만 정한다 | 모델 출력과 프로젝트 문서는 신뢰 경계 밖이다 | 프로젝트 문서로 권한 선언 |
| M-10 | 작업 공간 잠금, 쓰기 전 해시 비교, 추가 전용 실행 기록 | 중복 실행과 사용자 변경 덮어쓰기를 막는 최소 수단 | 데이터베이스, 자동 이어 하기 |
| M-11 | 취소 시 변경 유지 + 되돌리기 제공 | 자동 롤백은 사용자의 동시 변경을 지울 수 있다 | 취소 시 자동 롤백 |
| M-12 | 실제 호출은 키와 명시적 모델이 있을 때만. 없으면 호출 없이 거부. 구현과 모의 테스트에는 요구하지 않는다 | 기본 모델을 임의로 정하지 않고, 오프라인 검증을 키에 묶지 않는다 | 코드에 기본 모델 고정 |
| M-13 | 후보 채택은 수동, 자동 교체 없음 | M-15, M-16 | 검증 통과 시 자동 승격 |
| M-14 | 단계 1부터 최소 문서 작업 하나를 함께 검증 | 계약에 코딩 가정이 새는 것을 일찍 발견한다 | 단계 4까지 코딩만 |
| M-15 | 자기 수정 시 현재 실행본, 수정 후보, 보호된 검증기를 분리 | 후보가 자기 합격 기준이나 실행 중인 도구를 바꾸지 못하게 한다 | 실행본이 자기 디렉터리를 직접 수정 |
| M-16 | 검증 표현 규칙: 테스트 통과는 "지정 검증기 범위에서 통과"로만 쓰고 보안·정확성 전체 보장을 주장하지 않는다 | 검증기는 검사한 것만 말해 준다 | "검증 완료" 같은 포괄 표현 |
| M-17 | 도구 결과는 치환한 뒤 가림본만 기록·전달. 원문 복구 스냅샷은 별도 보호 저장소와 접근 정책 | 기록 후 치환하면 평문 로그가 생긴다 | 원문 기록 후 전송 시 치환 |
| M-18 | 도구 인자는 구조·목적지·권한 확인 → 허용된 목적·필드만 복원 → 실효 인자 재검증 → 실행. 로컬 도구라는 이유로 명령·경로 토큰을 자동 복원하지 않는다 | 무조건 복원은 정책이 보지 못한 값을 실행하게 한다 | 전체 복원 후 한 번 판정 |
| M-19 | 단계 1·2는 오프라인 검증과 실 API 검증을 하위 상태로 나눠 기록 | 모의 결과를 실제 검증으로 오인하지 않게 한다 | 단일 완료 표시 |
| M-20 | 핵심 계약과 실패 경로의 유닛 테스트를 먼저 또는 구현과 함께 작성한다. 외부 경계만 모의하고 관련 테스트부터 실행한다 | 실패를 빨리 찾고 구현 변경 비용을 줄인다 | 구현 내부를 그대로 모사한 테스트, 일괄적인 커버리지 목표 |
| M-21 | 단계 1a는 확인된 Windows 환경과 Node.js 26.13.0, npm 11.20.0, TypeScript 엄격 검사, Node 기본 테스트 러너로 시작한다. 개발 의존성은 typescript와 @types/node를 lock 파일로 고정한다 | 기존 환경을 활용하고 실행 의존성을 줄인다 | 별도 테스트 러너와 런타임 TS 로더 도입 |

## 4. 확인한 외부 사실

2026-11-11 작성 과정에서 확인했고 2026-11-12 관리자 검토에서 API 개요와 도구 실행 위치를 다시 확인했다. 실제 API 호출이나 SDK 설치로 검증한 것은 아니다. 구현 시작 시 다시 확인한다.

| 사실 | 출처 |
| --- | --- |
| Messages API는 `POST /v1/messages`이며 Claude API는 `https://api.anthropic.com`에서 제공된다 | [API overview](https://platform.claude.com/docs/en/api/overview) |
| API 사용에는 Claude Console 계정과 Console에서 발급한 API 키(또는 Workload Identity Federation)가 필요하다. 키는 `Authorization: Bearer` 또는 `x-api-key` 헤더로 보내고 `anthropic-version` 헤더가 필수다. SDK는 이 헤더들을 자동으로 보낸다 | [API overview](https://platform.claude.com/docs/en/api/overview) |
| 공식 클라이언트 SDK에 TypeScript가 있고 npm 패키지는 `@anthropic-ai/sdk`다. 문서는 Node.js, Deno, Bun, 브라우저 지원을 표기한다 | [SDKs, CLI, and libraries](https://platform.claude.com/docs/en/cli-sdks-libraries/overview) |
| 클라이언트 도구는 `name`, `description`, `input_schema`로 정의하고 애플리케이션이 실행한다. 모델은 `stop_reason: "tool_use"`와 `tool_use` 블록으로 요청하며 결과는 `tool_result` 블록으로 돌려보낸다 | [Tool use with Claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) |
| 서버 도구(`web_search`, `web_fetch`, `code_execution` 등)는 Anthropic 인프라에서 실행된다 | [Tool use with Claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) |
| SDK에는 도구 실행과 결과 반환을 자동화하는 tool runner가 있다 | [Tool use with Claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) |

작업공간에 한정되지 않은 API 키를 사용하는 경우 `anthropic-workspace-id` 헤더도 필요하다. SDK가 인증·버전·content-type 헤더를 관리해도 이 작업공간 헤더는 호출자가 설정해야 한다. 연결 단계에서 키의 범위와 필요한 작업공간 설정을 확인한다. [API overview](https://platform.claude.com/docs/en/api/overview)

위 문서에서 확인한 것은 API 자격증명의 발급 경로까지다. 구독 요금제와 API 과금의 관계는 확인하지 않았다. 따라서 구독을 API 키로 간주하지 않고, API 키가 없으면 호출하지 않는 것을 설계 규칙으로 둔다(M-12와 같은 취지).
SDK 버전, 모델 ID, 가격은 변하는 값이므로 이 문서에 고정하지 않는다.

## 5. 기록 규칙

- 확정 사항을 바꾸는 것은 사용자만 한다. 선택 사항은 Codex가 채택·변경하고 이유를 이 문서에 남긴다.
- 미정 항목을 구현으로 먼저 정하지 않는다. 결정이 필요해지면 Codex에 올린다.
- 외부 사실을 추가할 때는 공식 문서를 실제로 열어 확인하고 링크와 확인 날짜를 적는다.
