# 첫 사용 준비·실행 경계 설계와 적용 검토

2026-11-28 · 정적 검토 · 기준 `main ea70c122` · 역할 임시 PM·수석 아키텍트

**채택 권고.** 빠른 시작의 준비 단계, 실행 전에 보이는 보장 범위, 명시 JSON·미리보기 예시를 첫 묶음으로 채택할 수 있다. 현재 동작을 설명하는 문서부터 적용하고, 실행체가 없는 상태까지 판정해야 할 때 소스 배포용 점검 진입점을 별도 검토한다. 토큰 한도는 기존의 다음 요청 중단 계약을 따른다. 금액 송신 제한, OS 격리 실행기, 키 조회를 금지하는 모드는 각각 별도 계약과 승인 판단이 필요하다. 되돌리기 삭제의 대상 결속은 문서 개선과 별도로 우선 검토한다.

근거는 사용자가 제공한 익명 요청과 기준 main의 코드·문서다. A01~A12 원본은 열거나 첨부하지 않았다. G0의 낮은 런타임 경고와 오프라인 캐시 누락은 각각 보존한다. G1의 설치 성공과 실행체 부재로 인한 `NOT_RUN`, G2의 빌드·scripted 실행 성공과 첫 미리보기 `invalid_arguments`(rc 2), G3의 미리보기 `complete`(rc 0, `dryRun=true`)는 별도 관측이다. G3의 파일 목록·내용 지문 일치는 해당 미리보기 기록의 범위다. 이 검토에서 실행판·환경 호환성·실제 복구·청구·키 가림을 새로 측정하지 않았다.

## 2. 공통 설계와 수락 기준

### 소스·패키지의 준비 상태

- 배포 형태의 입력은 배포 주체가 가진 런타임 요구, 대상 플랫폼, 의존성 준비 방식, 실행 진입점, 판본이다. 소스의 `engines`와 `bin`은 `package.json`이 기준이다. 현재 CLI 소스 패키지의 의존성은 빌드·개발용이다(`devDependencies`). 의존성 상태는 하려는 작업이 소스 빌드인지 준비된 실행체의 실행인지에 따라 판정한다. 동봉 배포가 생기면 그 배포의 배치 정보가 런타임과 진입점을 정한다. 링크 설치도 실제 연결된 배포 정보를 사용한다. 사용자 홈·전역 PATH를 수정하지 않는 읽기 전용 확인을 전제로 한다.
- `런타임`, `의존성`, `실행체`를 각각 판정한다. `확인됨`, `부적합/부재`, `확인 불가`, `해당 없음`을 구분한다. 런타임 버전을 파싱할 수 없으면 확인 불가다. `node_modules` 디렉터리 존재나 이전 설치 rc 0만으로 의존성 전체를 확인했다고 표시하지 않는다. 실행 진입 파일 존재는 그 자체로 해당 소스 판의 빌드나 실행 성공을 증명하지 않는다. 엔트리포인트의 판본 결속 자료가 없으면 그 확인은 따로 미확인으로 둔다.
- 1차는 README와 사용자 절차에서 현재 버전 요구, 설치 성공의 의미, 별도 빌드, 첫 확인을 순서대로 안내한다. 예를 들어 설치 성공이 관측됐고 실행체가 없으면 두 상태를 표시하고 소스 빌드를 다음 단계로 안내한다. 향후 자동 점검이 필요하면 CLI를 불러오기 전에도 쓸 수 있는 배포용 진입점에서 준비 상태를 수집하고, 실행체가 뜬 뒤 기존 `doctor`가 설정·작업 공간·정책을 점검하는 구조가 적합하다. 런타임 요구는 배포 메타데이터와 `doctor`의 판정이 일치하도록 확인한다. 자동 설치나 자동 빌드는 초기 범위에서 제외한다.
- 수락 조건은 지원 런타임·실행체 부재, 비지원 런타임·파일 존재, 의존성 부재·실행체 존재, 권한 문제로 확인 불가, 동봉 런타임의 다섯 조건에서 올바른 항목과 다음 행동을 각각 표시하는 것이다. 판정 로직은 버전 문자열·파일 상태를 주입해 확인하도록 설계한다.

### 실행 전 보장과 금액 제한

현재 표시에는 다음 범위와 시점을 쓴다. CLI·GUI는 유효 작업·검증기·제공자 정보를 같은 앱 계층에서 읽어 각 화면의 언어로 표현할 수 있다. 정책을 복제하거나 표시 결과로 실행을 승인하는 경로를 추가하지 않는다.

| 항목 | 표시할 보장 |
| --- | --- |
| 모델 turn·도구 호출 | 로컬에서 한도에 이르면 다음 모델 turn 또는 다음 새 도구 호출을 제한한다. HTTP 재시도는 별개다. |
| `maxOutputTokens` | 지원하는 제공자 요청에 출력 토큰 상한을 전달한다. |
| `maxTotalTokens` | 응답 사용량을 집계해 다음 모델 호출을 막는다. 남은 토큰만큼 요청을 잘라 보내는 계약은 없다. 유한 한도에서 사용량이 없으면 응답 뒤 `budget-exhausted/usage_unknown`으로 멈춘다. |
| 시간·취소 | 로컬 제한과 중단 신호다. 이미 보낸 요청의 원격 처리와 요금은 독립적으로 남을 수 있다. |
| 명령 정책 | 명령·인자·작업 디렉터리를 검사하고 자식 환경을 필터링한다. 실제 자식은 사용자 권한으로 실행되며 OS 파일·네트워크 격리는 제공되지 않는다. 후손 수거는 최선 노력이다. |
| 로컬 되돌리기 | 기록·해시로 확인된 파일 도구 변경과 지원되는 적용 작업을 되돌린다. 자식 명령의 부작용, 원격 서비스 처리, 청구는 되돌리기 범위 밖이다. |

금액 제한을 추진할 경우에만 승인된 고정 제공자·모델과 요율 판본·통화를 등록한다. 어댑터가 실제 전송 형태의 전체 입력(대화·도구 정의·추가 문맥 포함), 최대 출력, 해당 모델의 모든 과금 범주에 보수적 상한값을 제공한다. 범주·가격·상한을 결정할 수 없거나 남은 예산이 부족하면 **송신 전에** 거부한다. 화폐 계산은 정수 최소 단위로 올림하고, 실행 범위의 예약과 차감이 동시 호출에서도 중복 사용되지 않게 한다. HTTP 공통층에서 재시도를 포함해 각 송신 전에 예약한다. 응답 손실이나 abort는 사용량 0의 근거가 없으므로 예약을 유지한다. 제공자 청구 제한은 제공자가 별도로 강제하는 계약을 확인한 경우에만 표시한다. 초기 표시 변경은 기존 기계 출력 스키마로 제공한다. 차후 송신 거부 표현은 저장 결과와 독자의 호환성 검토 후 결정한다.

수락 조건은 가짜 전송기로 한도 정확히 일치, 한 단위 부족, 가격·계측 불명, 재시도 직전 잔액 부족, 중단·응답 소실, 중복 예약을 확인하는 것이다. 송신 거부는 전송기 호출 수 0, 이전 송신의 결과 불명은 예약 유지로 확인한다. 현재 토큰 계약은 [기존 PM 결정](../pm-status.md)과 일치하게 유지한다. 강한 OS 격리가 필요하면 별도 실행기에서 승인된 파일 권한·네트워크 정책·프로세스 수명·플랫폼별 지원을 정의하고, 지원 불가 시 격리가 필요한 실행을 거부하도록 설계한다.

### 합성 예제와 로컬 원본

- 첫 시범 후보는 별도 새 작업 공간 한 개, 공개 합성 입력, 고정 scripted 응답, 빈 명령 허용 목록, 명령 검증기 없음, 실제 조건을 검사하는 파일 검증기다. 기존 `examples/demo`의 명령 거부 시범은 유지한다. 그 task의 명령은 비어 있고 파일 검증기만 있지만 대본에는 거부될 `run_command` 요청이 있다(`examples/demo/task.json:8–29`, `examples/demo/script.json:9`). 명령 요청도 전혀 없는 경로는 빠른 시작용 대본으로 따로 다룬다. 작업 유형과 자료는 바꿔도 같은 흐름이 유지돼야 한다.
- “제공자 API를 호출하지 않음”, “호스트 키 값을 읽지 않음”, “등록한 값에 대한 가림”, “로컬에 원문 보관”을 독립 항목으로 안내한다. 합성 실행 환경은 상속 전체에서 일부를 제거하는 방식 대신 필요한 비민감 변수만 명시적으로 주고, 임시 설정·작업 공간을 명시한다. 후자의 경우 기존 getter가 빈 합성 환경에 진입할 수 있으므로 “호스트 키를 상속하지 않음”까지만 표시한다. 호스트 키 **getter 미호출**이 제품 요구가 되면 입력 읽기·오류 출력·doctor·실행 결과를 포함한 진입점 전체에 키 소스를 주입하고, 실 제공자와 결합은 거부한다. 합성 등록값과 기존 가림 게이트는 유지한다.
- 저널과 출력의 등록값 가림은 해당 값의 적용 범위로 설명한다. 스냅샷·계획 원문·폐기 원본은 복구용 로컬 평문이다. 유지·삭제는 현재 기록 정리 절차와 복구 가능성에 연결한다. 자식 환경은 제품이 전달하는 이름과 플랫폼 런타임이 추가할 수 있는 이름을 설명하고 실제 값을 표시하지 않는다. [개인정보 보호](../privacy.md) · [사용 안내](../usage.md)
- 수락 조건은 가짜 값으로 입력 거부·가림 동작·출력·저널·보고·변경 보기의 경계를 각각 확인하는 것이다. 합성 파일의 로컬 원본 저장은 별도 확인하고, getter 미호출을 약속하는 판에서는 접근을 기록하는 가짜 키 소스로 직접 확인한다. G2의 단일 sentinel 결과는 이 후보의 포괄 검증 근거로 사용하지 않는다.

### 첫 사용자와 자동화의 결과 읽기

- 빠른 시작의 절차는 **준비 확인 → 새 합성 사본 → 검증 있는 실행의 명시 JSON → 같은 실행 ID의 보고 → 그 ID의 되돌리기 미리보기**다. 예시 재실행은 새 전용 디렉터리 사용 또는 기존 목적지 거부로 처리한다. 직접 실행·링크 설치 명령의 접두는 각 진입 방법을 따라야 한다. 경로 가림과 안전한 힌트 표시 조건을 만족할 때만 실제 호출 문자열을 출력한다. 실제로 들어갈 값인지 설명용 표기인지 구별한다.
- 자동화는 프로세스 종료 코드와 stdout의 `schemaVersion`·`kind`·`status`·해당 `reason`을 함께 읽는다. 사람용 진행·진단은 분리한다. `done/verified`와 `needs-input/no_verifier`를 구분하며 기본 통과 검증기를 추가하지 않는다. `budget-exhausted/usage_unknown`, 중단과 남은 변경, 되돌리기의 `partial`·건너뛴 이유도 그대로 드러낸다. 상황별 오류 위치·다음 행동은 기존 안정 코드를 우선 보존한다.
- 미리보기에는 명시 작업 공간과 관측한 실행 ID, `--dry-run --json`을 사용한다. `dryRun=true`에서 `deleted`는 예상 처리다. `complete`가 나와도 실제 되돌리기·복구 성공의 근거가 되지 않으며 디스크별 이동 안전성은 실제 처리 때 달라질 수 있다. `latest`는 기존 명령에서 계속 사용할 수 있다. 파괴 동작의 명시 대상·필요한 확인·digest 일치 절차는 유지한다.
- 수락 조건은 터미널과 파이프에서 명시 JSON 한 건, 고정 정답과 검증 없음의 분리, 잘못된 옵션·스키마 거부, 사용량 불명과 취소, 미리보기 전후 파일·기록 무변경이다. 실제 복구와 스냅샷 부재·불일치, 부분 되돌리기는 별도 소유의 폐기 가능한 합성 사본에서 확인할 항목이다. 시범 결과의 수락은 그때 검증표로 따로 남긴다.

## 4. 채택 순서와 검증 범위

1. **문서·데이터 작업 전문가**가 README 첫 화면과 사용 안내를 먼저 맞춘다. 런타임부터 미리보기까지, 사용 중인 진입점과 기존 상태 이름으로 설명한다. **CLI 개발자**가 옵션·코드·문구의 정적 일치를 교차 검토한다. 이 묶음은 기존 명령·출력·안전 장치 변경이 없어 채택 권고다.
2. **CLI 개발자**는 문서만으로 해결되지 않는 준비 상태와 실행 전 표시를 앱 경계에 설계한다. **검증 엔지니어**가 합성 입력·고정 oracle의 정상·음성·미실시 상태를 확인한다. 제품 실행·빌드가 필요한 검증은 이번 요청의 범위에 들어 있지 않다.
3. **보안·개인정보 검토자**는 IR-2를 먼저, IR-1·3·4·18·20·22·23과 가림·키 경계는 각 근거가 허용하는 범위로 검토한다. 파일시스템·시각 원천·복원 내구성은 정적 근거로 확인할 수 있는 수준까지만 판정한다. 경합 재현이나 취약점 재현 코드는 이 검토에 포함하지 않는다.
4. 금액 송신 제한·격리 실행기·엄격한 키 조회 금지·새 배포물은 **수석 아키텍트**가 경계와 호환성의 독립 설계로 올린다. 제공자별 청구나 플랫폼별 격리의 실제 보장은 증거와 승인이 생긴 뒤에 판정한다.

이 검토에서는 저장소의 코드·문서를 읽었다. 제품 실행, 빌드, 시험, 설치, 네트워크, 실제 API·키 조회, 배포는 수행하지 않았다.
