## 2. 대상 사용자와 원칙

**대상**

- 개발자: VS Code 확장이 없어졌으므로 개발자도 이 GUI를 쓴다(DR-20). task 파일 실행, 실행 id 복사, CLI와 같은 기록 공유를 둔다. 관리자 과업은 CLI가 주 경로다.

[설계] GUI 원칙. [UX 설계](ux-design.md) 1절에 더한다.
1. **그리기만 한다.** 정책, 가림, 검증, 경로 검사, 설정 쓰기 규칙은 앱 계층 함수를 부른다. GUI가 같은 검사를 따로 만들지 않는다.
2. **CLI에서 못 하는 것은 GUI에서도 못 한다.** GUI 전용 우회가 없다. GUI가 확인 없이 권한을 넓히지도 않는다(6.6).
3. **기본값은 "바꾸지 않음"·"거부"다.** 확인 창의 기본 단추도 같다.
4. **가림본만 그린다.** 화면, 창 제목, OS 알림, 클립보드, 작업 표시줄에 넣는 것 모두 같다.
   - DR-72: 텍스트 보기(3.14)도 같다. 앱 계층이 지금 등록한 가릴 값·키 모양으로 가린 글을 준다. 가리면 글이 달라지는 파일은 가린 글로 읽기만 한다. 그래서 고칠 수 있는 파일은 가린 글과 원래 글이 같고, 화면에 오는 글은 늘 가림본이다.
5. **낱말이 먼저다.** 상태는 낱말로 구분하고 색과 아이콘은 보조로만 쓴다.
6. **사용자 파일을 바꾸는 동작과 위험 동의는 메인이 확인한다.** 화면(렌더러)이 침해되어도 확인 없이 적용·되돌리기·삭제·권한 넓히기를 하지 못한다(6.6).
   - DR-72: 사람이 텍스트 보기에서 저장하는 것도 사용자 파일을 바꾼다(3.14).
     - 메인은 자기가 연 파일의 편집 토큰으로만 저장을 받는다. 화면은 경로를 보내지 못한다.
     - 저장은 실행과 같은 작업 공간 잠금을 잡고, 열 때의 해시와 디스크가 다르면 거부한다.
     - [결정] PM(DR-72 뒤, U-174): 메인은 연 파일마다 첫 저장에 한 번 OS 확인으로 묻는다(기본: 취소). 매번 묻지는 않는다. 원칙 6과 GUI-D22를 그대로 지킨다. UX 검토(`text-editing-ux.md` 5.5)의 제안이다.

### 3.2 작업 공간 열기와 최근 폴더

- 여는 길 세 가지. 모두 메인이 경로를 받아 **작업 공간 핸들**을 발급한다(6.5). 화면은 경로 문자열을 넘기지 못한다.
  1. "작업 공간 열기…"(Ctrl+O): OS 폴더 대화상자.
  2. 최근 폴더: 홈과 "작업 공간 ▾" 메뉴. `gui-state.json`의 목록(최대 20개, 4.5). 항목마다 "목록에서 빼기"가 있다. 없는 폴더는 "찾을 수 없음"으로 보이고 열리지 않는다.
  3. 명령줄 인자: `Codaryn.exe D:\work\notes`. 이미 떠 있으면 두 번째 실행이 인자를 기존 창에 넘기고 끝난다(6.9 단일 인스턴스). 메인이 폴더인지 확인한 뒤 핸들을 발급한다. 탐색기의 "Codaryn에서 열기" 메뉴는 설치 파일 단위에서 정한다(GUI-D9).
- 네트워크 위치(UNC)와 장치 경로(`\\.\…`, `\\?\…`, `CON` 같은 장치 이름, `/dev/…`)의 폴더는 세 길 모두에서 열지 않는다(R10b-L-2). CLI의 로컬 경로 규칙(S-5)과 같은 규칙으로, 파일 시스템에 묻기 전에 거절한다. 그래서 SMB 연결이나 파이프 연결이 생기지 않는다.
  - 대화상자에서 고른 경우: 홈 화면에 `workspace_not_local` 안내를 보인다.
  - 명령줄 인자인 경우: 열지 않는다.
  - `gui-state.json`에 그런 경로가 있는 경우: 읽을 때 버린다.
- 끌어 놓기로 여는 것은 v1에 두지 않는다. 화면이 경로를 넘기게 되기 때문이다(GUI-D19).
- 폴더를 열면 앱 계층의 점검(`doctor`, 작업 공간 항목)으로 미리 검사해 보여 준다. 막는 검사는 실행할 때 `startRun`이 다시 한다.
  - 거부(막음): 설치 위치와 겹침(U-3), UNC·장치 경로(S-5), 설정·task 파일이 작업 공간 안(S-1). 예: 사용자 홈 전체를 고르면 기본 설정 위치(`%APPDATA%\Codaryn`, N-1)가 그 안에 있어 거부된다. 카드에 "더 좁은 폴더를 고르세요"를 쓴다.

  - 다른 실행이 이 작업 공간을 쓰는 중(잠금): "다른 실행이 이 작업 공간을 쓰고 있습니다"를 보이고 새 작업 단추를 끈다. 잠금 회수는 엔진이 한다(P-4, N-25).
  - U-68(구현): 작업 공간을 열 때, 실행이 끝날 때, F5 때 `doctor`를 다시 부른다(`renderer/workspace/open-check.ts`). 작업 공간 화면의 "열 때 점검" 카드에 작업 공간 항목(`workspace`, `file_locations`, `install_dir`, `lock`) 가운데 ok가 아닌 것만 보인다. 상태 낱말과 공용 문구의 이름, 엔진의 영어 설명을 쓰고, "점검 모두 보기"로 점검 화면에 간다. 잠금은 점검의 문구 id(`doctor.lock.held`, 메인이 `text.id`만 넘기고 매개변수는 넘기지 않음)로 안다. 그래서 앱 계층에 따로 요청할 것은 없었다. 잠금이 다른 프로세스의 것이면 카드에 위 문장(알림 역할)이 뜨고, 새 작업의 실행 단추가 꺼지며 그 까닭이 그 자리에서 바뀐다(친 목표는 그대로). 이 창의 실행이 그 작업 공간에서 진행 중이면 잠금은 그 실행의 것이라 "다른 실행"이라 하지 않는다. task 파일 실행은 제 작업 공간을 쓰므로 끄지 않는다. `stale`, `unreadable`, `reclaim_left`는 카드에 경고 줄로 보이고, 단추는 끄지 않는다(시작할 때 엔진이 판정).
  - U-123(R-87 U-68 L1): 다른 프로세스의 잠금이 보이는 동안 작업 공간 화면이나 새 작업 화면을 다시 열면 창이 스스로 다시 점검한다. 잠금 문구는 "끝나면 F5를 누르거나 이 화면을 다시 여세요"를 말한다.
- 작업 공간 고지[설계, R-1 L-5]: 새 작업 화면에 늘 한 줄을 둔다. "이 폴더의 파일 내용은 작업 중 선택한 모델 제공자의 API로 보내질 수 있습니다. 가려지는 것은 설정에 등록한 값뿐입니다." 제공자 이름은 설정에서 받는다(DR-22).
  - 자료 분석(`analyze`, 작업 종류나 프로필의 작업 종류)을 고르면 한 줄을 더한다(U-61): 표의 행은 그대로 모델에 가고, 가려지는 것은 등록한 가릴 값뿐이며, 행 대신 집계만 보내는 도구는 아직 없으니 개인정보가 든 표·문서를 작업 공간에 두지 말라.
  - 처음 설계는 "개인정보 원자료 행을 모델로 보내지 않는다는 안내(DR-23)"였다. 그것은 집계 도구(GT-D8, P1)가 생긴 뒤의 일이다. 지금 엔진은 행을 그대로 보낸다(`src/workflows/index.ts`, 사용 안내 18.7). 그래서 있는 보호만 말한다(M-8).
- 작업 공간을 바꾸면 이전 작업 공간의 핸들, 파일 항목 id, 미리보기 토큰을 모두 버린다(6.5).

### 3.3 파일 트리

- 내용은 앱 계층의 작업 공간 목록 함수가 내준다(5절 "작업 공간 목록", 계약 추가 필요). GUI가 디렉터리를 직접 읽지 않는다. 함수가 지킬 것[가정]
  - U-103(G-list): 그 함수는 앱 계층의 `listWorkspaceDir`(U-89, [어댑터 계약](adapter-contract.md) 5.12)다. 엔진 호스트는 디렉터리를 직접 읽지 않고(GU-2의 임시 목록은 없앴다) 그 결과를 필드마다 확인해 넘긴다(`gui/src/engine-host/tree.ts`). 형식은 연 작업 공간과 설정 파일의 기본값(프로필·작업 종류 없음)이다. 그래서 가림과 보호 표시는 프로필 없는 간편 실행의 것이다. 이름은 제어 문자, 키 모양, 지금 설정된 모든 키 값, 설정에 등록한 가릴 값(`secretEnv`)으로 가린다. 가린 항목은 실제 이름 없이(`name: null`) 오므로 메인도 그 이름을 갖지 않는다. 설정 파일을 읽을 수 없으면(이름 붙인 설정 파일이 없음 등) 트리도 그 코드로 알린다.
  - 작업 공간 규칙(`src/workspace`)으로 경로를 해석한다. 링크와 정션은 따라가지 않고 "링크"로 표시만 한다.
  - 루트의 `.codaryn`은 펼치지 않는다. "Codaryn 기록(열지 않음)"으로 보인다.
  - 이름은 표시용으로 가린다: 제어 문자 정리, 키 모양 가림, 현재 등록한 가릴 값 가림(DR-7과 같은 "현재 등록한 값" 기준, AC-D14). 가린 이름의 항목은 펼치거나 고를 수 없다(경로를 되찾을 수 없다).
  - 디렉터리마다 나눠 읽는다(한 번에 최대 500개, 다음 쪽 토큰). 상한은 `inspect_files`(G-C)와 같은 수준이다.
- 항목은 메인이 발급한 **항목 id**로만 가리킨다(6.5). 화면은 상대 경로를 보내지 않는다.
- 표시
  - 디렉터리 먼저, 이름순(지역 정렬).
  - 고른 실행이 있으면 그 실행의 변경 표시: `[만듦]`, `[바꿈]`, `[옮겨 옴]`, `[보관함으로]`. 내용은 그 실행의 `changes` 출력에서 온다(3.4). 색은 보조다.
    - U-65: 고른 실행은 한 번에 하나다. 이 창에서 끝난 실행(연 작업 공간에서, 창이 아는 작업 형태로 시작한 것. task 파일의 실행은 아님)이면 그 결과의 바뀐 파일로, 변경 화면을 연 실행이면 그 화면이 읽은 파일과 상태로 표시한다. 낱말로 이름 뒤에 붙인다: "실행이 만듦", "실행이 바꿈", 상태가 `changed_since_run`이면 "그 뒤 다시 바뀜", 그 위 폴더에 "바뀐 파일 있음". 가린 이름(또는 가린 이름의 폴더 아래)은 맞추지 않는다. 트리 위에 어느 실행의 표시인지와 "표시 지우기"가 있다. 아무것도 바꾸지 않은 실행이 끝나면 앞 표시는 지운다. `[옮겨 옴]`, `[보관함으로]`는 적용 실행의 동작이라 `changes`에 없고(3.4) 아직 표시하지 않는다.
  - 보호 경로(설정의 `protectedPaths`)에 `[보호]`. 작업 공간 밖 파일은 없다.
    - U-65: 앱 계층 목록의 `protected`(U-89: 트리 형식, 곧 설정 파일 기본값의 실효 정책이 가진 보호 경로. U-102부터 글자와 실제 경로 둘 다로 맞춘다)를 메인이 참·거짓으로만 넘기고, 창이 낱말 "보호"로 이름 뒤에 붙인다. 프로필이나 작업 종류가 더하는 보호 경로는 표시하지 않고, 트리 위의 안내가 그렇다고 쓴다. 보호 폴더를 가리키는 링크·정션도 실제 경로로 표시된다(R-82 U-65 I1로 고침). 표시는 안내이고 쓰기는 엔진이 매번 확인한다.
  - 표시는 지금 디스크 기준이다. 실행 뒤 바뀐 파일은 `changes`의 `state`(`changed_since_run`, `missing`)를 따른다.
- 동작
  - 바뀐 파일을 고르면 변경 비교(3.4)가 그 파일로 열린다(U-65: 누르기나 Enter. 비교 화면은 그 파일 칸에 초점을 두고 한 번만 그렇게 연다).
  - 항목 메뉴: "탐색기에서 보기"(메인이 id를 경로로 바꿔 탐색기에서 선택 상태로 연다), "상대 경로 복사"(가린 이름으로 만든 경로). 상대 경로 복사(U-103, `copyPath`)는 초점 둔 항목의 id만 보낸다. 메인이 id를 경로로 풀고(가리지 않은 항목만 id가 있다), `/`로 나눈 마디, 길이 4096자, 숨은 글자(제어·줄·서식·방향·보이지 않는 글자)를 다시 확인해 쓴다. 경로의 이름은 앱 계층이 가리지 않은 이름이라 키 모양, 키 값, 등록한 값이 없다. 가린 항목은 id가 없어 열기·탐색기·복사 모두 없다.
  - U-123(R-82 U-103 L1): 설정을 쓰거나 새로 만들면 메인이 그때까지 준 트리·변경 항목 id를 모두 버리고(뒤의 복사·탐색기는 `unknown_entry`) 창에 알린다(`treeReset`). 창은 트리를 다시 읽는다. 나열한 뒤 새로 등록한 값이 옛 id로 복사되지 않는다.
  - DR-72: 파일 항목은 텍스트 보기(3.14)로 연다. 항목 메뉴의 "열기"다. 바뀐 파일을 누르거나 Enter를 누르면 지금처럼 변경 비교가 열린다. 기본 앱으로 열기는 없다(6.8).
  - 새로 고침(F5). 자동 감시(파일 시스템 감시)는 v1에 두지 않는다. 실행이 끝나면 한 번 새로 읽는다. U-65: 파일 영역 안의 F5와 "새로 읽기" 단추. 열려 있던 폴더는 이름 경로로 다시 열고 초점 둔 항목을 다시 찾는다. 창 전체의 F5는 U-67이다.

- [결정] DR-7: 다시 가린 비교만 보인다. 내용은 앱 계층의 `changes`(main에 있음, `ChangesOutput`)가 준다. GUI는 스냅샷 저장 형식을 읽지 않는다.

- 파일마다 보이는 것
  - `created`: "실행 전" 쪽이 비고 "이 실행이 만든 파일"을 쓴다.
  - `state`: `as_run_left` "실행이 남긴 그대로", `changed_since_run` "실행 뒤에 바뀜", `missing` "지금 없음", `unknown` "읽을 수 없음".
  - `unavailable`이면 글 대신 이유만 보인다: `masked_path`(경로가 가려져 파일을 찾을 수 없음), `snapshot_missing`, `not_text`, `too_large`, `mask_failed`. 원문 비교는 어떤 경우에도 없다.
  - 적용 실행(이동·폐기)은 내용 비교 대신 "어디서 어디로", "보관함으로" 목록을 보인다. 그 목록은 적용 결과(`run-applied`)와 보고서의 동작 탭에 있다. 적용 실행은 변경 화면을 열지 않는다(결과와 실행 목록의 "변경 보기"는 쓰기가 있는 실행에만 있다). 그래서 `changes`의 `applyRun`은 쓰지 않는다(U-61에서 확인).
- 비교 계산
  - 줄 단위 비교를 GUI가 한다. 입력은 이미 가린 두 글이다. 새 의존성 없이 순수 함수로 만든다(7절, 8절 `gui/src/renderer/diff`). 크기 상한은 앱 계층의 `MAX_READ_BYTES`를 넘지 않는다.
  - 보기: 나란히·한 줄 바꾸기, 줄 바꿈 켜기·끄기. 다음·이전 변경(F7, Shift+F7), 다음·이전 파일(Alt+F7, Alt+Shift+F7)[설계].
    - U-66: 화면 위의 두 스위치. 기본은 한 줄(지금까지의 모양)과 줄 바꿈 켬이다. 나란히 보기는 "실행 전 | 지금" 표다(`renderer/diff/side-by-side.ts`). 바뀌지 않은 줄은 양쪽에, 한 번의 변경 안에서는 지운 줄과 더한 줄을 차례로 마주 세우고, 남는 쪽은 빈 칸과 마주 선다. 변경마다 첫 줄에 F7이 선다. 스위치는 읽어 둔 파일을 다시 그릴 뿐 다시 묻지 않고, 창이 열려 있는 동안 남는다(창을 다시 열 때의 기억은 U-70). 한쪽 글만 있는 파일은 두 보기 모두 그 글만 보인다.
    - U-66: 파일마다 "탐색기에서 보기". 메인이 `changes` 답에 트리와 같은 항목 id를 붙인다. 경로가 평범하고(`copyablePath`), 상태 폴더 밖이며, 지금 없거나(`missing`) 가린 경로(`masked_path`)가 아닌 파일만이다. 화면은 그 id로 기존 `reveal`을 부르고 경로를 보내지 않는다. 메인은 작업 공간 안인지 다시 본 뒤 OS 파일 관리자에서 선택 상태로 보인다(연기 시험은 기록기). 보일 수 없으면 그렇다고 쓴다.
    - U-123(R-87 U-66 L1): 메인이 id를 주기 전에 그 경로가 작업 공간 안에 지금 있는 파일이나 폴더인지 `lstat`으로 본다(링크는 아님). 앱 계층이 가린 경로(키 모양을 `[key]`로 보인 이름)는 디스크에 없으므로 id를 받지 않는다.
- 비교 화면 안에서는 고치지 않는다. DR-72: 파일마다 "이 파일 열기"로 텍스트 보기(3.14)를 연다. 메인이 그 파일에 항목 id를 준 경우(위 U-66의 조건)만이다. 복사는 화면의 가린 글만 복사한다.
- 설정을 풀 수 없으면(AC-D13) 오류 카드와 바뀐 파일 목록만 보인다.


- 간편 형식: `startRun({input: {kind: "quick", workspace, goal}, profile, workflowRef})`(AC 5.1, DR-2). 작업 공간은 핸들로 정하고 메인이 경로로 바꾼다.
- 작업 종류: 내장 정의와 사용자 설정 `workflows`(GT-D1). 목록은 앱 계층의 설정 읽기 함수가 준다(5절).
- 프로필: N-8. 목록은 설정 읽기 함수가 준다. 마지막으로 고른 프로필 이름은 작업 공간별로 `gui-state.json`에 남긴다(권한이 아니다).
- 모델: 이 실행에 쓰일 모델을 보기 전용으로 보인다(설정과 프로필이 정한다). 실행마다 모델을 바꾸는 필드는 실행 요청에 없다. 바꾸려면 설정 > 모델(3.10)로 간다[설계].
- task 파일로 실행(개발자용): OS 파일 대화상자로 task 파일을 고른다. 작업 공간 안의 파일은 거부된다(S-1, `startRun`이 검사). 변수 파일은 GUI-D8에 따른다.
  - U-63: 새 작업 화면의 "task 파일 고르고 실행…"(변수 파일도 고르기 선택). 화면은 열린 작업 공간 핸들과 변수 파일 여부만 보낸다(`startTaskRun`). 메인의 OS 열기 대화상자가 task 파일과 변수 파일을 고르고, 경로는 엔진 호스트에만 가며 화면에도 `gui-state.json`에도 남지 않는다. 대화상자를 파일 없이 닫으면 아무것도 시작하지 않고 세션의 목표를 그대로 둔다.
  - task 파일은 자기 작업 공간을 정한다. 앱 계층은 그 작업 공간을 어댑터에 알리지 않는다(`StartOutcome`에 없음, 앱 계층 담당에 보고). 그래서 결과의 다음 행동은 열린 작업 공간의 실행 목록에 그 실행이 있을 때만 보이고, 아니면 그 폴더를 열라고 쓴다.
  - 작업 형태(task 파일)를 기억하지 않으므로, 그 실행은 이 앱 밖에서 시작한 실행처럼 다룬다: 계획은 보기만, 사람의 검토는 CLI로.
- 목표의 키 검사(S-8)와 사전 검사는 `startRun` 안에서 CLI와 같은 순서로 한다. 실패하면 `AppError`가 오고 아무것도 만들어지지 않는다.
- 고급은 접힌 상태가 기본이고 **보기 전용**이다. 실행 요청에는 정책·한도·보호 경로를 덮어쓰는 필드가 없다(AC 5.1, M-9). 바꾸려면 "설정 > 권한 규칙"으로 간다.
- 목표 원문은 저장하지 않는다(GUI-D11). 다시 실행은 같은 앱 세션 안에서만 원문으로 채운다.
- 실행은 앱 전체에서 하나다(GUI-D12). 실행 중에는 새 작업 단추가 꺼지고 상태 표시줄로 간다.

### 3.6 진행 표시와 취소

```
┌ 실행 중 · 작업 ux-doc ─────────────────────────────────────────┐
│ 상태: 실행 중   경과 0:42   턴 3/12   도구 5/24   토큰 12,400      │
├─────────────────────────────────────────────────────────────┤
│ 14:02:11  1턴 · 파일 읽기 README.md — 허용                      │
│ 14:02:15  파일 만듦 INSTALL.md                                  │
│ 14:02:16  명령 실행 — 거부: 허용 목록에 없음 (command/command_not_allowed) │
│ 14:02:20  검증 1 — 통과                                         │
├─────────────────────────────────────────────────────────────┤
│ [기록 종류 ▾]                                    [실행 취소…]   │
└─────────────────────────────────────────────────────────────┘
```

- 이벤트: 앱 계층의 `RunEvent`. 앱 계층이 엔진이 넘긴 메모리의 사건으로 만들고 글 필드를 다시 가린 것이다(DR-15). GUI는 기록 파일을 읽지 않는다.
  - 보이는 범위는 CLI 진행 줄(U-8)과 같다: 시작, 턴, 도구 허용·거부, 파일 변경, 검증, 재수정, 보호 대상 확인, 안내(`notice`), 끝. 검증기는 id가 아니라 순번으로 쓴다(N-24 (a)).
  - 문장은 공용 문구 카탈로그와 N-C의 순수 함수로 만든다(11절). 모르는 도구 이름은 `(unknown tool)`로 바꾼다(R-1 L-1, AC-D15).
  - 실행 시작은 핸들의 `runId`로, 끝은 `done`으로 안다(AC 5.2 보장 3). `seq`가 빠지면 "진행 표시 일부가 빠졌습니다. 결과의 기록 탭에서 전체를 보세요"를 한 줄 보인다.
  - 엔진 호스트가 이벤트를 모아 100 ms마다 한 묶음으로 보낸다[설계]. 화면 낭독기 알림도 이 묶음 단위로 한다(10절).
  - 메인은 실행을 시작한 뒤 gui-state를 쓰고 나서 창에 시작의 답을 준다. 그래서 묶음과 끝이 그 답보다 먼저 창에 올 수 있다(U-144). 창은 시작 중에 온 묶음(100개까지)과 끝을 두었다가, 답의 `runId`와 같은 실행의 것만 순서대로 받는다. 넘친 묶음은 진행 표시의 빠짐으로 알린다.
- 진행 기록 패널: 실행 화면 아래 목록. 종류 필터(전체, 거부만, 파일 변경만, 검증만). 실행이 끝나도 결과의 기록 탭에서 다시 본다.
- 상태 표시줄: 상태 낱말, 턴·도구 사용량, 경과 시간. 누르면 실행 화면으로 간다.
- 작업 표시줄: 실행 중에는 진행 중 표시(진행률 없는 형태)[추정 E-3]. 숫자나 목표는 넣지 않는다.
- 끝 알림: 창이 활성이면 앱 안 알림만. 비활성이면 OS 알림 하나. 내용은 고정 문구와 상태 낱말뿐이다("Codaryn 실행이 끝났습니다: 완료"). 목표, 경로, 파일 이름은 넣지 않는다(6.9).
- **취소**
  - `startRun`이 응답하기 전(사전 검사 중)에는 취소 대상이 없으므로 단추를 "준비 중"으로 끈다(AC 5.3).
  - 누르면 화면 안 확인: "취소해도 이미 한 변경은 남습니다. 결과 화면에서 되돌릴 수 있습니다." 기본 단추는 "계속 실행"이다. 취소는 파일을 바꾸지 않으므로 메인 확인을 쓰지 않는다.
  - 확인하면 `handle.cancel()`. CLI의 Ctrl+C·취소 파일과 같은 신호다. 끝 상태는 `cancelled`이고 변경은 남는다(AC 5.3). 적용 실행도 같은 취소를 쓴다(DR-2, DR-18 (d)).
  - 단일 키(Esc)는 취소에 쓰지 않는다.
- **창 닫기·앱 종료**
  - 실행 중이면 "실행을 취소하고 닫을까요?"를 묻는다.
  - 확인하면 `handle.cancel()`을 부르고 `done`이 풀릴 때까지 최대 10초 기다린 뒤 닫는다[설계, R-1 L-3]. `done`은 result.json 저장과 잠금 해제 뒤에 풀린다.
  - 10초 안에 오지 않으면 "결과를 알 수 없음, 다음에 열 때 실행 목록에서 확인"을 보이고 닫는다. 남은 잠금은 다음 실행이 회수한다(P-4, N-25 (b)).
- **실행 중 권한 확인**(AC 5.7, DR-3, DR-10, 어댑터 계약 5.9. U-124에서 구현. CLI의 터미널 질문은 cli-contract 18.17)
  - 권한 확인 전용이다. 계획 승인은 이것으로 하지 않는다(DR-1). 명령 권한만 묻는다. 다른 권한의 질문은 답이 없는 것, 곧 기본 거부다.
  - **화면 안의 패널이 아니라 메인의 OS 대화상자가 묻는다**(처음 설계의 "패널"을 바꿈).
    - 렌더러에는 답하는 통로가 없다. `window.codaryn`에 그런 함수가 없음을 연기 시험이 본다.
    - 그래서 화면의 글이나 스크립트가 허용을 누를 수 없다.
  - 흐름:
    1. 앱 계층의 `RunObserver.confirm`(U-108)이 질문을 받는다.
    2. 엔진 호스트가 질문을 `question` 메시지로 메인에 보낸다.
    3. 메인의 OS 대화상자가 묻는다.
    4. 답을 `answerQuestion` 호출로 엔진 호스트에 준다.
    5. 엔진이 정책 2차 판정을 다시 하고, 허용일 때만 그 호출 하나를 실행한다.
  - 질문 글은 엔진이 준 가림본뿐이다.
    - 실행 파일(`subject`): 엔진 호스트가 키 모양·키 값을 한 번 더 가린다.
    - 인자 개수. 인자 글은 없다.
    - 메인이 꼴을 다시 본다: 1000자 이하, 제어·방향·보이지 않는 글자 없음. 아니면 묻지 않고 답이 없는 것으로 친다.
  - 글의 뜻은 CLI의 `confirm.question.command`와 같다: "명령 하나를 이번 호출에만 허용할까요? 답하지 않으면 거부합니다. 보이는 것은 실행 파일 이름과 인자 개수뿐이며, 인자 자체는 보이지 않습니다."
  - 단추는 "이번 호출에만 허용"과 "거부"다. 기본과 Esc는 "거부"다. "항상 허용"은 없다.
  - 답과 기록:
    - "이번 호출에만 허용"은 `allow_once`(`user`)다.
    - "거부"와 Esc는 `deny`(`user`)다.
    - 창이 없거나 묻다가 실패하면 `dismissed`이고, 기록은 `deny`(`default`)다.
    - 실행이 취소되거나 시간 한도에 닿으면 엔진의 신호가 질문을 끝내고(`questionEnded`) 메인이 대화상자를 닫는다. 기록은 엔진이 정한다(`cancelled` 또는 `default`).
    - 실행이 끝나면 열린 질문은 모두 닫힌다.
  - 기다리는 시간도 실행 시간 한도에 든다(AC-D6).
  - 실행 결과에는 CLI 끝 요약(`summary.confirm_denied.*`)과 같은 뜻의 줄이 질문이 끝난 방식마다 하나씩 붙는다.
    - 줄의 종류: 사람이 그 호출에만 허용, 사람이 거부, 답이 없어 거부(질문을 보일 수 없었거나 시간 한도), 기다리는 동안 취소되어 거부.
    - 엔진 호스트가 그 실행의 `confirmation_answered` 기록으로 센다.
    - 진행 목록에는 질문과 답마다 CLI의 진행 줄이 보인다.
  - 설정 바꾸기의 넓히기 `confirm_removed`(묻던 명령을 묻지 않고 허용)는 넓히기 대화상자와 설정 화면이 이름으로 보인다.
  - 대화상자가 이름을 모르는 넓히기 종류가 든 제안은 쓰지 않는다(`unknown_widening`).

- 결과 화면은 앱 계층 `report`의 구조화된 `ReportOutput`으로 그린다. Markdown을 HTML로 바꿔 그리지 않는다.
- 보고서 저장: 메인의 OS 저장 대화상자로 Markdown을 저장한다. 내용은 `report`와 같은 가림본이다.
- **사람의 검토**(GT-D6, DR-1)
  - 단추는 앱 계층의 `review`를 부른다. 판정은 `review.json`에 남는다.
  - 끝 상태는 바뀌지 않는다. 받아들여도 "완료(검증 통과)"와 다른 표시("확인 필요 → 사람이 받아들임")를 쓴다(M-16).
  - U-163: 낱말은 CLI와 같다. 검토 단계는 "검토", 판정은 "받아들임"·"거절함"이고, "승인"은 계획 승인에만 쓴다(R-98 L-4: 정한 것은 이것뿐이다).
  - 메모는 키 검사를 거친다(S-8). 기본 단추는 없다. 판정은 파일을 바꾸지 않으므로 화면 안 확인으로 한다.
- 다시 실행: 같은 설정으로 새 실행을 만든다(architecture 8절). 목표 원문은 GUI-D11.

### 3.8 실행 목록과 되돌리기 미리보기

- 내용: 앱 계층의 실행 목록(DR-14, w3:pA 진행 중). 열: 시작 시각(지역 시간), 종류(실행·적용), 상태 낱말, 바뀐 파일 수, 작업 id(가림본).
  - "손상" 실행(N-23 (b), N-26)은 "손상(기록을 확인할 수 없음)"으로 보이고 보고서·비교·되돌리기 동작이 없다.
  - 기록 변경 표시가 있는 실행(UXM-14, DR-38)은 행에 CLI의 짧은 표시 "기록 변경됨"을 더한다. 그런 행이 있으면 목록 아래에 그 뜻을 한 줄 둔다(CLI `runs.records_changed_note`, U-157·U-163).
  - 되돌리기 기록만 손상된 실행(N-23 (g))은 정상 행에 "되돌리기 기록 손상" 표시를 더한다.
  - 되돌린 실행은 "되돌림"과 시각을 보인다(N-22).
- **GUI는 `latest`를 쓰지 않는다**[설계]. 사람이 목록에서 고른 행의 실행 id를 그대로 넘긴다. 자동 선택(R-2 M-2)과 대소문자만 다른 id(R-7 M-1)가 생기지 않는다.
- 행 메뉴: 보고서, 변경 비교, 되돌리기, (해당하면) 계획 보기·사람의 검토, 실행 id 복사.
- **되돌리기**
  1. 미리보기: `revert({dryRun: true})`(N-7, DR-14). 대상 파일과 동작(지움·되살림·제자리로 옮김·보관함에서 되살림), 건너뛸 파일과 이유를 보인다. 메인이 이 미리보기에 **미리보기 토큰**을 붙인다(6.6).
  2. "되돌리기…"를 누르면 메인이 OS 확인 대화상자를 띄운다. 내용: 실행 id, 되돌릴 파일 수, 건너뛸 파일 수, "미리보기 뒤에 바뀐 파일은 건너뜁니다". 기본 단추는 "되돌리지 않음"이다.
  3. 확인하면 `revert({dryRun: false})`. 결과는 `complete` 또는 `partial`과 건너뛴 파일마다 이유. 이미 되돌린 실행은 그렇게 표시한다.
  - 미리보기는 약속이 아니다. 두 호출 사이에 바뀐 파일은 두 번째 호출이 해시 비교로 건너뛴다(AC 5.5).
- 실행 기록 정리와 보관함 정리
  - 실행 기록 정리는 개수와 크기를 보이고 메인 확인을 받는다([UX 설계](ux-design.md) 7절, PV-D1). 폐기 보관함은 지우지 않는다(DR-9).
  - 보관함 정리는 따로 둔다. 파일 수와 크기를 보이고 "이 파일들은 영구히 지워집니다"를 메인 확인으로 받는다. 기본 단추는 "지우지 않음"이다. GUI는 보관함 파일의 내용을 그리지 않는다.

### 3.9 계획 승인 (DR-1, DR-21)

결과가 `needs-input`/`plan_pending`이면 요약 탭의 다음 행동이 "계획 보기"다. 실행 중 질문이 아니다(DR-1).

```
┌ 계획 확인 · 작업 photos-by-year ────────────────────────────────┐
│ 이동 120개 · 보관함으로 3개 · 다이제스트 3f9a1c0b7e21 [복사]        │
├────────────────────────────────────────────────────────────┤
│ 이동    IMG_0001.jpg      → 2023/IMG_0001.jpg                  │
│ 보관함  Thumbs.db         → 보관함                              │
│ …                                                            │
├────────────────────────────────────────────────────────────┤
│ 적용 전 점검: 하드 링크를 쓸 수 없는 드라이브의 이동 12개           │
│   기본으로 옮기지 않습니다. 이번 적용에 한해 동의하면 옮깁니다.       │
├────────────────────────────────────────────────────────────┤
│ 모델이 제안한 계획입니다. 적용 전에 파일이 바뀌면 적용하지 않습니다.  │
│                       [적용 안 함]  [이 계획 적용…]               │
└────────────────────────────────────────────────────────────┘
```

- 계획 내용: 앱 계층의 `plan`이 `plan.json`을 다시 가려 준다(DR-5, DR-17, `PlanView`). 화면은 기록이나 파일을 직접 읽지 않는다.
- 다이제스트는 GT의 다이제스트 하나다(DR-1). 앞 12자를 보이고 복사 단추를 둔다.
- `inventoryLimitReached`이면 적용 전에 알린다(DR-6). 그때는 적용 뒤 검증이 사람의 검토에 더 기댄다는 점을 쓴다.
- **적용 전 점검**[가정, 계약 w3:p9·앱 계층 w3:pA]
  - 계획 화면을 열 때 앱 계층의 적용 전 점검 함수를 부른다. 적용기의 `check`(G-C)와 같은 판정을 아무것도 옮기지 않고 돌려준다. 볼륨마다 하드 링크를 쓸 수 있는지 보려고 시험 링크를 잠깐 만들었다 지운다(G-C 적용기의 사전 점검과 같다).
  - 행동별 문제(`source_changed`, `destination_exists` 등)가 있으면 그 행에 표시하고 "다시 실행해 새 계획 만들기"를 권한다.
  - 하드 링크를 쓸 수 없는 드라이브의 이동(`unsafe_move`, DR-18 (b))이 있으면 위 화면처럼 따로 보인다.
  - U-119(구현): 앱 계층 `checkApply`(U-91, 어댑터 계약 5.14)를 쓴다.
    - 화면은 계획 보기의 승인 토큰만 보낸다(`checkPlan`). 메인이 토큰을 쓰지 않고 들여다보고, 자기가 보인 계획의 실행·작업 형태·다이제스트로 엔진 호스트에 묻는다. 그래서 화면이 다른 계획이나 다이제스트를 고를 수 없다.
    - 응답은 순번·코드·수뿐이다. 메인이 순번이 계획 안인지, 그 계획의 답인지 확인한다.
    - 계획의 행에 문제 낱말("계획 뒤에 파일이 바뀜" 등)과 "적용할 때 동의가 필요함"을 붙이고, 수를 문장으로 쓴다.
    - 점검이 거두지 못한 것을 알린다: 남은 시험 링크(`probesLeft`, 알림), 지운 앞선 시험 링크(`probesRemoved`), 풀지 못한 잠금(`lockLeft`, 알림, `.codaryn/lock.json` 안내).
    - "점검은 승인이 아닙니다"를 늘 쓴다. 적용은 그대로 토큰과 OS 확인을 거치고, DR-21 동의도 지금처럼 적용 때 따로 묻는다.
    - 점검은 작업 공간 잠금을 잠깐 잡으므로, 점검의 답이 올 때까지 적용 단추를 끈다. 점검이 실패해도(예: `workspace_locked`) 켠다. 적용이 다시 점검하기 때문이다.
- **"이 계획 적용…"**
  1. 메인이 OS 확인 대화상자를 띄운다: 이동·보관함 개수, 다이제스트 앞 12자, "폐기는 `.codaryn/discarded/<적용 실행 id>/` 보관함으로 옮깁니다. 실행 기록을 정리해도 보관함은 지워지지 않습니다". 기본 단추는 "적용 안 함"이다.
  2. **DR-21 동의**: 점검에 하드 링크 없는 이동이 있으면 메인이 **별도의** OS 대화상자를 하나 더 띄운다.
     - 내용: "이 드라이브는 하드 링크를 쓸 수 없습니다. 옮기는 도중 같은 이름의 파일이 새로 생기면 그 파일을 덮어쓸 수 있습니다. 이번 적용 한 번에만 동의합니다."
     - 단추: "동의하지 않음"(기본), "이번 적용에 동의". 동의하지 않으면 적용하지 않는다. 그 이동만 빼고 적용하는 선택지는 두지 않는다(계획은 통째로 승인한다, GT-D4).
     - 동의 값은 메인이 이 대화상자의 결과로만 만든다. 화면이 보낸 인자로는 받지 않는다(6.6). task 파일과 모델은 줄 수 없다(DR-21). 동의는 적용 기록에 남는다(계약 w3:p9).
  3. 확인하면 `applyPlan({settings, planRunId, digest}, observer)`(DR-1, DR-2). 적용은 새 실행이다(GT-D13). 진행 표시와 취소(3.6)를 같이 쓰고, 끝나면 적용 실행의 결과로 간다.
- 계획 뒤 원본이 바뀌었으면 아무것도 옮기지 않고 `plan_stale` 카드가 뜬다. 다음 행동은 "다시 실행해 새 계획 만들기"다.
- 이미 적용한 계획(`status: "applied"`)은 적용 단추 없이 "적용함: <적용 실행>"을 보인다.

### 3.10 설정·프로필·모델 선택

| 쪽 | 내용 | 확인 |
| --- | --- | --- |
| 일반 | 언어(자동·한국어·English), 설정 파일 위치(보기 전용, "탐색기에서 보기"). `CODARYN_LANG`·`CODARYN_CONFIG`가 정하면 그 사실. U-69: "탐색기에서 보기"는 메인이 엔진 호스트의 `configFile`에서 받은 경로를 OS 파일 관리자에서 선택 상태로 보인다. 경로는 창에 오지 않고, 파일이 없으면 `config_missing`이다 | 언어는 확인 없음 |
| 모델 | 제공자별 현재 모델, "목록 가져오기"(접속 고지), 고르기. `CODARYN_MODEL`이 덮어쓰면 그 사실(Y-3) | 고르기는 확인 없음 |
| 프로필 | N-8 프로필 목록과 각 프로필의 한도·허용 명령·검증(보기). 새 작업의 기본 프로필 고르기 | 프로필 내용 바꾸기는 권한 규칙과 같은 확인 |
| 권한 규칙 | 허용 명령, 보호 경로, 한도 | 넓히는 변경은 메인 OS 확인(6.6) |
| 가릴 값 | `secretEnv` 이름과 설정 여부. 이름 추가·삭제만, 값 입력란 없음(S-3) | 삭제는 메인 확인 |
| 키 | 제공자별 키 변수의 있음·없음과 등록 방법. 값은 보이지 않는다 | — |
| 점검 | `doctor` 항목과 낱말 상태(ok·warn·fail·skipped) | — |

- 읽기와 쓰기는 앱 계층의 설정 함수로 한다(5절 "설정 읽기·변경 제안·적용", 계약 추가 필요). 쓰기 규칙(원자적 쓰기, 형식 검사)은 `models --use`와 한 곳에 둔다. GUI가 설정 파일을 직접 쓰지 않는다.
- 변경은 두 단계다: 변경 제안(무엇이 어떻게 바뀌는지, 넓히는 변경인지를 앱 계층이 판정) → 적용(넓히는 변경이면 메인 OS 확인 뒤). 넓히는 변경의 목록은 [UX 설계](ux-design.md) 7절이다.
- **모델 목록**: 실제 API에 접속한다(Y-2). 사람이 "목록 가져오기"를 누를 때만 부른다. 단추 옆에 "<제공자> API에 접속합니다"를 쓴다. 화면을 열 때 자동으로 접속하지 않는다.
- **제공자 중립**(DR-22): 제공자 이름, 키 변수 이름, 모델 목록은 설정과 앱 계층에서 받는다. 화면 코드에 "Anthropic"이나 `ANTHROPIC_API_KEY`를 고정해 넣지 않는다.
  - 제공자 표는 계약의 `API_PROVIDERS`에서, 목록을 잇는 제공자는 앱 계층의 `CONNECTED_MODEL_PROVIDERS`(지금 anthropic, openai)에서 온다. 키 없는 체험용 대본 제공자는 CLI에서만 쓴다.
  - 제공자 바꾸기는 설정 파일의 `provider`를 바꾸는 변경 제안이다. 앱 계층이 넓히기(`provider_changed`)로 판정하므로 메인 OS 확인 뒤에 쓴다(SP-D3, F-3, 14.4).
  - 제공자마다 응답의 최대 길이(`maxOutputTokens`)를 보이고 편집 하나(`outputCap`)로 정한다(U-80). 그 제공자가 읽는 곳에 쓴다: anthropic은 `providers.anthropic`이 없으면 최상위, 아니면 `providers.<이름>.maxOutputTokens`(CLI의 `providerSettingsOf`, 모델을 쓰는 자리와 같다). 없으면 그 제공자로 하는 실행은 아무것도 보내기 전에 `provider_not_configured`로 멈춘다고 그 줄에 쓴다.
  - U-80 전에는 첫 설정(init)이 최상위 값(anthropic의 것)만 쓰고 GUI에 이 편집이 없어, GUI만으로 openai를 고르면 실행이 멈췄다. 앱 계층의 넓히기 판정에는 이 필드가 없어(`src/app/settings-change.ts`) 메인 OS 확인 없이 쓴다.
- **키**: 키 입력란은 어디에도 없다(C-1, N-10). 키는 앱을 실행한 환경의 변수로만 받는다. 등록한 뒤에는 앱을 다시 시작해야 한다(GUI-D7). 안내 문구는 OS별로 다르다(E-8).

### 3.11 첫 실행 안내 (마법사 4쪽, `init` 대응)

1. **설정 폴더**: 기본 위치(N-1)를 보여 주고 만든다. 설정 파일이 이미 있으면 덮어쓰지 않고 "기존 설정 사용"으로 간다(N-2).
2. **모델**: 키가 있으면 "목록 가져오기" 단추(접속 고지)를 보인다. 키가 없으면 자리표시자를 남기고 "키를 등록한 뒤 설정 > 모델에서 고르세요"로 넘어간다(N-2, N-3). 키 없이 체험하는 대본 예시로 가는 단추를 둔다([사용 안내](../usage.md) 3절).
3. **권한**: 한도 기본값, 허용 명령 제안, 보호 경로 제안. 제안은 항목마다 체크 상자이고 기본은 꺼짐이다. 명령 인자는 고정한다. 첫 선택지는 "문서만 고칩니다(명령 실행 없음)"다.
4. **점검**: `doctor`와 같은 항목을 낱말로. 키가 없으면 등록 방법을 안내한다. **키 입력란은 없다.**

설정을 읽지 못하면(파일이 없거나 깨짐, R45-L-1) 1~3쪽은 그 오류와 "4쪽 점검에서 이유를 보세요", 4쪽으로 가는 단추를 보인다. 4쪽은 설정 없이도 점검을 돌리고 그 결과(설정 파일 항목)로 이유를 보인다.

### 3.12 오류 카드와 상태 표현

- 오류 카드: [UX 설계](ux-design.md) 4.9의 세 부분(무엇이, 고치는 법, 코드). 고치는 법이 화면 이동이면 그 화면으로 가는 단추를 둔다. 문구는 CLI 사람용 오류(N-5)와 같은 함수에서 받는다.
- 엔진 호스트가 끝난 경우(4.4)는 어댑터 쪽 오류 카드다: "실행 결과를 알 수 없습니다. 실행 목록에서 확인하세요."
- 상태 낱말은 [UX 설계](ux-design.md) 6절의 표를 그대로 쓴다. 다음 행동 단추. U-61부터 결과 화면에 다음이 있다: 보고서·보고서 저장·변경 보기·계획 보기·사람의 검토(전부터), 바뀐 것이 있는 실행·적용의 "되돌리기 미리보기"(실행 목록에서 그 실행의 미리보기로), `protected_changed`의 보호 대상 탭, `budget-exhausted`의 설정(한도), `plan_stale`의 안내와 "다시 실행해 새 계획 만들기"(새 작업, 같은 세션의 목표와 형태로)
  - `done/verified`: 보고서 저장, 변경 비교, 되돌리기.
  - `needs-input/protected_changed`: 보호 대상 탭.
  - `needs-input/plan_pending`: 계획 보기(3.9).
  - `needs-input/awaiting_review`: 검토 탭.
  - `failed/plan_stale`: 다시 실행해 새 계획 만들기.
  - `failed/apply_incomplete`: 보고서, 되돌리기.
  - `budget-exhausted/*`: 설정 > 권한 규칙(한도), 새 작업.
  - `cancelled`: 되돌리기. 적용 실행이 취소됐으면 옮긴 항목 목록과 되돌리기.

### 3.13 명령 찾기와 단축키

- 명령 찾기(Ctrl+Shift+P): 이 절의 동작을 이름으로 찾아 실행한다. 목록은 고정이다(새 작업, task 파일로 실행, 작업 공간 열기, 최근 폴더, 실행 목록, 변경 비교, 되돌리기, 점검, 모델 고르기, 언어 바꾸기, 실행 취소). 모델이 만든 글이나 파일 이름으로 명령을 만들지 않는다.
- 단축키: 새 작업 Ctrl+N, 작업 공간 열기 Ctrl+O, 실행 Ctrl+Enter, 설정 Ctrl+쉼표, 영역 이동 F6, 새로 고침 F5, 다음·이전 변경 F7·Shift+F7. 취소에는 단일 키를 쓰지 않는다.
- U-67(구현): 명령 찾기는 창 위의 대화상자다(`renderer/shell/palette.ts`, 콤보 상자와 목록 상자). 위의 고정 목록에 설정과 새로 고침을 더했고, 이름은 창의 문구 표에서 온다. 친 낱말이 모두 들어간 이름만 남긴다. 위·아래로 고르고 Enter로 실행하며(대화상자를 닫은 뒤), Esc로 닫으면 초점이 원래 자리로 돌아간다. 열려 있는 동안 창의 단축키는 쉰다. 지금 쓸 수 없는 명령(진행 중인 실행이 없을 때의 실행 취소)은 "지금은 쓸 수 없음"으로 보이고 실행되지 않는다. 실행 취소는 실행 화면의 확인(기본 "계속 실행")을 거친다. task 파일로 실행은 새 작업 화면의 그 단추를 누른다. Ctrl+N(새 작업)과 Ctrl+쉼표(설정)를 더했다. F5는 트리를 다시 읽고, 양식이 없는 화면(작업 공간, 실행 목록, 점검, 변경, 보고서, 계획, 정리, 설정)만 다시 그린다. 새 작업과 실행 화면은 친 글을 잃지 않게 다시 그리지 않는다. 파일 영역 안의 F5는 트리만 다시 읽는다(U-65).

### 3.14 텍스트 보기와 고치기 (DR-71, DR-72)

사용자 요청 DR-71과 PM 결정 DR-72로 처음 설계의 "편집은 없다"(3.4)와 GUI-D20을 바꾼다. 가능성 검토와 UX 검토(`text-editing-ux.md`) 뒤 범위를 작게 정했다.

- **범위(DR-72)**
  - 여는 곳: 파일 트리(3.3)와 변경 화면(3.4).
  - 기본 입력란(`textarea`)이다. 새 의존성은 없다(GUI-D10, GUI-D15).
  - 다음 파일은 읽기 전용이다.
    - 가리면 글이 달라지는 파일. 가린 글로 보인다.
    - 보호 경로의 파일, 줄 끝이 섞인 파일.
    - 크기 상한(`MAX_READ_BYTES`, 256 KiB)을 넘는 파일, 텍스트가 아닌 파일. 이 둘은 글을 보이지 않고 까닭만 쓴다.
    - 실행이 작업 공간 잠금을 가진 동안의 모든 파일.
    - [결정] PM(U-174): 가린 값이 든 파일과 보호 경로의 파일은 읽기 전용이다. UX 검토의 "가린 값이 든 줄만 잠그는 편집기"(5.3)와 "보호 경로는 저장 전 확인"(5.7)은 쓰지 않는다.
  - 저장
    - 실행과 같은 작업 공간 잠금을 잡는다. 열 때의 해시와 디스크가 다르면 거부한다.
    - 줄 끝과 BOM은 열 때 그대로 지킨다.
  - 실행 기록과 되돌리기
    - 사람이 고친 것은 실행 기록에 넣지 않는다.
    - 실행이 바꾼 파일을 고치면 그 실행의 되돌리기가 이 파일을 건너뛴다. 그것을 저장 전에 알린다.
  - 넣지 않는 것: task·설정 파일 편집, 파일 만들기·이름 바꾸기·지우기, 구문 강조, 여러 탭.
- **단위**: 앱 계층 읽기·쓰기(U-172, p5a-adapter) → GUI 읽기 전용 보기 → GUI 편집·저장. 각 단위는 보안 검토를 거친다.
- **앱 계층(U-172)에 기대는 것** [가정: U-172 계약이 오면 이 줄을 그 이름으로 바꾼다]
  - 읽기: (설정 형식, 상대 경로) → 상태와 가린 글.
    - 상태: 읽음, 너무 큼, 텍스트 아님, 없음, 거부(뿌리 밖·상태 디렉터리·링크), 읽을 수 없음.
    - 읽었을 때 함께 오는 것: 열 때의 해시, 줄 끝(`lf`·`crlf`·섞임·없음), BOM 여부, 보호 여부, 편집 가능 여부와 읽기 전용 까닭.
    - 경로 규칙은 `listWorkspaceDir`(어댑터 계약 5.12)와 같다: `Workspace.resolve`, 조각마다 `lstat`(링크 거부), 상태 디렉터리 거부, 보호는 정책의 판정.
  - 쓰기: (설정 형식, 상대 경로, 글, 열 때의 해시) → 씀(새 해시) 또는 거부 까닭(충돌, 잠금, 편집 불가, 너무 큼).
    - 앱 계층이 잠금을 잡고 줄 끝·BOM을 되돌려 원자적으로 쓴다.
  - 설정 형식은 트리와 같은 "트리 형식"(U-89: 설정 파일 기본값의 실효 정책)이다. 그래서 트리의 `[보호]`와 보기의 보호가 같다.
- **화면(읽기 전용 보기, 첫 GUI 단위)**
  - 화면 하나(`data-screen="text"`). 머리에 파일의 보이는 이름(트리와 같은 가린 이름), 낱말 표시 `읽기 전용`과 그 까닭, `보호`.
  - 본문은 읽기 전용 입력란(`readonly`)이다. 글은 `value`로만 넣는다(HTML로 해석되지 않음, 6.2의 `textContent` 원칙과 같은 뜻).
    - 줄 번호는 입력란 밖의 열로 그리고 낭독기에서 숨긴다(`aria-hidden`).
    - 커서 줄과 전체 줄 수는 상태 줄에 글로 쓴다.
  - 줄 바꿈 스위치(비교 화면 U-66과 같은 꼴), "다시 읽기", "탐색기에서 보기", "닫기"(앞 화면으로).
  - 글을 보이지 않는 경우(너무 큼, 텍스트 아님, 없음, 거부, 읽을 수 없음)에는 까닭과 "탐색기에서 보기"만 보인다.
  - 낱말이 먼저다(원칙 5). 읽기 전용 까닭은 색이 아니라 글이다.
- **통로(읽기 전용 보기)**
  - 화면: `openText(workspace, item)`
    - `item`은 트리 목록이나 `changes` 답에서 메인이 준 항목 id다(6.5). 경로는 보내지 않는다.
  - 메인
    - 핸들과 id를 풀어(`TreeIds`) 상대 경로를 얻는다. 모르는 id면 `unknown_entry`다.
    - 엔진 호스트에 읽기를 부른다.
    - 답을 다시 본다: 글은 문자열이고 `MAX_READ_BYTES` 이하, 해시는 64자 16진, 까닭은 허용 목록 안.
    - 화면에는 보이는 이름, 가린 글, 읽기 전용 여부와 까닭, 보호 여부, 줄 수만 준다. 해시·줄 끝·BOM은 메인이 가진다(편집 단위의 편집 토큰에 묶을 값).
    - 설정이 바뀌면(U-123의 `treeReset`) 연 보기의 id도 버린다. 화면은 "다시 읽기"를 권한다.
  - 엔진 호스트: 앱 계층 읽기를 부르고 값의 꼴만 맞춘다(`tree.ts`·`plan-check.ts`와 같은 꼴).
  - 연기 시험
    - 등록한 값이 없는 파일은 글이 파일과 같다.
    - 등록한 값이 든 파일은 가린 글이고 읽기 전용이다.
    - 큰 파일·이진 파일은 글 없이 까닭만 보인다.
    - 화면의 함수 목록에 `openText`가 더해진다(연기 시험 API 목록의 고정값이 바뀜).
- **편집·저장(둘째 GUI 단위, 줄기만)**
  - 편집할 수 있는 파일이면 입력란이 쓰기가 된다. Ctrl+S 또는 "저장", "연 때로 되돌리기"(저장 전까지), 저장 상태 낱말.
  - 화면: `saveText(editToken, text)`
    - 편집 토큰은 메인이 열 때 내준다. (작업 공간, 상대 경로, 열 때의 해시, 줄 끝, BOM)에 묶인다.
    - 저장하면 새 해시로 새 토큰을 준다.
  - 메인
    - 글을 다시 본다: 문자열, UTF-8로 `MAX_READ_BYTES` 이하, NUL 없음.
    - 연 파일마다 첫 저장을 OS 확인으로 묻는다(원칙 6, [결정] PM).
    - 거부 까닭은 충돌, 잠금, 편집 불가, 너무 큼이다. 화면이 낱말로 보이고, 입력란의 글은 남긴다.
  - `textarea`는 값을 LF로 바꾼다(HTML의 값 정규화). 앱 계층이 열 때의 줄 끝으로 되돌린다. 섞인 파일은 처음부터 읽기 전용이다.
  - 저장 전 알림: 고른 실행이 바꾼 파일이면 "저장하면 그 실행을 되돌릴 때 이 파일은 건너뜁니다". 문구는 nb-i18n이 정한다.
  - 저장하지 않은 고침
    - 화면을 바꿀 때는 창 안에서 묻는다(기본: 취소).
    - 창을 닫을 때는 메인이 OS 확인으로 묻는다. 화면이 "저장 안 함" 상태를 메인에 알린다. 실행 중 닫기 확인(GU-3)과 같은 꼴이다.
  - 탭 키는 입력란에서 초점을 옮긴다(초점 가두기를 피함). 들여쓰기 키는 UX 확정 뒤 정한다.
  - 클립보드: 입력란의 기본 복사는 메인의 복사 길(U-62)을 지나지 않는다. 고칠 수 있는 파일은 가린 글과 원래 글이 같으므로 새 노출은 없다(목표 입력란과 같다).

## 4. 프로세스 구조

### 4.1 구성

```
┌ 렌더러(화면) ───────────────────────┐  샌드박스, Node 없음, 원격 콘텐츠 없음
│ app://codaryn/ 의 HTML·CSS·JS       │  글은 textContent로만 넣는다
│ preload: window.codaryn (좁은 통로)  │
└───────────────┬───────────────────┘
                │ IPC 요청·응답(invoke) (네트워크 포트 없음)
┌───────────────▼───────────────────┐
│ 메인(Electron 주 프로세스, Node 24)  │  창, 보안 설정, app 프로토콜, OS 대화상자,
│                                    │  IPC 검사, 핸들, 메인 확인, gui-state.json
└───────────────┬───────────────────┘
                │ 표준 입출력: 한 줄에 JSON 하나 (stdin 요청, stdout 준비·응답)
┌───────────────▼───────────────────┐
│ 엔진 호스트(별도 Node 26+ 프로세스)   │  createCodarynApp(createNodeAppEnvironment())로
│ = 앱 계층 src/app + 엔진             │  만든 CodarynApp의 함수를 직접 부른다.
│ = CLI와 같은 엔진·정책·기록          │  명령은 기존 명령 실행기의 자식 프로세스
└───────────────────────────────────┘
```

- [결정] DR-26: 엔진 호스트는 Electron의 내장 Node가 아니라 **Node 26 이상의 별도 프로세스**다.
  - 확인한 사실(DR-26, 2026-11-12): 안정판 Electron 45.3.1의 내장 Node는 24.22.2다. GU-1에서 `ELECTRON_RUN_AS_NODE`로 같은 판을 확인했다.
  - 엔진은 Node 26 이상에서만 검증했다(M-21).
- 엔진 호스트는 앱 계층 함수를 직접 부른다(AC 3절, 5절). CLI 자식과 줄 프로토콜(AC 6절)은 쓰지 않는다. 메인과의 통로(4.2)는 GUI 내부 형식이고 어댑터 계약이 아니다.
- 메인을 거치는 이유: 화면과 엔진 사이에 경로 해석, 인자 검사, 메인 확인을 둔다. 화면은 엔진 호스트와 직접 통하지 않는다.
- 엔진 호스트를 따로 두는 이유
  - 엔진이 Node 26 이상에서 돈다(DR-26).
  - 엔진의 긴 동기 작업(가림, 해시)이 창 처리를 멈추지 않는다.
  - 엔진이 비정상 종료해도 창이 남아 안내한다.
  - 엔진 코드와 키 변수(지금은 `ANTHROPIC_API_KEY`)를 쓰는 곳이 한 프로세스에 모인다. 메인도 OS 환경을 물려받지만 키를 읽지 않는다(4.3).
  - Electron 실행 파일을 Node로 쓰는 기능(RunAsNode)을 켜지 않아도 된다(6.7).
- [결정] DR-8: 듣는 소켓이 없고, 앱이 끝나면 엔진 호스트도 끝난다(4.4). 허용된 명령이 띄운 분리된 자손은 알려진 한계다(DR-11, T-2).
- Electron이 Node 26 이상을 내장한 안정판을 내면 내장 방식으로 바꿀지 다시 본다(DR-26). 통로의 메시지 형식(`gui/src/shared/protocol.ts`)은 전송과 나눠 두어 그때도 쓸 수 있다.

### 4.2 메시지 통로

- 전송: 엔진 호스트의 stdin(메인 → 호스트)과 stdout(호스트 → 메인)뿐이다. stderr는 진단용이고 제품 빌드에서 버린다. 앱 코드가 여는 다른 파이프나 소켓은 없다. Windows에서 libuv가 표준 입출력에 쓰는 이름 있는 파이프(`uv…`)는 6.1의 규칙에서 뺀 내부 파이프다.
- 형식(판 1)[설계, GU-1 구현]
  - UTF-8, 한 줄에 JSON 객체 하나, 줄 끝 LF(앞의 CR은 버린다). 모든 메시지에 `"v": 1`.
  - 한 줄의 상한은 8 MiB다. 넘는 줄은 끝까지 건너뛰고 일부도 전달하지 않는다.
  - 호스트는 형식이 틀린 요청에 id가 있으면 오류로 답하고, 없으면 stderr에 한 줄 남기고 버린다. 요청 내용은 남기지 않는다.
  - 메인은 호스트가 보낸 잘못된 줄, 두 번째 준비 메시지, 기다리는 요청이 없는 응답을 프로토콜 위반으로 본다. 그때 호스트를 끝내고 기다리던 요청을 모두 실패시킨다.

| 종류 | 방향 | 모양 |
| --- | --- | --- |
| 준비 | 호스트 → 메인, 처음 한 번 | `{v, type: "ready", node: "<process.versions.node>"}` |
| 요청 | 메인 → 호스트 | `{v, id, call, args}`. `id`는 메인이 정하는 양의 정수, `call`은 정해진 이름 |
| 응답 | 호스트 → 메인 | `{v, id, ok: true, value}` 또는 `{v, id, ok: false, error: {code, message}}`. `value`는 앱 계층의 `AppCallOutcome` 그대로 |
| 이벤트 | 호스트 → 메인 | `{v, type: "events", runToken, events: [...]}`(100 ms 묶음, GU-3에서 더함) |
| 실행 끝 | 호스트 → 메인 | `{v, type: "done", runToken, outcome}`(GU-3에서 더함) |

- 호출 이름: GU-1은 `doctor`(앱 계층 `doctor`)와 `messages`(공용 문구 카탈로그, 11절) 둘이다. 그 뒤 단위가 5절의 함수를 하나씩 더한다. 모르는 이름은 `unknown_call`이다.
- 통로 오류 코드: `invalid_message`, `unknown_call`, `invalid_args`, `host_error`(앱 함수의 예외. 예외 글은 넘기지 않는다), `adapter_host_exited`, `adapter_timeout`. 앱 계층 자신의 오류는 `value` 안의 `AppError`로 온다.
- 호스트의 stdout은 통로 전용이다. 호스트는 시작할 때 `console.log·info·debug`와 `process.stdout.write`를 stderr로 돌린다. 엔진 코드가 stdout에 써도 통로가 깨지지 않는다(유닛 시험으로 확인).
- 준비 메시지의 Node가 26 미만이면 메인은 호스트를 끝내고 `node_too_old` 오류 카드를 보인다. 호스트도 26 미만에서는 준비 메시지만 보내고 엔진을 불러오지 않은 채 끝난다.
- 메인과 화면 사이(IPC)

| 흐름 | 방향 | 형식 |
| --- | --- | --- |
| 요청 | 화면 → preload → 메인 | `ipcRenderer.invoke("codaryn:<영역>:<함수>", 인자)`. 채널은 6.4의 목록뿐이다 |
| 해석·검사 | 메인 | 보낸 쪽 확인, 인자 검사, 핸들 → 절대 경로, 필요하면 메인 확인 |
| 호출 | 메인 → 엔진 호스트 | stdin에 요청 한 줄. 계약 요청 타입 그대로(함수 필드 없음) |
| 응답 | 엔진 호스트 → 메인 → 화면 | 메인이 화면에 필요한 필드만 골라 검사한 보기(예: `toDoctorView`)와 코드 |
| 실행 이벤트, 취소, 끝 | 양쪽 | 실행 토큰으로 짝짓는다(GU-3) |

- `RunHandle`의 `cancel()`·`done`과 `RunObserver`의 콜백은 메시지로 바꾼다. 그래서 계약 타입은 함수 필드를 빼면 JSON으로 옮길 수 있어야 한다(15절).
- 화면이 받는 경로는 앱 계층이 가린 표시용 글과, 사용자가 고른 폴더의 이름뿐이다. 메인은 엔진 호스트에 넘긴 절대 경로를 화면에 돌려주지 않는다.

### 4.3 엔진 호스트의 실행과 환경

- Node 실행 파일(DR-26)
  - 개발: 설치된 Node 26 이상. 메인은 `npm start`가 넘기는 `npm_node_execpath`(절대 경로이고 파일이 있을 때)를 먼저 쓰고, 없으면 `PATH`의 절대 경로 항목에서 `node`를 찾는다. 판은 준비 메시지로 확인한다.
  - 배포: Node 실행 파일을 함께 묶는 방법은 배포 전에 정한다(DR-26, GUI-D9). 그 전의 패키지 빌드는 Node를 찾지 않고 `node_not_found` 오류 카드를 보인다.
- 실행: `node <gui>/build/src/engine-host/main.js --engine-dir <엔진 디렉터리>`. 셸을 거치지 않고(`shell: false`) 창 없이(`windowsHide`) 띄운다.
  - 엔진 디렉터리는 개발 중에는 루트 빌드 산출 `dist/src`다. 호스트는 그 안의 `app/index.js`와 `i18n/index.js`가 있고 필요한 함수를 내보낼 때만 시작한다.
  - 작업 디렉터리는 사용자 홈이다.
- 환경: 메인이 자기 환경을 복사해 넘긴다. `NODE_OPTIONS`, `NODE_PATH`, `ELECTRON_RUN_AS_NODE`를 대소문자를 가리지 않고 뺀다(Windows 환경 이름은 대소문자를 가리지 않는다). VX-D13 (a)의 기준에 Electron 변수를 더한 것이다.
- `AppEnvironment`(AC 4절): 호스트가 앱 계층의 `createNodeAppEnvironment()`로 만든다. CLI와 같은 규칙이다.

| 필드 | 값 |
| --- | --- |
| `env` | 호스트 프로세스 환경(위에서 걸러낸 사본). 대소문자 무시 조회와 명령 실행기의 부모 환경은 앱 계층이 한다(DR-4) |
| `cwd` | 사용자 홈. GUI는 절대 경로만 넘긴다 |
| `installDir` | 엔진 코드에서 찾은 `codaryn` 패키지 루트(CLI와 같은 방법). 개발 중에는 저장소 루트다. 찾지 못하면 null이고 모든 실행이 거부된다(U-3) |
| `nodeVersion` | 호스트의 Node(26 이상) |
| 나머지 | Node 기본 구현(CLI와 공용) |

- 배포 때 `installDir`이 GUI 설치 디렉터리 전체를 가리키게 하는 방법은 패키징 단위(GU-9)에서 정한다.
- 키는 OS가 앱에 준 환경 변수로만 들어온다. 메인은 환경을 복사해 넘길 뿐 값을 보지 않고, 화면에는 `process`가 없다(6.2, 연기 시험으로 확인).

### 4.4 수명과 비정상 종료

- 앱 시작: 메인이 보안 설정(6절)을 먼저 하고, 엔진 호스트를 띄우고, 창을 만든다. 화면의 요청은 호스트가 준비될 때까지 기다린다. 준비 메시지가 15초 안에 오지 않으면 호스트를 끝내고 `ready_timeout` 오류 카드를 보인다.
- 시작이 실패하면(`node_too_old`, `ready_timeout`, 프로토콜 위반) 메인은 호스트를 끝내고, 그 프로세스가 끝난 뒤에(최대 3초) 실패를 알린다. 남는 프로세스가 없다.
- 함께 끝나기(DR-8)
  - 호스트는 stdin이 닫히면 끝난다. 엔진이 열어 둔 핸들이 있어도 0.5초 뒤에는 끝난다. 메인이 비정상 종료해도 파이프가 닫혀 호스트가 끝난다.
  - 앱 종료 때 메인이 stdin을 닫고, 3초 안에 끝나지 않으면 강제로 끝낸다.
  - 실행 중이면 3.6의 순서(취소 → `done` 대기)를 먼저 한다(GU-3).
- 호스트가 끝나면(비정상 종료, 프로토콜 위반)
  - 진행 중 호출과 그 뒤 호출은 `adapter_host_exited`로 끝난다(AC 5.8의 어댑터 쪽 오류).
  - 자동으로 다시 띄우지 않는다. 오류 카드의 "엔진 다시 시작" 단추로만 띄운다(U-64). 호스트가 끝나면 메인이 창에 알리고(`engineState`), 창은 위쪽에 카드(진행 중이던 실행의 결과는 알 수 없고 실행 목록이 보여 준다는 글과 단추)를 보인다. 메인은 앞 호스트가 정말 끝났을 때만 새로 띄운다(돌고 있으면 `engine_running`, 띄우는 중이면 `engine_starting`, 앱을 끝내는 중이면 `app_closing`). 처음 시작에 실패해도 같은 카드다. 메인이 가진 토큰(미리보기·계획·제안)은 한 번만, 짧은 시간만 쓰이고 앱 계층이 다시 확인하므로 그대로 둔다.
  - 잠금은 다음 실행이 회수한다(P-4, N-25 (b)).
- 호출마다 시간 상한을 둔다: 점검 60초, 문구 10초. 넘으면 그 호출만 `adapter_timeout`으로 끝나고 호스트는 그대로 둔다. 실행(`startRun`)은 시간 상한 대신 실행 한도와 취소를 쓴다(GU-3).

### 4.5 GUI 전용 상태

- 위치: 설정 디렉터리의 `gui-state.json`(N-1과 같은 디렉터리). Chromium 프로필 자료는 이 디렉터리에 두지 않는다(6.3).

### 6.2 렌더러 격리 [추정 E-3]

- 앱 전체: `app.enableSandbox()`를 준비 전에 부른다.
- 창(`BrowserWindow`의 `webPreferences`)
  - `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `nodeIntegrationInWorker: false`, `nodeIntegrationInSubFrames: false`
  - `webviewTag: false`, `webSecurity: true`, `allowRunningInsecureContent: false`, `experimentalFeatures: false`
  - `spellcheck: false`. 세션에서도 맞춤법 검사기를 끄고 사전 주소를 열 수 없는 주소로 둔다. 창이 쓰지 않는 기본 세션에도 같은 설정을 한다. 켜 두면 Electron 45.3.1은 창 하나만 있어도 사전을 바깥에서 내려받는다(E-11, 실행으로 확인)
  - [결정] PM(GU-1 검수): **맞춤법 검사기는 끈다.** 연기 시험이 바깥 요청 0건을 확인한다. 새 Chromium 프로필에 내려받은 파일이 없고(GS-17), 앱의 모든 프로세스에 바깥 TCP 연결·TCP 대기 소켓·UDP 끝점이 0개다(GS-1, GS-11). 이 확인은 시험이 끝날 때의 상태를 본 것이다. 시험 중 잠깐 열렸다 닫힌 연결까지 보는 것은 아니다.
  - `devTools`: 제품 빌드에서 `false`
  - `preload`: 6.4의 한 파일
  - `partition`: 저장하지 않는 세션(`persist:` 없음). 화면 저장소(localStorage, IndexedDB, 캐시)가 디스크에 남지 않는다. 화면은 상태를 메인에 맡긴다
- 화면 코드: 신뢰할 수 없는 글(목표, 파일 이름, 검증 근거, 계획, 기록, 모델이 쓴 글)은 `textContent`로만 넣는다. `innerHTML`, `insertAdjacentHTML`, `document.write`, 문자열 `eval`류를 쓰지 않는다. 링크를 자동으로 만들지 않는다. 화면 코드 검사(8.3)로 이 목록의 사용을 막는다.

### 6.3 원격 콘텐츠 금지와 앱 프로토콜

- 화면은 사용자 정의 프로토콜 `app://codaryn/`에서만 불러온다[설계, GUI-D16].
  - `protocol.registerSchemesAsPrivileged`(standard, secure)와 `protocol.handle`로 등록한다[추정].
  - 처리기는 빌드한 화면 파일과 화면이 쓰는 공용 모듈(문구 카탈로그·계약 상수, 11절)만 내준다. 허용 디렉터리 목록 밖, `..`, 절대 경로, 링크는 거부한다.
  - HTML 응답에 CSP 헤더를 붙인다: `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. HTML에도 같은 `meta`를 둔다.
  - `file://`로 화면을 열지 않는다. 그래서 파일 프로토콜에 추가 권한을 주는 기능을 끈다(6.7).
- 요청 막기: 세션의 요청 처리기(`webRequest.onBeforeRequest`)가 `app://codaryn/` 밖의 모든 요청(`http`, `https`, `ws`, `wss`, `file`, `data`의 문서 등)을 취소한다[추정].
- 탐색과 창
  - `will-navigate`, `will-redirect`, `will-frame-navigate`: 모두 막는다.
  - `setWindowOpenHandler`: 모두 `deny`. 외부 주소를 OS 브라우저로 넘기지도 않는다. 도움말은 앱에 동봉한 문서다.
  - `will-attach-webview`: 막는다.
- 권한: `setPermissionRequestHandler`, `setPermissionCheckHandler`, 장치 권한 처리기 모두 거부(카메라, 알림, 클립보드 읽기, 위치 등). 클립보드 쓰기는 6.4의 `copyText`로만 한다.
- Chromium 프로필 위치: `userData`를 준비 전에 설정 디렉터리와 다른 곳(`%LOCALAPPDATA%\Codaryn\gui-profile`)으로 정한다[설계]. 기본값이 `%APPDATA%\<앱 이름>`이면 설정 디렉터리(N-1)와 겹치기 때문이다[추정 E-10].

  - `models()`·`useModel(provider, model)`은 `listModels(provider)`·`selectModel(entryId)`가 되었다. 메인이 목록 항목마다 id를 주고, 화면은 그 id만 보낸다.
  - 이벤트는 `onEvents` 하나가 아니라 실행 이벤트, 실행 끝, 작업 공간 열림의 세 구독이다. 모두 메인이 검사한 값의 복사본이다.
- 복사(U-62, 검토 R-73과 PM 결정): 화면은 클립보드에 쓰지 않는다. `copyText`를 받은 메인은 실행 id 꼴이나 다이제스트 앞 12자(소문자 16진)만 쓰고, 그 밖은 `invalid_args`다. 그래서 화면이 다른 글을 클립보드에 쓸 수 없다. 실행 id(결과, 실행 목록, 보고서)와 다이제스트 앞 12자(계획)에 복사 단추가 있다. 연기 시험은 OS 클립보드 대신 기록기를 쓴다. 트리의 상대 경로 복사는 R-73 M1(임시 트리가 등록한 가릴 값을 가리지 않음)로 뺐다가, 트리가 앱 계층의 작업 공간 목록을 쓰게 된 U-103(G-list)에서 따로 된 통로 `copyPath`로 다시 넣었다(3.3). `copyText`는 지금도 경로를 받지 않는다.
- `restartEngine()`(U-64)과 `onEngineState(listener)`: 엔진이 끝난 뒤의 카드와 다시 시작(4.4).
- 아직 없는 것: `planCheck`(앱 계층의 적용 전 점검 함수 뒤).

- 메인의 검사
  - 보낸 쪽: 요청이 앱 창의 주 프레임이고 그 프레임의 주소가 `app://codaryn/`인지 본다. 아니면 거부한다.
  - 인자: 함수마다 손으로 쓴 검사기(형식, 길이 상한, 허용 값 목록)로 본다. 목표 길이 상한은 CLI와 같다. 모르는 필드가 있으면 거부한다. 검사 라이브러리를 새로 들이지 않는다(7절).
  - 실패하면 엔진을 부르지 않고 `invalid_arguments` 성격의 어댑터 오류를 돌려준다.
- 이벤트는 위 표의 세 구독(`onRunEvents`, `onRunDone`, `onWorkspaceOpened`)으로만 받는다. preload가 콜백에 넘기는 값은 복사본이다.

### 6.5 핸들과 토큰

- **작업 공간 핸들**: 메인이 발급하는 임의 값(128비트, 16진수). 발급하는 곳은 폴더 대화상자, 최근 목록, 명령줄 인자뿐이다. 메인의 표가 핸들 → 절대 경로를 갖는다. 앱을 끝내면 사라진다.
- **항목 id**: 작업 공간 목록과 `changes` 응답의 파일마다 메인이 발급한다. (작업 공간 핸들, 엔진이 준 상대 경로)에 묶인다. 이름이나 경로가 가려진 항목(`masked_path` 포함)에는 발급하지 않는다. "탐색기에서 보기"는 이 id만 받는다. 작업 공간을 바꾸면 버린다. 개수 상한(예: 10만)을 두고 넘으면 오래된 것부터 버린다[설계].
- **미리보기·계획·제안 토큰**: 미리보기(`revertPreview`, `cleanupPreview`), 계획(`plan`), 설정 변경 제안의 응답에 메인이 붙인다. (작업 공간, 실행 id, 다이제스트 또는 제안 내용)에 묶이고 한 번 쓰면 버린다. 실행 동작(`revert`, `applyPlan`, `applyChange`, `cleanup`)은 이 토큰만 받는다. 화면이 실행 id나 다이제스트를 바꿔 넣을 수 없다.
- **실행 토큰**: `startRun`·`applyPlan`이 성공하면 메인이 발급한다. 취소와 이벤트 짝짓기에만 쓴다.
- **편집 토큰**(DR-72, 편집 단위): 텍스트 보기를 열 때 편집할 수 있는 파일에만 메인이 발급한다. (작업 공간, 상대 경로, 열 때의 해시, 줄 끝, BOM)에 묶인다. 저장은 이 토큰만 받는다. 저장하면 새 해시로 바뀌고, 설정이 바뀌면 버린다.

### 6.6 메인 확인

- 대상: 사용자 파일을 바꾸거나 지우는 동작, 위험 동의, 권한 넓히기.
  - 계획 적용(3.9), DR-21 동의(3.9), 되돌리기(3.8), 실행 기록 정리와 보관함 정리(3.8)
  - DR-72: 텍스트 보기의 저장(3.14). 연 파일마다 첫 저장만 묻는다([결정] PM).
  - 넓히는 설정 변경과 가릴 값 삭제([UX 설계](ux-design.md) 7절: 허용 명령 추가, `allowExtraArgs: true`, 한도 올리기, 보호 경로·`integrity.paths` 비우기, 가릴 값 삭제)
- 방식: 메인이 띄우는 **OS 기본 대화상자**(`dialog.showMessageBox`, 앱 창을 부모로 한 모달)[추정]. 내용은 메인이 토큰에 묶인 값(개수, 실행 id, 다이제스트 앞부분, 앱 계층이 판정한 넓히기 내용)으로 만든다. 화면이 보낸 문장은 넣지 않는다. 기본 단추는 "바꾸지 않음" 쪽이다.
- 화면 안 확인도 먼저 보일 수 있다(설명과 미리보기). 그러나 효력은 메인 확인에만 있다.
- 이유: 화면이 침해되어도 확인 없이 파일을 바꾸거나 정책을 넓히지 못하게 한다. 위험 동의는 사람이 준 입력이어야 한다(DR-21).

### 6.7 빌드에서 끄는 실행 기능 [추정 E-4]

- 패키지할 때 `@electron/fuses`로 정한다.
- 꾸러미에는 `build/tests`(연기 시험 진입점)를 넣지 않는다. 그 진입점은 OS 대화상자에 자동으로 답하고(`answerDialog`) 시험 전송을 켠다. 제품 시작 경로(`build/src/main/main.js`)는 이 선택지를 넘기지 않는다(R29-I4).
  - 끔: `RunAsNode`, `EnableNodeOptionsEnvironmentVariable`, `EnableNodeCliInspectArguments`, `GrantFileProtocolExtraPrivileges`
  - 켬: `EnableEmbeddedAsarIntegrityValidation`, `OnlyLoadAppFromAsar`
- 시작할 때 메인이 원격 디버깅 스위치(`--remote-debugging-port`, `--remote-debugging-pipe`)와 `--inspect` 계열 인자, 그 인자를 담은 `NODE_OPTIONS`, 이미 열린 검사기(`inspector.url()`)를 보면 검사기를 닫고 바로 끝낸다[설계, R-10 L-1]. Chromium 스위치는 fuses로 막히지 않을 수 있기 때문이다[추정].
  - 한계(실행으로 확인): Node가 앱 코드보다 먼저 검사기 포트를 열므로 `--inspect`와 `NODE_OPTIONS`의 포트는 잠깐 열렸다 닫힌다. `--inspect-brk`는 앱 코드 전에 Node가 멈춰 이 검사가 돌지 않는다. 둘 다 fuses(`EnableNodeCliInspectArguments`, `EnableNodeOptionsEnvironmentVariable` 끔, GU-9)만 막는다. 연기 시험이 세 형태의 종료를 확인하고 `--inspect-brk`는 알림으로 보인다.
- 제품 빌드에 시험용 스위치나 숨은 개발 메뉴를 넣지 않는다. 시험은 8.3의 별도 진입점으로 한다.
- 충돌 보고(`crashReporter`), 자동 업데이트, 원격 측정을 켜지 않는다(GUI-D9).

### 6.8 파일과 외부 주소

- 바뀐 파일을 OS 기본 처리기로 "열면" 실행 파일·스크립트가 실행될 수 있다. 그래서 "탐색기에서 보기"(`shell.showItemInFolder`)만 둔다. 경로는 메인이 핸들·항목 id로 정한다. `shell.openPath`, `shell.openExternal`은 쓰지 않는다.
  - DR-72: 파일 내용은 앱 안의 텍스트 보기(3.14)로만 본다. 글은 앱 계층이 가린 것이고, 파일을 실행하거나 OS 처리기에 넘기지 않는다.
- 스냅샷은 평문이다(R-8, PV-D1). GUI는 스냅샷과 보관함의 원문을 그리지 않는다.

### 6.9 OS 통합과 그 밖의 노출

- 창 제목, 작업 표시줄, OS 알림, 점프 목록: 고정 문구, 상태 낱말, 작업 공간 폴더 이름까지만. 목표, 전체 경로, 파일 이름, 모델이 쓴 글은 넣지 않는다.
- 단일 인스턴스: `app.requestSingleInstanceLock()`[추정]. 두 번째 실행의 인자는 메인이 받아 3.2의 명령줄 인자 규칙으로 처리한다.
  - Windows에서는 이 기능이 듣는 소켓을 쓰지 않는다고 보지만 확인이 필요하다(E-9). macOS·Linux에서는 유닉스 도메인 소켓을 쓸 수 있어(E-9) 그 OS로 넓힐 때 다시 정한다(GUI-D18).
- 로그: 제품 빌드는 파일 로그를 만들지 않는다. 개발 빌드의 콘솔 출력에도 환경 변수와 목표 원문을 찍지 않는다.
- 접근성 API: 화면의 글을 다른 프로세스에 보여 준다. 가림본만 그리므로 같은 범위다.

## 7. 개발 의존성

- [결정] DR-20, DR-26
  - `gui/package.json`에 `electron` 45.3.1을 개발 의존성으로 고정한다.
  - 루트 패키지의 실행 의존성은 0개 그대로다.
  - Electron 설치 때의 실행 파일 내려받기는 PM이 승인한 설치 단계다.
- [설계] 원칙
  - `gui/package.json`의 `dependencies`는 없다. 모두 `devDependencies`다. 패키저가 Electron 런타임을 실행 파일에 넣는다[추정].
  - 판은 정확히 적는다(`^`, `~` 없음). `gui/package-lock.json`을 커밋하고 그 뒤로는 `npm ci`로 설치한다.
  - 루트의 `typescript`(7.0.2)를 그대로 쓴다. `gui/`에 다시 넣지 않는다. GUI 빌드 스크립트가 루트의 `tsc`를 부른다.
  - 설치 스크립트: 처음 설계는 `gui/.npmrc`의 `ignore-scripts=true`였다. 루트 `.gitignore`가 비밀 보호를 위해 모든 `.npmrc`를 막으므로 커밋할 수 없다. 그래서 `gui/scripts/build/check-lock.mjs`가 대신 지킨다(`npm test`에서 실행).
    - `package.json`에 실행 의존성이 없고, 개발 의존성이 승인 목록과 같다.
    - lock의 모든 패키지가 npm 레지스트리에서 오고, sha512 무결성이 있고, 개발 전용이다.
    - 설치 스크립트(`hasInstallScript`)가 있는 패키지가 없다.
- 확인한 사실(GU-1 설치, 2026-11-12, `npm install` 한 번)
  - `electron` 45.3.1에는 설치 스크립트가 없다. 실행 파일은 처음 쓸 때 패키지의 `install.js`가 `@electron/get`으로 내려받고, 패키지에 든 `checksums.json`의 SHA-256과 대조한다.
  - GU-1에서는 승인된 설치 단계로 `node node_modules/electron/install.js`를 한 번 실행했다. 실행 파일은 `gui/node_modules/electron/dist/`에 있다. `@electron/get`은 내려받은 zip을 사용자 캐시 디렉터리에도 남긴다[추정: 그 위치는 보지 않았다].
  - lock에 든 패키지는 13개다: `electron`, `@electron/get`, `@electron-internal/extract-zip`, `@types/node`(24.19.2), `debug`, `env-paths`, `graceful-fs`, `ms`, `progress`, `semver`, `sumchecker`, `undici`, `undici-types`. 모두 개발 전용이고 설치 스크립트가 없다.

| 패키지 | 쓰임 | 넣는 단위 | 판 | 근거 | 상태 |
| --- | --- | --- | --- | --- | --- |
| `electron` | 셸 런타임(Chromium 156, 내장 Node 24.22.2). 개발 실행, 연기 시험 실행기, 패키지의 원본 | GU-1 | **45.3.1**(고정) | DR-20, DR-26 | 추가함(GU-1) |
| `@electron/fuses` | 패키지 뒤 실행 기능 끄기(6.7) | GU-9 | 그때의 최신 판[추정] | 6.7 | 아직 넣지 않음. 추가 전에 PM 승인 |
| `@electron/packager` | Windows x64 실행 파일 디렉터리, asar | GU-9 | 그때의 최신 주 버전[추정] | 의존이 가장 적은 공식 패키저[추정] | 아직 넣지 않음. 추가 전에 PM 승인 |

- 배포용 Node 26 실행 파일: 의존성이 아니라 배포물이다. 묶는 방법(판 고정, 체크섬, 서명)은 배포 전에 정한다(DR-26).
- 지금 넣지 않는 것과 이유
  - 설치 파일 도구(electron-builder의 NSIS, WiX 기반 MSI 등): 첫 배포는 실행 파일 디렉터리를 묶은 zip이다. 설치 파일과 서명은 배포 전에 정한다(GUI-D9, DR-20).
  - E2E 도구(Playwright의 Electron 지원[추정]), 접근성 자동 검사(axe-core[추정]): 화면이 생긴 뒤 필요하면 PM 승인으로 넣는다. 그 전에는 8.3의 Electron 실행기 연기 시험과 수동 점검표다.
  - UI 프레임워크(React 등), 번들러(esbuild, webpack, Vite), 상태 관리, CSS 프레임워크: 쓰지 않는다(GUI-D15). 화면은 TypeScript와 DOM으로 만들고 `tsc`만으로 빌드한다.
  - 비교 계산, 인자 검사, 상태 저장 라이브러리(diff, zod, electron-store 등): 작은 순수 함수로 직접 만든다.
  - `@types/electron`: 필요 없다. `electron` 패키지가 `electron.d.ts`를 담고 있다(확인함).
- 형 정의
  - 메인과 preload는 `electron.d.ts`와 Electron이 데려온 `@types/node` 24.19.2로 검사한다(`tsconfig.main.json`). 실행되는 곳이 Node 24다.
  - 엔진 호스트와 유닛 시험은 루트의 `@types/node` 26.6.6으로 검사한다(`tsconfig.host.json`, `tsconfig.test.json`의 `typeRoots`). 실행되는 곳이 Node 26이다.
  - 화면은 DOM 형만 쓴다(`tsconfig.renderer.json`, `types: []`).

## 9. 지원 OS

| 영역 | 규칙 |
| --- | --- |
| 키보드 | 모든 동작을 키보드로 한다. 포커스 순서는 보이는 순서와 같고 포커스가 늘 보인다. 단축키는 3.13. 트리와 목록은 화살표·Home·End·첫 글자 이동(트리는 U-67: 글자·숫자 하나로 다음에 그 글자로 시작하는 보이는 항목, 끝에서 처음으로, 대소문자 무시) |

| 움직임 | 애니메이션은 최소로 하고 OS의 동작 줄이기를 따른다 |
| 시간 | 권한 확인 대기 시간도 실행 시간 한도에 든다(AC 5.7 의미 6). 남은 시간을 글로 보이고 1분 남았을 때 한 번 알린다 |

## 11. 두 언어 (N-4)

- [결정] N-4: 한국어와 영어. 선택은 `CODARYN_LANG` > 설정 `language` > OS 표시 언어다. 오류 코드, JSON 필드, 종료 코드, 명령 이름, 실행 id는 고정한다.
- [권고] 문구 카탈로그 두 층(GUI-D21). 처음 설계의 "공용 카탈로그에 `gui.` 접두 키"를 이것으로 바꾼다.
  - **공용 문구**(상태 낱말, 이유, 거부, 오류, 조언, 진행 문장, 검증 순번): N-B의 `src/i18n`을 그대로 쓴다. CLI와 같은 뜻을 같은 글로 보인다.
  - **GUI 전용 문구**(메뉴, 단추, 탭, 화면 제목, 대화상자, 도움말): `gui/src/renderer/i18n/{ko,en}.ts`. 언어 선택 함수와 자리표시자 규칙은 `src/i18n`의 것을 부른다.
  - 이유: GUI 화면 글이 바뀔 때마다 계약의 메시지 id 목록(`src/contracts`)과 공용 카탈로그(N-B)를 함께 고치지 않아도 된다. 소유가 겹치지 않는다(14절).
  - [코드] `src/i18n`과 `src/contracts`는 지금 `node:` 모듈을 부르지 않는다(main `86c5f64`, `grep`). 그래서 화면에서 앱 프로토콜로 그대로 불러온다. 바뀌면 메인이 문구 표를 데이터로 보낸다.
- 메인 확인 대화상자의 문구도 같은 두 층에서 메인이 고른다.
- 창의 언어는 CLI와 같은 순서로 고른다: `CODARYN_LANG` → 설정 파일 `language` → OS 표시 언어 → 영어(U-78). 엔진 호스트가 `messages` 때마다 앱 계층의 설정 읽기로 설정의 언어를 읽는다. 읽지 못하면 OS가 정한다. U-78 전에는 엔진 호스트가 설정의 언어를 넘기지 않아, 설정 화면이 바꾼 언어가 다시 시작해도 쓰이지 않고 OS 언어가 이겼다.
- 언어 바꾸기: 설정 > 일반에서 바꾸면 설정 파일 `language`에 쓴다(CLI와 공유, 앱 계층 설정 함수). `CODARYN_LANG`이 있으면 그것이 이긴다고 표시한다. 바꾸면 창을 다시 그린다(재시작 없음).
  - U-69(구현): 설정 쓰기가 끝나면 창이 `info`로 언어를 다시 묻는다(엔진 호스트가 `CODARYN_LANG` → 설정 `language` → OS 순으로 고르고, 메인도 대화상자 언어를 그것으로 바꾼다). 달라졌으면 틀, 트리, 화면, 명령 찾기를 새 문구로 다시 짓고 같은 화면을 보인다(`renderer/app.ts`의 `mountUi`). 연 작업 공간, 진행 중인 실행, 엔진 상태, 메인에서 오는 사건 수신은 그대로다. 트리는 다시 읽으므로 펼친 폴더와 실행의 변경 표시는 처음으로 돌아간다. 앞 틀의 문서 단축키 수신은 떼어 낸다.
- 값 넣기 금지(S-6, S-12): 문구 틀에 파일·환경의 값을 넣지 않는다. 사용자가 고른 작업 공간 경로는 자기 자리에만 보이고 오류 문구에는 넣지 않는다.
- 형식: 날짜·시간·숫자는 지역 형식, 실행 id는 UTC 원문. 영어가 더 길다. 고정 폭 단추를 쓰지 않는다. 글꼴은 OS 기본이고 동봉하지 않는다.
- 모델이 만든 글(계획 항목, 검증 근거, 파일 내용)은 번역하지 않는다.

## 14. 구현 분할안과 첫 구현 단위

| 변경 보기(3.4, DR-29, DR-32 (c)) | 바뀐 파일의 경로와 상태. 쓰기 도구가 가린 표기의 다이제스트를 기록하고, 앱 계층이 지금 같은 가림임을 확인한 파일은 글을 줄 단위로 비교해 보인다(F7·Alt+F7). 아니면 이유를 쓴다. 파일마다 따로 정한다: 한 실행 안에서도 확인된 파일은 가린 글을, 아닌 파일(실행 뒤 바뀜 등)은 경로와 상태만 보인다. 한쪽 글이 메인의 한도(300,000자)를 넘거나 합계 예산을 넘으면 그 파일만 글 없이 `too_large`이다. 원본 사본 없이 지금 글만 있으면(또는 그 반대) 비교 없이 그 글만 보이고 그렇다고 쓴다. 기록 변경 표시(U-48, U-43, DR-38): 앱 계층 `changes`의 `recordsChanged`가 있으면 실행 목록·계획·보고서와 같은 문구 체계의 경고(`changes.recordsChanged`)가 맨 앞에 오고, 글 없는 파일마다 표시가 그 까닭이라고 쓴다 | 나란히 보기, 줄 바꿈 끄기, 비교 화면의 탐색기에서 보기는 U-66에서 더했다(3.4). 적용 실행은 변경 화면을 열지 않는다(3.4). 트리에서 바뀐 파일을 고르면 이 화면이 그 파일에서 열리고, 이 화면이 읽은 파일은 트리의 표시가 된다(U-65에서 더함) |

- DR-21 동의의 순서: 적용 전 점검 함수가 없어 첫 적용이 `needs-input`/`consent_required`로 끝난다(아무것도 옮기지 않음). 결과 화면의 "동의 여부를 묻고 다시 적용…"을 누르면 메인이 별도 OS 대화상자(기본 "동의하지 않음")로 묻는다. 동의 값은 그 답으로만 만들고, 그 계획의 다이제스트로 한 번의 적용에만 쓴다. 화면은 동의나 다이제스트를 보낼 수 없다.
- 작업 종류: 앱 계층의 작업 형태(`TaskForm`)가 R-14 L-3부터 `workflowRef`를 받는다. 엔진 호스트의 작업 형태는 그 형과 필드마다 같게 두어, 빠진 필드를 컴파일러가 잡는다(R21-M-1). 작업 종류를 직접 골라 만든 계획도 보기·적용된다.
- 최근 목록(R21-I-1): 폴더 이름과 그 폴더가 든 폴더의 이름만 보인다. 전체 경로는 메인에만 있다.
- 키 값(R21-I-2): 엔진 호스트는 계약의 제공자 표(`API_PROVIDERS`)에 있는 모든 키 변수의 값을 화면으로 가는 글에서 가린다.
- 시험의 전송(R21-I-3): 연기 시험과 실제 엔진 호스트를 띄우는 유닛은 엔진 호스트에 `--transport loopback-only`를 준다. 그러면 앱 계층의 `fetch`가 이 컴퓨터(loopback)만 부르고, 다른 곳은 보내기 전에 거절한다. 앱의 시작(`main.ts`)은 이 인자를 주지 않는다.
  - 거절하는 곳(R21b-I-1, PM 지시): 앱 계층의 `providerDeps`로 제공자 표의 제공자마다 주는 `fetch`(F-2), `net.Socket.prototype.connect`(node:net·http·https·tls). 전역 `fetch`를 바꾸던 임시 우회는 F-2 뒤 걷어냈다. 전역 `fetch`를 쓰는 길은 소켓 감싸기가 막는다. 이 컴퓨터로 치는 것은 127.0.0.1, ::1, localhost뿐이다. 이름은 찾기 전에 거절한다. `node:dgram`과 `node:dns`를 직접 쓰는 길은 막지 않는다(엔진에 그런 사용이 없다). 엔진 호스트 프로세스 안만 감싼다. 허용 명령(`run_command`)과 명령 검증기는 자식 프로세스라 감싸지 않는다. 시험은 바깥으로 가는 허용 명령을 두지 않는다(R29-I1).
  - 거절은 센다. 엔진 호스트의 `transport` 호출이 방식과 거절 수를 준다. 실제 엔진 호스트를 띄우는 유닛과 연기 시험(7단계 뒤, 끝, 수명 진입점)은 끝에 거절 0을 단언한다. 거절을 일부러 보는 시험 두 개는 정확히 1을 단언한다.
  - 닿지 않는 주소가 필요한 시험·탐침은 예약 주소(TEST-NET 등)를 쓰지 않는다. 127.0.0.1의 닫힌 포트를 쓰고, 거절을 보는 시험은 127.0.0.2의 닫힌 포트를 쓴다. 127.0.0.2는 loopback 대역이라 이 컴퓨터를 떠나지 않지만, 전송은 이 컴퓨터로 치지 않는다. 방어를 지워 보는 확인도 이 조건에서만 한다.
