# 텍스트 편집 기능의 UX 검토 (DR-71)

- 단위: U-171. 작성: w3:p7(nd-docs, UX·문서). 기준: main `f53af2b`.
- 요청(DR-71, 사용자): "소스 코드 같은 텍스트를 편집할 수 있는 기능을 넣을 수 있는지 가능성과 UX를 검토하고, 가능하면 넣는다."
  - PM은 두 가지로 읽었다. (가) 에이전트의 부분 편집 도구, (나) GUI에서 사람이 작업 공간의 텍스트 파일을 열어 고치는 화면.
- 이 문서는 **UX만** 본다. 기능 가능성(계약·보안)은 p5u-gui와 p4g가 따로 본다. 그쪽에 넘길 물음은 6절에 모았다.
- 표기:
  - **[사실]**: main `f53af2b`의 코드나 문서에서 확인한 것. 파일을 함께 적었다.
  - **[제안]**: 이 문서의 안.
  - **화면 글은 초안이다.** 문구 담당(nb-i18n)의 확정 전이다.

## 1. 요약과 권고

| 읽기 | 권고 | 까닭 한 줄 |
| --- | --- | --- |
| (가) 에이전트의 부분 편집 | **새 도구는 넣지 않는다.** 지금의 `write_file` 부분 바꾸기를 그대로 쓰고, 보이는 글만 작게 다듬는다 | 부분 바꾸기(`replace_text`)는 이미 있다. 실제 모델로 돌려 본 적이 없어, 더 넓은 편집 꼴이 필요한지 알 근거가 없다 |

| (나') task·설정 파일을 글로 고치기 | **넣지 않는다** | 설정 화면과 "넓히는 변경은 메인이 확인한다"(GUI 원칙 6)를 우회하게 된다 |

- (나)를 넣을 수 없다고 판정되면(6절의 가린 글 편집이 어렵다면), 대신 "탐색기에서 보기"로 넘어가는 길을 다듬는다. 원문을 그리는 편집기는 만들지 않는다(5.12절).

## 2. 기준이 된 사실

- **[사실] `write_file`은 두 가지 바꾸기를 받는다**(`src/contracts/tool.ts` `FileChange`).
  - `replace_all`(파일 전체)과 `replace_text`(정확히 한 번 나오는 `oldText`를 `newText`로)다.
  - 따라서 DR-71 행의 "지금은 파일 전체를 쓰는 `write_file`뿐"은 맞지 않는다. 부분 바꾸기는 단계 1a부터 있었다.
- **[사실] 부분 바꾸기는 모델이 본 가린 글에서 한다**(`src/tools/index.ts`).
  - 지금 파일을 가린 글에서 `oldText`를 찾는다.
  - 결과를 원문으로 되살릴 때 가린 값이 든 구간은 제자리를 지켜야 한다.
  - 실패 코드는 `no_match`("text to replace not found"), `ambiguous_match`("…found more than once"), `conflict`(마지막 읽기 뒤 파일이 바뀜), `protected_span_violation`("change splits a placeholder")이다.
  - 사용 안내 16절의 한계: "가릴 값이 든 줄: 수정, 이동, 삭제할 수 없다. 사람이 직접 고친다."
- **[사실] 사람에게 보이는 쓰기의 흔적**
  - 진행 줄은 `write file — allowed (write_file)`와 `created`/`changed` 줄이다. 실패는 `write file — failed (<code>)`다(U-18). 진행 줄에는 파일 내용이 없다.
  - 변경 화면(CLI `changes`, GUI 3.4)은 실행 전 원본과 지금을 다시 가려 줄 단위로 비교한다(DR-7). 어떤 바꾸기로 썼는지는 보지 않는다.
  - 되돌리기는 실행의 첫 쓰기 전에 둔 원본으로 파일 전체를 돌린다. 실행 뒤에 다시 바뀐 파일은 건너뛴다: `changed again after the run`(`revert.skip.changed_since_run`).
- **[사실] 계획·승인은 이동과 폐기만 다룬다**(`planActions`). 적용 전에 계획 대상의 해시를 다시 보고, 맞지 않으면 `plan_stale`("the plan no longer fits the workspace")이다.
  - 쓰기를 미리 승인받는 `plan: "run"`과 `writablePaths`(P1 묶음 B)는 DR-69로 범위에 들어왔고 아직 없다.
- **[사실] GUI의 정해진 원칙과 결정**(`docs/design/standalone-gui.md`)
  - 원칙 1: 그리기만 한다. 검사는 앱 계층이 한다.
  - 원칙 4: 가림본만 그린다.
  - 원칙 6: 사용자 파일을 바꾸는 동작은 메인이 확인한다.
  - 3.1·6.8: "편집기에서 파일 열기: 하지 않는다. 탐색기에서 보기만 둔다." 기본 앱 열기는 실행 위험이 있다.
  - 3.4: "편집은 없다."
  - GUI-D20: "바뀌지 않은 파일의 내용 보기: v1에 두지 않음. 필요하면 앱 계층이 가린 읽기 전용 미리보기."
- **[사실] GUI는 작업 공간이 잠기면 새 작업을 끈다**(U-68). 글은 "Another run is using this workspace…"다.
- **[사실] 읽기 상한** `MAX_READ_BYTES`는 262,144바이트(256 KiB)이고, 변경 화면도 이 상한을 넘지 않는다.

## 3. 대상 사용자

- [UX 설계](ux-design.md) 2절과 GUI 2절의 주 사용자는 "문서 작업자(비개발자 포함)"다. 터미널·JSON·Git에 익숙하지 않고 폴더 단위로 일한다.
- 개발자도 GUI를 쓴다(DR-20). 그러나 개발자에게는 이미 본격 편집기(VS Code 등)가 있다.
- 그래서 이 제품의 편집 기능이 노릴 일은 "코드를 짜는 일"이 아니다. "에이전트가 남긴 글을 조금 고치고 넘기는 일"이다.

## 4. (가) 에이전트의 부분 편집

### 4.1 지금 있는 것

- 모델은 `write_file`에 `replace_text`를 주어 한 군데를 바꿀 수 있다. 한 번에 한 곳이고, 바꿀 글은 파일 안에서 하나뿐이어야 한다.
- 여러 곳을 고치려면 호출을 여러 번 한다. 호출마다 `read_file`로 새 해시를 받아야 한다(`expectedHash`).

### 4.2 더할 수 있는 꼴과 사람 쪽 효과

| 꼴 | 모델 쪽 | 사람에게 보이는 차이 | 판단 |
| --- | --- | --- | --- |
| 한 호출에 여러 곳(`edits: [...]`, 모두 되거나 모두 안 됨) | 호출과 다시 읽기가 준다 | 진행 줄 한 줄에 여러 곳이 바뀐다. 실패하면 몇 번째 바꾸기가 틀렸는지 알려야 한다 | 실제 모델로 돌려 다시 읽기가 많을 때만 |
| 줄 번호 범위로 바꾸기 | 모델이 줄 번호를 세야 한다 | 가린 줄과 원문 줄 수가 같아야 해서 설명이 어렵다. 틀린 줄 번호는 조용히 엉뚱한 곳을 바꾼다 | 넣지 않는다 |
| 뒤에 넣기·끝에 붙이기 | 짧다 | `replace_text`로 같은 일을 할 수 있다 | 넣지 않는다 |
| 통합 diff(패치) 적용 | 모델이 diff를 잘 쓰면 짧다 | 적용 실패 까닭이 사람에게 어렵다(덩어리, 문맥 줄) | 넣지 않는다 |

### 4.3 사람에게 보이는 것이 어떻게 달라지나

- **진행 줄:** 도구가 하나(`write_file`)로 남으면 줄 꼴이 그대로다. 새 도구(`edit_file` 등)를 두면 진행 줄, 끝 요약의 실패 수, 정책 설명, 보고서에 이름이 하나 더 생긴다. 그래서 같은 쓰기 권한에 이름만 둘이 된다.
- **변경 화면의 비교:** 바뀌지 않는다. 비교는 실행 전 원본과 지금을 견준다.
  - 부분 바꾸기의 실제 이득은 이 화면에 있다. 전체 쓰기는 모델이 파일을 다시 써서 고치지 않은 줄(공백, 줄 끝, 빠뜨린 줄)까지 바뀔 수 있다. 부분 바꾸기는 바꾼 곳만 비교에 남는다.
- **되돌리기:** 바뀌지 않는다. 원본으로 파일 전체를 돌린다.
- **계획·승인:** 지금의 계획(이동·폐기)과는 관계가 없다. 앞으로의 `plan: "run"`(DR-69)도 "어느 경로에 쓸 수 있나"(`writablePaths`)를 승인한다. 어떤 꼴로 쓰는지는 승인 대상이 아니어야 승인 화면이 단순하다.
- **가린 값이 든 줄:** 부분 바꾸기도 그 줄을 바꿀 수 없다. 실패하면 사람이 볼 까닭 글이 이미 있다(`change splits a placeholder`).

### 4.4 사용 흐름(지금 그대로)

1. 모델이 `read_file`로 `README.md`를 읽는다(가린 글과 해시).
2. 모델이 `write_file`에 `replace_text`(옛 글 한 줄 → 새 글 한 줄)를 준다.
3. 진행 줄: `write file — allowed (write_file)`, 그다음 `changed README.md`.
4. 끝난 뒤 변경 화면에는 그 한 줄만 바뀐 비교가 보인다. 되돌리기는 실행 전 `README.md`로 돌린다.

### 4.5 화면 글 초안 ([제안], 넣을 때만)

| 자리 | 한국어 | English |
| --- | --- | --- |
| 바뀐 곳 수(여러 곳 꼴을 넣을 때) | `README.md 바꿈 — 3곳` | `changed README.md — 3 places` |
| 여러 곳 가운데 하나가 틀림 | `파일 쓰기 — 실패 (no_match: 3개 중 2번째 바꿀 글을 찾지 못함)` | `write file — failed (no_match: the 2nd of 3 texts to replace was not found)` |
| 보고서의 실패 까닭 | `바꿀 글이 파일에 두 번 이상 있음` | `the text to replace occurs more than once` |

### 4.6 하지 말 것

- 같은 쓰기에 도구를 둘 두지 않는다(이름만 다른 권한).
- 여러 곳 바꾸기를 일부만 적용하지 않는다. 모두 되거나 아무것도 쓰지 않는다.
- 진행 줄이나 끝 요약에 `oldText`, `newText`를 싣지 않는다. 지금처럼 경로와 결과만 보인다.
- 부분 바꾸기를 "더 안전한 쓰기"로 다루지 않는다. 보호 경로, 해시 확인, 가린 줄 규칙은 같다.

### 4.7 권고

- **넣지 않는다(새 도구).** 지금의 `replace_text`를 쓴다.
- 실제 모델 점검(사용자가 허락할 때) 뒤에 `no_match`·`ambiguous_match`·다시 읽기가 많으면 4.2의 "한 호출에 여러 곳"만 다시 본다. 그때 4.5의 글을 쓴다.
- 문서에서 "부분 바꾸기가 있다"를 사람에게 알린다: 사용 안내 13절이나 보고서 설명에서 `write_file`의 두 꼴을 적는다(문서 몫).

## 5. (나) GUI에서 사람이 텍스트 파일을 고치는 화면

### 5.1 쓸모

- **있는 경우:**
  - 에이전트가 만든 보고서·요약의 문장 하나를 고친다.
  - 분석 결과 표의 값 하나를 고친다.
  - 문서 작업 결과에서 오타를 바로잡는다.
  - 지금은 GUI를 떠나 파일 관리자를 열고, 다른 편집기를 찾아 열어야 한다. 비개발자에게는 이 왕복이 크다.
- **크지 않은 경우:** 개발자의 코드 작업. 이미 쓰는 편집기가 낫다.
- **부작용:**
  - 사람이 고친 파일은 그 실행의 되돌리기에서 건너뛴다(`changed_since_run`).
  - 검증은 실행이 남긴 파일 기준이라, 고친 뒤의 파일은 다시 확인되지 않는다.
  - 둘 다 사람이 모르면 놀랄 일이라 화면이 먼저 말해야 한다(5.6, 5.11).

### 5.2 어디에 두나

| 자리 | 판단 | 까닭 |
| --- | --- | --- |
| 변경 화면(3.4)의 파일마다 "이 파일 고치기" | **둔다** | 비교를 보다가 바로 고치는 흐름이 가장 흔하다. 상태가 "실행이 남긴 그대로"일 때 되돌리기 영향을 함께 말할 수 있다 |
| 파일 트리 항목 메뉴(3.3)의 "고치기" | **둔다** | 실행과 관계없는 작은 고침. 가린 이름의 항목은 지금처럼 고를 수 없다 |
| 결과·사람 확인 화면(3.7)의 "결과 파일 고치기" | **변경 화면으로 보내기만** | 사람 확인 전에 고칠 수 있게 하되, 고친 사실은 판정 화면이 알린다(5.11) |
| task 파일·설정 파일 편집 | **두지 않는다** | 설정은 설정 화면이 있고, 넓히는 변경은 메인이 확인한다(원칙 6, U-107의 넓히기 판정). 글 편집은 그 확인을 비켜 간다. task 파일은 작업 공간 밖에 있어야 한다 |
| 상태 디렉터리(`.codaryn`), 스냅숏, 폐기 보관함 | **두지 않는다** | 기록 변조(DR-38)와 같다. 트리도 열지 않는다 |

### 5.3 가림과의 관계 — 가린 글 편집기

- GUI는 원문을 그리지 않는다(원칙 4, GUI-D20, 6.8). 편집기도 이 원칙을 지켜야 한다.
- [제안] **가린 글로 보이고, 가린 값이 든 줄은 잠근다.** 에이전트의 `replace_text`와 같은 규칙이다.
  - 화면에는 앱 계층이 가린 글이 나온다. 등록한 가릴 값과 키 모양은 `[가린 값]` 꼴이다.
  - 그런 값이 든 줄은 읽기만 된다. 그 줄에 커서를 두면 "가린 값이 든 줄은 여기서 고칠 수 없습니다"를 알린다.
  - 저장은 앱 계층이 가린 글을 원문으로 되살려 쓴다. 가린 구간이 옮겨지거나 쪼개지면 저장하지 않는다(`protected_span_violation`과 같은 판정).
  - 이렇게 하면 편집기 화면, 클립보드 복사, 화면 공유 어디에도 등록 값이 나오지 않는다.
- 가린 값이 든 줄을 고쳐야 하면, 사람은 지금처럼 "탐색기에서 보기"로 자기 편집기를 쓴다. 이 한계는 사용 안내 16절과 같다.
- 이름이 가려진 파일은 열 수 없다(지금 트리와 같다).

### 5.4 실행 중인 에이전트와 겹칠 때

| 상황 | [제안] 편집기 | 까닭 |
| --- | --- | --- |
| 이 작업 공간의 잠금이 있음(실행·적용·되돌리기 중) | **읽기 전용**으로만 연다. 저장 단추는 없고 까닭을 쓴다 | 사람이 고친 뒤 에이전트가 쓰면 `conflict`가 나고 모델이 다시 읽는다. 보호 대상이면 실행이 `protected_changed`로 멈춘다. 실행의 원본 기록과 섞인다 |
| 계획을 만든 뒤 적용 전 | 고칠 수 있다. 저장 전에 "적용할 계획의 대상이면 적용이 거절된다"를 알린다 | 적용은 대상 해시를 다시 보고 `plan_stale`로 거절한다. 거절은 안전하지만 사람이 이유를 모르면 헤맨다 |
| 사람 확인을 기다리는 실행 | 고칠 수 있다. 판정 화면이 "실행 뒤에 손으로 고친 파일"을 센다 | 판정은 사람이 본 글에 대한 것이어야 한다 |
| 편집 중에 실행을 시작하려 함 | 저장하지 않은 고침이 있으면 새 작업 시작 전에 묻는다(기본: 취소) | 실행이 반쯤 고친 상태를 원본으로 삼지 않게 한다 |

### 5.5 저장

- [제안] 저장은 사람이 한다(Ctrl+S 또는 단추). 자동 저장은 없다.
- 열 때의 해시를 기억하고, 저장할 때 디스크가 같은지 본다. 다르면 저장하지 않는다. 덮어쓰기 단추는 두지 않는다.
- 머리의 BOM은 열 때 그대로 지킨다(에이전트의 쓰기도 BOM을 지킨다). 줄 끝은 입력란이 CRLF를 LF로 바꾸므로, 저장할 때 열 때의 줄 끝(CRLF 또는 LF)으로 되돌려 쓴다. 섞여 있던 파일은 읽기 전용으로 연다.
- UTF-8 텍스트만 고친다. 256 KiB를 넘거나, UTF-8이 아니거나, 이진 파일이면 읽기 전용이거나 열지 않는다.
- [가능성은 6절] 원칙 6("사용자 파일을 바꾸는 동작은 메인이 확인한다")에 따라 메인이 저장을 확인해야 한다.
  - [제안] 한 파일을 연 동안 **첫 저장만** OS 확인 상자로 묻고, 같은 세션의 다음 저장은 묻지 않는다.
  - 매번 묻는 편집기는 쓸 수 없고, 묻지 않는 편집기는 렌더러 침해 때 막을 것이 없다.

### 5.6 되돌리기

- 편집기 안의 실행 취소(Ctrl+Z)는 브라우저 입력란의 것을 쓴다. "연 때로 되돌리기" 단추는 저장 전까지만 있다.
- **Codaryn의 `revert`는 사람의 저장을 되돌리지 않는다.** 사람의 저장은 실행이 아니라 기록이 없다. 저장 확인 상자에 그렇게 쓴다.
- 실행이 바꾼 파일을 사람이 고치면, 그 실행을 되돌릴 때 이 파일은 건너뛴다(`changed again after the run`). 사람의 고침을 지키는 쪽이라 맞다. 다만 저장 전에 알린다(5.11의 글).
- 사람의 저장도 되돌리게 할지(편집 전 원본을 기록에 남길지)는 6절의 물음이다. UX로는 "넣지 않는다"를 권한다. 기록 형식이 늘고, 실행 목록에 실행이 아닌 줄이 생겨 헷갈린다.

### 5.7 보호 경로

- 보호 경로는 "에이전트가 쓰지 못하는 곳"이다. 사람은 원래 고칠 수 있다.
- [제안] 보호 경로의 파일은 열 때 머리에 `보호`를 보이고, 저장 전에 한 번 확인한다(기본: 취소).
  - 보호 대상은 검증 기준(시험, 원자료)이라 사람이 무심코 바꾸면 다음 실행의 판정이 달라진다.
  - 실행 중에는 5.4대로 저장할 수 없다.

### 5.8 접근성

- **입력:** 기본 `textarea`를 쓴다. 화면 낭독기, 한글 입력기(IME), 글꼴 확대, 고대비가 따로 손대지 않아도 된다.
  - 줄 번호는 입력란 밖의 줄 번호 열로 그리고, 낭독기에는 숨긴다(`aria-hidden`). 커서 줄 번호는 상태 줄에 글로 보인다.
- **잠긴 줄:** 색만으로 표시하지 않는다. 줄 앞에 `잠김` 낱말을 두고, 커서가 들어가면 한 번 알린다(`aria-live="polite"`).
- **키보드:**
  - Ctrl+S 저장, Esc 닫기(저장하지 않은 고침이 있으면 묻기), Ctrl+Z·Ctrl+Y 실행 취소·다시.
  - 탭 키는 입력란 안에서 탭 문자를 넣는다. 초점을 빼려면 Ctrl+M으로 탭 이동 방식을 바꾼다. 이 방식은 상태 줄에 낱말로 보인다(초점 가두기를 피함).
  - F6로 지금처럼 화면 영역을 오간다.
- **알림:** 저장됨·저장 안 됨(충돌)·잠김은 낱말로 쓰고 낭독기에 알린다.
- **크기:** 200% 배율에서 가로 넘침 없이 줄 바꿈을 켤 수 있다. 줄 바꿈은 비교 화면처럼 켜고 끄는 스위치로 둔다.

### 5.9 범위 — 최소 편집기와 본격 편집기

| 기능 | 최소 편집기(권고) | 넣지 않음(본격 편집기의 일) |
| --- | --- | --- |
| 열기 | 변경 화면·트리에서 파일 하나 | 여러 탭, 분할 창, 최근 파일 |
| 고치기 | 글 입력, 실행 취소, 줄 바꿈 스위치 | 구문 강조, 자동 완성, 서식 맞춤, 여러 커서 |
| 찾기 | Ctrl+F 찾기(바꾸기 없음) | 바꾸기, 정규식, 여러 파일 찾기 |
| 저장 | 해시 확인 저장, 충돌 때 저장 안 함 | 자동 저장, 덮어쓰기 강제, 다른 이름으로 저장 |
| 그 밖 | 상태 줄(줄 번호, 잠긴 줄 수, 저장 상태) | 터미널, 확장, Git, 실행 단추, 미리보기 렌더링 |

- 이 범위면 새 GUI 의존성이 필요 없다(입력란과 기존 비교 모듈). 본격 편집기 부품(코드 편집기 라이브러리)은 DR-20의 "GUI 개발 의존성은 근거와 고정 버전"을 거쳐야 하고, 이 제품의 사용자에게 득이 작다.

### 5.10 사용 흐름

1. **결과 다듬기**
   1. 실행이 끝난다.
   2. 변경 화면에서 `report.md`의 비교를 본다.
   3. "이 파일 고치기"를 누른다.
   4. 머리에 "이 파일은 실행이 바꾼 파일입니다. 저장하면 그 실행을 되돌릴 때 이 파일은 건너뜁니다"가 보인다.
   5. 문장 하나를 고치고 Ctrl+S를 누른다.
   6. 첫 저장이라 메인의 확인 상자가 뜬다. 저장한다.
   7. 변경 화면의 상태가 "실행 뒤에 바뀜"이 된다.
2. **사람 확인 전에 고치기**
   1. 분석 실행이 `awaiting_review`로 끝난다.
   2. 결과 화면에서 "결과 파일 고치기"를 누르면 변경 화면으로 간다.
   3. `summary.csv`의 값 하나를 고쳐 저장한다.
   4. 판정 화면에 "실행 뒤에 손으로 고친 파일: 1개. 검증은 실행이 남긴 파일 기준입니다"가 보인다.
   5. 사람이 받아들인다.
3. **실행 중에 열기**
   1. 실행이 도는 동안 트리에서 파일을 연다.
   2. 읽기 전용이고 "이 작업 공간에서 실행이 진행 중이라 고칠 수 없습니다"가 보인다.
   3. 실행이 끝나면 다시 열어 고친다.

### 5.12 하지 말 것

- 원문(가리지 않은 글)을 화면에 그리지 않는다. 가린 글 편집이 안 되면 편집기를 만들지 않는다.
- task 파일·설정 파일을 글로 고치게 하지 않는다. 설정 화면과 넓히기 확인을 비켜 간다.
- 실행·적용·되돌리기가 잠금을 가진 동안 저장하지 않는다.
- 자동 저장과 덮어쓰기 강제를 두지 않는다.
- OS 기본 앱으로 열지 않는다(6.8). 실행 파일이 돌 수 있다.
- 사람이 고친 뒤 검증을 몰래 다시 돌리지 않는다. 다시 확인이 필요하면 사람이 실행을 다시 한다.
- 상태 디렉터리, 스냅숏, 폐기 보관함을 열지 않는다.
- 구문 강조·확장·터미널·Git처럼 VS Code를 대신하려는 기능을 넣지 않는다.

### 5.13 권고

- **작게 넣는다.** 단, 다음 조건을 모두 채울 때다.
  1. 가린 글 편집(5.3)을 앱 계층이 줄 수 있다. 같은 되살림 규칙을 에이전트와 함께 쓴다.
  2. 메인의 저장 확인(5.5)을 둔다.
  3. 잠금 동안 읽기 전용(5.4)을 지킨다.
  4. 5.9의 최소 범위를 넘지 않는다.
- 조건을 채울 수 없으면 **넣지 않는다.** 대신 변경 화면과 트리의 "탐색기에서 보기" 옆에 "다른 편집기로 고친 뒤 F5로 다시 읽으세요" 같은 안내를 둔다.
- 넣는다면 GUI 설계 문서의 원칙 4·6 설명, 3.1 표의 "편집기에서 파일 열기" 행, 3.4의 "편집은 없다", GUI-D20을 함께 고쳐야 한다(PM 결정).

## 6. 가능성 검토로 넘기는 물음 (p5u-gui, p4g)

1. **가린 글 편집:** 앱 계층이 "편집용으로 읽기"(가린 글, 잠긴 줄 범위, 열 때의 해시)와 "가린 글로 저장"(되살림, 가린 구간 검사, 해시 확인 쓰기)을 내줄 수 있나.
   - 엔진의 `rebuildDocument` 규칙을 실행 밖에서 써도 되나.
   - 가리기는 지금 등록한 값 기준(변경 화면과 같음)인가.
2. **메인 확인:** 렌더러가 침해돼도 임의 파일에 쓰지 못하게 할 방법은 무엇인가.
   - 메인이 연 항목 id에만 저장을 받는가.
   - 첫 저장의 OS 확인을 두는가.
   - 크기 상한을 메인이 다시 보는가.
3. **잠금:** 편집기 저장도 작업 공간 잠금을 잡아야 하나(실행과 겹치지 않게). 잡는다면 저장 중에 실행을 시작하면 어떻게 되나.
4. **기록:** 사람의 저장을 어떤 기록에도 남기지 않는 것이 맞나(5.6). 실행 기록 감시(DR-38)는 작업 공간 파일을 보지 않으니 영향이 없나.
5. **보호 경로·`writablePaths`:** 사람의 저장에 보호 경로 확인을 붙이는 것이 정책 계약과 어긋나지 않나(보호는 에이전트 쪽 규칙).
6. **(가):** 여러 곳 바꾸기를 넣는다면 모두-또는-없음과 실패 위치 보고(`edits[i]`)를 도구 결과에 담을 수 있나.
