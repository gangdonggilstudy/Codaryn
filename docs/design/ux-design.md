## 1. 원칙

1. **엔진은 하나다.** CLI·GUI·IDE는 실행 시작, 진행 이벤트 구독, 취소, 결과·보고서·되돌리기 호출만 하는 어댑터다. 작업 논리, 권한 판단, 가림은 엔진에만 둔다.
2. **사람용 출력과 기계용 출력을 나눈다.** CLI stdout의 JSON 한 줄, 오류 코드, 종료 코드는 고정 계약이다. 사람용 문장은 stderr나 화면에 둔다.
3. **가림본만 보여 준다.** 화면, 진행 줄, 요약, 오류 문구에 비밀 값이나 키를 넣지 않는다. 파일에서 읽은 값은 오류 문구에 넣지 않는다(S-6, S-12).
4. **있는 보호만 말한다.** "통과"는 "지정한 검증 범위에서 통과"다(M-16). OS 격리가 없으므로 "안전", "샌드박스", "차단"이라고 하지 않는다(M-8).
5. **결정은 사람이 한다.** 모델 출력은 권한을 넓히지 못한다. 권한을 넓히는 동작은 사람이 확인한다(7절). 확인의 기본값은 "바꾸지 않음"·"거부"이고, 확인한 답은 그 한 번에만 쓴다(AC-D5).
6. **다음 행동을 알려 준다.** 모든 결과와 오류는 무엇이 일어났는지, 다음에 무엇을 하면 되는지를 함께 말한다.

## 2. 대상 사용자와 주요 과업

| 사용자 | 상황 | 주요 과업 |
| --- | --- | --- |
| 개발자 | 저장소에서 작은 코딩 작업을 맡긴다 | 테스트 명령 허용, 실행 관찰, 변경 검토, 되돌리기 |
| 문서 작업자(비개발자 포함) | 폴더의 문서를 고치게 한다 | 쉬운 초기 설정, 한 줄 실행, 결과 요약, 되돌리기 |
| 관리자(PM) | 자기 개발 후보를 검토·채택한다 | 후보 준비, 보고서, 보호 대상 확인, 병합 판단 |

공통 과업: 초기 설정, 모델 선택, 비밀 등록, 작업 지정, 실행 관찰, 결과 확인, 되돌리기·재실행, 권한 거부 대처, 오류 복구.

## 3. 정보 구조

- **사용자 설정**(설정 파일, 프로필[제안], 변수 파일 경로. 항상 작업 공간 밖, S-1) → **작업 공간**(대상 폴더. 기록은 `<작업 공간>/.codaryn/`[구현]) → **작업**(목표, 권한 규칙, 검증, 한도. task 파일 또는 간편 형식[구현]).
- **실행**(실행 id, 상태와 이유, 진행 이벤트, 변경 목록, 검증 결과, 사용량, 보호 대상 확인 기록[구현]) → **동작**(보고서·되돌리기[구현], 재실행[제안]).
- 단계 4에서 더해지는 것[설계: GT]
  - **워크플로 정의**: 사용자 설정이나 내장. 프로필이나 `--workflow`로 고른다.
  - **계획**(계획 실행의 `plan.json`, 다이제스트) → **적용**(새 실행).
  - **사람 확인**(`review.json`).

## 4. 핵심 흐름

### 4.1 초기 설정 [설계: `codaryn init`, N-1, N-2, N-10]

```
$ codaryn init
설정 폴더: C:\Users\<사용자>\AppData\Roaming\Codaryn (작업 공간 밖) — 만들까요? [Y/n]
모델: 키가 없어 목록을 가져올 수 없습니다. 키를 등록한 뒤 `codaryn models --use`로 고르세요.
한도(기본값): 턴 12 · 도구 호출 24 · 토큰 150000 · 10분 — [Enter] 그대로
허용 명령 제안(작업 공간의 package.json에서): [ ] npm test  [ ] npm run build
보호 경로 제안: tests, package.json, tsconfig.json — [Enter] 그대로
키: 설정되지 않음. 사용자 환경 변수 ANTHROPIC_API_KEY로 등록하세요(값은 묻지 않습니다).
저장했습니다: ...\Codaryn\config.json   다음: codaryn doctor
```

- 키 값은 묻지 않는다(C-1). 명령 제안은 사람이 하나씩 고르고 인자는 고정한다(`allowExtraArgs: false`). 터미널이 아니면 묻지 않는다. 기존 설정 파일은 덮어쓰지 않는다(N-2). 언어(N-4)도 이 단계에서 정한다.
- GUI는 같은 단계를 마법사 4쪽(폴더 → 모델 → 권한 → 점검)으로 둔다([독립 GUI](standalone-gui.md) 3.2). 첫 선택지로 "문서만 고칩니다(명령 실행 없음)"를 둔다.

### 4.2 모델 선택 [구현: Y-1~Y-4]

```
$ codaryn models
 #  id          이름          입력 한도   출력 한도
 1  <모델 id>   <표시 이름>   <토큰 수>   <토큰 수>   ← 현재 설정
 2  <모델 id>   <표시 이름>   <토큰 수>   <토큰 수>
$ codaryn models --use 2 --config <설정 파일>
```

- 키가 필요하고 실제 API에 접속한다(Y-2). `doctor`는 모델 존재를 확인하지 않는다는 사실을 출력에 적는다(Y-4). 실제 API로는 아직 실행하지 않았다.
- 어댑터는 사람이 명시적으로 고를 때만 목록을 부른다. 화면을 열거나 확장이 켜질 때 자동으로 접속하지 않는다(AC 5.6, VS Code 확장 4.1).
- [설계: N-3] `<…>` 꼴 자리표시자와 빈 값은 `doctor`와 `run`이 "설정 안 됨"으로 본다.

### 4.3 비밀 등록

- [구현] 설정·task의 `secretEnv`에 환경 변수 **이름**만 적는다. API 키와 `--vars-file`이 새로 설정한 값은 자동으로 등록된다(S-2, S-4).
- [제안] `doctor`가 "가릴 값 N개: 이름 A, B — 모두 설정됨"처럼 이름과 설정 여부만 보여 준다. GUI 설정 화면에도 같은 목록을 두고 값 입력란은 두지 않는다.
- [설계] 어댑터에도 키 입력란과 키 보관이 없다. VS Code 확장은 VS Code 비밀 저장소를 쓰지 않는다(VX-D7). 사용자 환경 변수를 등록한 뒤에는 VS Code나 GUI 앱을 다시 시작해야 보일 수 있다고 안내한다[추정, 확인 안 함].

### 4.4 작업 지정

- [구현] task 파일 형식과 간편 형식(`--workspace`, `--goal`, 정책·검증·한도는 설정 파일)이 있다.
- [설계: N-8, N-9] 프로필로 흔한 작업을 한 줄로 한다: `codaryn run --workspace D:\work\notes --goal "README에 설치 절을 추가한다" --profile doc`, 또는 작업 공간 폴더에서 `codaryn run "<목표>"`.
- [설계: GT-D1, GT-D2, DR-2] 작업 종류는 워크플로 정의로 고른다. 프로필의 `workflowRef`, 간편 형식의 `--workflow <id>`, 어댑터 실행 요청의 `workflowRef`를 쓴다. 내장 정의는 `general`, `code`, `document`, `analyze`, `organize`다.
- GUI 새 작업 화면: 작업 공간(폴더 선택), 목표(여러 줄), 작업 종류, 프로필, 접힌 "고급"(한도, 허용 명령, 검증).
  - "고급"은 보기 전용이다. 실행 요청에는 정책·한도를 덮어쓰는 필드가 없다(AC 5.1, M-9). 바꾸려면 설정 화면으로 간다.
  - 작업 공간이 Git 저장소도 사본도 아니면 경고 한 줄을 낸다(막지 않음. 엔진은 Git을 요구하지 않는다, M-4). 파일 정리 워크플로에서는 이 경고를 꼭 보인다.
  - [설계: R-1 L-5] 작업 공간 아래 파일 내용이 API로 갈 수 있다는 고지를 늘 보인다. 가려지는 것은 등록한 값뿐이다. 넓은 폴더(드라이브 루트, 사용자 홈 등)는 경고한다. 읽기를 막지는 않는다([독립 GUI](standalone-gui.md) 3.3).

### 4.5 실행 관찰

[구현] 진행 줄은 영어이고 코드가 그대로 나온다(예: `codaryn: tool run_command: denied (command/command_not_allowed)`). [설계: N-4, N-5] 문구:

```
codaryn: 실행 시작 — 작업 ux-doc, 모델 scripted
codaryn: 1턴 · 파일 읽기 README.md — 허용
codaryn: 파일 만듦 INSTALL.md
codaryn: 명령 실행 — 거부: 허용 목록에 없음 (command/command_not_allowed)
codaryn: 검증 install-doc — 통과
codaryn: 끝 — 완료: 지정한 검증 1개 통과 (done/verified)
```

- 어댑터[설계: AC 5.2, 5.3]
  - 같은 이벤트(가림본 기록)를 받아 문구 카탈로그로 문장을 만든다.
  - 취소는 CLI의 Ctrl+C·`--cancel-file`과 같은 신호다[구현: CLI].
  - GUI는 시간순 목록, 진행 표시, 취소 단추를 둔다.
  - VS Code 확장은 진행 알림, 출력 채널, 상태 표시줄을 둔다.
  - 취소 단추의 확인 창은 실수 방지용이다. 취소의 의미(`cancelled`, 변경 유지)를 바꾸지 않는다.

### 4.6 권한 거부와 확인

- [구현] 거부된 도구 호출은 모델에 오류로 돌아가고, 기록에 권한 종류와 코드가 남는다.
- [설계: N-5, N-11, N-17] 끝 요약에 거부를 모아 보여 준다(거부 수는 `report`의 `deniedToolCalls`와 같은 뜻). 예: "거부 1건: 명령 실행(허용 목록에 없음). 허용하려면 설정 `policy.commands`에 규칙을 더하세요. 인자까지 고정하길 권합니다." 단계 4까지는 실행 중에 사람이 허용하는 확인 창이 없다.
- [설계: GT-D9, AC 5.7, AC-D5, AC-D6, AC-D10, DR-3] 단계 5 시작에 실행 중 권한 확인을 연다. 이 통로는 권한 확인 전용이다. 계획 승인은 4.10의 실행 사이 확인으로 한다(DR-1).
  - 묻는 경우: 사용자 설정이나 프로필이 "확인 후 허용"(`confirm: true`)으로 둔 명령 규칙뿐이다. 모델 출력이나 task 파일은 질문을 만들 수 없다(DR-3, M-9). 루트 밖, 상태 디렉터리, 보호 경로, 토큰 복원 거부는 묻지 않고 거부한다.
  - 답: "이번 한 번 허용" 또는 "거부". 기본은 거부다. "항상 허용"은 없다. 늘 허용하려면 설정을 고친다.
  - 허용해도 엔진이 답을 받은 뒤 실효 인자 검사를 다시 하므로 거부될 수 있다(DR-3). 기다리는 동안 작업 공간이 바뀔 수 있기 때문이다.
  - 기다리는 시간도 실행 시간 한도에 든다. 한도에 닿으면 `budget-exhausted`다. 기다리는 중 취소면 `cancelled`다.
  - 질문 글은 가림본이다. 경로·명령이 가림 표시로 보일 수 있고, 화면에 보이려고 복원하지 않는다.
  - 어댑터별 방식
    - CLI 터미널: stderr에 묻고 stdin에서 읽는다. stdout은 그대로다. 터미널이 아니면 묻지 않고 거부한다.
    - VS Code 확장: 모달 대화상자를 띄운다. 닫으면 거부다.
    - GUI: 실행 화면의 질문 패널을 쓴다.
  - 질문과 답(`by`: user, default, cancelled)이 새 사건 `confirmation_requested`·`confirmation_answered`로 기록에 남는다. 물을 수 없으면 거부하고 `by: "default"`다(DR-3).
  - 같은 사람 행동(질문 대기 중 창 닫기, 대화상자 닫기)이 어댑터마다 다른 `by`로 남을 수 있다는 지적이 있다(R-1 L-2). 어댑터 계약 담당이 맞춘다.

### 4.7 결과 확인 [설계: 끝 요약을 stderr로, N-5]

```
── 결과: 완료 (지정한 검증 1개 통과) ──
변경 1개: INSTALL.md (새로 만듦)        거부 1건 · 4턴 · 도구 2회 · 78 ms
보고서:   codaryn report --workspace D:\work\notes --run latest
되돌리기: codaryn revert --workspace D:\work\notes --run 20261111T233839Z-d9c21658
```

- GUI 결과 화면 탭: 요약, 변경, 검증(근거, 검사하지 않은 범위), 보호 대상 확인, 사용량, 기록. 보고서는 구조화된 `ReportOutput`에서 그리고 Markdown을 HTML로 바꾸지 않는다([독립 GUI](standalone-gui.md) 3.5).
- [설계: DR-7] 변경 비교는 VS Code 확장과 독립 GUI 모두 다시 가린 비교만 보인다(VX-D6을 바꿈).
  - 비교 내용은 CLI와 앱 계층의 함수가 내준다. 어댑터는 스냅샷 저장 형식을 직접 읽지 않는다.
  - 화면에 "현재 등록한 가릴 값 기준"이라고 쓴다. 실행이 끝나면 대응표가 없어서 지금 등록한 값으로 다시 가린다(privacy.md 8절).
  - 비교를 내줄 수 없으면 파일 목록과 "폴더에서 보기"만 보인다. 원문 비교는 어떤 어댑터에서도 열지 않는다. 열린 문서를 읽는 다른 확장이나 화면 공유로 원문이 나갈 수 있기 때문이다(R-1 M-6).
  - 비교 내용은 로그·알림·출력 채널에 넣지 않는다.
- [설계: GT-D6, GT-E4] 사람 확인이 있는 워크플로(자료 분석 기본값)는 자동 검증 통과 뒤 "확인 필요: 사람 확인 대기"로 끝난다.
  - 결과 화면에 확인 목록과 승인·반려 단추를 둔다. CLI는 `codaryn review --run <id> --accept|--reject [--note]`다.
  - 판정은 `review.json`에 남는다. 끝 상태는 바뀌지 않는다. "완료"는 지정한 검증 통과만 뜻하기 때문이다(M-16).
  - `report`는 "사람 확인: 승인(시각)"처럼 보인다.

### 4.8 되돌리기·재실행

- [구현] `revert --workspace --run`. 실행 뒤 바뀐 파일은 건너뛰고 `partial`로 알린다.
- [설계: N-7] 미리보기:

```
$ codaryn revert --workspace D:\work\notes --run latest --dry-run
되돌릴 파일 1개: INSTALL.md — 삭제 (이 실행이 만든 파일)
건너뛸 파일 0개.  되돌리려면 --dry-run 없이 다시 실행하세요.
```

- 어댑터의 미리보기는 `--dry-run`(또는 `revert({dryRun: true})`) 뒤 확인을 받고 다시 부르는 두 번의 호출이다. 사이에 바뀐 파일은 두 번째 호출이 건너뛴다. 미리보기는 약속이 아니라고 확인 창에 쓴다(AC 5.5).
- [설계: GT 6.4, DR-9] 파일 정리의 적용 실행을 되돌리면 이동한 파일을 원래 자리로 옮기고 보관함(`.codaryn/discarded/<runId>/`)의 파일을 되살린다. 대상이 바뀌었거나 원래 자리에 파일이 있으면 건너뛴다.
- 재실행: GUI는 결과 화면의 "같은 작업 다시 실행"이 같은 task로 새 실행을 만든다. 이전 실행과 합치지 않는다(architecture 8절). 목표 원문은 디스크에 저장하지 않는 것을 권고한다(GUI-D11).

### 4.9 오류 복구 [설계: 사람용 오류를 stderr에, N-5, N-6]

```
codaryn: 오류 — 설정 파일이 없습니다 (invalid_config)
  고치는 법: --config <파일> 또는 CODARYN_CONFIG. 예시: examples\config.example.json
  점검: codaryn doctor
```

- 오류 문구의 형식: 무엇이(한 줄), 고치는 법(하나 또는 둘), 코드(괄호). 파일·환경 값은 넣지 않는다.
- [설계: N-15] 설정·task 오류의 위치는 구조화 진단(고정 진단 코드, 필드 위치, 줄·열)에서 만든다. 파서 예외 문구와 알 수 없는 키 이름은 보이지 않는다.
- GUI: 같은 내용을 카드로 보여 준다. 고치는 법이 화면 이동이면 그 화면으로 가는 단추를 둔다.
- 어댑터는 오류 코드로 문구를 찾는다. 오류 `message`는 "자세히"에만 두고 자식 CLI의 stderr 원문을 알림에 넣지 않는다(AC 5.8, VX 6.1).
- 어댑터 쪽 오류(자식 실행 실패, 출력이 계약과 다름, 엔진 프로세스가 결과 없이 끝남)는 "실행 결과를 알 수 없음, 보고서로 확인"으로 보이고 `report`를 안내한다(AC 5.8).

### 4.10 계획 확인과 적용 [설계: GT-D4, GT-D5, GT-D13, DR-1, DR-2, DR-5, DR-6, DR-9]

파일 정리(`organize`)는 계획 확인이 필수다. 계획은 실행 사이에서 확인한다. 실행 중에 묻는 질문이 아니다(DR-1). 엔진은 기다리지 않는다.

```
$ codaryn run --workspace D:\work\photos --goal "사진을 연도별 폴더로 나눈다" --workflow organize
codaryn: 끝 — 확인 필요: 계획 확인 대기. 파일은 아직 바뀌지 않았습니다 (needs-input/plan_pending)
  계획 보기: codaryn plan --workspace D:\work\photos --run latest
$ codaryn plan --workspace D:\work\photos --run latest
이동 120개, 폐기 3개(보관함으로 옮김). 다이제스트 3f9a1c0b7e21…
  IMG_0001.jpg → 2023/IMG_0001.jpg
  …
적용하려면: codaryn apply --workspace D:\work\photos --run <id> --digest 3f9a1c0b7e21
```

- `plan`은 `plan.json`을 다시 가려 보인다. `plan.json`에는 행동과 원본 해시만 있다. 적용 때의 정책과 검증기는 그때의 설정과 task에서 읽는다(DR-5).
- 승인은 다이제스트로 묶는다. 사람이 본 목록과 적용될 계획이 같다는 증거다. 해시는 이 다이제스트 하나다(DR-1).
  - 비대화형에서 `--digest`가 없거나 틀리면 아무것도 옮기지 않는다(`plan_not_approved`).
  - 터미널이면 목록을 보이고 `[y/N]`으로 묻는다.
  - 앞 12자 승인은 실수 방지용이다. 작업 공간에 쓸 수 있는 공격자는 막지 못한다(R-1 I-3).
- 계획 뒤 원본이 바뀌었거나 대상이 생겼으면 아무것도 옮기지 않는다(`plan_stale`). 다시 실행해 새 계획을 만든다.
- 폴더가 커서 적용 뒤 확인(`inventory`)의 상한에 닿으면 적용 전에 알린다(DR-6).
- 적용도 실행처럼 진행 이벤트와 취소를 쓴다(`apply --events jsonl --cancel-file`, DR-2). 적용을 취소했을 때의 끝 상태는 아직 정하지 않았다(R-1 L-7).
- "삭제"는 보관함 `.codaryn/discarded/<runId>/`로 옮기는 "폐기"다. 되돌리기가 되살린다(DR-9).
  - 보관함은 실행 디렉터리 밖이다. 실행 기록을 정리해도 지워지지 않는다.
  - 보관함 정리는 파일 수와 크기를 보이고 따로 확인한다(7절).
- 기존 파일 위로 옮기지 않는다. 계획 검증에서 거부한다.
- GUI·VS Code의 계획 화면은 `needs-input`/`plan_pending` 결과 뒤에 연다(DR-1).
  - 내용: 이동 표, 폐기 목록, 개수, 다이제스트, "적용" 단추. 기본은 "적용 안 함"이다.
  - 화면은 앱 계층의 계획 보기와 `applyPlan(runId, digest)`를 부른다(DR-1, 계약 갱신 대기). 적용 뒤에는 적용 실행의 결과 화면으로 간다.
- 작업 공간이 Git도 사본도 아니면 실행 전에 경고한다(4.4).

## 6. 상태와 진행 표현

| 상태/이유 | 표현(ko) | 다음 행동 안내 |
| --- | --- | --- |
| done/verified | 완료: 지정한 검증 모두 통과 | 보고서, 필요하면 되돌리기 |
| failed/verifier_failed, repeated_failure | 실패: 검증 미통과(재수정 한도 소진 / 같은 실패 반복) | 보고서의 근거 확인, 목표·검증 수정 후 다시 실행 |
| failed/model_error | 실패: 모델 호출 오류(종류) | `doctor`, `models`, 잠시 뒤 다시 실행 |
| needs-input/no_verifier, verifier_inconclusive, unknown_tool_outcome | 확인 필요: 검증 없음 / 검증 판단 불가 / 결과 모르는 호출 | 검증 추가, 시간 한도 조정, 기록 확인 |
| needs-input/protected_changed | 확인 필요: 보호 대상이 바뀌어 검증 무효 | 보고서의 "보호 대상" 절, 원래대로 돌린 뒤 다시 실행 |
| budget-exhausted/* | 한도 도달: 턴·도구 호출·토큰·시간·사용량 미보고 | 한도 조정 또는 목표 나누기 |
| cancelled | 취소됨: 이미 한 변경은 남아 있음 | 되돌리기 |
| needs-input/plan_pending [설계] | 확인 필요: 계획 확인 대기. 파일은 아직 바뀌지 않음 | `plan`으로 보고 `apply --digest`로 적용 |
| needs-input/awaiting_review [설계] | 확인 필요: 지정한 검증 통과, 사람 확인 대기 | 확인 목록을 보고 `review --accept` 또는 `--reject` |
| failed/plan_stale [설계] | 실패: 계획 뒤 파일이 바뀌어 적용하지 않음. 아무것도 옮기지 않음 | 다시 실행해 새 계획 만들기 |
| failed/apply_incomplete [설계] | 실패: 적용 도중 멈춤. 한 것까지 기록됨 | 보고서 확인, `revert` |

- 실행 전 오류에 더해질 코드[설계: GT 9절]: `plan_not_approved`(다이제스트 없음·틀림), `plan_already_applied`, `run_not_plan`(계획 실행이 아님).

- 표현은 낱말을 먼저 쓴다(완료·실패·확인 필요). 색과 기호는 보조로만 쓴다.
- 시간은 단위와 함께 쓰고, 사람용 시각은 지역 시간으로 쓴다(실행 id는 UTC).

## 7. 위험한 동작의 확인

| 동작 | 확인 방식 |
| --- | --- |
| 되돌리기 | [설계: N-7] CLI: `--dry-run` 미리보기(명시 명령이므로 묻지 않음). GUI·VS Code: 미리보기와 확인. 기본은 "되돌리지 않음" |
| 계획 적용(이동·폐기) | [설계: GT-D4] 비대화형은 `--digest` 필수, 터미널은 `[y/N]`, GUI·VS Code는 계획 화면의 확인. 기본은 "적용 안 함" |
| 실행 중 권한 확인의 답 | [설계: AC-D5, DR-3] 기본 거부, 이번 한 번만. 답할 수 없으면 거부(`by: "default"`) |
| 실행 기록과 폐기 보관함 정리(`cleanup`) | [구현: DR-39, DR-44] 명령 하나가 둘을 다룬다(DR-9의 "따로 한다"는 확인을 따로 받는 것으로 바뀌었다). 기본은 미리보기다: 고른 실행 기록과 폐기 보관함을 항목마다 파일 수, 크기, 경고와 함께 보이고 아무것도 지우지 않는다. 지우려면 미리보기의 다이제스트를 `--confirm`으로 준다. 되돌리지 않은 실행의 기록은 `--include-not-reverted`, 폐기 보관함(사람의 파일, 되살릴 수 없음)은 `--delete-discarded`를 더해야 지운다. 확인은 인자로만 받는다. 미리보기 뒤에 상태가 바뀌었으면 아무것도 지우지 않는다(`plan_changed`). [결정: DR-53] 폐기 보관함에 파일이 남는 적용 실행의 기록은 보관함을 함께 지우기로 확인하지 않으면 남긴다(단위 U-13, main `a9a98fd`에는 아직 없다) |
| 강제 종료(VS Code 확장) | [설계: VX-D12] 취소 뒤 응답이 없을 때 결과를 알 수 없게 된다는 점을 보이고 확인받은 뒤에만 |
| 허용 명령 추가, `allowExtraArgs: true`, 한도 올리기 | 결과("이 명령은 어떤 인자든 실행합니다")를 보여 주고 확인한다. 비대화형은 명시 플래그 없이는 바꾸지 않는다 |
| 보호 경로·`integrity.paths` 비우기 | 경고와 확인 |
| Git도 사본도 아닌 작업 공간에서 실행 | 경고만(막지 않음) |

입력이 터미널이 아니면 묻지 않는다. 기본값은 항상 "바꾸지 않음"이다.

- 아래 행은 [제안]이며 결정 전이다: 허용 명령 추가·한도 올리기, 보호 경로 비우기, Git 아닌 작업 공간 경고. 실행 기록 삭제는 `cleanup`으로 구현됐다(위 표, 사용 안내 18.8절).
- GUI에서는 권한을 넓히는 변경의 확인을 화면이 아니라 메인 프로세스의 OS 대화상자로 받기를 권고한다([독립 GUI](standalone-gui.md) 9.2절 4, 설계만).

## 8. 접근성과 언어

- 언어[N-4. 카탈로그 모듈은 구현, CLI 연결 전]
  - 한국어·영어 고정 문구 카탈로그(`src/i18n`, CLI와 어댑터가 함께 쓴다).
  - [설계: N-20, N-21] 거부 사유·권한 종류·모델 오류 종류의 사람 말, 초 단위 소요 시간, 예·아니오 질문의 기본 답("바꾸지 않음"), 언어가 어디서 정해졌는지의 안내, `doctor` 점검 문구와 `--help`도 카탈로그에 넣는다.
  - 선택: `CODARYN_LANG` > 설정 `language` > OS 표시 언어.
  - VS Code 확장은 OS 표시 언어 자리에 VS Code 표시 언어를 쓴다(VX-D11).
  - 코드, JSON 필드, 명령 이름은 영어로 고정한다.
  - 문구에 넣는 값은 숫자, 고정 코드, 필드 위치, 고정 표시 문자열뿐이다. 파일에서 온 이름(검증기 id 등)은 순번으로 보인다(N-14).
  - stdout JSON은 비 ASCII 문자를 `\uXXXX`로 낸다. 사람용 글(stderr, 화면)은 그대로 쓴다(N-19).
- 텍스트만으로 뜻이 통하게 한다(색 없음·`NO_COLOR`·화면 낭독기에서도 상태 낱말로 구분). 줄 너비는 100자 안팎, 경로·id는 한 줄, 진행 줄은 `codaryn:` 접두사를 유지한다.
- GUI는 키보드만으로 모든 동작을 할 수 있게 하고 상태 변화를 낭독기에 알린다. 독립 GUI의 목표는 WCAG 2.2 AA다([독립 GUI](standalone-gui.md) 7절, 설계만).
- VS Code 확장은 첫 판에 웹뷰를 쓰지 않는다. 기본 구성 요소의 키보드·낭독기 지원을 따른다(VX-D5).

## 10. 다른 문서와 맞출 점

PM이 R-1 뒤에 DR-1~DR-9로 정했다. 아래는 그 결정대로 각 담당이 고칠 곳이다(이 문서는 고치지 않는다).

- [어댑터 계약](adapter-contract.md)
  - 5.7의 `ConfirmRequest`에서 `plan`을 빼고 권한 확인 전용으로 둔다(DR-1).
  - 계획 보기, `applyPlan(runId, digest)`, 사람 확인 `review` 함수(DR-1). 실행 요청의 `workflowRef`와 적용의 이벤트·취소(DR-2).
  - 대소문자 무시 환경 조회와 실행기 부모 환경(DR-4). 다시 가린 변경 비교 함수(DR-7).
  - 진행 이벤트에 `plan_proposed`, `file_moved`, `file_discarded`가 더해진다(general-tasks 12절).
- [VS Code 확장](vscode-extension.md)
  - `plan`·`apply`·`review` 명령과 계획 화면(DR-1).
  - 변경 비교를 다시 가린 비교로(DR-7, VX-D6 대체).
  - 질문 대기 중 창 닫기의 기록(R-1 L-2).
- [독립 GUI](standalone-gui.md): DR-1·DR-7·DR-8·DR-9를 반영했다(D3, `462e386`).
- [범용 작업](general-tasks.md): `plan.json` 내용(DR-5), `inventory`(DR-6), 보관함 위치(DR-9), 권한 확인 형태(DR-3), 적용 취소의 끝 상태(R-1 L-7).
- [사용성 검토](usability-review.md): D-1~D-6은 N-1~N-13으로 정해졌다. 그 문서는 검토 기록으로 둔다.
- 사용 문서(`usage.md`): 4.10의 계획 확인과 적용, 4.7의 사람 확인, 파일 정리 전 사본·Git 권고는 해당 기능 병합 뒤에 더한다(G-H).
