# 사용성 중간 점검 (2026-11-12)

페르소나: 사용성·UX 전문가(이 점검에만 쓰는 역할). 개발자가 아닌 일반 사용자의 눈으로 명령을 직접 쳐 보고 적었다. 고친 파일은 이 문서 하나다. 제품 코드, 다른 문서, 커밋은 건드리지 않았다.

## 0. 점검한 판, 방법, 한계

- **판:** 문서와 코드는 worktree `pm-docs`(브랜치 `unit/U-12-pm`, main `a7f3a2f`과 같음)에서 읽었다. 실행한 CLI는 `pm-integration`의 빌드(`e0e1180`)다. 지시서에 따르면 두 판은 코드가 같고 검토 기록 문서만 다르다. 이 점은 내가 따로 확인하지 않았다.
- **방법**
  - 처음 쓰는 사람의 순서대로 CLI를 약 125번 실행했다. 한국어(`CODARYN_LANG=ko`)와 영어(`en`) 둘 다 봤다.
  - 작업 공간은 모두 임시 폴더(scratchpad의 `ux\`)에 새로 만들었다. 저장소 폴더는 작업 공간으로 쓰지 않았다.
  - 모델이 필요한 실행은 `examples/demo`, `examples/organize-demo`의 scripted 대본만 썼다. 실제 API 호출과 외부 네트워크 접속은 없다.
  - 실행할 때 제공자 키 변수 둘을 프로세스 환경에서 뺐고(값은 읽지 않았다), `APPDATA`를 임시 폴더로 돌려 사용자의 실제 기본 설정 파일을 읽거나 쓰지 않게 했다. 그래서 "키도 설정도 없는 새 사용자"의 상태로 봤다.
  - 기록 변경 표시는 유닛 시험(`g-u1-apply-marked-plan`)과 같은 방법으로, 계획 실행 폴더에 표시 파일을 손으로 넣어 만들었다. 잠긴 작업 공간은 통합 시험(`n03`)과 같은 방법으로, 살아 있는 프로세스 번호를 넣은 잠금 파일로 만들었다.
  - GUI는 띄우지 않았다. `gui/src/renderer/**`의 화면 코드와 문구(`i18n/ko.ts`, `en.ts`), 메인의 대화상자 문구(`gui/src/main/dialog-texts.ts`), `docs/design/standalone-gui.md`, 연기 시험의 단계 주석을 읽었다.
- **한계**
  - **GUI의 실제 화면을 보지 못했다.** 배치, 글자 크기, 대화상자의 실제 모양, 키보드 이동은 평가하지 않았다. GUI 항목은 모두 "코드와 문구로 본 것"이다.
  - 터미널 질문(`[y/N]`)은 보지 못했다. 내 실행은 터미널이 아니어서 묻지 않는 길만 탔다. `init`도 묻지 않는 길만 봤다.
  - 실제 모델이 내는 진행 줄의 양과 속도는 모른다. 대본 실행만 봤다.
  - 사람 확인(`review`)과 `analyze` 흐름, 하드 링크 없는 드라이브의 동의 흐름은 실행하지 않았다. 문서로만 읽었다.
  - Windows 한 대, Git Bash에서 실행했다. PowerShell 창에서의 글자 깨짐, 줄 접힘은 보지 않았다.

## 1. 한 쪽 요약

가장 중요한 문제 일곱 개다. 뒤의 번호는 3절의 문제 id다.

1. **정리가 사람의 파일을 주인 없는 상태로 남길 수 있다(UXM-1, 높음).** `cleanup --confirm … --include-not-reverted`만 주면 적용 실행의 기록은 지워지고 보관함의 파일은 `2`라는 이름으로 남는다. 원래 이름과 자리를 알려 주는 것이 어디에도 없고, 결과 줄도 그 사실을 말하지 않는다. → 이 조합을 기본으로 막거나, 원래 경로 목록을 보관함에 남기고 결과에 알린다.
2. **오류의 진짜 이유가 영어 JSON 안에만 있다(UXM-2).** 사람용 줄은 "명령 인수가 올바르지 않습니다", "task 파일을 읽을 수 없거나 값이 올바르지 않습니다"처럼 넓은 말이고, "어느 옵션이 빠졌는지", "파일이 없다", "task 파일이 작업 공간 안에 있다" 같은 이유는 stdout JSON의 `message`(영어)에만 있다. → 이유를 사람용 줄에 고정 문구로 올린다.
3. **계획·적용 흐름에서 상태 표시가 실제와 어긋난다(UXM-4, 5, 6).** 적용한 뒤에도 계획 실행은 목록에 "확인 필요"로 남는다. 적용 실행의 `changes`는 "the run changed no file"인데 목록은 변경 3이다. 기록 변경 표시가 있는 계획을 `plan`은 경고 없이 보여 주고 적용 명령까지 안내하지만 `apply`는 거부한다. 그 거부의 고치는 법은 없는 길("codaryn plan으로 계획을 새로 만들고")을 가리킨다.
4. **한국어 출력에 영어가 많이 남았다(UXM-7).** `plan`·`apply`·`review`·`changes`·`cleanup`의 도움말, `plan`과 `changes`의 본문, `report` 전체, `cleanup`의 끝 안내가 영어다. 도움말에는 내부 결정 번호(`DR-39`, `DR-29`)가 나온다.
5. **끝 요약의 "다음 명령"을 그대로 쓸 수 없다(UXM-8).** `codaryn report --workspace <workspace> --run …`처럼 자리표시자가 들어 있어 복사해 붙이면 실패한다. 새로 생긴 `changes`는 안내에 없다.
6. **처음 시작이 어렵다(UXM-9, UXM-13).** `--help`는 사용법 줄 열네 개뿐이고 무엇부터 할지 말하지 않는다. `doctor`는 실패 항목을 나열할 뿐 "다음에 이것을 하라"는 한 줄이 없고, 키 없이 해 볼 수 있다는 안내도 없다. GUI에는 설계된 첫 실행 안내(3.11절)가 아직 없다.
7. **같은 것을 가리키는 말이 여러 개다(UXM-16).** 동작/행동, 폐기 보관함/보관함, 작업 종류(workflow)/작업 종류/워크플로, digest/다이제스트. 영어는 CLI가 workflow·discarded files, GUI가 task kind·discard box, 설계 문서가 task type·run archive다.

## 2. 잘 된 것 (유지할 것)

- **"아무것도 바꾸지 않았습니다"를 늘 말한다.** 거부·오류·미리보기마다 바뀐 것이 없다는 말이 있다. 불안을 줄인다.
- **오류의 꼴이 같다.** `오류 — 무엇 (코드)` / `고치는 법:` / `점검:` 세 줄. 값은 보이지 않고 필드 위치만 말한다. JSON 문법 오류는 줄과 열을 준다(`3줄 13열`).
- **잠긴 작업 공간의 안내가 좋다.** 기다리라는 말과, 실행 중인 것이 없을 때 지울 파일 이름을 함께 준다. `doctor`도 같은 말을 한다.
- **되돌리기 미리보기.** `--dry-run`이 파일마다 무엇을 할지 보이고, "되돌리려면 --dry-run 없이 다시 실행하세요"로 끝난다. 이미 되돌린 실행은 목록에 `· 되돌림`으로 붙는다.
- **`--run latest`가 고른 실행을 먼저 말한다.** `가장 최근 실행을 골랐습니다: <id> (시작 …)`. 승인이 필요한 `apply`와 `cleanup`은 `latest`를 받지 않는다. 옳은 구분이다.
- **계획 승인이 다이제스트다.** 실수로 다른 계획을 적용하기 어렵다. 틀린 다이제스트, 이미 적용한 계획, 표시가 붙은 계획을 모두 거부하고 아무것도 옮기지 않는다.
- **`init`이 조심스럽다.** 있는 파일을 덮어쓰지 않고, 키를 묻지 않고, 키 등록 방법과 `다음: codaryn doctor`를 준다.
- **`doctor`의 마지막 줄.** "네트워크에 접속하지 않았고 아무것도 바꾸지 않았습니다."
- **정리의 기본이 미리보기다.** 고르기만 하면 지우지 않고, 지울 것과 경고와 다이제스트를 보인다. 미리보기 뒤에 상태가 바뀌면 지우지 않는다.
- **GUI 대화상자의 기본 답이 모두 "바꾸지 않음" 쪽이다**(코드에서 `defaultId: 1`, 단추 이름이 "되돌리지 않음", "적용 안 함", "정리하지 않음", "그 기록은 남김", "보관함은 남김"). 단추 이름이 "예/아니오"가 아니라 하는 일을 말한다.
- **GUI의 변경 단추는 일반 실행에만 붙는다**(`runs-screen.ts`의 `run.kind === "run"` 조건). CLI의 UXM-4 같은 어긋남이 GUI에는 없다.

## 3. 문제 목록

심각도: **높음** 사용자가 일을 끝내지 못하거나 되돌릴 수 없는 실수를 하게 됨 / **중간** 헷갈리거나 여러 번 시도하게 됨 / **낮음** 다듬기.
출력 인용에서 `…`은 내가 줄인 곳이다. 명령의 `codaryn`은 실제로는 `node …\dist\src\cli\main.js`로 실행했다.

### UXM-1 정리 뒤 보관함의 파일이 주인 없이 남는다 — 높음

- **어디:** `cleanup --confirm <digest> --include-not-reverted`(CLI), GUI 정리의 대화상자 둘째·셋째.
- **실제로 본 것:** 파일 정리 체험을 적용만 하고 되돌리지 않은 작업 공간에서.

  ```
  $ codaryn cleanup --workspace cl1/workspace --older-than 0 --discarded-older-than 0 --confirm <미리보기의 digest> --include-not-reverted
  지웠습니다: 실행 기록 2개, 폐기 보관함 폴더 0개, 13703바이트
  - discarded 20261112T135834Z-86b30b72: 폐기 보관함 삭제를 확인하지 않음
  ```

  그 뒤 `runs`는 `이 작업 공간에는 실행 기록이 없습니다.`이고, 요약만 보는 `cleanup`은 `폐기 보관함(…): 1개(17바이트)` 아래에 `정리할 것이 없습니다.`를 낸다. 폴더에는 `.codaryn/discarded/20261112T135834Z-86b30b72/2`만 남았다. 이 파일은 원래 `inbox/old-draft.tmp`였다.
- **왜 문제인가**
  - 사람의 파일이 번호 이름(`2`)으로 숨은 폴더에 남는다. 원래 이름과 자리를 적은 기록(계획 실행의 `plan.json`)은 방금 지워졌다. 되돌리기로는 돌아오지 않는다.
  - 미리보기는 이것을 경고한다. 하지만 230자쯤 되는 한 줄 안에 다른 경고와 섞여 있다. 정작 **지운 뒤의 결과 줄은 "삭제를 확인하지 않음"뿐**이라, 그 파일이 이제 손으로만 살릴 수 있다는 것도, 어디에 무슨 이름으로 있는지도 말하지 않는다.
  - "되돌리지 않은 실행의 기록도 지움"에 예라고 한 사람은 보관함을 "남기는 것이 안전한 쪽"이라고 여기기 쉽다. 그런데 이 조합에서는 남기는 쪽이 파일을 잃어버리는 쪽이다. GUI도 같다. 셋째 대화상자의 기본 단추 "보관함은 남김"이 이 결과로 간다(대화상자 설명에 한 줄 경고는 있다).
- **개선안**(셋 중 고르기. 권장은 (a)+(c))
  - (a) 적용 실행의 기록을 지우는데 그 보관함이 남는 조합이면, 그 적용 실행과 계획 실행의 기록은 **남긴다**. 이유 줄: `보관함에 파일이 남아 있어 이 적용 실행의 기록은 남김. 먼저 되돌리거나, 보관함도 함께 지우세요.` 지금도 "남긴 적용이 쓰는 계획 실행은 남김" 규칙이 있으니 같은 생각의 연장이다.
  - (b) 조합을 허용하되, 지우기 전에 보관함 폴더에 원래 경로 목록 파일(예: `original-paths.txt`, 번호 → 원래 상대 경로)을 남긴다.
  - (c) 어느 쪽이든 결과 줄을 바꾼다.
    - before: `- discarded <id>: 폐기 보관함 삭제를 확인하지 않음`
    - after: `- 보관함 <id>: 남김. 파일 1개가 .codaryn/discarded/<id>/ 에 있습니다. 이 실행의 기록을 지웠으므로 되돌리기로는 돌아오지 않습니다. 필요하면 손으로 꺼내세요.`
  - 요약만 보는 `cleanup`에도 `기록이 없는 보관함: N개`를 따로 세어 보인다.
- **영향 범위:** 계약(정리 결과의 사유 코드, (b)면 보관함 형식), CLI 출력, 문구, GUI 대화상자·결과 화면, 문서(usage 18.8).
- **예상 크기:** 중간((a)+(c)). (b)까지 하면 큼.

### UXM-2 오류의 구체적 이유가 영어 JSON에만 있다 — 중간

- **어디:** 모든 명령의 인자 오류, `invalid_task`, `invalid_config`, `key_in_file`, `provider_not_configured`.
- **실제로 본 것**(한국어, 사람용 줄과 JSON의 `message`를 나란히)

  | 한 일 | 사람용 줄(stderr) | 이유(stdout JSON, 영어) |
  | --- | --- | --- |
  | `codaryn frobnicate`(없는 명령) | `명령 인수가 올바르지 않습니다` / `codaryn help <명령>으로 사용법을 확인하세요.` | `usage: codaryn run … \| codaryn revert …`(900자쯤) |
  | `run --workspace ws1`(목표 없음) | 같음 | `--workspace and --goal must be given together. usage: …` |
  | `run … --verbose`(없는 옵션) | 같음 | `unknown or repeated option. usage: …`(어느 옵션인지 없음) |
  | `apply … --run latest` | 같음 | `apply needs the plan run's id; latest is not accepted, so the approval names one plan` |
  | `apply … --digest 4695b9`(짧음) | 같음 | `--digest must be 12 to 64 lowercase hexadecimal characters …` |
  | `run --task err/none.json`(없는 파일) | `task 파일을 읽을 수 없거나 값이 올바르지 않습니다` / `task 파일에서 알려 준 필드를 고치세요.` | `the task file cannot be read as JSON` |
  | task 파일을 작업 공간 안에 둠 | 같음(필드 줄 없음) | `the task file is inside the workspace … keep it outside so a run cannot change it` |
  | `run … --profile nope` | `설정 파일을 읽을 수 없거나 값이 올바르지 않습니다` / `설정 파일에서 알려 준 필드를 고치세요.` | `the config file has no profile with the name given by --profile` |
  | `run … --workflow nope` | 같음 | `workflowRef names no built-in workflow and no workflows entry of the config file` |
  | task에 키 필드 | `task·설정 파일이나 목표에 키 필드나 키 값이 있습니다` | `the task file has a key field or key value at apiKey; …` |
  | 목표 문장에 키 모양 | 같음 | `the goal contains a key value; …` |
  | 키 없이 `models` | `모델 제공자 설정(키, 모델, 출력 상한)이 끝나지 않아 …` | `not set: ANTHROPIC_API_KEY. Nothing was sent` |

- **왜 문제인가**
  - 한국어 사용자는 영어 JSON 덩어리에서 이유를 찾아야 한다. `--quiet`가 아니면 두 줄이 붙어 나와 화면에서 JSON이 사람용 줄을 가린다.
  - 사람용 줄만 읽으면 틀린 곳으로 간다. 파일이 없는데 "필드를 고치세요", 프로필 이름을 틀렸는데 "설정 파일의 필드를 고치세요", 없는 명령인데 "인수가 올바르지 않습니다".
  - `key_in_file`은 세 군데(task, 설정, 목표) 중 어디인지 말하지 않는다. 엔진은 이미 알고 있다(JSON에 있다).
  - N-5("무엇이, 어떻게 고치나")와 N-6("어느 필드인지")의 뜻에 못 미친다. 값은 넣지 않아도 되는 이유들이다.
- **개선안:** 이유마다 고정 문구 id를 두고 사람용 줄 둘째 줄에 낸다(값은 넣지 않는다. 옵션 이름과 파일 종류는 고정 문자열이다).
  - 없는 명령 → `오류 — 그런 명령이 없습니다 (invalid_arguments)` / `명령 목록: codaryn --help`
  - 빠진 옵션 → `  --workspace와 --goal은 함께 줘야 합니다.` / 모르는 옵션 → `  모르는 옵션이거나 두 번 준 옵션입니다: 3번째 인자`(이름 대신 순번. 이름을 그대로 되풀이해도 되는지는 6절 질문 3)
  - `apply --run latest` → `  apply는 계획 실행 id를 정확히 받아야 합니다(latest 불가). 실행 목록: codaryn runs`
  - 파일 없음 → `오류 — task 파일을 찾을 수 없습니다 (invalid_task)` / `고치는 법: --task의 경로를 확인하세요.`
  - 작업 공간 안의 task → `  task 파일이 작업 공간 안에 있습니다. 작업 공간 밖으로 옮기세요.`
  - 프로필 → `오류 — 설정 파일에 그 이름의 프로필이 없습니다 (invalid_config)` / `고치는 법: 프로필 이름은 codaryn doctor --profile <이름>으로 확인하거나 설정 파일의 profiles를 보세요.` 작업 종류도 같은 꼴.
  - `key_in_file` → `오류 — 목표 문장에 키 값이 있습니다`, `task 파일의 apiKey 필드에 키가 있습니다`처럼 장소별 세 문구.
  - `provider_not_configured` → `  빠진 것: 키 변수(ANTHROPIC_API_KEY), 모델`처럼 빠진 항목의 고정 이름을 나열. 지금은 `doctor`를 한 번 더 돌려야 안다.
- **영향 범위:** 계약(오류의 구조화 진단에 이유 코드 더하기), 문구 카탈로그(ko·en), CLI 사람용 출력, GUI(같은 이유 코드를 받으면 화면에도 쓸 수 있다), 문서(usage 17절).
- **예상 크기:** 중간~큼(이유가 스무 개 안팎. 인자 오류 / 파일·설정 오류로 둘로 나눌 수 있다).

### UXM-3 읽기만 하는 `changes`가 간편 형식에서 키와 모델을 요구한다 — 중간

- **어디:** `changes --workspace <dir> --run …`.
- **실제로 본 것:** 체험 실행(`run --task`) 직후, 끝 요약이 `report --workspace <workspace> …`를 안내하므로 같은 꼴로 쳤다.

  ```
  $ codaryn changes --workspace demo-ko/workspace --run latest
  codaryn: 오류 — 모델 제공자 설정(키, 모델, 출력 상한)이 끝나지 않아 아무것도 보내지 않았습니다 (provider_not_configured)
    고치는 법: codaryn doctor로 제공자의 키 변수를 포함해 빠진 항목을 확인하세요. …
  ```

  `changes --task demo-ko/task.json --run latest`는 잘 된다. 한편 같은 환경에서 `apply --workspace … --workflow organize --run … --digest …`는 키 없이 **적용까지 됐다.**
- **왜 문제인가:** `changes`는 도움말이 "Reads only"라고 하는 명령이다. 모델을 부르지 않는데 "아무것도 보내지 않았습니다"라는 오류가 나오면 사용자는 변경 보기가 모델을 쓰는 줄 안다. 바꾸는 명령(`apply`)은 되고 읽는 명령(`changes`)은 막히는 것도 거꾸로다. `report`·`runs`·`revert`는 `--workspace`만으로 되므로, 사용자는 `changes`도 그럴 것이라 기대한다.
- **개선안:** 모델을 부르지 않는 명령(`changes`, `plan`, `apply`, `review`)의 간편 형식은 제공자 설정(키·모델·출력 상한)을 요구하지 않는다. 가림에 필요한 비밀 이름만 읽는다. 그때까지는 오류 뒤에 한 줄을 더한다(지금 `plan`의 한도 오류에 붙는 안내와 같은 방식): `changes는 모델을 부르지 않습니다. 그 실행에 쓴 task 파일이 있으면 --task로 주세요.`
- **영향 범위:** CLI(간편 형식의 조립), 문구, 문서(usage 10절·18.1절).
- **예상 크기:** 작음~중간. 요구를 없애는 것이 계약에 닿는지는 6절 질문 5.

### UXM-4 적용 실행의 `changes`가 "바꾼 파일 없음"이라고 한다 — 중간

- **어디:** `changes --run <적용 실행 id>`와 `runs`.
- **실제로 본 것**

  ```
  $ codaryn runs --workspace org-ko/workspace
  20261112T135733Z-194379b2  2026-11-12 22:57:33  3     완료 (done/verified)
  $ codaryn changes --task org-ko/task.json --run 20261112T135733Z-194379b2
  changes of run 20261112T135733Z-194379b2, masked with the secrets registered now (not the run's own masking)
  the run changed no file
  ```

- **왜 문제인가:** 방금 파일 셋을 옮긴 실행이다. 목록은 변경 3, 변경 보기는 0이다. "변경"이 한쪽에서는 적용한 동작 수, 다른 쪽에서는 파일 쓰기 도구의 기록이라는 내부 구분이 그대로 드러난다.
- **개선안:** 적용 실행이면 `changes`가 동작 목록을 보인다(글 비교는 없이). 최소한 문구를 바꾼다.
  - before: `the run changed no file`
  - after(ko): `이 실행은 계획을 적용한 실행입니다. 옮기거나 폐기한 파일 3개는 codaryn report --workspace … --run <id>의 "동작" 절에 있습니다.`
  - `runs`의 열 이름도 적용 실행 줄에서는 `동작 3`처럼 구분한다(UXM-5와 함께).
- **영향 범위:** CLI 출력, 문구, (동작 목록을 보이면) 계약의 `changes` 출력.
- **예상 크기:** 작음(문구만) / 중간(동작 목록).

### UXM-5 실행 목록이 계획 실행과 적용 실행의 관계를 말하지 않는다 — 중간

- **어디:** `runs`, 계획 실행을 `revert`한 경우.
- **실제로 본 것**

  ```
  실행 id                    시작                 변경  결과
  20261112T135733Z-194379b2  2026-11-12 22:57:33  3     완료 (done/verified)
  20261112T135722Z-79868fe5  2026-11-12 22:57:22  0     확인 필요 (needs-input/plan_pending)
  ```

  둘째 줄은 이미 적용이 끝난 계획이다. 실수로 계획 실행 id를 되돌리면:

  ```
  $ codaryn revert --workspace org-ko/workspace --run 20261112T135722Z-79868fe5
  codaryn: 되돌린 파일 0개 (complete):
  ```

  그 뒤 목록의 그 줄은 `확인 필요 (needs-input/plan_pending) · 되돌림 (complete)`이 된다.
- **왜 문제인가**
  - 적용한 계획이 계속 "확인 필요"로 남아, 할 일이 남은 것처럼 보인다. 어느 줄이 계획이고 어느 줄이 그 적용인지도 표에 없다(둘의 id 앞부분이 같아 더 헷갈린다).
  - 계획 실행을 되돌리면 아무 일도 없이 "완료"이고 목록에 "되돌림"이 붙는다. 사용자는 적용을 되돌렸다고 믿을 수 있다. 실제 파일은 그대로다.
  - GUI의 실행 목록도 `reason === "plan_pending"`이면 "계획 보기" 단추를 붙이고, 적용 여부는 계획 화면에 들어가야 보인다(코드로 본 것).
- **개선안**
  - 결과 칸: 적용된 계획 실행은 `계획 적용됨 → 194379b2`, 적용 실행은 `완료 (done/verified) · 계획 79868fe5의 적용`. 종류를 한 낱말로 앞에 붙여도 된다(`계획`, `적용`).
  - 계획 실행을 되돌리려 하면 바꾸지 않고 안내한다: `이 실행은 계획만 만들었고 파일을 바꾸지 않았습니다. 적용을 되돌리려면: codaryn revert --workspace … --run <적용 실행 id>`. 되돌리기 기록도 남기지 않는다(목록에 "되돌림"이 붙지 않게).
- **영향 범위:** 계약(`runs` 항목에 적용 여부·상대 실행 id), CLI 출력, 문구, GUI 실행 목록.
- **예상 크기:** 중간.

### UXM-6 기록 변경 표시가 있는 계획: 보여 주고 나서 거부하고, 고치는 법이 틀렸다 — 중간

- **어디:** `plan`, `apply`의 `plan_records_changed`, `revert`.
- **실제로 본 것:** 표시가 붙은 계획 실행에서.

  ```
  $ codaryn plan --task org-tamper/task.json --run 20261112T135810Z-6a6d0044
  Plan of run 20261112T135810Z-6a6d0044: 3 action(s), pending
  …
  To apply it: codaryn apply <the same task form> --run 20261112T135810Z-6a6d0044 --digest 51f72f5df6bb
  $ codaryn apply --task org-tamper/task.json --run 20261112T135810Z-6a6d0044 --digest 51f72f5df6bb
  codaryn: 오류 — 계획 실행에 기록 변경 표시가 있습니다. 실행이 아닌 것이 기록을 바꿔 그 계획이 읽은 것과 다를 수 있어, 아무것도 묻거나 바꾸지 않았습니다 (plan_records_changed)
    고치는 법: codaryn plan으로 계획을 새로 만들고, 새 계획을 확인한 뒤 그것을 적용하세요. 표시가 있는 실행은 무슨 일이 있었는지의 증거로 남겨 두세요.
  ```

  영어도 `Make the plan again with codaryn plan`이다. `revert --dry-run`의 사람용 줄에는 표시에 관한 말이 없고 JSON에만 `"recordsChanged":true`가 있다.
- **왜 문제인가**
  - `plan`은 계획을 만들지 않는다. 보기만 한다. 계획은 `codaryn run`으로 만든다. 안내대로 `plan`을 다시 치면 같은 계획이 또 나오고 `apply`는 또 거부된다. 빠져나올 길이 문구에 없다.
  - `plan`이 경고 없이 "To apply it: …"까지 안내하므로, 사용자는 거부될 명령을 권유받는다.
  - "그 계획이 읽은 것과 다를 수 있어"는 뜻이 통하지 않는다. 영어는 "may not be the one you read"(당신이 읽은 계획이 아닐 수 있다)다.
  - "기록 변경 표시"가 무엇이고 왜 붙었는지, 사용자가 무엇을 의심해야 하는지(허용한 명령이나 다른 프로그램이 `.codaryn`을 건드림) 한마디가 없다.
- **개선안**
  - 고치는 법(ko) after: `codaryn run으로 계획 실행을 새로 하고, 새 계획을 codaryn plan으로 확인한 뒤 그것을 적용하세요. 표시가 붙은 실행은 지우지 말고 남겨 두세요. 허용한 명령이나 다른 프로그램이 .codaryn 폴더를 바꿨는지 살펴보세요.`
  - 무엇(ko) after: `이 계획 실행의 기록이 실행 밖에서 바뀌었습니다(기록 변경 표시). 지금의 계획이 전에 본 계획과 다를 수 있어, 아무것도 묻거나 바꾸지 않았습니다`
  - `plan`: 표시가 있으면 맨 위에 경고 줄을 내고 "To apply it" 줄을 빼고 대신 `이 계획은 적용할 수 없습니다(기록 변경 표시). 새로 실행하세요.`를 낸다.
  - `revert`: 카탈로그에 이미 있는 `revert.records_changed` 문구를 사람용 줄에 실제로 낸다.
- **영향 범위:** 문구(ko·en), CLI 출력(`plan`, `revert`), GUI 오류 문구(UXM-12), 문서(usage 16절 "실행 기록 변조").
- **예상 크기:** 작음.

### UXM-7 한국어 출력 곳곳이 영어다 — 중간

- **어디:** 도움말(`plan`, `apply`, `review`, `changes`, `cleanup`), `plan`·`changes`의 본문, `report`의 Markdown 전체, `cleanup`의 항목 크기 조각과 끝 안내, `models`의 표(문서로 확인), 터미널 질문(문서로 확인).
- **실제로 본 것**(모두 `CODARYN_LANG=ko`)

  ```
  $ codaryn help cleanup
  Shows how much the state directory holds and what a selection would remove; … Parked files, the lock and what a revert still needs are never removed (DR-39).
  $ codaryn cleanup --workspace … --older-than 0
  지울 실행 기록: 2개(13703바이트)
  - 20261112T135834Z-86b30b72: 2 file(s), 6161 bytes; 되돌리지 않은 실행: …
  Nothing was removed. To remove the run records, run the same command with --confirm 9dc50cb8992b.
  The records of 1 run(s) not reverted, only partly reverted, or whose records cannot be checked are kept unless you add --include-not-reverted yourself; …
  $ codaryn report … → "# Codaryn run report", "## Verification", "## Not checked" …
  ```

- **왜 문제인가**
  - `cleanup`에서 **가장 중요한 줄**(지우는 법, 되돌리지 않은 실행의 경고)이 영어다. 지우는 결정을 영어 문장으로 해야 한다.
  - 도움말의 `(DR-39)`, `(DR-29)`는 사용자에게 뜻이 없는 내부 번호다. 다섯 명령은 옵션 설명도 없다(`run`·`doctor` 등은 옵션 목록과 종료 코드가 있다).
  - `report`는 사람이 읽으라고 만든 요약인데 통째로 영어다. N-4·N-21과 어긋난다. usage 16절이 "알려진 한계"로 적어 두긴 했다.
- **개선안:** 우선순위 순으로 메운다. ① `cleanup`의 끝 안내 세 줄과 크기 조각 ② 다섯 명령의 도움말(옵션 목록과 종료 코드까지, 결정 번호 삭제) ③ `plan`과 `changes`의 본문 ④ 터미널 질문 ⑤ `report`의 제목·고정 문장(검증기의 `checked`·`limits`처럼 엔진이 만드는 영어 근거는 그대로 두고 "원문(영어)"라고 표시).
- **영향 범위:** 문구 카탈로그, CLI 출력, 문서(usage 16절의 한계 목록을 줄임), 시험(문구 대조).
- **예상 크기:** ①② 중간, ③④ 중간, ⑤ 큼(따로 한 단위).

### UXM-8 끝 요약의 다음 명령을 복사해 쓸 수 없고, `changes` 안내가 없다 — 중간

- **어디:** `run`·`apply`의 끝 요약, `plan`의 마지막 줄, `report`의 `Undo` 절.
- **실제로 본 것**

  ```
  실행 id: 20261112T135701Z-34b54f56
  보고서: codaryn report --workspace <workspace> --run 20261112T135701Z-34b54f56
  되돌리기: codaryn revert --workspace <workspace> --run 20261112T135701Z-34b54f56
  …
  계획 보기: codaryn plan --task <task.json> --run 20261112T135722Z-79868fe5
  승인해 적용: codaryn apply --task <task.json> --run 20261112T135722Z-79868fe5 --digest <digest>
    4695b92f09cc1bc7b6d0bc7ac8f24f8ca6aa5005571a15da764e29d9d06394cd
  To apply it: codaryn apply <the same task form> --run … --digest 4695b92f09cc
  ```

- **왜 문제인가**
  - 처음 쓰는 사람은 줄을 통째로 복사한다. `<workspace>`가 든 줄은 PowerShell에서 문법 오류다. 세 군데를 손으로 채워야 한다.
  - 적용 안내는 `--digest <digest>` 다음 줄에 64자를 따로 준다. 앞 12자면 된다는 말은 `plan`을 봐야 나온다.
  - 실행이 파일을 바꿨는데 "무엇이 어떻게 바뀌었나 보기"(`changes`)는 안내에 없다. 오늘 더해진 명령이 흐름에 연결되지 않았다.
  - `<the same task form>`은 사용자의 말이 아니다.
- **개선안**
  - 사용자가 **이번 명령에 준 인자 그대로**(`--task`에 준 글자, `--workspace`에 준 글자)를 다음 명령에 되풀이한다. 한 줄 실행이면 현재 폴더이므로 `--workspace .`. 파일에서 읽은 값이 아니라 사용자가 친 인자이므로 "값을 문구에 넣지 않는다"의 대상이 아니라고 본다(6절 질문 3에서 확인).
  - 적용 줄은 `--digest 4695b92f09cc`(앞 12자)를 채워서 준다. 전체 값은 그 아래 `전체 다이제스트:`로.
  - `변경 보기: codaryn changes … --run <id>` 줄을 `바뀐 파일`이 1 이상일 때 더한다.

### UXM-9 처음 시작: 무엇부터 할지 화면이 말하지 않는다 — 중간

- **어디:** `--help`, 인자 없는 실행, `doctor`.
- **실제로 본 것**
  - `--help`: 소개 한 문장 뒤 사용법 줄 14개. `codaryn cleanup --workspace <dir> [--older-than <days>] [--run <id>[,<id>...]] [--reverted] …`처럼 한 줄이 200자를 넘는다. 명령이 무슨 일을 하는지 한마디도 없고, 순서도 없다(`run`, `revert`, `report`, `doctor`, `models`, `init` … 순).
  - 인자 없이 `codaryn`: `오류 — 명령 인수가 올바르지 않습니다 (invalid_arguments)`와 900자 JSON. 종료 2.
  - 설정이 없을 때 `doctor`: `[실패] 한도 한도 limits.maxModelTurns가 없거나 올바르지 않습니다`(무엇을 하라는 말 없음), 마지막 줄 `doctor: 실패 (종료 코드 1). …`. `init` 뒤에도 키와 모델 때문에 `실패`다.
- **왜 문제인가**
  - 문서(usage 머리말)에는 "설치 → init → doctor → 체험 → …" 순서가 있지만 화면에는 없다. 도움말만 본 사람은 `run`부터 치고 `provider_not_configured`를 만난다.
  - 키가 없는 사람에게 `doctor`는 "실패"만 말한다. 키 없이 흐름을 익힐 수 있는 체험(usage 3절)이 있다는 사실은 CLI 어디에도 없다.
  - `doctor`의 "실패"는 "고장"처럼 읽힌다. 실제로는 "아직 안 한 설정"이다.
- **개선안**
  - `--help`를 두 층으로: 위에는 명령마다 한 줄 설명을 순서대로, 전체 사용법 줄은 `codaryn help <명령>`으로 미룬다.

    ```
    처음이라면:  init → doctor → run → report (키 없이 해 보기: docs/usage.md 3절)
      init      기본 설정 파일을 만듭니다
      doctor    실행에 필요한 것을 점검합니다(네트워크 없음)
      models    쓸 수 있는 모델을 보고 고릅니다
      run       작업 하나를 실행합니다
      runs      실행 목록
      report    실행 하나의 보고서
      changes   실행이 바꾼 파일 보기
      revert    실행의 변경 되돌리기
      plan / apply   계획 보기 / 승인해 적용
      review    사람 확인 남기기
      cleanup   실행 기록과 폐기 보관함 정리
    ```

  - 인자 없는 실행은 오류가 아니라 이 짧은 도움말을 낸다(종료 코드는 6절 질문 4).
  - `doctor` 끝에 "다음에 할 일"을 실패 항목에서 뽑아 번호로 낸다: `다음: 1) 키 등록(위 안내) 2) codaryn models --use로 모델 고르기. 키 없이 흐름만 보려면 examples/demo(docs/usage.md 3절).` 설정 파일이 없으면 `다음: codaryn init`.
  - 한도 실패 줄에 `codaryn init이 기본 한도를 넣은 설정을 만듭니다`를 붙인다.
- **영향 범위:** 문구, CLI 출력(도움말·`doctor`), 문서.
- **예상 크기:** 중간.

### UXM-10 정리 명령의 문구와 구조가 어렵다 — 중간

- **어디:** `cleanup`(요약, 미리보기, 결과).
- **실제로 본 것**
  - 아무것도 고르지 않으면: `실행 기록: 2개(13703바이트)` … `정리할 것이 없습니다.` 실행 기록이 둘 있는데 "정리할 것이 없다"고 한다. 실제 뜻은 "고른 것이 없다"다.
  - `--confirm`만 주고 지운 것이 없을 때: `지웠습니다: 실행 기록 0개, 폐기 보관함 폴더 0개, 0바이트`.
  - 미리보기의 한 줄: `- 2026…: 2 file(s), 6161 bytes; 되돌리지 않은 실행: 기록을 지우면 더는 되돌릴 수 없음; 적용 실행의 기록은 지워짐: 폐기 보관함이 남으면(고르지 않았거나 삭제를 확인하지 않으면) 그 파일은 되돌리기로 제자리에 돌려놓을 수 없음`(160자쯤, 경고 둘이 세미콜론으로 이어짐).
  - 옵션이 여덟 개다. 고르기 다섯(`--older-than`, `--run`, `--reverted`, `--discarded-older-than`, `--discarded-run`)과 확인 셋(`--confirm`, `--include-not-reverted`, `--delete-discarded`). 이름만으로는 어느 것이 "고르기"이고 어느 것이 "확인"인지 알 수 없다. `--include-…`는 고르기처럼, `--delete-…`는 동작처럼 읽힌다.
- **왜 문제인가:** 지우는 명령은 한 번에 이해돼야 한다. 지금은 미리보기를 읽고도 "그래서 무엇이 지워지고 무엇이 남는지"를 표로 그려 봐야 안다. 처음 요약에서 다음에 칠 명령이 나오지 않는다.
- **개선안**
  - 고른 것이 없을 때: `고른 것이 없습니다. 예: 30일보다 오래된 실행 기록 → codaryn cleanup --workspace … --older-than 30 (미리보기만 합니다)`.
  - 지운 것이 0일 때: `지운 것이 없습니다.` 뒤에 남긴 이유.
  - 미리보기를 세 묶음으로 나눈다: **이대로 지워지는 것** / **따로 확인해야 지워지는 것**(되돌리지 않은 실행 → `--include-not-reverted`, 사람의 파일 → `--delete-discarded`) / **지우지 않는 것**. 경고는 항목 줄 아래에 한 줄씩 들여 쓴다. 끝에 "지금 `--confirm`만 주면: 기록 N개 지움, M개 남김"을 한 줄로 요약한다.
  - 옵션 이름은 6절 질문 2에서 정한다(`--also-not-reverted`, `--also-discarded`처럼 "추가 확인"임이 보이게).
- **영향 범위:** CLI 출력, 문구, (이름을 바꾸면) 계약·CLI 인자·문서·GUI는 영향 없음.
- **예상 크기:** 중간.

### UXM-11 제공자를 고르는 길이 한 군데뿐이고 설정이 비대칭이다 — 중간

- **어디:** `init`, `run`, `models`, 설정 파일, GUI 설정.
- **실제로 본 것**
  - `init`은 제공자를 묻지 않고 Anthropic 꼴만 만든다(터미널이 아닌 길에서 본 것. 터미널 질문에 제공자가 있는지는 문서 기준으로 "없다").
  - `models`에는 `--provider`가 있고 `run`·`doctor`에는 없다. 제공자는 설정 파일의 `provider`(간편 형식)나 task의 `model.provider`로만 고른다.
  - 설정 파일에서 Anthropic의 모델은 최상위 `model`·`maxOutputTokens`, OpenAI는 `providers.openai.model`·`providers.openai.maxOutputTokens`다. `init`이 만든 파일에 `"provider": "openai"`만 더하면:

    ```
    {"…","code":"provider_not_configured","exitCode":7,"message":"not set: OPENAI_API_KEY; the model (… config providers.openai.model); maxOutputTokens (… config providers.openai.maxOutputTokens). Nothing was sent"}
    ```

  - GUI: OpenAI를 고르면 `이 제공자의 모델 목록은 아직 앱에 연결되지 않았습니다. 모델은 CLI로 고릅니다: codaryn models --provider openai`(문구로 본 것).
- **왜 문제인가:** 두 번째 제공자를 쓰려면 JSON을 손으로 고쳐야 하고, 같은 뜻의 필드가 자리마다 다르다. GUI만 쓰는 사람은 OpenAI 모델을 고를 수 없다. `doctor`는 채울 곳을 알려 주므로 막히지는 않는다.
- **개선안:** `init`이 제공자를 묻고(기본 Anthropic) 그 제공자의 꼴로 만든다. `models --provider openai --use N`이 `provider`도 함께 바꿀지 묻거나 안내한다. `run --provider <이름>`은 6절 질문 6. GUI의 OpenAI 모델 목록 연결.
- **영향 범위:** 계약(설정 형식은 그대로 둘 수 있음), CLI(`init`, `models`), 문구, GUI 설정, 문서.
- **예상 크기:** 중간.

### UXM-13 GUI에 첫 실행 안내가 없다 — 중간 (코드와 설계로 본 것)

### UXM-15 계획 실행과 다른 형식으로 적용해도 경고가 없다 — 중간

- **어디:** `apply`.
- **실제로 본 것:** 계획은 `run --task org-ko/task.json`으로 만들고, 적용은 `apply --workspace org-ko/workspace --workflow organize --run … --digest …`로 했다. 적용은 됐고 `검증: 1개 중 1개 통과`였다. 같은 계획을 task 파일로 적용한 다른 사본에서는 `Checks passed: 2 of 2`였다. 보고서의 `Task:`는 `quick`이 됐다.

- **개선안:** 계획 실행의 작업 id와 적용의 작업 id가 다르면 적용 시작 줄과 끝 요약에 알린다: `알림: 계획은 작업 "organize-demo"로 만들었고 적용은 간편 형식으로 합니다. 그 작업의 검증과 규칙은 쓰이지 않습니다.` 터미널이면 승인 질문 앞에 보인다. 막을지는 6절 질문 7.
- **영향 범위:** CLI(적용 조립), 문구, 계약(적용 결과의 `notices`), GUI는 실행을 시작한 형식을 기억하므로 영향 적음.
- **예상 크기:** 작음.

  | protectedPaths / integrity | 보호 대상(6), 보호 경로(2) | 보호 경로(7), 보호 대상(3) | 보호 경로, 보호 대상, 보호 자료 | 보호 경로 / 보호 대상 확인 |

  영어: workflow는 CLI가 `workflow`, GUI가 `task kind`, 설계가 `task type`. 보관함은 CLI가 `discarded files`·`discarded-files folder`, GUI가 `discard box`, 설계가 `run archive`.
  검증 결과도 한 화면 안에서 `검증 1번 — 미통과 (fail)`(CLI 진행 줄)과 GUI의 `실패`(`outcome.fail`)로 다르다. "실패"는 실행 상태의 낱말이기도 하다.
- **왜 문제인가:** 문서에서 "행동"을 읽고 화면에서 "동작"을 보면 다른 것인지 망설인다. CLI와 GUI를 오가는 사람, 한국어 문서를 보며 영어 출력을 쓰는 사람(usage의 예시는 영어 출력이다)이 가장 헷갈린다.
- **개선안:** 용어표 하나를 정하고(`ux-design.md` 5절을 기준으로 갱신) 세 군데를 맞춘다. 권장: 동작 / 폐기 보관함(처음 한 번, 뒤로는 보관함) / 작업 종류(괄호 없이. 옵션 이름 `--workflow`를 말할 때만 영어) / 다이제스트 / 가릴 값 / 보호 경로(쓰기 막음)·보호 대상 확인(사후 탐지). 영어: task type / discarded files / digest. 검증 결과는 통과·미통과·판단 불가. 확정은 6절 질문 1.
- **영향 범위:** 문구(CLI·GUI·메인 대화상자), 문서(usage, README, 설계 문서들), 시험(문구 대조).
- **예상 크기:** 중간(글자 바꾸기가 넓다. 계약과 코드는 그대로).

### UXM-17 터미널에서 사람용 요약 뒤에 긴 JSON 한 줄이 붙는다 — 낮음

- **어디:** `run`, `apply`, `revert`, 모든 오류.
- **실제로 본 것:** 체험 실행의 끝 요약 12줄 뒤에 stdout JSON 한 줄(1,700자쯤, 한글은 `결정` 꼴)이 이어진다. 오류에서는 사람용 두세 줄 뒤에 사용법 전체가 든 JSON(900자쯤)이 붙는다.
- **왜 문제인가:** 터미널에서 직접 쓰는 사람에게는 요약이 화면 위로 밀려나고 마지막에 보이는 것이 기계용 글이다. N-5의 계약(stdout JSON 한 줄)은 스크립트에는 맞지만 사람이 보는 터미널에는 소음이다.
- **개선안:** stdout이 터미널일 때는 JSON 줄을 내지 않고, 파이프·파일로 받을 때와 `--json`을 줬을 때만 낸다. 또는 오류 JSON의 `message`에서 사용법 전체를 뺀다(작은 쪽). 계약 변경이므로 6절 질문 4.
- **영향 범위:** 계약, CLI 출력, 문서, 통합 시험(시험은 파이프라 영향이 적을 것으로 추측).
- **예상 크기:** 작음~중간.

### UXM-18 진행 줄이 촘촘하고 100자를 넘는 줄이 있다 — 낮음

- **어디:** `run`의 진행 줄, `runs`, `cleanup`.
- **실제로 본 것:** 파일 하나를 만드는 체험에 진행 줄 23개. `보호 대상 확인 — 바뀌지 않음`이 다섯 번 나온다. 실행 시작 줄에 알림이 이어 붙으면 한 줄이 길다: `codaryn: 실행 시작 — 모델 제공자 scripted · 작업 종류(workflow) 자체 규칙 때문에, 설정한 정책이 허용한 경로 토큰 복원을 끕니다`. `runs`의 표시 붙은 줄은 영어로 155자(usage 16절에도 적혀 있다).
- **왜 문제인가:** `ux-design.md` 8절은 줄 너비를 100자 안팎으로 정했다. "정책에서 빠진 것"은 사용자가 꼭 봐야 하는 알림인데 시작 줄 끝에 붙어 있어 지나치기 쉽다.
- **개선안:** 빠진 것 알림은 시작 줄 아래 따로 한 줄씩(`codaryn: 알림 — …`), 끝 요약에도 한 번 더. "바뀌지 않음"인 보호 대상 확인은 진행 줄에서 빼고 끝 요약에 `보호 대상 확인 5회: 바뀐 것 없음` 한 줄로(바뀌었을 때만 그 자리에서 낸다). `runs`의 표시는 `· 기록 변경됨`만 붙이고 설명은 표 아래 한 줄로.
- **영향 범위:** CLI 사람용 출력, 문구, 문서 예시.
- **예상 크기:** 작음.

### UXM-19 `--workspace`를 생략할 수 있는 명령이 `runs`뿐이다 — 낮음

- **어디:** `runs` 대 `report`·`revert`·`cleanup`·`changes`.
- **실제로 본 것:** 작업 공간 안에서 `codaryn runs`는 된다. `codaryn report --run latest`는 `--workspace and --run are required`(JSON)다. `cleanup`도 `--workspace is required`다. 한 줄 실행(`codaryn run "<목표>"`)은 현재 폴더를 쓴다.
- **왜 문제인가:** 한 줄 실행으로 시작한 사람은 그 폴더에 서 있다. 끝 요약이 준 명령에서 `<workspace>`를 채워야 하는 이유를 모른다.
- **개선안:** 읽기 명령(`report`, `changes`, `plan`)은 `--workspace`가 없으면 현재 폴더를 쓴다. 바꾸는 명령(`revert`, `cleanup`, `apply`)은 지금처럼 명시를 요구하되 오류에 `현재 폴더라면 --workspace . 을 주세요`를 붙인다. 6절 질문 5.
- **영향 범위:** CLI 인자, 계약(사용법), 문서.
- **예상 크기:** 작음.

### UXM-20 도움말과 사용법의 빠진 곳 — 낮음

- **실제로 본 것**
  - `help run`의 옵션 목록에 `--workflow`가 없다(사용법 줄에는 있다).
  - 오류 JSON의 사용법 묶음이 `… | codaryn plan|apply|review ... | codaryn --help | codaryn --version`이다. `changes`와 `cleanup`이 없다.
  - `doctor`의 한국어 표가 열이 맞지 않는다(`[정상]      Node.js 버전  …` / `[건너뜀]     설정 파일       …`). 한글 너비를 한 칸으로 센 것으로 보인다(추측).
  - `init`·`doctor`의 설정 위치가 `%APPDATA%\Codaryn\config.json`처럼 풀리지 않은 꼴로 나온다. 의도(값을 문구에 넣지 않음)는 이해하지만, 탐색기 주소창에 그대로 붙이면 열린다는 말을 한 번 해 주면 좋다.
- **개선안:** 옵션 목록에 `--workflow <id>: 작업 종류를 고릅니다(간편 형식)`를 더한다. 사용법 묶음은 UXM-2의 개선으로 사라진다. 표는 표시 너비로 맞춘다.
- **영향 범위:** 문구, CLI 출력.
- **예상 크기:** 작음.

### UXM-21 되돌리기의 가장자리 문구 — 낮음

- **실제로 본 것**
  - 되돌릴 것이 없는 미리보기: `되돌릴 파일 0개(미리보기, 아무것도 바꾸지 않음) (complete):` 다음에 `되돌리려면 --dry-run 없이 다시 실행하세요.` 할 일이 없는데 다시 실행하라고 한다.
  - 두 번째 되돌리기: `이 실행은 이미 되돌린 적이 있습니다. 그래서 파일이 실행 뒤에 바뀐 것으로 보일 수 있습니다. (complete, 2026-11-12 22:57:22)`. 둘째 문장이 무엇을 하라는 것인지 알기 어렵다.
  - 머리 줄이 `되돌린 파일 1개 (complete):`처럼 영어 상태 낱말로 끝난다. 실행 결과는 `완료 (done/verified)`처럼 한국어 낱말이 먼저다.
- **개선안:** 0개면 `되돌릴 것이 없습니다.`로 끝낸다. 두 번째 되돌리기는 `이 실행은 2026-11-12 22:57:22에 이미 되돌렸습니다. 더 할 일이 없습니다.` 머리 줄은 `되돌리기 완료 — 파일 1개 (complete)`, `일부만 되돌림 — … (partial)`.
- **영향 범위:** 문구, CLI 출력.
- **예상 크기:** 작음.

### UXM-22 되돌린 뒤 같은 계획을 다시 적용하려 할 때의 안내 — 낮음

- **실제로 본 것:** 적용을 되돌린 뒤 같은 계획을 다시 `apply`하면 `이 계획은 이미 적용했습니다. 아무것도 바꾸지 않았습니다 (plan_already_applied)` / `고치는 법: 결과는 codaryn report로 보고, 되돌리려면 codaryn revert를 쓰세요.`
- **왜 문제인가:** 이미 되돌린 사람에게 되돌리라고 한다. 문서(usage 18.3절)는 "다시 하려면 되돌린 뒤 계획 실행부터 새로 한다"고 적는다. 그 말이 화면에 없다.
- **개선안:** 고치는 법 끝에 `같은 정리를 다시 하려면 codaryn run으로 계획을 새로 만드세요.`를 더한다.
- **영향 범위:** 문구.
- **예상 크기:** 작음.

### UXM-23 시각 표기가 섞여 있다 — 낮음

- **실제로 본 것:** `runs`와 `latest` 안내는 지역 시각(`2026-11-12 22:57:33`), `plan`의 적용 줄은 `Applied by run … at 2026-11-12T13:57:33.864Z`(UTC), 실행 id는 UTC(`…T135733Z…`).
- **왜 문제인가:** 같은 일의 시각이 아홉 시간 다르게 보인다. `ux-design.md` 6절은 "사람용 시각은 지역 시간"으로 정했다.
- **개선안:** `plan`·`report`의 사람용 시각을 지역 시각으로. 실행 id가 UTC라는 말을 `runs` 표 아래나 도움말에 한 번 적는다.
- **영향 범위:** CLI 출력, 문구.
- **예상 크기:** 작음.

### UXM-24 GUI가 안내하는 CLI 명령이 실행되지 않는 꼴이다 — 낮음 (문구로 본 것)

- **실제로 본 것:** `plan.formUnknown`: `… 적용은 시작한 방식 그대로 CLI에서 하세요: codaryn apply {runId}`. 실제 `apply`는 `--task` 또는 `--workspace`, `--run`, `--digest`가 필요하다. 이 꼴은 `invalid_arguments`다.
- **개선안:** `codaryn apply --task <그 실행의 task 파일> --run {runId} --digest <계획의 다이제스트 앞 12자>`로 고치거나, 명령 대신 "CLI의 `codaryn plan`이 적용 명령을 알려 줍니다"로 바꾼다.
- **영향 범위:** GUI 문구(ko·en).
- **예상 크기:** 작음.

### UXM-25 문서가 지금 제품과 어긋난 곳 — 낮음

- **실제로 본 것**

## 6. 사용자 결정이 필요한 것

제품 방향이나 계약에 닿는 선택이다. 각 질문에 권장안을 붙였다.

1. **용어를 무엇으로 확정할까?**(UXM-16) 권장: 동작 / 폐기 보관함 / 작업 종류 / 다이제스트 / 가릴 값 / 보호 경로, 영어는 task type / discarded files. 문서의 "행동"·"워크플로"·"비밀"을 화면의 말로 맞춘다. (반대 방향, 곧 화면을 문서에 맞추는 것도 가능하다. 문서 쪽 횟수가 더 많다.)
2. **정리에서 "적용 기록은 지우고 보관함은 남김"을 막을까?**(UXM-1) 권장: 막는다(그 적용 실행의 기록을 남기고 이유를 말함). 대안: 허용하되 원래 경로 목록을 보관함에 남긴다. 함께 물을 것: 확인 옵션 이름을 `--include-not-reverted`·`--delete-discarded`에서 "추가 확인"임이 보이는 이름으로 바꿀까? 권장: 지금은 이름을 두고 미리보기 글을 고친다(이름 변경은 문서·시험·습관에 드는 값이 크다).
3. **끝 요약의 다음 명령에 사용자가 준 경로를 그대로 넣어도 될까?**(UXM-8) "파일이나 환경의 값을 문구에 넣지 않는다"(N-4, N-14)와 닿는다. 권장: 넣는다. 대상은 **이번 명령에 사용자가 직접 친 인자**뿐이고, 키 모양 검사는 그대로 거친다. 한 줄 실행은 `--workspace .`.
4. **터미널에서 stdout JSON 한 줄을 숨길까? 인자 없는 `codaryn`을 오류가 아니라 도움말로 할까?**(UXM-17, 9) N-5의 계약을 바꾼다. 권장: stdout이 터미널이면 JSON을 내지 않고 `--json`으로 켠다. 인자 없는 실행은 짧은 도움말에 종료 0. 스크립트는 파이프로 받으므로 영향이 없을 것으로 본다(확인 필요).
5. **읽기 명령의 `--workspace`를 생략하면 현재 폴더로 볼까? 읽기 명령의 간편 형식에서 제공자 설정 요구를 없앨까?**(UXM-19, 3) 권장: 둘 다 예. 바꾸는 명령(`revert`, `apply`, `cleanup`)은 지금처럼 명시.
6. **`run --provider <이름>`을 둘까, `init`이 제공자를 물을까?**(UXM-11) 권장: `init`이 묻는 것만 먼저 한다. `run --provider`는 "제공자를 바꾸면 작업 내용이 다른 API로 간다"는 무게가 있어 설정 파일에 두는 지금 방식이 더 조심스럽다.
7. **계획 실행과 다른 형식의 적용을 막을까, 알리기만 할까?**(UXM-15) 권장: 알리기만 한다(적용 때의 정책으로 다시 판정한다는 설계는 유지). 터미널 승인 질문에는 그 알림을 함께 보인다.
8. **GUI 첫 실행 안내를 지금 넣을까, 그리고 "키 없이 체험" 단추를 둘까?**(UXM-13) 권장: 한 화면 점검표를 다음 GUI 단위로 넣는다. 체험 단추는 대본 예시를 앱에 싣는 일이라 따로 결정한다.

## 7. 확인하지 못한 것

- GUI의 실제 화면 전부(배치, 초점 이동, 대화상자의 실제 모양과 순서, 낭독기). UXM-12·13·14·24는 코드와 문구에서 읽은 것이다. UXM-12에서 어떤 오류 코드가 실제로 화면까지 오는지는 모른다.
- 터미널 질문: 적용 승인 `[y/N]`, 위험한 이동의 동의, `init`의 질문들. 문구와 기본 답을 직접 보지 못했다.
- 실제 API를 쓰는 실행: 진행 줄의 실제 양, 모델 오류(`model_error`)의 문구, `models`의 표, 재시도 중의 표시.
- `review`와 `analyze` 흐름, `consent_required`(하드 링크 없는 드라이브) 흐름, `plan_stale`·`apply_incomplete`, `plan_secrets_differ`, 취소(`--cancel-file`, Ctrl+C), 한도 도달(`budget-exhausted`)의 끝 요약.
- 프로필(`--profile`)이 있는 설정에서의 흐름, 사용자 정의 작업 종류. 설정에 프로필을 만들어 보지 않았다.
- 정책에서 빠진 것 알림은 한 가지(경로 토큰 복원 끔)만 실제로 봤다. 명령 규칙이 빠지는 경우와 검증이 빠지는 경우는 문서의 예시로만 읽었다.
- `--delete-discarded`로 실제로 보관함을 지우는 길, 지우다 실패한 경우(`partly_removed`)와 남은 폴더 안내.
- `--json` 출력의 모양(기계용이라 범위 밖으로 뒀다), `--quiet`의 여러 조합.
- PowerShell 5.1·Windows Terminal에서의 한글 표시와 줄 접힘, 영어 Windows에서의 언어 자동 선택.
- 실행한 빌드(`e0e1180`)와 문서를 읽은 판(`a7f3a2f`)의 코드가 같다는 것은 지시서의 말을 따랐다.
- `docs/decision-register.md` 11절과 `usability-review.md`는 항목마다 대조하지 않았다. `cli-contract.md`는 읽지 않았다.
