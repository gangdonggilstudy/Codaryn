# VS Code 확장 설계

VS Code에서 Codaryn을 쓰는 확장을 설계한다. 엔진을 부르는 방식, 화면과 명령, 확인 질문·취소가 CLI와 같은 의미로 동작하는 방법, 설정·키 규칙을 지키는 방법, 패키징과 시험, 구현 분할을 다룬다.

- 기준: main `b386166`(2026-11-12), 어댑터 계약 [adapter-contract.md](adapter-contract.md)(이 브랜치 `dba7805`). 작업 지시: [단계 4·5 설계 작업 지시](../work-orders/phase-4-5-design.md) P5-A.
- 입력: [UX 설계](ux-design.md)(UX-D1, 4·6·7절), [사용성 개선 지시](../work-orders/phase-4-usability.md)(N-1~N-13), [설계 결정](../decisions.md)(M-1, M-2, M-9, M-21, C-1~C-8, S-1~S-12, O-6), [CLI 계약](../cli-contract.md).
- 이 문서는 설계다. 확장 코드, 시험, 의존성은 만들지 않았다. 실제 API는 호출하지 않았다.
- **VS Code API의 이름과 동작은 공식 문서를 열어 확인하지 않았다(외부 네트워크 금지).** 이 문서에서 VS Code 쪽 사실은 모두 [추정]이다. 구현 전에 공식 문서로 확인하고, 확인한 것은 decisions.md 5절 규칙대로 링크와 날짜를 남긴다.

표기는 [어댑터 계약](adapter-contract.md)과 같다: [확정], [선택], [제안], [미정], [코드], [추정].

## 1. 목표와 범위

- [선택] GUI는 VS Code 확장을 먼저 만든다. 코딩이 첫 워크플로이고 단일 프로세스 원칙을 지킨다(N-13, UX-D1).
- [확정] 단계 5 완료 기준: 확장이 CLI와 같은 엔진·정책·기록을 쓰고, 확장에 작업 논리가 없고, 확인 질문과 취소가 CLI와 같은 의미로 동작한다(roadmap 단계 5).
- [제안] 첫 판의 범위
  - 포함: 새 작업 실행(간편 형식, task 파일), 진행 보기, 취소, 실행 목록, 보고서, 되돌리기(미리보기 → 확인), 점검(`doctor`), 모델 고르기(사람이 명령으로 부를 때만).
  - 미포함: 원격 작업 공간(Remote-SSH, WSL, 컨테이너, 가상 파일 시스템), 웹뷰, 채팅 화면, 마켓플레이스 게시(외부 발송), 확장 안의 키 보관.
  - 비개발자용 독립 GUI는 P5-U가 설계한다.

## 2. 엔진을 부르는 방식

### 2.1 선택지

| --- | --- | --- | --- | --- |

| Node 버전 | 확장 호스트의 Node는 VS Code가 정한다 [추정]. Codaryn은 Node 26에서만 검증했다(M-21, `package.json:8-10`, `src/cli/doctor.ts:59`) [코드] | 사용자가 지정한 Node 26 이상으로 띄운다. `doctor`의 `node_version` 점검을 그대로 쓴다 | B와 같다 | — |

### 2.2 권고: B

- **같은 의미를 구조로 보장한다.** 확장이 부르는 것은 사용자가 터미널에서 부르는 것과 같은 프로그램, 같은 인자, 같은 검사 순서다. 종료 상태, 오류 코드, 기록이 다를 수 없다. 단계 5 완료 기준(같은 엔진·정책·기록)을 시험 없이도 대부분 만족하고, 남는 것은 줄 프로토콜의 시험뿐이다.
- **키와 변수 파일 값이 다른 확장과 같은 프로세스에 들어가지 않는다.** A는 `process.env`, 전역 `fetch`, 신호 처리기를 공유한다. 앱 계층이 사본 환경을 쓰게 해도(어댑터 계약 4절) 전역 `fetch` 공유는 남는다.
- **검증된 Node에서 돈다.** M-21의 Node 26과 다른 런타임을 새로 검증하지 않아도 된다.
- 비용: 실행마다 프로세스 시작 시간이 든다. 실행은 모델 호출로 초 단위 이상이므로 무시할 수 있다 [추정, 재지 않음]. 사용자가 Node 26 이상을 따로 설치해야 한다(VX-D2).
- A를 다시 볼 조건: 확장 호스트의 Node가 26 이상이 되고, 제공자가 전역 `fetch` 대신 주입된 전송을 쓰며, 앱 계층에 프로세스 전역 사용이 없음을 시험으로 확인했을 때. 그때도 B의 줄 프로토콜은 GUI 등 다른 어댑터를 위해 남긴다.

## 3. 구성

```
VS Code
 └ 확장 (vscode/)
    ├ ui/    명령, 출력 채널, 실행 목록, 상태 표시줄, 확인 대화상자   ← vscode API를 쓰는 유일한 곳
    └ core/  인자 만들기, 자식 실행, 줄 해석, 실행 상태 모델           ← vscode API 없음, node --test로 시험
          │ spawn(Node 26 절대 경로, [동봉 CLI main.js, "run", …], shell 없음)
          ▼
       Codaryn CLI 자식 하나 (실행 하나 동안만)
          stdin  ← 확인 답 줄
          stderr → started / event / confirm 줄
          stdout → CliOutput JSON 한 줄, 종료 코드
          취소   ← 확장 저장 폴더의 취소 파일(작업 공간 밖)
```

- 확장 코어는 엔진, 정책, 가림을 import하지 않는다. 하는 일은 인자 배열을 만들고, 줄을 해석하고, 화면 상태를 바꾸는 것뿐이다. 이것이 "어댑터에 작업 논리가 없다"의 구체적 경계다.
- 자식 실행 규칙 [제안]
  - 셸 없이 인자 배열로 띄운다. 목표 문장 등 사용자 입력을 셸 문자열로 만들지 않는다.
  - Node 실행 파일은 절대 경로로 정한다(VX-D2). 작업 공간 안으로 풀리면 띄우지 않는다. 이름만 주어 PATH와 현재 디렉터리에서 찾게 하지 않는다(Windows 실행 파일 탐색은 현재 디렉터리를 먼저 볼 수 있다 [추정]. CLI의 T-4와 같은 이유).
  - 자식의 cwd는 작업 공간 밖(확장 저장 폴더)으로 두고 모든 경로를 절대 경로로 넘긴다. 한 줄 실행(N-9, cwd를 작업 공간으로 씀)은 쓰지 않고 `--workspace`를 명시한다.
  - 자식 환경은 확장 호스트의 환경을 그대로 넘긴다. 확장이 값을 더하거나 바꾸지 않는다(6절).
- 줄 해석 규칙 [제안]
  - stderr의 JSON이 아닌 줄(Node 런타임 경고 등)은 표시하지 않고 개수만 센다.
  - 한 줄에 상한을 둔다. 넘는 줄은 버리고 "이벤트 일부를 보이지 못함"으로 표시한다. 값은 구현 때 정한다(기록은 journal에 그대로 있으므로 보고서로 볼 수 있다).
  - stdout은 끝난 뒤 전부 읽어 JSON 한 줄인지 확인한다. 아니거나 JSON의 `exitCode`가 프로세스 종료 코드와 다르면 전송 오류(`adapter_protocol_error`)다.
  - `seq`가 건너뛰면 "일부 이벤트 누락"을 표시하고 계속한다.

## 4. 화면과 명령

### 4.1 명령

| 명령(팔레트) | 하는 일 | 부르는 CLI | UX 흐름 |
| --- | --- | --- | --- |
| Codaryn: 새 작업 | 작업 공간 폴더 고르기 → 목표 입력(여러 줄) → 프로필 고르기 → 실행 | `run --workspace <폴더> --goal <목표> [--profile] [--config] [--vars-file] --cancel-file <파일> --events jsonl --confirm stdio` | 4.4, 4.5 |
| Codaryn: task 파일 실행 | task 파일 고르기(작업 공간 밖이어야 함, S-1) → 실행 | `run --task <파일> …` | 4.4 |
| Codaryn: 실행 취소 | 실행 중인 것을 취소 | 취소 파일 생성 | 4.5 |
| Codaryn: 실행 목록 | 작업 공간의 최근 실행 | `runs --workspace <폴더>`(N-7)의 JSON 출력 | 3절 홈 |
| Codaryn: 보고서 열기 | 고른 실행의 보고서를 읽기 전용 Markdown 문서로 | `report --workspace --run <id>` | 4.7 |
| Codaryn: 되돌리기 | 미리보기 → 모달 확인 → 되돌리기 → 결과 | `revert --dry-run` 뒤 `revert`(N-7) | 4.8, UX-D4 |
| Codaryn: 점검 | 점검 결과를 출력 채널에 | `doctor --json [--config] [--vars-file] --workspace <폴더>` | 설정 > 점검 |
| Codaryn: 모델 고르기 | 모델 목록을 빠른 선택으로 보여 주고 고른 것을 설정에 기록 | `models --json`, `models --use <id> --config` | 4.2 |
| Codaryn: 출력 보기 | 출력 채널 열기 | — | — |

- 확장은 명령을 실행할 때만 켜진다(모든 이벤트에 켜지는 방식은 쓰지 않는다) [제안].
- `models`는 실제 API에 접속한다(Y-2). 사람이 이 명령을 부를 때만 부른다. 확장이 켜질 때나 실행 전에 자동으로 부르지 않는다.
- 점검은 자동으로 돌리지 않는다. 실행이 `provider_not_configured`, `invalid_config` 등으로 실패하면 오류 알림에 "점검" 단추를 둔다(UX 4.9 "고치는 법이 화면 이동이면 그 화면으로 가는 단추").

### 4.2 화면

| 화면 | 내용 | 근거 |
| --- | --- | --- |
| 진행 알림 | 실행 중 표시와 취소 단추. 단추는 "실행 취소"와 같다 | UX 4.5 |
| 출력 채널 "Codaryn" | 이벤트를 사람 문장으로 한 줄씩. 문장은 N-4 문구 카탈로그(ko/en)로 만든다. 끝에 요약(상태, 검증, 바뀐 파일 수, 실행 id, 다음 명령) | UX 4.5, 4.7, N-5 |
| 상태 표시줄 | 실행 중인 작업 공간과 상태 낱말(실행 중, 확인 필요, 완료, 실패) | UX 6절, 8절 |
| 실행 목록(탐색기 옆 트리) | 최근 실행: 시각, 상태 낱말, 바뀐 파일 수. 항목 메뉴: 보고서, 되돌리기, 변경 보기 | UX 3절 |
| 보고서 | `report`의 Markdown을 읽기 전용 문서로 연다 | UX 4.7 |
| 변경 보기 | 파일별 이전·이후 비교(VX-D6) | UX 4.7 |
| 확인 대화상자 | 모달. "허용(이번 한 번)"·"거부", 계획이면 "승인"·"거부". 닫으면 거부 | 5절 |

- 웹뷰는 첫 판에 쓰지 않는다(VX-D5). 모든 화면이 VS Code 기본 구성 요소이므로 키보드 조작과 화면 낭독기 지원은 VS Code의 것을 따른다 [추정]. 상태는 색이 아니라 낱말로 구분한다(UX 8절).
- 표시하는 글은 모두 이벤트·결과의 가림본이다. 화면에 내기 전에 제어 문자를 정리한다(어댑터 계약 5.2 보장 5). 경로가 토큰으로 보일 수 있다.
- 실행 전에 그 작업 공간에 저장하지 않은 편집기가 있으면 경고하고 "모두 저장"을 제안한다. 자동으로 저장하지 않는다. Codaryn은 디스크의 내용을 읽고 해시로 덮어쓰기를 막으므로(architecture 7절) 저장 안 된 편집과 실행 결과가 엇갈릴 수 있다.
- 작업 공간의 `.codaryn/`이 탐색기에 보인다. 숨기기는 사람이 `files.exclude`로 한다. 확장이 사용자 설정을 자동으로 바꾸지 않는다.

## 5. 확인 질문과 취소: CLI와 같은 의미

| 상황 | CLI | VS Code 확장 | 기록과 결과 |
| --- | --- | --- | --- |
| 사람이 취소 | Ctrl+C, SIGTERM, `--cancel-file` | 진행 알림의 취소 단추나 "실행 취소" → 취소 파일 생성 | `cancelled`/`cancelled`, 종료 5, 적용된 변경 유지(M-11) |
| 권한·계획 확인 질문 | 터미널이면 stderr에 묻고 stdin에서 읽음(AC-D10) | 모달 대화상자. 답을 stdin 줄로 보냄(`--confirm stdio`) | `confirmation_requested`·`confirmation_answered` 기록(어댑터 계약 5.7) |
| 답할 수 없음 | 터미널 아님 → 묻지 않고 거부 | 대화상자를 닫음, 창을 닫음 → 거부 | `by: "default"`, 그 호출은 거부 |
| 답을 기다리는 중 취소 | Ctrl+C | 취소 단추 | `by: "cancelled"`, `cancelled` |
| 답을 기다리는 중 시간 한도 | 엔진 타이머 | 같음 | `budget-exhausted`/`max_duration`(AC-D6) |
| 실행 중 확장이 꺼짐(창 닫기, 다시 불러오기) | 해당 없음 | 취소 파일을 만들고 짧게 기다린다. 자식의 stdin이 닫혀 남은 질문은 거부로 끝난다 | 자식이 끝나면 `cancelled`. 확장이 결과를 받지 못해도 result.json과 journal은 남는다 |
| 되돌리기 확인 | 명시 명령이므로 묻지 않음, `--dry-run`으로 미리보기(UX-D4) | `--dry-run` 결과를 보여 주고 모달 확인 뒤 실행 | 되돌리기 결과(`complete`/`partial`) |

- 의미가 같은 이유: 질문을 만들고 판정하고 기록하는 것은 자식 CLI 안의 앱 계층과 엔진이다. 확장은 질문을 보여 주고 답 한 줄을 돌려줄 뿐이다. 확장이 답을 바꾸거나 "항상 허용"을 만들 수 없다(답의 종류가 계약에 없다).
- 취소 파일은 확장 저장 폴더(작업 공간 밖) 안에 실행마다 새 이름으로 만들고, 실행이 끝나면 지운다. 작업 공간 안이면 CLI가 거부한다(T-12).
- 강제 종료 [제안]: 취소 파일을 만든 뒤 일정 시간 안에 자식이 끝나지 않으면, 사람에게 "강제 종료하면 결과를 알 수 없고 잠금은 다음 실행이 회수한다"를 보이고 확인을 받은 뒤에만 프로세스 트리를 끝낸다. 결과는 전송 오류로 표시하고 보고서(`incomplete` 가능)를 안내한다. 기다리는 시간은 구현 때 정한다.
- 확장이 꺼질 때 자식이 함께 끝나는지는 OS와 Node의 자식 프로세스 처리에 달려 있다 [추정, 확인 안 함]. 그래서 꺼질 때도 먼저 취소 파일로 정상 종료를 요청한다.

## 6. 설정·키 규칙을 지키는 방법

### 6.1 규칙별

| 규칙 | 확장에서 |
| --- | --- |

| C-3/N-1 설정 파일 위치 | `codaryn.configPath`가 있으면 `--config`, 없으면 넘기지 않아 CLI 규칙(`CODARYN_CONFIG` > 기본 위치)을 그대로 따른다 |
| C-4 모델 | 확장은 모델 기본값을 두지 않는다. "모델 고르기"는 `models --use`로 사용자 설정 파일에 기록한다 |
| C-5 API 주소 | 확장 설정에 주소 필드가 없다 |
| C-6/S-7 한도 | 확장은 한도를 넘기지 않는다. 설정 파일·프로필이 정한다 |
| C-7 새 실행 의존성 없음 | 확장은 VS Code API와 Node 내장 모듈만 쓴다. 개발 의존성은 7절(PM 승인 필요) |

| S-3, S-6, N-6 오류 문구에 값 없음 | 확장은 오류 JSON의 `code`로 문장을 찾고 `message`는 "자세히"에만 둔다. 자식의 stderr 원문을 알림에 넣지 않는다 |
| S-5 UNC·장치 경로 | `file` 방식의 로컬 폴더만 받는다. 원격·가상 작업 공간이면 실행하지 않는다. UNC는 CLI도 거부한다 |
| S-8 목표의 키 검사 | 자식 CLI가 한다. 목표는 명령줄 인자로 넘어가 같은 사용자의 다른 프로세스가 볼 수 있다(VX-D9) |
| S-9~S-12 제공자 | 자식 CLI의 제공자가 한다. 확장은 바꾸지 않는다 |
| M-9 권한은 사용자 설정과 인자로만 | 권한·경로에 영향을 주는 확장 설정은 사용자(또는 머신) 범위에서만 읽는다. 작업 공간의 `.vscode/settings.json`이 바꿀 수 없게 한다(VX-D10) |
| U-3 설치 위치 | 동봉 CLI의 설치 위치는 확장 안의 동봉 폴더다(7절). 작업 공간이 그 폴더와 겹치면 CLI가 거부한다 |

### 6.2 확장 설정 [제안]

| 설정 | 뜻 | 범위 |
| --- | --- | --- |
| `codaryn.nodePath` | Node 26 이상 실행 파일의 절대 경로 | 머신 |
| `codaryn.configPath` | 설정 파일 경로. 비우면 CLI 기본 규칙 | 머신 |
| `codaryn.varsFile` | 변수 파일 경로. 비우면 넘기지 않음 | 머신 |
| `codaryn.defaultProfile` | "새 작업"에서 먼저 고를 프로필 이름 | 사용자 |

- 작업 공간 범위 설정은 두지 않는다. 범위 이름(머신, 사용자, 작업 공간)과 그 강제 방식은 VS Code의 설정 기여 방식을 확인해 정한다 [추정].
- 프로필은 사용자 설정 파일에만 정의된다(N-8). 작업 공간이 프로필을 고르게 하면 저장소가 사용자의 더 넓은 프로필을 고를 수 있으므로 기본 프로필도 사용자 범위다.
- 확장은 작업 공간 신뢰 기능이 "신뢰하지 않음"인 작업 공간에서는 실행 명령을 막는다 [추정, API 미확인]. Codaryn 자신의 원칙(작업 공간의 내용은 자료일 뿐 권한을 넓히지 못한다, M-9)은 신뢰 여부와 무관하게 그대로다.

## 7. 패키징

- 위치 [제안]: 저장소의 `vscode/` 폴더. 확장 매니페스트(`vscode/package.json`)와 `vscode/tsconfig.json`을 따로 둔다. 루트 `package.json`은 바꾸지 않는다. 확장 매니페스트는 CLI 패키지와 필드가 달라 한 파일에 합칠 수 없으므로 M-1(단일 패키지)의 예외가 된다(VX-D3).
- CLI 동봉: 확장을 묶을 때 같은 커밋에서 빌드한 `dist/src`를 확장 안에 복사한다. 확장과 CLI 버전이 늘 같다. 사용자가 따로 설치한 `codaryn`을 찾지 않는다.
  - CLI는 진입 파일에서 위로 올라가며 이름이 `codaryn`인 `package.json`을 찾아 설치 위치로 삼고(U-3, U-7), 못 찾으면 모든 실행을 거부한다(`src/cli/install.ts:30-48`, `src/cli/run.ts:295-305`) [코드]. 확장 매니페스트의 이름은 다르므로, 동봉 위치(예: `<확장>/cli/`)에 루트 `package.json`의 `name`·`version`을 담은 파일을 함께 둔다. 그러면 U-3의 설치 위치는 그 동봉 폴더가 된다.
  - 이 배치가 실제로 `findInstall`에 맞는지는 V5 통합 시험에서 확인한다.
- Node: 사용자가 설치한 Node 26 이상을 `codaryn.nodePath`로 지정한다. 비어 있으면 "Node 26 이상이 필요합니다"와 점검 안내를 보이고 실행하지 않는다. VS Code 자체 런타임을 Node로 쓰는 방법은 검증 환경과 달라 쓰지 않는다(VX-D2).
- 실행 의존성은 없다. 확장 코드는 VS Code API와 Node 내장 모듈만 쓴다.
- 새 개발 의존성 — **모두 PM 승인 필요**
  - VS Code API 타입(`@types/vscode`): `ui/`의 타입 검사에 필요하다. 대안은 쓰는 API만 손으로 선언한 타입 파일이다(VX-D4).
  - 확장 묶음 도구(`@vscode/vsce`): `.vsix` 파일을 만든다. 대안은 없다(형식을 손으로 만들지 않는다).
  - VS Code 안 시험 도구(`@vscode/test-electron` 또는 `@vscode/test-cli`): 시험 때 VS Code를 내려받는다(외부 네트워크). 첫 판은 쓰지 않고 수동 점검표로 대신한다.
- 배포: 로컬 `.vsix` 설치만. 마켓플레이스 게시는 외부 발송이므로 범위 밖이다.

수동 점검표(첫 판) [제안]
1. 키 없이 대본 모델 task로 실행 → 진행 → 완료 요약 → 보고서 → 되돌리기 미리보기 → 확인 → 되돌리기.
2. 실행 중 취소 단추 → `cancelled`, 바뀐 파일 유지, 실행 목록에 표시.
3. 설정 파일 없음 → 오류 알림의 "점검" → `doctor` 결과.
4. 작업 공간 `.vscode/settings.json`에 `codaryn.nodePath`를 넣어도 쓰이지 않음.
5. 신뢰하지 않는 작업 공간에서 실행 명령이 막힘.
6. 화면 낭독기와 키보드만으로 새 작업 → 취소 → 보고서.

- 모의와 실제를 나눈다(M-19). 위 시험은 모두 대본 모델이며 실제 API 검증이 아니다. 시험 이름에 그렇게 적는다.

- P5-U [독립 GUI](standalone-gui.md): 같은 줄 프로토콜을 쓰면 확장 코어(`vscode/src/core`)의 줄 해석과 상태 모델을 공용 위치로 옮길 수 있다. 공용화는 두 번째 사용처가 생길 때 한다. 이 문서를 커밋할 때 P5-U 문서는 main에 없었다.
- [usage.md](../usage.md): V7에서 VS Code 절을 더한다(사용 문서 담당).
