# VS Code 확장 설계 — DR-20으로 추진하지 않음 (참고용)

> **사용자 결정 DR-20(2026-11-12): VS Code 확장(플러그인)은 개발하지 않는다.** 독립 GUI 하나만 만들고(Electron, Windows 11 64비트 먼저), 플러그인과 같은 편의성(작업 공간 폴더 열기, 파일 트리와 변경 비교, 실행 목록, 계획 승인, 설정·프로필·모델 선택, 진행 표시와 취소)을 그 GUI가 갖는다. GUI는 Electron의 엔진 전용 프로세스가 앱 계층 함수를 직접 부른다([독립 GUI](standalone-gui.md) 5.1, [어댑터 계약](adapter-contract.md)).
>
> - 이 문서의 결정(VX-D1~D14)과 N-13의 "VS Code 확장 먼저"는 DR-20이 대체한다. 아래 내용은 결정 전의 설계 기록으로만 남긴다.
> - 이미 커밋된 `vscode/src/core/**`(`11d5676`)와 `tests/unit/vscode/**`는 지우지 않았다. 쓰임이 없으면 GUI 묶음 때 정리 여부를 PM이 정한다.
> - 여기서 GUI로 옮겨 쓸 수 있는 생각: 다시 가린 변경 비교(DR-7), 시작 전 취소 비활성과 창 닫기 순서(R-1 L-2), 자식 Node 환경에서 `NODE_OPTIONS`·`NODE_PATH` 빼기(VX-D13), 권한·경로 설정을 작업 공간이 바꾸지 못하게 하기(VX-D10).

VS Code에서 Codaryn을 쓰는 확장을 설계한다. 다룰 것은 다음과 같다.
- 엔진을 부르는 방식
- 화면과 명령(실행, 계획 확인과 적용, 사람 확인, 변경 비교 포함)
- 권한 질문·취소가 CLI와 같은 의미로 동작하는 방법
- 설정·키 규칙을 지키는 방법
- 패키징과 시험, 구현 분할

- 기준: 설계는 main `b386166`(2026-11-12)에서 썼다. 작업 지시: [단계 4·5 설계 작업 지시](../work-orders/phase-4-5-design.md) P5-A.
- 이 판은 [설계 교차 검토 R-1](../reviews/2026-11-12-r1-review-stage-4-5-designs.md) 뒤 PM 결정 DR-1, DR-2, DR-7, DR-8과 낮음 항목 L-2, L-4를 반영했다.
- 어댑터 계약은 [adapter-contract.md](adapter-contract.md)(같은 날 R-1 반영판)를 따른다.
- 입력: [UX 설계](ux-design.md)(UX-D1, 4·6·7절), [사용성 개선 지시](../work-orders/phase-4-usability.md)(N-1~N-13), [설계 결정](../decisions.md)(M-1, M-2, M-9, M-21, C-1~C-8, S-1~S-12, O-6), [CLI 계약](../cli-contract.md), [범용 작업](general-tasks.md) 6·8절.
- PM 채택: VX-D1~D3, D5, D7~D12(권고대로). VX-D6은 DR-7로 바뀌었다. VX-D4는 사용자 확인 대기다(Q-3).
- 이 문서는 설계다. 확장 코드, 시험, 의존성은 만들지 않았다. 실제 API는 호출하지 않았다.
- **VS Code API의 이름과 동작은 공식 문서를 열어 확인하지 않았다(외부 네트워크 금지).** 이 문서에서 VS Code 쪽 사실은 모두 [추정]이다. 구현 전에 공식 문서로 확인하고, decisions.md 5절 규칙대로 링크와 날짜를 남긴다.

표기는 [어댑터 계약](adapter-contract.md)과 같다: [확정], [선택], [제안], [미정], [가정 G-A], [코드], [추정].

## 1. 목표와 범위

- [선택] GUI는 VS Code 확장을 먼저 만든다. 코딩이 첫 워크플로이고 단일 프로세스 원칙을 지킨다(N-13, UX-D1).
- [확정] 단계 5 완료 기준(roadmap 단계 5)
  - 확장이 CLI와 같은 엔진·정책·기록을 쓴다.
  - 확장에 작업 논리가 없다.
  - 확인 질문과 취소가 CLI와 같은 의미로 동작한다.
- 첫 판의 범위
  - 포함
    - 새 작업 실행(간편 형식과 워크플로 선택, task 파일), 진행 보기, 취소
    - 실행 목록, 보고서, 다시 가린 변경 비교, 되돌리기(미리보기 → 확인)
    - 계획 확인과 적용, 사람 확인(범용 작업 명령이 생긴 뒤)
    - 점검(`doctor`), 모델 고르기(사람이 명령으로 부를 때만)
  - 미포함: 원격 작업 공간(Remote-SSH, WSL, 컨테이너, 가상 파일 시스템), 웹뷰, 채팅 화면, 마켓플레이스 게시(외부 발송), 확장 안의 키 보관.
  - 비개발자용 독립 GUI는 P5-U가 설계한다.

### 2.2 권고: B (VX-D1 채택)

- **같은 의미를 구조로 보장한다.** 확장이 부르는 것은 사용자가 터미널에서 부르는 것과 같은 프로그램, 같은 인자, 같은 검사 순서다.
  - 종료 상태, 오류 코드, 기록이 다를 수 없다.
  - 단계 5 완료 기준(같은 엔진·정책·기록)을 대부분 구조로 만족하고, 남는 것은 줄 프로토콜의 시험이다.
- **다른 확장과 공유하는 상태가 줄어든다(R-1 L-4로 근거를 고침).**
  - B가 실제로 분리하는 것은 변수 파일의 값, 전역 `fetch`, 신호 처리기다.
  - 키는 다르다. 사용자가 환경 변수로 등록한 `ANTHROPIC_API_KEY`는 이미 확장 호스트의 환경에 있고, 자식은 그것을 물려받는다(6절). B는 키를 확장 호스트에서 빼 주지 않는다.
- **검증된 Node에서 돈다.** M-21의 Node 26과 다른 런타임을 새로 검증하지 않아도 된다.
- 비용
  - 실행마다 프로세스 시작 시간이 든다. 실행은 모델 호출로 초 단위 이상이므로 무시할 수 있다 [추정, 재지 않음].
  - 사용자가 Node 26 이상을 따로 설치해야 한다(VX-D2).
- A를 다시 볼 조건(모두 만족해야 함)
  - 확장 호스트의 Node가 26 이상이 된다.
  - 제공자가 전역 `fetch` 대신 주입된 전송을 쓴다.
  - 앱 계층에 프로세스 전역 사용이 없음을 시험으로 확인했다. A-1은 사본 환경과 명령의 부모 환경 전달(DR-4)까지 했다.
  - 그때도 B의 줄 프로토콜은 다른 어댑터를 위해 남긴다.

## 3. 구성

```
VS Code
 └ 확장 (vscode/)
    ├ ui/    명령, 출력 채널, 실행 목록, 상태 표시줄, 질문 대화상자, 계획·비교 문서   ← vscode API를 쓰는 유일한 곳
    └ core/  인자 만들기, 자식 실행, 줄 해석, 실행·적용 상태 모델                    ← vscode API 없음, node --test로 시험
          │ spawn(Node 26 절대 경로, [동봉 CLI main.js, "run"|"apply"|…, …], shell 없음)
          ▼
       Codaryn CLI 자식 하나 (실행·적용·조회 하나 동안만)
          stdin  ← 권한 질문의 답 줄(run만)
          stderr → started / event / confirm 줄
          stdout → 결과 JSON 한 줄(또는 --json 출력), 종료 코드
          취소   ← 확장 저장 폴더의 취소 파일(작업 공간 밖, started 뒤에만 만든다)
```

- 확장 코어는 엔진, 정책, 가림, 저장 형식을 import하거나 읽지 않는다.
  - 하는 일은 인자 배열을 만들고, 줄과 JSON 출력을 해석하고, 화면 상태를 바꾸는 것뿐이다.
  - 스냅샷, `plan.json`, 기록 파일은 열지 않는다. 필요한 내용은 CLI 명령(`report`, `changes`, `plan`)의 출력으로 받는다(DR-7, DR-1).
  - 이것이 "어댑터에 작업 논리가 없다"의 구체적 경계다.
- 자식 실행 규칙 [제안]
  - 셸 없이 인자 배열로 띄운다. 목표 문장 등 사용자 입력을 셸 문자열로 만들지 않는다.
  - Node 실행 파일은 절대 경로로 정한다(VX-D2). 작업 공간 안으로 풀리면 띄우지 않는다.
    - 이름만 주어 PATH와 현재 디렉터리에서 찾게 하지 않는다. Windows 실행 파일 탐색은 현재 디렉터리를 먼저 볼 수 있다 [추정]. CLI의 T-4와 같은 이유다.
  - 자식의 cwd는 작업 공간 밖(확장 저장 폴더)으로 두고 모든 경로를 절대 경로로 넘긴다. 한 줄 실행(N-9, cwd를 작업 공간으로 씀)은 쓰지 않고 `--workspace`를 명시한다.
  - **자식 환경(R-1 L-4).** 확장 호스트의 환경을 넘기되 자식 Node의 동작을 바꾸는 변수는 뺀다.
    - 빼는 것: `NODE_OPTIONS`(미리 불러올 코드, 검사기 등), `NODE_PATH`.
    - 그 밖에는 값을 더하거나 바꾸지 않는다(6절). 무엇을 더 뺄지는 VX-D13.
- 줄 해석 규칙 [제안]
  - stderr의 JSON이 아닌 줄(Node 런타임 경고 등)은 표시하지 않고 개수만 센다.
  - 한 줄에 상한을 둔다. 넘는 줄은 버리고 "이벤트 일부를 보이지 못함"으로 표시한다. 값은 구현 때 정한다. 기록은 journal에 있으므로 보고서로 볼 수 있다.
  - stdout은 끝난 뒤 전부 읽어 JSON 한 줄인지 확인한다. 아니거나 JSON의 `exitCode`가 프로세스 종료 코드와 다르면 전송 오류(`adapter_protocol_error`)다.
  - `seq`가 건너뛰면 "일부 이벤트 누락"을 표시하고 계속한다.
  - 이벤트의 레코드는 이미 다시 가린 것이다(모델이 준 이름·id 포함, 어댑터 계약 5.2 보장 5). 표시 전에 제어 문자만 정리한다.

| Codaryn: 출력 보기 | 출력 채널 열기 | — | — |

- 확장은 명령을 실행할 때만 켜진다(모든 이벤트에 켜지는 방식은 쓰지 않는다) [제안].
- `models`는 실제 API에 접속한다(Y-2). 사람이 이 명령을 부를 때만 부른다. 확장이 켜질 때나 실행 전에 자동으로 부르지 않는다.
- 점검은 자동으로 돌리지 않는다. 실행이 `provider_not_configured`, `invalid_config` 등으로 실패하면 오류 알림에 "점검" 단추를 둔다(UX 4.9).
- 결과에 따라 다음 화면을 연다.
  - `needs-input`/`plan_pending`: 계획 화면을 연다(DR-1).
  - `needs-input`/`awaiting_review`: 확인 목록을 연다.
  - 이 두 이유와 명령은 범용 작업 계약(G-A)과 CLI 연결(G-E) 뒤에 생긴다. 그 전에는 명령을 보이지 않는다.

- 웹뷰는 첫 판에 쓰지 않는다(VX-D5). 모든 화면이 VS Code 기본 구성 요소이므로 키보드 조작과 화면 낭독기 지원은 VS Code의 것을 따른다 [추정]. 상태는 색이 아니라 낱말로 구분한다(UX 8절).
- 표시하는 글은 모두 CLI 출력의 가림본이다. 화면에 내기 전에 제어 문자를 정리한다. 경로가 토큰으로 보일 수 있다.
- **비교 문서는 가상 문서다(DR-7).**
  - 작업 공간의 파일을 직접 열지 않는다. 스냅샷 원문은 어디에도 열지 않는다.
  - 열린 문서를 읽는 다른 확장(언어 서버, AI 보조 등)이 받는 것도 가린 글뿐이다 [추정: 가상 문서가 다른 확장에 어떻게 보이는지는 확인하지 않음].
  - 사람이 원문을 보려면 VS Code에서 그 파일을 직접 연다. 확장은 원문 비교를 제공하지 않는다.
- 실행 전에 그 작업 공간에 저장하지 않은 편집기가 있으면 경고하고 "모두 저장"을 제안한다. 자동으로 저장하지 않는다. Codaryn은 디스크의 내용을 읽고 해시로 덮어쓰기를 막으므로(architecture 7절) 저장 안 된 편집과 실행 결과가 엇갈릴 수 있다.
- 작업 공간의 `.codaryn/`이 탐색기에 보인다. 숨기기는 사람이 `files.exclude`로 한다. 확장이 사용자 설정을 자동으로 바꾸지 않는다.

## 5. 질문과 취소: CLI와 같은 의미

| 상황 | CLI | VS Code 확장 | 기록과 결과 |
| --- | --- | --- | --- |
| 사람이 실행·적용을 취소 | Ctrl+C, SIGTERM, `--cancel-file` | 진행 알림의 취소 단추나 "실행 취소" → 취소 파일 생성 | `cancelled`/`cancelled`, 종료 5, 적용된 변경 유지(M-11) |
| 시작 전 취소 | 실행 전 검사 중 Ctrl+C는 JSON 없이 끝남(AC-D12, 한계) | `started` 전에는 취소 단추가 꺼져 있다. 취소 파일을 미리 만들지 않는다(R-1 L-2) | 실행이 생기지 않는다 |
| 계획 승인 | `plan`으로 보고 `apply --digest`(터미널이면 `[y/N]`) | 계획 문서와 "적용" 모달 → `apply --digest` | `plan_approved`(승인 경로 `adapter`), 적용은 새 실행(DR-1) |
| 권한 질문(단계 5 시작) | 터미널이면 stderr에 묻고 stdin에서 읽음(AC-D10) | 모달 대화상자. 답을 stdin 줄로 보냄(`--confirm stdio`) | `confirmation_requested`·`confirmation_answered`(어댑터 계약 5.9) |
| 답할 수 없음 | 터미널 아님 → 묻지 않고 거부 | 대화상자를 닫음 → `dismissed` 줄 | `by: "default"`, 그 호출은 거부 |
| 답을 기다리는 중 취소 | Ctrl+C | 취소 단추 → 취소 파일 | `by: "cancelled"`, `cancelled` |
| 답을 기다리는 중 시간 한도 | 엔진 타이머 | 같음 | `budget-exhausted`/`max_duration`(AC-D6) |
| 실행 중 확장이 꺼짐(창 닫기, 다시 불러오기) | 해당 없음 | **취소 파일을 먼저 만들고** 그 뒤에 stdin을 닫는다(R-1 L-2). 짧게 기다린다 | EOF 때 CLI가 취소를 먼저 확인하므로 `by: "cancelled"`, 실행은 `cancelled`. GUI의 창 닫기와 같은 기록이다. 확장이 결과를 받지 못해도 result.json과 journal은 남는다 |
| 되돌리기 확인 | 명시 명령이므로 묻지 않음, `--dry-run`으로 미리보기(UX-D4) | `--dry-run` 결과를 보여 주고 모달 확인 뒤 실행 | 되돌리기 결과(`complete`/`partial`) |

- 의미가 같은 이유: 질문을 만들고 판정하고 기록하는 것은 자식 CLI 안의 앱 계층과 엔진이다.
  - 확장은 질문을 보여 주고 답 한 줄을 돌려줄 뿐이다.
  - 확장이 답을 바꾸거나 "항상 허용"을 만들 수 없다(답의 종류가 계약에 없다).
  - 계획 승인도 확장이 판정하지 않는다. CLI가 다이제스트를 기록·`plan.json`과 대조한다.
- 취소 파일은 확장 저장 폴더(작업 공간 밖) 안에 실행마다 새 이름으로 만들고, 실행이 끝나면 지운다. 작업 공간 안이면 CLI가 거부한다(T-12).
- 강제 종료 [제안, VX-D12 채택]
  - 취소 파일을 만든 뒤 일정 시간 안에 자식이 끝나지 않으면, 사람에게 "강제 종료하면 결과를 알 수 없고 잠금은 다음 실행이 회수한다"를 보인다.
  - 확인을 받은 뒤에만 프로세스 트리를 끝낸다.
  - 결과는 전송 오류로 표시하고 보고서(`incomplete` 가능)를 안내한다. 기다리는 시간은 구현 때 정한다.
- 확장이 꺼질 때 자식이 함께 끝나는지는 OS와 Node의 자식 프로세스 처리에 달려 있다 [추정, 확인 안 함]. 그래서 꺼질 때도 먼저 취소 파일로 정상 종료를 요청한다.

### 6.2 확장 설정 [제안]

| 설정 | 뜻 | 범위 |
| --- | --- | --- |
| `codaryn.nodePath` | Node 26 이상 실행 파일의 절대 경로 | 머신 |
| `codaryn.configPath` | 설정 파일 경로. 비우면 CLI 기본 규칙 | 머신 |
| `codaryn.varsFile` | 변수 파일 경로. 비우면 넘기지 않음 | 머신 |
| `codaryn.defaultProfile` | "새 작업"에서 먼저 고를 프로필 이름 | 사용자 |

- 작업 공간 범위 설정은 두지 않는다. 범위 이름(머신, 사용자, 작업 공간)과 그 강제 방식은 VS Code의 설정 기여 방식을 확인해 정한다 [추정].
- 프로필은 사용자 설정 파일에만 정의된다(N-8). 작업 공간이 프로필을 고르게 하면 저장소가 사용자의 더 넓은 프로필을 고를 수 있다. 그래서 기본 프로필도 사용자 범위다. 워크플로는 실행마다 사람이 고른다.
- 확장은 작업 공간 신뢰 기능이 "신뢰하지 않음"인 작업 공간에서는 실행 명령을 막는다 [추정, API 미확인]. Codaryn 자신의 원칙(작업 공간의 내용은 자료일 뿐 권한을 넓히지 못한다, M-9)은 신뢰 여부와 무관하게 그대로다.

## 7. 패키징

- 위치: 저장소의 `vscode/` 폴더(VX-D3 채택, M-1 단일 패키지의 예외로 decisions에 기록).
  - 확장 매니페스트(`vscode/package.json`)와 `vscode/tsconfig.json`을 따로 둔다. 루트 `package.json`은 바꾸지 않는다.
- CLI 동봉: 확장을 묶을 때 같은 커밋에서 빌드한 `dist/src`를 확장 안에 복사한다. 확장과 CLI 버전이 늘 같다. 사용자가 따로 설치한 `codaryn`을 찾지 않는다.
  - CLI는 진입 파일에서 위로 올라가며 이름이 `codaryn`인 `package.json`을 찾아 설치 위치로 삼는다(U-3, U-7). 못 찾으면 모든 실행을 거부한다(`src/cli/install.ts:30-48`, `src/cli/run.ts:295-305`) [코드].
  - 확장 매니페스트의 이름은 다르다. 그래서 동봉 위치(예: `<확장>/cli/`)에 루트 `package.json`의 `name`·`version`을 담은 파일을 함께 둔다. U-3의 설치 위치는 그 동봉 폴더가 된다.
  - 이 배치가 실제로 `findInstall`에 맞는지는 V5 통합 시험에서 확인한다.
- Node: 사용자가 설치한 Node 26 이상을 `codaryn.nodePath`로 지정한다(VX-D2 채택).
  - 비어 있으면 "Node 26 이상이 필요합니다"와 점검 안내를 보이고 실행하지 않는다.
  - VS Code 자체 런타임을 Node로 쓰지 않는다.
- 실행 의존성은 없다. 확장 코드는 VS Code API와 Node 내장 모듈만 쓴다.
- 새 개발 의존성 — **모두 PM 승인 필요**
  - VS Code API 타입(`@types/vscode`): `ui/`의 타입 검사에 필요하다. **사용자 확인 대기(VX-D4, Q-3).** 그 전에는 VS Code API에 의존하지 않는 확장 코어까지만 구현한다.
  - 확장 묶음 도구(`@vscode/vsce`): `.vsix` 파일을 만든다. 형식을 손으로 만들지 않는다.
  - VS Code 안 시험 도구(`@vscode/test-electron` 또는 `@vscode/test-cli`): 시험 때 VS Code를 내려받는다(외부 네트워크). 첫 판은 쓰지 않고 수동 점검표로 대신한다.
- 배포: 로컬 `.vsix` 설치만. 마켓플레이스 게시는 외부 발송이므로 범위 밖이다.

| 통합(프로세스) | 확장 코어가 실제 동봉 CLI를 대본 모델로 띄운다 — 아래 목록 | `node --test`, 임시 디렉터리, 키와 네트워크 없음. `vscode/tests/integration/**` | 없음 |
| VS Code 안 | 명령 등록, 대화상자, 트리, 가상 비교 문서, 신뢰하지 않는 작업 공간에서 막힘 | 첫 판은 수동 점검표. 자동화는 시험 도구 승인 뒤 | 시험 도구(PM 승인 필요) |
| 실제 API | 하지 않는다. `models`와 실제 실행은 사용자가 직접 확인한다 | — | — |

유닛(확장 코어)
- 인자 배열: 셸 문자 그대로 전달, 절대 경로, 금지 조합, 자식 환경에서 `NODE_OPTIONS`·`NODE_PATH` 제외
- 줄 해석: 정상, JSON 아님, 상한 초과, `seq` 건너뜀
- stdout 판정: 한 줄, `exitCode` 불일치
- 실행·적용 상태 모델
  - 시작 → 이벤트 → 질문 → 끝, 취소, 전송 오류
  - `started` 전 취소 불가
  - 끝 이유에 따른 다음 화면(`plan_pending`, `awaiting_review`)
- 답 줄 만들기(`allow_once`, `deny`, `dismissed`), 종료 순서(취소 파일 → stdin 닫기)

통합(프로세스)
- `started` → 이벤트 → 결과 한 줄
- 취소 파일 → `cancelled`
- stdin 닫힘 → 질문 기본 거부(단계 5 뒤)
- 실행 전 오류 → `started` 없이 오류 한 줄
- `changes --json`의 글에 가짜 비밀이 없음
- 동봉 배치에서 `findInstall`이 설치 위치를 찾음

수동 점검표(첫 판) [제안]
1. 키 없이 대본 모델 task로 실행 → 진행 → 완료 요약 → 보고서 → 변경 비교 → 되돌리기 미리보기 → 확인 → 되돌리기.
2. 실행 중 취소 단추 → `cancelled`, 바뀐 파일 유지, 실행 목록에 표시.
3. 설정 파일 없음 → 오류 알림의 "점검" → `doctor` 결과.
4. 작업 공간 `.vscode/settings.json`에 `codaryn.nodePath`를 넣어도 쓰이지 않음.
5. 신뢰하지 않는 작업 공간에서 실행 명령이 막힘.
6. 화면 낭독기와 키보드만으로 새 작업 → 취소 → 보고서.
7. (범용 작업 뒤) `organize` 대본으로 `plan_pending` → 계획 문서 → 적용 → 결과 → 되돌리기.

- 모의와 실제를 나눈다(M-19). 위 시험은 모두 대본 모델이며 실제 API 검증이 아니다. 시험 이름에 그렇게 적는다.

  - 확장 호스트의 Node 버전에서 그 코드가 도는지 V4에서 확인한다 [미정].
  - 안 되면 확장은 코드와 상태 낱말만 보이고 문장은 다음 판으로 미룬다.
- 확장 코드는 루트 `tsconfig.json`의 범위(`src`, `tests`) 밖이다. 루트의 `npm test`는 확장 시험을 돌리지 않는다. 병합 전 검사에 넣으려면 루트 스크립트를 바꿔야 하고 이는 `package.json` 변경(역할 1)이다.
