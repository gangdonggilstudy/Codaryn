# 개발 절차

Codex와 여러 Claude 세션이 함께 작업할 때의 배분, 격리, 인수인계, 통합 절차다. 현재는 문서 단계이며 제품 코드, 패키지 설치, 실제 API 호출은 없다. 구현과 자기 개발에 관한 절은 이후 단계에 적용할 설계다. 역할 정의는 [전문 페르소나](personas.md)를 따른다.

표기: **[확정]** 사용자 확정 요구, **[관리]** 관리자(Codex) 설계 선택, **[미정]** 아직 결정하지 않은 항목.

## 1. 브랜치와 worktree

- [관리] `main`(`D:\project\Codaryn`)은 Codex의 관리·통합용이다. Claude는 main을 수정하지 않는다.
- [관리] Claude 작업마다 별도 브랜치와 worktree를 쓴다. 같은 브랜치나 디렉터리에서 동시에 수정하지 않는다.

| worktree | 브랜치 | 담당 문서 범위 |
| --- | --- | --- |
| `D:\project\Codaryn\.worktrees\claude-design` | `claude/design-ready` | 설계 담당 준비 공간 |
| `D:\project\Codaryn\.worktrees\claude-quality` | `claude/quality-ready` | 보안·검증 담당 준비 공간 |
| `D:\project\Codaryn\.worktrees\claude-operations` | `claude/operations-ready` | 개발 운영 담당 준비 공간 |

준비용 브랜치는 문서 통합이 끝난 main에서 생성한다. 초안 브랜치 `claude/design`, `claude/quality`, `claude/operations`는 보존하며 이력을 재작성하지 않는다. 다음 작업은 Codex가 최신 main 기준의 작업 브랜치를 별도로 배정한 뒤 시작한다. 실제 소유 파일과 브랜치는 각 작업 요청이 정한다.

- [관리] worktree는 파일 변경을 분리하는 수단이다. 파일 접근이나 네트워크를 막는 보안 샌드박스가 아니다. 다른 경로도 읽고 쓸 수 있으므로 격리는 절차로 지킨다.

## 2. 시작 전 확인

터미널의 초기 cwd는 지정 worktree와 다를 수 있다. 수정 전에 반드시 확인한다.

```
git -C <지정 worktree> status --short
git -C <지정 worktree> branch --show-current
git -C <지정 worktree> rev-parse --show-toplevel
```

- 브랜치와 최상위 경로가 작업 요청과 다르면 수정하지 않고 보고한다.
- 모든 Git 명령은 `git -C <절대 경로>`로, 모든 파일 작업은 지정 worktree의 절대 경로로 한다. cwd에 의존하는 상대 경로를 쓰지 않는다.
- 시작 시점에 예상하지 못한 변경이 있으면 건드리지 않고 관리자에게 알린다.

## 3. 작업 요청

Codex가 작성한다. 다음 항목을 모두 포함한다.

| 항목 | 내용 |
| --- | --- |
| 목표 | 무엇을 왜 만드는지, 현재 단계 |
| 페르소나 | 적용할 역할 하나(필요하면 보조 관점) |
| worktree·브랜치 | 절대 경로와 브랜치 이름 |
| 소유 파일 | 수정해도 되는 파일 전체 목록 |
| 기준 | 완료 기준과 검증 방법 |
| 한도 | 분량, 금지 행위, 커밋 허용 범위, 중단 조건 |

예시:

```
목표: 민감정보 치환·복원 설계 초안 작성(문서 단계, 구현 없음)
페르소나: 보안·개인정보 검토자
worktree: D:\project\Codaryn\.worktrees\claude-quality
브랜치: claude/task-privacy-doc
소유 파일: docs/privacy.md
기준: 치환 대상, 복원 권한, 대응표 보관 위치를 확정/관리/미정으로 구분.
      git diff --check 통과, 문서 자체 검토 완료
한도: 150줄 이내. API 호출·패키지 설치 금지. 자기 브랜치에 한 커밋, push 금지.
의존: docs/architecture.md(main 통합본, 읽기 전용)
```

## 4. 사전 교육과 이해 확인

1. 지정 worktree의 `AGENTS.md`, `CLAUDE.md`, `README.md`, `docs/README.md`를 읽는다.
2. `docs/personas.md`에서 지정된 페르소나를 읽는다. 없으면 작업 요청의 역할 설명을 따른다.
3. 역할, 작업 범위, 완료 기준을 확인한 뒤 작업한다. 완료 보고에 적용한 지침의 핵심을 적어 이해를 증명한다.
4. 지침끼리 충돌하거나 요청이 범위를 벗어나면 임의로 해석하지 않고 관리자에게 보고한다. 범위 안의 일상 선택은 스스로 정하고 보고서에 남긴다.

## 5. 의존 파일 인수인계

- 다른 담당자의 파일은 읽기 전용이다. 고칠 점을 발견하면 직접 고치지 않고 보고서에 적는다.
- 아직 통합되지 않은 문서에 의존할 때는 참조한 브랜치와 커밋 ID를 보고서에 남긴다.
- 의존 문서가 없거나 미완성이면 가정을 명시하고 [미정]으로 표시한다. 내용을 지어내지 않는다.
- 통합 후 어긋난 부분의 조정은 Codex가 다음 작업으로 배정한다.

## 6. 커밋, 검토, 통합

- 커밋은 작업 요청이 허용한 경우에만, 자기 브랜치에, 소유 파일만 담아 만든다.
- 커밋 전에 `git -C <경로> diff --check`와 문서 자체 검토(사실 구분, 링크, 분량, 금지 내용)를 한다.
- 파일을 이름으로 지정해 스테이징한다. `git add -A`나 `git add .`를 쓰지 않는다.
- [관리] 커밋은 하나의 목적을 가진 변경 단위로 만든다. 서로 무관한 변경을 한 커밋에 섞지 않고, 한 변경을 의미 없이 쪼개지 않는다.
- [확정] 커밋 작성자는 `gangdonggil <gangdonggilstudy@gmail.com>`이다. 저장소 공통 `user.name`/`user.email`은 관리자가 설정했으며 담당자는 바꾸지 않는다.
- [확정] 커밋 메시지에 Git trailer를 붙이지 않는다. `Co-authored-by`, `Signed-off-by`, `Claude-Session`, `Reviewed-by`와 도구가 자동으로 넣는 귀속 문구가 모두 해당한다. `--signoff`, `--trailer`를 쓰지 않는다.
- 커밋 직전에 `git -C <경로> config user.name`/`user.email`과 메시지 전문을 확인하고, 커밋 후 `git -C <경로> log -1 --format='%an <%ae>%n%B'`로 다시 확인한다.
- 이미 만든 커밋에 trailer나 잘못된 작성자가 있으면 amend, rebase, 추가 커밋으로 고치지 않는다. 해당 해시를 관리자에게 보고하고 처리를 맡긴다.
- 병합, cherry-pick, 브랜치 삭제는 Codex가 한다. Claude는 지시 없이 하지 않는다.
- [관리] push는 Codex 검토 후에 Codex가 한다. Claude는 직접 push하지 않는다.
- Codex는 diff와 보고서를 검토한 뒤 채택, 수정 요청, 보류 중 하나를 정하고 main에 통합한다.

## 7. 사용자 변경 보호

- 사용자나 다른 담당자의 변경을 지우거나 덮어쓰지 않는다.
- 금지: `git reset --hard`, `git checkout -- <파일>`, `git clean`, 강제 push, 타인 커밋의 재작성.
- 작업 중 소유 파일에 자신이 만들지 않은 변경이 나타나면 중단하고 보고한다.

## 8. Git 공용 영역 보호

worktree들은 하나의 저장소를 공유하지만 모든 것이 공용은 아니다. 적용 범위를 구분해 다룬다.

| 대상 | 적용 범위 | Claude의 규칙 |
| --- | --- | --- |
| index, HEAD, 작업 파일 | worktree별로 따로 있다 | 자기 worktree 것만 다룬다. 다른 worktree나 main을 대상으로 `git -C`로 스테이징·커밋하지 않는다 |
| `.gitignore`, `.gitattributes` | 추적 파일이다. 수정은 그 worktree의 체크아웃에만 적용되고, 다른 worktree에는 해당 커밋이 병합된 뒤에 적용된다 | 소유 파일이 아니면 수정하지 않는다 |
| 브랜치·태그·원격 refs, 객체 저장소 | 저장소 공용이다 | 자기 브랜치에 커밋을 더하는 것만 한다. 다른 ref를 만들거나 옮기거나 지우지 않는다 |
| stash | 저장소 공용이다(`refs/stash`) | `git stash`를 쓰지 않는다. 임시 보관이 필요하면 보고한다 |
| 공통 Git 설정(`.git/config`), hooks, `.git/info/exclude` | 추적되지 않으며 기본적으로 모든 worktree에 즉시 적용된다 | 변경하지 않는다. 작성자 설정도 관리자가 관리한다 |

- `git worktree add/remove/prune`, `git gc`는 Codex만 실행한다.

## 9. 작업 상태와 완료 보고

상태는 **배정 → 진행 → 검토 대기 → 채택/수정 요청/보류** 순으로 관리한다. 막히면 "차단"으로 보고하고 원인과 필요한 판단을 적는다.

완료 보고는 10줄 이내로 쓴다. 긴 내용은 소유 문서에 남긴다.

```
페르소나: Development Process Architect
worktree/브랜치: D:\project\Codaryn\.worktrees\claude-operations / claude/task-process-doc
적용 지침: (핵심 3개)
파일: docs/personas.md, docs/development-workflow.md
검토: git diff --check 통과, 자체 검토 완료 / 제품 테스트·실제 API: 미실행(문서 단계)
커밋: <ID>
미정: (항목)
```

## 10. 자기 개발 단계(후속 단계 설계)

- [확정] 초기 CLI가 코드 수정 → 테스트 → 실패 피드백 → 재수정을 수행하고, 이후 별도 후보 worktree에서 자기 소스를 개발한다.
- [관리] 현재 실행본, 수정 후보, 보호된 검증기를 분리한다.

| 구분 | 역할 | 규칙 |
| --- | --- | --- |
| 현재 실행본 | 후보를 만들고 검증을 돌리는 버전 | 실행 중 자기 자신을 수정하지 않는다 |
| 수정 후보 | 후보 worktree의 다음 버전 소스 | 후보 worktree 안에서만 변경한다 |
| 보호된 검증기 | 고정된 테스트와 판정 기준 | 후보가 수정할 수 없다. 변경은 별도 작업으로 Codex가 승인한다 |

- [관리] **중단 기준**: 수정 루프는 다음 중 하나에 해당하면 멈추고 보고한다. 구체 수치는 [미정].
  - 정해진 최대 반복 횟수 또는 토큰·시간 한도 도달
  - 같은 실패가 반복되거나 실패 수가 줄지 않음
  - 수정이 작업 범위나 소유 파일을 벗어남
  - 검증기나 검증 기준을 바꿔야만 통과할 수 있음
- [관리] **채택**: 승인된 범위 안의 후보 채택은 Codex가 검증 결과, 변경 내용, 사용자 변경과의 충돌 여부를 보고 결정한다. 후보마다 사용자 승인을 다시 요구하지 않는다. 범위 변경과 결정적 장애만 사용자에게 올린다.
- [관리] **허용 범위 재사용**: 코딩 외 작업(문서, 자료 분석, 파일 정리)에도 같은 원칙을 적용한다. 범용 작업이라는 이유로 동작마다 사용자 승인을 추가하지 않고, 이미 허용된 범위와 정책을 재사용한다. 허용 범위를 넘는 동작만 관리자에게 올리며 최종 채택은 Codex가 판단한다.
- [관리] 테스트 통과만으로 보안이나 정확성 전체가 보장된다고 주장하지 않는다. 채택 기록에 검증한 범위와 한계를 적는다.

## 11. 자격증명과 단계 전환

- [관리] API 키는 추후 로컬 환경 변수 `ANTHROPIC_API_KEY`로, 모델은 명시적인 `CODARYN_MODEL`로 설정할 예정이다. 값은 채팅, 문서, 로그, 커밋에 넣지 않으며 키 파일을 읽거나 출력하지 않는다.
- [확정] API 전송 전 민감정보를 가역 치환하고 로컬에서 복원한다. 세부는 민감정보 처리 문서가 정한다.
- [관리] 문서 단계에는 API 호출, 패키지 설치, 구현이 없다. 개발 단계로 넘어가는 판단은 Codex가 문서와 검증 결과를 보고 내린다. 담당자는 스스로 단계를 넘기지 않는다.

## 미정

- [미정] 수정 루프의 최대 반복 횟수와 토큰·시간 한도
- [미정] 후보 worktree의 경로·브랜치 이름 규칙과 폐기 절차
- [미정] 보호된 검증기의 보관 위치와 무결성 확인 방법
- [미정] 구현 단계의 커밋 단위와 코드 검토 기준
