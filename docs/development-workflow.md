# 개발 절차

Codex(또는 위임받은 임시 PM)와 여러 Claude 세션이 함께 작업할 때의 배분, 격리, 인수인계, 검토, 통합 절차다.
- 2026-11-12에 단계 1a, 1b(모의 API까지), 2, 3의 오프라인 구현이 main에 병합됐다. 그 뒤의 상태(단계 4·5, 2026-11-13 main `3aca6b5`)는 [단계별 계획](roadmap.md)에 있다.
- 실제 API 호출과 실제 모델의 자기 개발은 사용자의 실제 호출 점검 뒤로 미뤘다.
- 역할 정의는 [전문 페르소나](personas.md)를 따른다.

표기:
- **[확정]** 사용자 확정 요구
- **[관리]** 관리자 설계 선택. 위임 기간에는 임시 PM이 같은 권한으로 정한다.
- **[운영]** 임시 PM이 실제로 써 온 절차. 근거는 작업 지시서와 `docs/pm-status.md`.
- **[미정]** 아직 결정하지 않은 항목.

## 1. 관리 권한과 위임

- [관리] 기본 관리자는 Codex다. 하는 일: 기술 판단, 작업 배정, 검토, main 통합, push.
- [운영] 사용자가 임시 PM(Herdr pane `w1:p3`)에게 관리 권한을 위임했다.
  - 위임 상태와 범위: `docs/pm-control.json`(상태, 위임 id, 담당 pane, 회수 문구)
  - 인계 내용: `docs/pm-handoff.md`
  - PM은 배정·커밋·병합·push 전에 매번 위임 상태를 확인한다.
  - 사용자가 회수 문구("PM 회수")를 보내거나 상태가 바뀌면 새 변경과 지시를 멈추고, `pm-status.md`의 회수 절차대로 넘긴다.
  - 위임 범위(`pm-control.json`)는 PM이 바꾸지 않는다.
- [운영] PM의 기록
  - 결정과 근거: `docs/work-orders/*.md`
  - 현재 상태와 세션 배치: `docs/pm-status.md`
  - 단계별 진행: `docs/progress.md`
  - 검토 원문: `docs/reviews/`
- 위임은 관리 권한만 옮긴다. 작업자의 격리·소유 범위 규칙은 그대로다.

## 2. 브랜치와 worktree

- [관리] `main`(`D:\project\Codaryn`)은 관리·통합용이다. 작업자는 main을 수정하지 않는다.
- [관리] 작업자마다 별도 브랜치와 worktree를 쓴다. 같은 브랜치나 디렉터리에서 동시에 수정하지 않는다.
- 현재 pane, worktree, 브랜치 배치는 `docs/pm-status.md`의 세션 표가 기준이다. 단계 0의 준비용 브랜치(`claude/*-ready`)와 초안 브랜치는 보존하며 이력을 재작성하지 않는다.
- [운영] 작업자는 작업을 시작할 때 자기 worktree에서 `git merge main`을 한다. 지시가 있으면 기준 브랜치도 병합한다. 병합 커밋에도 trailer를 넣지 않는다.
- [관리] worktree는 파일 변경을 분리하는 수단이다. 파일 접근이나 네트워크를 막는 보안 샌드박스가 아니다. 격리는 절차로 지킨다.

## 3. 시작 전 확인

터미널의 초기 cwd는 지정 worktree와 다를 수 있다. 수정 전에 확인한다.

```
git -C <지정 worktree> status --short
git -C <지정 worktree> branch --show-current
git -C <지정 worktree> rev-parse --show-toplevel
```

- 브랜치와 최상위 경로가 작업 요청과 다르면 수정하지 않고 보고한다.
- 모든 Git 명령은 `git -C <절대 경로>`로, 모든 파일 작업은 지정 worktree의 절대 경로로 한다.
- 시작 시점에 예상하지 못한 변경이 있으면 건드리지 않고 관리자에게 알린다.

## 4. 작업 지시와 결정

- [운영] 작업 지시는 관리자가 쓴다. 대화로 받은 지시도 같은 항목을 갖춘다.

| 항목 | 내용 |
| --- | --- |
| 목표 | 무엇을 왜 만드는지, 현재 단계, 결정 번호 |
| 페르소나 | 주 역할 하나와 필요하면 보조 관점 |
| worktree·브랜치 | 절대 경로와 브랜치 이름, 기준 브랜치 |
| 소유 파일 | 수정해도 되는 경로 전체 |
| 기준 | 완료 기준, 실행할 검사(typecheck, 유닛, 통합), 회귀 시험 규칙 |
| 한도 | 금지 행위(실제 API, 외부 네트워크, 키 파일, 작업 디렉터리 밖 읽기, 새 의존성), 커밋·push 규칙 |
| 보고 | 보고서 위치와 대화 답 형식 |

- [운영] **결정 번호**
  - 지시서 `docs/work-orders/<단계>.md`에 표로 남긴다. 계열은 P, C, R, S, T, U, V, W, X, Y다.
  - 각 행은 "번호, 결정, 대상 결함, 담당"이다. 고치지 않고 한계로 기록하는 것도 같은 절에 적는다.
  - 요약과 연결은 [decisions.md](decisions.md) 3절에 있다.
- [운영] **소유 분할**
  - 한 파일의 소유자는 하나다. 다른 파일은 읽기 전용이다.
  - 계약(`src/contracts/**`)과 `package.json`은 역할 1만 바꾼다. 다른 작업자가 계약 변경이 필요하면 고치지 않고 보고한다.
  - 통합 시험 담당은 `tests/integration`, `tests/support`, `tests/fixtures`를 소유한다. 제품 결함은 고치지 않고 재현 사례로 보고한다.
- [운영] **작업 순서**: 역할 1이 계약 추가분을 먼저 커밋한다 → 담당자들이 그것을 병합해 병렬로 구현 → 연결 담당이 조립 → 통합 시험과 함께 병합.

## 5. 사전 교육과 이해 확인

1. 지정 worktree의 `AGENTS.md`, `CLAUDE.md`, `README.md`, `docs/README.md`를 읽는다.
2. `docs/personas.md`에서 지정된 페르소나를 읽는다. 없으면 작업 지시의 역할 설명을 따른다.
3. 필요한 설계 문서(architecture, privacy, testing, cli-contract)와 해당 작업 지시서를 읽는다.
4. 지침끼리 충돌하거나 요청이 범위를 벗어나면 임의로 해석하지 않고 보고한다. 범위 안의 일상 선택은 스스로 정하고 보고서에 남긴다.

## 6. 의존 파일 인수인계

- 다른 담당자의 파일은 읽기 전용이다. 고칠 점을 발견하면 직접 고치지 않고 보고서에 적는다(파일:줄과 근거).
- 아직 병합되지 않은 문서나 코드에 의존할 때는 참조한 브랜치와 커밋 ID를 보고서에 남긴다.
- 의존 문서가 없거나 미완성이면 가정을 명시하고 [미정]으로 표시한다. 내용을 지어내지 않는다.

## 7. 커밋

- 커밋은 작업 지시가 허용한 경우에만, 자기 브랜치에, 소유 파일만 담아 만든다.
- 커밋 전
  - `git -C <경로> diff --check`를 실행한다.
  - 문서는 자체 검토(사실 구분, 링크, 금지 내용)를 한다.
  - 코드는 typecheck와 관련 시험을 실행한다.
- [확정] 검사의 결과를 읽고 통과를 확인한 뒤에만 커밋한다. 검사와 커밋을 한 명령에 묶어 검사가 실패해도 커밋되게 하지 않는다. 실패한 상태로 커밋했으면 이력을 고치지 않고 다음 커밋으로 바로잡은 뒤 보고한다(2026-11-12 사용자 확인, G-4).
- 파일을 이름으로 지정해 스테이징한다. `git add -A`나 `git add .`를 쓰지 않는다.
- [관리] 커밋은 하나의 목적을 가진 변경 단위다. 결함 수정은 결정 번호별로 나눈다.
- [확정] 작성자는 `gangdonggil <gangdonggilstudy@gmail.com>`이다. 저장소 공통 `user.name`·`user.email`은 관리자가 관리하며 담당자는 바꾸지 않는다.
- [확정] Git trailer를 붙이지 않는다. `Co-authored-by`, `Signed-off-by`, `Claude-Session`, `Reviewed-by`와 도구가 넣는 귀속 문구가 모두 해당한다. `--signoff`, `--trailer`를 쓰지 않는다.
- 커밋 후 `git -C <경로> log -1 --format='%an <%ae>%n%B'`로 다시 확인한다.
- 이미 만든 커밋에 trailer나 잘못된 작성자가 있으면 amend, rebase, 추가 커밋으로 고치지 않는다. 해시를 관리자에게 보고하고 처리를 맡긴다.
- [확정] 관리자에게 보고했거나 다른 브랜치가 받은 커밋은 고쳐 만들거나 되돌리지 않고 새 커밋으로 바로잡는다. 아직 보고하지 않은 자기 커밋은 고칠 수 있지만 그 사실(옛 해시와 새 해시, 이유)을 보고서에 적는다. 작업 트리를 버리는 `git reset --hard`는 계속 금지다(2026-11-12 사용자 확인, G-2).
- [운영] **비밀 검사 훅**
  - 공용 `.git/hooks/pre-commit`이 `scripts/check-secrets.mjs --staged`와 같은 사본을 실행한다. 모든 worktree에 적용된다.
  - 문서와 시험에 키 모양 문자열이나 키 대입 형태를 쓰면 거부된다. 가짜 값은 실제 키 형식과 구별되게 쓴다.
  - `--no-verify`는 금지다.
  - 훅은 Git이 추적하지 않으므로 새로 복제한 저장소에는 관리자가 다시 설치한다. 설치: `scripts/check-secrets.mjs`를 공용 hooks 폴더에 복사하고 `pre-commit`에서 `--staged`로 실행한다.
  - [확정] 훅이 없는 환경에서는 커밋 전에 `node scripts/check-secrets.mjs --staged`를 직접 실행하고 결과를 보고서에 적는다. 관리자는 병합 전에 한 번 더 검사한다(2026-11-12 사용자 확인, G-1. 현재 작업 환경은 훅 없이 이 방식으로 진행한다).
- [확정] **도구 주의**: TypeScript 7 컴파일러는 정규식 리터럴 안의 U+2028 이스케이프를 원문자로 내보내 실행 때 구문 오류가 난다. 그런 정규식은 리터럴 대신 문자열로 만든다(`new RegExp("...")`) (2026-11-12 사용자 확인, G-5).
- [확정] **시험의 프로세스 종료**: 시험은 자기가 띄운 자식의 핸들로만 프로세스를 끝낸다. 기록해 둔 pid 번호로 끝내지 않는다(끝난 pid는 다른 프로세스에 다시 주어진다). 유닛과 통합 시험 모두에 적용한다(2026-11-12 사용자 확인, G-7).
- [확정] **계약이 움직일 때**: 여러 담당이 계약을 함께 따라가는 동안에는 자기 소유 범위의 검사를 통과시키고, 물려받은(다른 담당 몫의) 오류는 고치지 않고 파일 목록으로 보고한다(2026-11-12 사용자 확인, G-8).
- [확정] **수치와 판**: 보고하는 수치는 실제로 올리는 판에서 잰 것이어야 하고 그 판의 해시를 함께 적는다. 관리자는 고정 판을 만든 직후 직접 빌드와 전체 시험을 돌린 뒤에만 검토에 넘긴다(2026-11-12 사용자 확인, G-9).
- [확정] **키 모양 예시**: 문서와 보고서에 키 모양으로 보일 합성 예시는 쪼개어 쓰거나 설명으로 대신한다. 비밀 검사를 우회하지 않는다(2026-11-12 사용자 확인, G-10).
- [확정] **닿지 않는 주소**: 닿지 않는 주소가 필요한 시험과 탐침은 예약 주소(TEST-NET, `.test`)를 쓰지 않고 `127.0.0.1`의 닫힌 포트를 쓴다. 방어를 일부러 지워 보는 확인은 바깥으로 나갈 수 없는 조건에서만 한다(2026-11-12 사용자 확인, G-11).

## 8. 검토와 통합

- [운영] **병합 전 검토**(관리자)
  1. `node scripts/review-branch.mjs <브랜치> <소유 경로>...`가 PASS여야 한다. 검사 항목:
     - 작성자·커미터
     - trailer와 귀속 문구 없음
     - 소유 경로 밖 변경 없음
     - main과 충돌 없음
     - 공백 오류 없음
     - 추가된 줄의 비밀 검사
  2. 작업자 보고서와 diff의 내용을 검토한다.
  3. **main과 합친 트리에서 typecheck, 유닛, 통합을 모두 실행한다.** 브랜치마다 따로 통과해도 합친 결과가 깨질 수 있다. review-branch는 시험을 돌리지 않는다.
  4. 통과하면 "merge: accept …" 형식으로 병합하고 수치를 `pm-status.md`에 남긴다.
- 병합, cherry-pick, 브랜치 삭제, push는 관리자만 한다. 작업자는 지시 없이 하지 않는다.
- [확정] 원격 push는 오케스트레이터(관리자) 한 세션만 한다. 작업자는 자기 브랜치도 push하지 않는다. 오케스트레이터는 합친 트리에서 타입 검사, 유닛, 통합, 비밀 검사를 직접 실행해 통과를 확인한 변경만 main에 병합해 push하고, 작업 브랜치는 검수한 상태로만 원격에 올린다(2026-11-12 사용자 확인, G-6).
- [확정] **병합·푸시 단위**: 결정(DR) 하나 또는 기능 하나를 계약, 문구, 구현, 연결까지 묶은 것이 한 단위다. 서로 무관한 결정을 한 단위에 섞지 않는다. 기준은 약 1,500줄 이하, 검토 1건이며, 관리자의 전체 검증과 검토를 통과하면 바로 병합해 push한다. 한 단위가 막혀도 다른 단위는 계속 들어간다. 계약에 문구 id가 더해지는 단위에는 문구 담당을 처음부터 넣는다. 기준을 넘는 단위는 나누고, 나눌 수 없으면 그 까닭을 병합 기록에 적는다(2026-11-12 사용자 확인, G-12).
- 관리자는 채택, 수정 요청, 보류 중 하나를 정한다. 수정은 결정 번호를 붙여 다음 지시로 배정한다.

## 9. 교차 검토

- [확정] 새 모듈과 보안·파일 변경에 닿는 변경은 구현자가 아닌 세션의 교차 검토 결과를 본 뒤 main에 병합한다. 문서나 시험만 바꾸는 변경은 병합 뒤에 검토해도 된다(2026-11-12 사용자 확인, G-3. 검토 전에 병합한 모듈에서 비밀 노출과 사용자 파일 삭제 결함이 main에 들어간 일이 있었다).
- [운영] 구현자가 아닌 세션에게 읽기 전용 검토를 배정한다. 구현자는 자기 모듈을 검토하지 않는다.
- 검토자 규칙
  - 어떤 저장소 파일도 수정·커밋하지 않는다.
  - 실험은 자기 worktree의 `.codaryn/` 안에서만 한다. 빌드 사본(`git archive`, `tsc --outDir`)을 쓴다.
  - 실제 API·외부 네트워크·키 파일은 쓰지 않는다. 가짜 값만 쓴다.
  - 작업 디렉터리 밖은 읽지 않는다.
- 결함은 실제로 깨지는 입력을 찾아 재현한다(실제 CLI 프로세스면 더 좋다). 추측은 추측으로 표시한다.
- 보고서는 `.codaryn/report-<작업>.md`에 쓴다. 담을 것:
  - 심각도별 발견: 높음, 중간, 낮음, 정보
  - 파일:줄
  - 깨지는 입력과 결과, 재현 방법
  - 문제 없던 범위, 검사하지 않은 범위
- 관리자는 원문을 `docs/reviews/<날짜>-<이름>.md`로 보관한다. 고칠 것은 결정 번호로, 고치지 않을 것은 "한계로 기록"으로 지시서에 남긴다.
- 수정 작업은 검토 보고서의 재현 입력으로 실패하는 회귀 시험을 먼저 추가한다.

## 10. 사용자 변경과 Git 공용 영역 보호

- 사용자나 다른 담당자의 변경을 지우거나 덮어쓰지 않는다. 금지: `git reset --hard`, `git checkout -- <파일>`, `git clean`, 강제 push, 타인 커밋의 재작성.
- 작업 중 소유 파일에 자신이 만들지 않은 변경이 나타나면 중단하고 보고한다.

| 대상 | 적용 범위 | 작업자 규칙 |
| --- | --- | --- |
| index, HEAD, 작업 파일 | worktree별 | 자기 worktree 것만 다룬다 |
| `.gitignore`, `.gitattributes` | 추적 파일, 병합 뒤 다른 worktree에 적용 | 소유 파일이 아니면 수정하지 않는다 |
| 브랜치·태그·원격 refs, 객체 저장소 | 공용 | 자기 브랜치에 커밋을 더하는 것만 한다 |
| stash | 공용(`refs/stash`) | `git stash`를 쓰지 않는다. 임시 보관은 자기 브랜치의 임시 커밋으로 하거나 보고한다 |
| 공통 Git 설정, hooks, `.git/info/exclude` | 추적되지 않고 모든 worktree에 즉시 적용 | 변경하지 않는다. 비밀 검사 훅은 관리자가 설치·관리한다 |

- `git worktree add/remove/prune`, `git gc`는 관리자만 실행한다. 후보 worktree는 관리자 판단 아래 `scripts/new-candidate.mjs`로 만든다(13절).

## 11. 작업 상태와 완료 보고

상태: **배정 → 진행 → 검토 대기 → 채택/수정 요청/보류**. 막히면 "차단"으로 보고하고 원인과 필요한 판단을 적는다.

- [운영] 긴 내용은 worktree의 `.codaryn/report-<작업>.md`(Git 추적 제외)에 쓴다. 대화 답에는 지시가 정한 짧은 형식만 쓴다.
  - 구현: 커밋 해시와 통과·실패 수, 3줄 이내
  - 검토: 심각도별 발견 수와 보고서 경로, 2줄
- 진행 중인 작업 중에 새 지시가 오면 하던 작업을 끝내 보고한 뒤 새 작업을 시작한다.
- 보고서에 넣을 것
  - 페르소나, worktree·브랜치, 기준 커밋
  - 커밋(작성자 확인)
  - 실행한 검사와 수치(유닛·통합의 통과·실패·건너뜀), 실제 API 미실행 여부
  - 고치기 전 실패 확인
  - 다른 담당자 확인이 필요한 점
  - 검사하지 않은 범위

```
페르소나: CLI 개발자(주), 검증 엔지니어(보조)
worktree/브랜치: D:\project\Codaryn\.worktrees\<이름> / claude/<브랜치> (main <해시> 병합)
커밋: <해시> <제목>
검사: typecheck 통과 / 유닛 N건 중 N 통과·0 실패·1 건너뜀 / 통합 N건 통과 / 실제 API 미실행
다른 담당자 확인: (항목)
```

## 12. 사용 한도로 멈춘 세션의 인계

- [운영] 세션이 사용 한도로 멈추면 관리자는 그 세션의 사용·결제 선택 질문에 대신 답하지 않는다. 결제는 사용자의 선택이다.
- 멈춘 세션의 커밋되지 않은 변경은 관리자가 내용을 확인한 뒤에만 이어받는다.
  - 예: p1의 계약 변경을 확인하고 `f45959a`로 커밋했다.
- 그 세션의 worktree는 건드리지 않는다. 남은 작업은 다른 세션에 다시 배정한다.
  - 예: 역할 1(계약)은 p7로 옮겼다. CLI 연결은 p7, 엔진은 p5가 맡았다.
- 재배정은 `pm-status.md`의 세션 표와 작업 지시서의 담당 열에 남긴다.

## 13. 자기 개발 단계

- [확정] 초기 CLI가 코드 수정 → 테스트 → 실패 피드백 → 재수정을 하고, 이후 별도 후보 worktree에서 자기 소스를 개발한다.
- [관리] 현재 실행본, 수정 후보, 보호된 검증 자료를 분리한다.

| 구분 | 역할 | 구현 |
| --- | --- | --- |
| 현재 실행본 | 후보를 만들고 검증을 돌리는 버전 | 작업 공간이 설치 위치와 겹치면 실행을 거부한다(U-3(단계 3)) |
| 수정 후보 | 후보 worktree의 다음 버전 소스 | `scripts/new-candidate.mjs --repo --name --out --state`가 `candidate/<이름>` 브랜치와 worktree, 작업 공간 밖 설정·task 틀을 만든다. 기존 대상이 있으면 아무것도 바꾸지 않는다(U-4(단계 3), W-3) |
| 보호된 검증 자료 | 고정된 테스트와 판정 기준 | `protectedPaths`와 `integrity.paths`의 무결성 확인(U-1, U-2(단계 3), W-1, W-2) |

- [관리] **중단 기준**(구현): 다음이면 멈춘다.
  - 재수정 한도(`maxRepairAttempts`)
  - 같은 실패 연속(`maxSameFailures`)
  - 턴·도구·토큰·시간 한도
  - 보호 자료 변경(`protected_changed`)
  - 과제별 값은 [미정]이다.
- [관리] **채택**: `codaryn report`로 결과·변경·무결성·검사하지 않은 범위를 읽고 관리자가 결정한다. 자동 병합·교체는 없다.
- [관리] 테스트 통과만으로 보안이나 정확성 전체가 보장된다고 주장하지 않는다. 채택 기록에 검증한 범위와 한계를 적는다.
- 실제 모델로 자기 소스를 고치는 실행은 사용자의 실제 호출 점검 뒤에 연다. 지금까지는 대본 모델 예행만 했다.

## 14. 자격증명

- [관리] 키는 로컬 환경 변수 `ANTHROPIC_API_KEY`로만 받는다(또는 작업 공간 밖의 `--vars-file`로 적재). 모델은 task, `CODARYN_MODEL`, 설정 파일 중 하나로 명시한다.
- 키 값은 채팅, 문서, 로그, 커밋에 넣지 않는다. 작업자는 키 파일을 읽거나 출력하지 않는다.
- [확정] API 전송 전 민감정보를 가역 치환하고 로컬에서 복원한다. 세부는 [privacy.md](privacy.md).
- [관리] PM과 작업자는 실제 API를 호출하지 않는다. 실제 호출 점검(`tests/live`)은 사용자가 직접 실행한다.
