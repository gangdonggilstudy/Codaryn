# 작업 지침 통합본

담당 페르소나: 임시 PM 보좌(개발 프로세스·품질 관리), 검증 엔지니어(보조).

상태: 2026-11-12, `unit/U-6-pm`의 `6df2eae` 기준으로 원천 문서를 읽어 정리했다.

## 1. 머리말

### 1.1 목적

작업 지침이 여러 문서에 흩어져 있다. 이 문서는 그것을 한 곳에 모아, 작업자(여러 Claude 세션과 Codex)와 관리자가 지금 지켜야 할 규칙을 찾게 한다.

- 이 문서는 **통합 색인이자 요약**이다. 새 규칙을 만들지 않고 기존 규칙의 뜻을 바꾸지 않는다.
- **기준은 원천 문서다.** 이 문서와 원천이 다르면 원천을 따르고, 다른 점을 관리자에게 보고한다.

### 1.2 원천 문서와 줄임 표기

| 줄임 | 문서 | 담긴 것 |
| --- | --- | --- |
| CL | `CLAUDE.md` | Claude 세션의 기본 지침 |
| AG | `AGENTS.md` | 공통 개발 지침 |
| WF | `docs/development-workflow.md` | 개발 절차. 사용자 확인 지침 G-1 ~ G-12의 확정 문장 |
| PS | `docs/pm-status.md` | 사용자 지시, 사용자 답, 지침 후보 표, 체크포인트 |
| PH | `docs/pm-handoff.md` | 임시 PM 위임의 권한과 회수 |
| PC | `docs/pm-control.json` | 위임 상태, 위임 id, 담당, 회수 문구 |
| PE | `docs/personas.md` | 페르소나별 금지사항과 제출 기준 |
| TS | `docs/testing.md` | 시험 원칙, 검증 층, 보고 항목 |

"WF 7절"은 `development-workflow.md`의 7절을 뜻한다.

원천의 표기도 그대로 쓴다.
- **[확정]** 사용자 확정 요구
- **[관리]** 관리자 설계 선택
- **[운영]** 임시 PM이 써 온 절차
- 표기가 없는 것은 원천에 표기 없이 적힌 규칙이다.

### 1.3 규칙이 어긋날 때

원천에 적힌 것은 다음뿐이다. **문서 전체의 일반 우선순위는 어느 원천에도 없다.**

- 지침끼리 충돌하거나 요청이 범위를 벗어나면 임의로 해석하지 않고 보고한다(WF 5절).
- 페르소나 문서가 없거나 작업 지시와 다르면 작업 지시의 역할 설명이 우선한다. 문서 간 충돌은 Codex가 해결한다(PE 적용 원칙). 위임 기간에는 임시 PM이 그 권한을 대신한다(AG, PE).
- 위임 권한의 기준은 관리용 main의 `docs/pm-control.json`이다. worktree의 복사본은 기준이 아니다(PH).
- 단계별 완료 기준은 `docs/roadmap.md`, 작업 절차는 `docs/development-workflow.md`를 따른다(AG).
- 세션, worktree, 브랜치의 현재 배치는 `docs/pm-status.md`의 세션 표가 기준이다(WF 2절, PH).

### 1.4 갱신 방법

- 작업 중 필요해진 새 지침은 PM이 바로 추가하지 않는다. `pm-status.md`의 "지침 후보" 표에 모으고, **사용자가 확인한 뒤에만** 추가한다(PS 사용자 지시 CP-12).

아래 셋은 원천에 없는 절차다. **제안(PM 승인 전)**이며 규칙이 아니다.

- 제안(PM 승인 전): 확정된 지침은 먼저 원천(`development-workflow.md`)에 적는다. 이 문서는 그 뒤에 맞춘다.
- 제안(PM 승인 전): 이 문서만 고쳐서 규칙을 더하거나 바꾸지 않는다.
- 제안(PM 승인 전): 8절 "정리하면서 발견한 것"은 기록이다. 그 항목을 규칙으로 삼으려면 사용자 확인이 필요하다.

## 2. 한 쪽 요약

1. 실제 API를 호출하지 않는다. 실제 호출 점검은 사용자가 직접 한다.
2. API 키와 키 파일을 읽거나 출력하지 않는다. 채팅, 문서, 로그, 커밋에 넣지 않는다.
3. 지정 worktree 안의 소유 파일만 고친다. main, 다른 worktree, 다른 담당자의 파일은 고치지 않는다.
4. 커밋 작성자는 `gangdonggil <gangdonggilstudy@gmail.com>`이다. trailer와 자동 귀속 문구를 붙이지 않는다.
5. 검사 결과를 읽고 통과를 확인한 뒤에만 커밋한다(G-4). `--no-verify`를 쓰지 않는다.
6. 원격 push는 오케스트레이터(관리자) 한 세션만 한다(G-6). 병합, cherry-pick, 브랜치 삭제도 관리자만 한다.
7. `git reset --hard`, `git checkout -- <파일>`, `git clean`, `git stash`, 강제 push, 타인 커밋의 재작성을 하지 않는다.
8. 실행하지 않은 시험과 API 호출을 성공으로 적지 않는다. 수치는 실제로 올리는 판에서 재고 그 판의 해시를 함께 적는다(G-9).
9. 새 모듈과 보안·파일 변경에 닿는 변경은 구현자가 아닌 세션의 교차 검토 결과를 본 뒤 main에 병합한다. 문서나 시험만 바꾸는 변경은 병합 뒤에 검토해도 된다(G-3).
10. 시험을 약하게 하거나 지우거나 건너뛰게 해서 통과시키지 않는다. 보호된 검증 기준을 바꾸지 않는다.
11. 병합·푸시 단위는 결정 하나 또는 기능 하나다. 무관한 결정을 섞지 않는다(G-12).
12. 새 지침은 사용자 확인 뒤에만 추가한다. 위임 상태가 active가 아니거나 위임 id가 다르면 PM은 새 변경과 지시를 멈춘다.

| A-6 | **허용 의존성.** PH는 "설치 허용 개발 의존성은 typescript와 @types/node"라고 한다. 사용자 답 Q-3은 GUI 개발 의존성을 PM이 근거를 기록하고 추가하게 했다. PE 공통 금지의 "문서 단계에서의 제품 코드 구현, 패키지 설치"는 단계 0의 표현이 남은 것으로 보인다(애매하다). | PH, PS Q-3, PE |

### B. 같은 규칙의 서로 다른 표현

| 번호 | 내용 | 위치 |
| --- | --- | --- |
| B-1 | **push하는 주체.** CL, AG, PE는 "Codex가 한다", G-6은 "오케스트레이터(관리자) 한 세션만", PS는 "오케스트레이터"라고 쓴다. AG의 위임 예외로 이어지지만 낱말이 셋이다(Codex, 관리자, 오케스트레이터/임시 PM). | CL, AG, PE, WF 8절 |
| B-2 | **G-2의 후보와 확정 문장.** 후보는 "`git reset --keep`만 허용, 되돌리기 전에 보고서에 먼저 기록"을 예로 들었다. 확정 문장에는 `reset --keep`과 "먼저 기록"이 없다. | PS, WF 7절 |
| B-3 | **G-4의 범위.** 후보는 `git diff --cached --check`의 실패를 말한다. 확정 문장은 "검사" 전체로 넓다. 7절의 커밋 전 명령은 `diff --check`(`--cached` 없음)다. | PS, WF 7절 |
| B-4 | **G-8과 커밋.** 후보는 "파일 목록을 커밋 메시지나 보고서에 적은 뒤 커밋한다"와 "G-4의 보완"을 적었다. 확정 문장에는 "커밋한다"와 G-4와의 관계가 없다. 물려받은 타입 오류가 남은 상태의 커밋이 G-4에 어긋나지 않는지는 확정 문장만으로는 애매하다. | PS, WF 7절 |
| B-5 | **G-9와 병합 뒤 다시 재기.** 후보는 "병합하거나 고정 판을 만든 뒤에는 그 판에서 빌드와 시험을 다시 돌린다"고 한다. 확정 문장은 "고정 판을 만든 직후"만 적는다. | PS, WF 7절 |
| B-6 | **G-3의 범위.** 후보는 "새 모듈"이다. 확정 문장은 "새 모듈과 보안·파일 변경에 닿는 변경"이고 문서·시험만 바꾸는 변경의 예외가 더해졌다. | PS, WF 9절 |
| B-7 | **관리자가 합친 트리에서 돌리는 검사.** WF 8절 [운영]과 TS 9절은 typecheck, 유닛, 통합이다. G-6은 여기에 비밀 검사를 더한다. PS의 실제 기록은 `npm ci`와 `check-secrets --tracked`도 적는다. | WF 8절, TS 9절, PS |
| B-8 | **trailer 목록.** CL은 `Reviewed-by`를 이름으로 들지 않고 "등"으로 쓴다. AG와 WF는 이름으로 든다. | CL, AG, WF 7절 |
| B-9 | **이력 다시 쓰기.** AG와 PE는 "임의로" 다시 쓰지 않는다고 하고, PH와 PS는 "기존 이력 재작성은 하지 않는다"고 한다. G-2는 보고 전 자기 커밋에 한해 허용한다. | AG, PE, PH, WF 7절 |
| B-10 | **수치의 항목.** WF 11절과 TS 10절의 보고 항목은 통과·실패·건너뜀이다. PS의 실제 기록은 todo 수도 적는다. | WF 11절, TS 10절, PS |

### C. 확정으로 적히지 않았는데 실제로 적용 중인 관행

| 번호 | 관행 | 근거 |
| --- | --- | --- |
| C-1 | **병합 조건으로 쓰는 심각도.** 병합 시점에 열린 "높음·중간" 지적이 없어야 병합하고, 낮음은 다음 단위로 넘긴다. 중간 지적 때문에 병합을 멈춘 기록이 있다. 원천의 규칙은 심각도 네 단계의 이름뿐이고 병합 조건은 없다. | PS CP-14 ~ CP-19 |
| C-2 | **고정 시험 값.** 고정 시험 파일이 main과 같은지, 바뀐 곳이 승인한 곳뿐인지 검토자가 확인한다. "고정 값을 바꾸기 전에 보고한다"는 문장은 어느 원천에도 없다. 가까운 규칙은 "기존 시험을 약하게 하지 않는다"(TS 1절)뿐이다. | PS CP-16, CP-18, CP-19 |
| C-3 | **시간에 기대는 시험.** 부하에 흔들리는 시간 시험이 고정 전 검증에서 떨어진 기록이 있다. 시간 시험을 어떻게 쓰는지에 관한 규칙은 원천에 없다. | PS CP-19 |
| C-4 | **고정 판과 통합 worktree.** PM이 통합 worktree(`pm/integration`, `pm/bundle-N`)에서 브랜치를 합쳐 고정 판을 만들고, 병합 뒤 main과 트리 해시가 같은지 확인한다. G-9는 "고정 판"이라는 말만 쓰고 이 절차는 WF 8절에 없다. | PS CP-14 ~ CP-19 |
| C-5 | **고정 판에 넣을 것 고르기.** 다음 단위로 넘기기로 한 계약이 브랜치의 최신 판을 합치면서 섞여 들어간 일이 있었다. 빌드를 하지 않은 쪽은 G-9로 확정됐다. "넘기기로 한 것이 섞이지 않게 한다"는 쪽은 G-12의 "무관한 결정을 섞지 않는다"에 가깝지만 따로 적혀 있지 않다. | PS CP-15 "PM의 실수와 조치" |
| C-6 | **GUI 시험을 누가 돌리는가.** GUI 유닛과 연기 시험은 PM이 아니라 검토자가 같은 판에서 돌린다. G-6은 오케스트레이터가 "직접" 실행할 검사로 타입 검사, 유닛, 통합, 비밀 검사를 들고 GUI 시험은 말하지 않는다. | PS CP-17, CP-18, CP-19 |
| C-7 | **Codex의 독립 재검증.** Codex가 같은 판에서 독립으로 전체 시험을 돌려 수치를 맞춰 본다. 규칙으로는 "Codex는 검증 작업만 맡긴다"(사용자 지시)뿐이다. | PS CP-15, CP-19 |
| C-8 | **바깥 연결 시도의 자진 보고.** 작업자가 바깥으로 나간 연결 시도를 스스로 보고했고 PM이 기록했다. 보고 의무는 규칙으로 적혀 있지 않다. | PS CP-16 |
| C-9 | **지침 후보의 임시 적용.** PM이 G-11을 사용자 확인 전에 "임시 적용"했다고 적었다. "새 지침은 사용자 확인 뒤 추가한다"는 지시와의 관계(임시 적용이 허용되는지)는 적혀 있지 않다. | PS CP-16, PS 사용자 지시 |
| C-10 | **한 단위 안의 반복 검토.** 같은 변경이 R-34, R-34b, R-34c처럼 여러 번 검토를 거친다. G-12의 기준은 "검토 1건"이다. 재검토를 어떻게 세는지는 적혀 있지 않다. | PS CP-19, WF 8절 |
| C-11 | **한 커밋만 골라 더하기.** PM이 고정 판에 문구 커밋 하나를 골라 더해 바로잡았다. cherry-pick은 관리자 권한이지만 고정 판을 고치는 절차는 적혀 있지 않다. | PS CP-15 |
| C-12 | **프로젝트 스크립트로 재기.** 보고하는 시험 수치를 프로젝트 스크립트(`npm run test:unit` 등)로 잰다. 원천에는 실행 명령의 목록(TS 3절)만 있고 "수치는 그 스크립트로 잰다"는 규칙 문장은 없다. | 이 문서의 작성 지시에 관행으로 언급됨. 원천 문서에는 규칙으로 없음 |
