## 중간 1건 — 일반 이름도 대문자와 숫자가 함께 있으면 계속 거부된다

위치: `ec7e4a1:src/contracts/config.ts:311`.

새 정규식은 단어 경계의 접두사 뒤에 허용 문자 32자 이상, 숫자 1개 이상, 대문자 1개 이상을 요구한다. 일반 이름을 식별하는 규칙은 아니므로 오탐을 줄이지만 없애지는 않는다. 추가된 테스트의 소문자 폴더·가지·CSS·경로·UUID·한글 뒤 이름은 대문자가 없어 매칭되지 않는다. 그 테스트 집합에 대한 수정은 맞다.

아래에서 `p = 'sk' + '-'`이며, 실제 키를 사용하지 않은 합성 입력 표현이다.

| 용도 | 입력 표현 | 정적 판단 |
| --- | --- | --- |
| 폴더 | `p + 'Mobile-app-redesign-final-draft-v2'` | 매칭: 접두사 뒤 32자, M과 2가 있음 |
| Git 가지 | `p + '1234-Implement-provider-table-and-key-list'` | 매칭: I와 숫자가 있음 |
| CSS 클래스 | `p + 'Circle-fade-in-animation-delay-long-2'` | 매칭 |
| 경로 조각 | `'docs/' + p + 'Onboarding-guide-for-new-team-members-v2.md'` | 매칭: 점 앞 조각만으로 조건 충족 |
| UUID 접두 ID | `p + '550E8400-E29B-41D4-A716-446655440000'` | 매칭: 대문자 UUID도 평범한 식별자 |
| 한글 바로 뒤 | `'폴더' + p + 'Mobile-app-redesign-final-draft-v2'` | 매칭: JavaScript의 이 정규식에서 한글은 ASCII 단어 문자가 아니므로 한글과 s 사이도 단어 경계 |

따라서 “한글 바로 뒤에서는 잡지 않는다”는 경계 수정은 이루어지지 않았다. 테스트의 한글 예가 통과하는 이유도 소문자 구성이다. 경로 구분자 `/`는 반복 문자 집합에 없어 다음 경로 조각의 대문자/숫자를 빌려오지는 않는다. 반면 하이픈·밑줄 뒤의 일반 단어는 같은 조각으로 검사한다.

놓치는 입력과 계속 잡는 입력도 다음처럼 구분된다.

- 계속 잡음: `p + 'Q7mZ2rV9aB4tN8xC6dF3hJ5kL0pR1sW9'`처럼 32자 이상의 영숫자 조각에 숫자·대문자가 함께 있으면 매칭한다. 테스트의 `'Aa1'.repeat(16)`과 프로젝트 접두사 뒤 `'Ab3_Cd4-'.repeat(20)`도 매칭한다. 문자열의 실제 무작위성은 검사하지 않는다.
- 놓침: `p + 'q7mz2rv9ab4tn8xc6df3hj5kl0pr1sw9'`는 대문자가 없고, `p + 'QmZrVaBtNxCdFhJkLpRsWyEuIoPgHaBcD'`는 숫자가 없어 매칭하지 않는다. 접두사 뒤 31자 이하도 놓친다.
- 놓침: `'x' + p + 'Aa1'.repeat(16)`은 x와 s 사이가 단어 경계가 아니므로 매칭하지 않는다. 등록된 키 값의 별도 검색이 이 경우까지 잡는지는 이 diff만으로 검증하지 않았다.
- 위 “놓침”은 **키 모양 탐지의 한계**다. 해당 합성 문자열을 실제 서비스가 발급할 수 있다고 주장하지 않는다. 등록된 실제 값 일치가 주 방어이고 모양 검사가 보조라는 새 주석은 이 한계를 명시한다.

영향: 위 일반 이름이 실행 거부 검사에 들어가면 정규식은 여전히 키 모양으로 판정한다. 실제 CLI의 최종 거부는 **[추측: 호출부를 이 범위에서 읽거나 실행하지 않음]**이다. 권고: 대문자 UUID·대문자와 숫자가 섞인 이름·한글 경계 예를 회귀 사례로 추가하고, 잔여 오탐을 허용할지 PM이 명시한다. 모양만으로 모든 일반 이름과 키를 완전히 분리한다고 설명해서는 안 된다.

## 22f8b4a — 취소 없는 목록 실패의 분류는 유지됨

위치: `22f8b4a:src/engine/apply.ts:307`.

catch에서 추가로 호출하는 `interrupted()`는 사용자 signal이 aborted일 때만 cancelled를 반환한다. 사용자 취소가 없고 마감 signal도 없으며 경과 시간이 한도 미만이면 null이므로, 일반 목록 오류는 기존 `INVENTORY_FAILED_NOTICE`와 `PLAN_STALE`로 진행한다. 따라서 **취소·시간 초과가 없는 진짜 목록 실패를 무조건 cancelled로 바꾸는 결함은 발견하지 않았다.** diff에는 기존 `captureThrows: true` 실패 사례도 남아 있다.

주의할 정확한 범위: 예외 이름·원인은 검사하지 않는다. 실제 접근 오류와 사용자 취소가 함께 발생하면 cancelled가 우선하고, 시간 초과와 함께 발생하면 max_duration이 우선한다. 반대로 AbortError라는 이름만 있고 중단 상태가 없다면 plan_stale다. 이는 현재 코드의 분류 우선순위이며, 취소 없는 실패를 취소로 바꾸는 것과는 다르다. 동시 발생 시 반드시 원래 I/O 오류를 보존해야 한다는 요구는 제공된 diff에 없어 별도 결함으로 세지 않았다.

## abeec2b — 조각 경계를 보존하는 인코딩

위치: `abeec2b:src/contracts/plan.ts:228`, `abeec2b:src/contracts/changes.ts:38`.

`maskedPartsEncoding`은 단순 연결 대신 문자열 배열 전체에 `JSON.stringify(parts)`를 적용하고, 주석은 그 결과의 UTF-8 바이트를 SHA-256으로 계산하도록 정한다. 배열 구분자·문자열 따옴표·이스케이프·빈 원소가 유지된다.

- `["ab", "c"]`와 `["a", "bc"]`는 연결하면 같지만 JSON은 각각 `["ab","c"]`, `["a","bc"]`로 다르다.
- `["a", "", "b"]`와 `["a", "b"]`도 다르다.
- 원소 안의 따옴표·역슬래시·줄바꿈은 JSON 문자열로 이스케이프되어 배열 경계로 오인되지 않는다. 현대 JavaScript의 JSON.stringify는 고립 surrogate도 이스케이프하므로 UTF-8 변환 시 대체 문자로 합쳐지는 문제도 피한다.

**요청한 조각 경계 모호성은 발견하지 않았다.** diff의 테스트도 `["ab"]`와 `["a", "b"]`의 인코딩 후 다이제스트가 다른지 확인하도록 추가되어 있다. 이는 인코딩 모호성이 없다는 판단이며 수학적으로 모든 SHA-256 충돌이 불가능하다는 뜻은 아니다. 실제 저장·표시 호출부가 모두 이 함수와 UTF-8 규칙을 쓰는지는 계약 diff 밖이므로 검사하지 않았다.
