## 3. 중간 — 명령 허용 목록이 비어 있어도, 검증기가 모델이 쓴 코드를 실행하고 그 출력이 모델에 돌아옴

- **위치:**
  - `src/engine/index.ts:543`, `:560-576`. 실패 근거를 재수정 메시지로 모델에 보낸다.
  - `src/verify/index.ts:117-170`. 검증기 명령은 정책 검사를 거치지 않는다.
- **입력(E3):**
  - `policy.commands: []`. 모델은 명령을 하나도 실행할 수 없다.
  - 검증기: `node --test`. `maxRepairAttempts: 1`.
  - 모델이 `write_file`로 `leak.test.mjs`를 새로 만든다. 이 파일은 작업 공간 밖 `../outside-secret.txt`를 읽어 뒤집은 문자열을 오류 메시지로 던진다.
- **결과:**
  - 뒤집은 비밀이 재수정 요청(모델 전송 내용)과 journal에 그대로 들어갔다.
  - 원문 S는 가려져 남지 않았다.
  - 등록하지 않은 파일(예: 사용자 홈의 다른 키 파일)이면 변형 없이 원문 그대로 돌아온다(추측. 등록 비밀이 아닌 파일로는 실험하지 않았다).
- **판단:**
  - 검증기가 모델이 쓴 코드를 실행하는 것은 단계 1부터 있었다. 그 코드가 직접 네트워크를 쓸 수 있다는 점도 OS 격리 없음 한계에 포함된다.
  - 새로 생긴 것은 그 출력이 정책을 거치지 않고 모델에게 돌아가는 상호작용 경로다. 모델이 읽기 결과를 보고 다음 시도를 조정할 수 있다.
  - 실행 허용 목록이 빈 정책이라도 `command` 검증기와 재수정이 있으면, 모델에게 "임의 코드 실행 + 결과 회신"이 주어진다.
  - `protectedPaths`로는 막을 수 없다. 테스트 탐색 패턴에 맞는 새 파일을 아무 곳에나 만들 수 있기 때문이다.
- **해결 방향 예:**
  - 재수정에 넣는 `command` 근거를 끝 몇 줄로 줄이거나, 실패 테스트 이름과 단언 메시지로만 좁힌다.
  - 문서에 "재수정을 켜면 검증기 명령은 모델에게 실행 권한을 주는 것과 같다"고 적고, 검증기 명령을 정책 허용 목록에도 있어야 하는 것으로 묶는다.
- **재현 유닛 테스트 제안:** "명령이 허용되지 않은 정책에서 재수정 메시지가 담는 검증기 출력의 범위". 기대 동작은 PM 결정에 따른다.

## 4. 낮음 — 실행 시간 한도가 마지막 검증기 도중에 끝나면 `needs-input`(종료 코드 3)으로 보고됨

- **위치:** `src/engine/index.ts:535-542`.
  - 검증기 반복이 끝난 뒤 사용자 취소(`signal.aborted`)만 확인한다.
  - 시간 한도(`deadline`)는 확인하지 않는다.
  - 다음 검증기가 남아 있으면 `:502`의 `interrupted()`가 잡지만, 마지막 검증기는 그대로 지나간다.
- **입력(E4):** `maxDurationMs: 3000`, 검증기 `node -e "setTimeout(() => {}, 20000)"`(`timeoutMs` 60000).
- **결과:**
  - 3.3초에 끝났다. 근거는 `cancelled while the command was running`.
  - 상태는 `needs-input`/`verifier_inconclusive`, 종료 코드 3.

  - 다른 검증기가 `fail`이었다면 `failed`/`verifier_failed`로 보고된다(코드 읽기로 추정).
- **안전성:** 재수정으로 이어지지는 않는다. 취소나 한도 소진이 재수정을 부르는 경로는 찾지 못했다.
- **재현 유닛 테스트 제안:** "마지막 검증기 실행 중 시간 한도가 끝나면 budget-exhausted/max_duration".

## 5. 정보 — 검증기가 아주 많으면 재수정 메시지가 8192바이트를 넘음

- **원인:** 몫이 생략 표시(약 30바이트)보다 작아도, 블록마다 생략 표시와 머리글(id, outcome)이 붙는다.
- **결과:** 실패 검증기 400개, 근거 100바이트씩일 때 메시지가 28,440바이트였다(`fuzz-cut.mjs`).
- **판단:** 검증기 수는 사용자 설정이라 위험은 작다. R-4의 상한이 근거 단위인지 메시지 전체인지 문구로 정하면 된다.

## 7. 정보 — 근거가 user 역할 메시지로 들어감 (프롬프트 주입 표면)

- 재수정 메시지는 고정 머리글 뒤에 검증기 근거를 붙인 user 역할 메시지다.
- 테스트 출력에 심은 지시가 모델에게 사용자 지시처럼 보일 수 있다.
- 권한 확대 여부: 재수정 경로는 메시지 하나를 추가할 뿐이다. 정책, 복원 필드, 보호 경로, 한도를 바꾸는 코드는 없다(`repair()` 확인). 그래서 주입으로 도구 권한이 넓어지는 경로는 찾지 못했다.
- 다만 3번처럼 "검증기 명령 자체"가 이미 넓은 권한이다.

## 8. 정보 — `fail`과 `inconclusive`가 섞이면 `failed`/`verifier_failed`

- **위치:** `src/engine/index.ts:542`.
- R-1 본문은 "`inconclusive`는 재수정하지 않고 `needs-input`"이라고 적었다. 섞인 경우는 `failed`로 끝내며 유닛 테스트도 그렇게 정했다.

- 관련: `maxSameFailures: 1`이면 첫 실패가 반복이 아닌데도 이유가 `repeated_failure`로 남는다. 계약 주석이 이를 명시하고 있다.

## 문제 없던 범위 (실험이나 코드로 확인)

- **`cutMiddle` 절단 (3000건 퍼즈, `fuzz-cut.mjs`):**
  - 입력 조합: 토큰, 한글, 이모지, CRLF, 긴 문자열. 상한 40~3040바이트.
  - 결과: 상한 초과 0건, 토큰 중간 절단 0건(잘린 `CODARYN_SECRET` 조각 없음), 짝 없는 서로게이트 0건.
  - 완성 메시지도 다시 `mask`를 거친다(`index.ts:565`).
- **한도 합산:** 턴, 도구 호출, 토큰, 시간이 반복 전체에 한 번만 누적된다(`modelTurns`, `toolCalls`, `inputTokens`/`outputTokens`, `startedAt`과 `deadline`).
  - `repair()` 앞에서 `budgetStop()`을 확인한다.
  - 같은 호출 id 재사용은 실행되지 않으므로 도구 호출 한도를 우회하지 않는다.
- **상태 전이:** 반복 경로의 전이는 모두 `RUN_TRANSITIONS`에 있다.
  - `verifying → running`
  - `verifying → budget-exhausted`, `cancelled`, `failed`, `needs-input`, `done`
  - `created → running → …`
- **`repair_started` 기록:** 재수정 메시지를 대화에 넣는 유일한 경로(`repair()`)에서, 가림이 성공한 뒤 메시지 추가 전에 항상 기록한다. 가림이 실패하면 기록도 전송도 없이 `failed`/`model_error`다.
- **취소와 재수정:** 검증 도중이나 직후의 사용자 취소는 `cancelled`다. 재수정 직전 `budgetStop()`도 취소와 시간 한도를 확인한다. `inconclusive`만 있으면 `needs-input`이다.
- **`maxRepairAttempts: 0`:** 첫 실패에서 `failed`/`verifier_failed`다(R-2). 횟수 소진이 반복 감지보다 우선한다.

## 검사하지 않은 범위

- 실제 Anthropic API. 가짜 서버(`fake-anthropic`)를 쓰는 재수정 통합 경로도 직접 돌리지 않았다. 통합 테스트 `r01` 등은 실행하지 않았다.
- node 외 검증기 도구(pytest, cargo 등)의 출력이 서명에 주는 영향(1번의 일반화는 추측).
- 명령 실행기의 65536바이트 상한 절단이 현재 main에서 가리기 전인지 여부(2번의 관련 항목, 추측).
- 스냅샷, 되돌리기(`src/store`), 보호 경로 정책(`src/policy`). F6의 다른 대상이다.
- 유닛·통합 테스트는 실행하지 않았다. 코드 변경이 없어서다.
