## 2. 낮음

### L-1 키의 부분 메아리에서 끝 4자가 오류 문구에 남는다

- 위치: `src/model/http/index.ts`의 `createRedactor`. 전체 키, 키의 연속 8자 조각(`KEY_FRAGMENT_CHARS`), 키 모양만 지운다.
- 재현(2절): 401 본문의 `message`가 "키 앞 12자 + 별표 30개 + 키 끝 4자" 형태일 때 결과는 `HTTP 401: Incorrect API key provided: [redacted]******************************<끝 4자>.`이다.
  - 앞 12자는 8자 조각으로 지워진다.
  - 끝 4자는 8자보다 짧아 남는다.
  - 키 모양 가짜 키로 해도 같다.
- 결과: 이 문구는 실행 기록의 `model_error`와 stderr로 간다. 키의 끝 4자가 기록에 남는다.
- [추정] 실제 OpenAI 401 문구가 이런 부분 메아리 형식인지는 사실 확인 문서에 없다(C-5는 본문 구조만 확인).
- 권고(둘 중 하나)
  - 별표 줄(`*` 4개 이상) 앞뒤의 영숫자 덩어리를 함께 지운다.
  - 401·403의 `message`는 인용하지 않고 고정 문구만 쓴다.

### L-2 본문이 4096바이트를 넘는 할당량 429는 재시도된다

- 위치: `src/model/openai/index.ts`의 `classifyStatus` → `errorObject`. 본문이 오류 본문 상한(`MAX_ERROR_BODY_BYTES` 4096)을 넘으면 읽지 않고 `null`이다.
- 재현(3절): `error.type`이 `insufficient_quota`이고 `message`가 길어 본문이 4096 B를 넘으면, `rate_limited`로 4회 시도한다(500·1000·2000 ms 대기).
- 결과: 할당량이 다 된 계정에 요청이 3번 더 간다. 기록의 종류도 `quota_exhausted`가 아니라 `rate_limited`라 안내가 틀린다(DR-31 (f)).
- 권고: 상한을 넘은 본문도 앞부분에서 `type`·`code`를 찾거나, 429는 분류용으로 조금 더 큰 상한을 둔다.

### L-3 원래 `call_id`가 실행 기록에 남는다(PM 기대와 DR-31 (e) 문구 대조 필요)

- 재현(엔진 실행 7절): 제공자가 준 `call_id`(형식이 맞는 `call_…` 꼴) 세 개가 모두 journal에 그대로 있다(`model_request`, `model_response`, `tool_decision`, `tool_result`). 결과 객체에는 없다.
- 원인: 어댑터가 `call_id`를 `ToolCall.id`로 엔진에 넘기고, 엔진은 AC-D15에 맞는 id(`[A-Za-z0-9_-]{1,64}`, 비밀 없음)를 바꾸지 않는다.
- DR-31 (e)는 "기록에는 AC-D15 규칙대로 안전한 id를 남기되 원래 `call_id`는 실행 중 메모리의 대응으로 유지한다"다. 지금 동작은 이 문구와 맞는다. 지시문 중점 (2)의 "원래 `call_id`가 기록에 남지 않는다"와는 다르다.
- 영향: `call_id`는 제공자가 정한 무작위 식별자라 그 자체로 민감하지는 않다. `store: false`라 제공자 쪽 대응 기록도 남지 않는다. [추정]
- 권고(PM 판단)
  - 기록에 원래 id를 남겨도 된다면 지금대로 두고 문서에 적는다.
  - 남기지 않아야 한다면 openai 제공자의 id는 늘 `codaryn-call-<n>`으로 바꿔 기록한다. 어댑터의 `echoes`가 이미 바뀐 id를 받아들인다.

### L-4 되돌려 보낼 출력 항목의 크기 상한이 없다

- 위치: `src/model/openai/index.ts`의 `kept`(실행 동안 모든 응답의 `output` 항목)와 `buildBody`(매 요청에 모두 다시 넣음). 요청 본문 크기 상한이 없다.
- 재현(5절): 7 MiB `encrypted_content`의 추론 항목 하나를 받아들이고 보관한다. 이후 모든 요청이 그것을 다시 보낸다.
- 결과: 응답 하나는 8 MiB 상한이 있지만 누적에는 상한이 없다.
  - 턴이 많으면(`maxModelTurns` 상한 1000, `src/cli/security/limits.ts:17`) 메모리와 요청 크기가 커진다.
  - 결국 제공자가 413으로 거부하거나 프로세스 메모리가 부족해진다.
  - 사용자가 정한 주소(프록시)가 큰 항목을 보내는 경우도 같다. 가용성 문제이고 유출은 아니다.
- 권고: 보관 항목의 총 바이트(또는 요청 본문)에 상한을 두고, 넘으면 `api_error`로 끝낸다. 예외 없이 고정 문구로 끝낸다.
