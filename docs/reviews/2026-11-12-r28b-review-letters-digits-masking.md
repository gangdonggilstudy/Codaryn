## 1. 남는 글자 수 (실제 CLI, `exp/e2e28b.mjs`)

칸은 키/비밀의 남은 글자 수다(구분 문자를 빼고 본 연속 6자 기준, 키 106자·비밀 40자).

| 경우 | main 요청 / journal | 브랜치 요청 / journal / 결과 / stdout / stderr |
|---|---|---|
| goal의 비밀을 끊음 (8종) | 0/40 / 0/40 | **0/0 모두** |
| `read_file` 결과의 키와 비밀을 끊음 (8종) | 106/40 / 106/40 | **0/0 모두** |
| task 파일 goal, 짝 없는 대리 문자(JSON 이스케이프 `\ud800`) | 0/40 / 0/40 | **0/0 모두** |
| 읽은 뒤 다른 줄만 고친 `write_file`(U+FE0F, 한글 채움 문자) | 106/40 / 106/40 | **0/0 모두**. 파일은 바이트 단위로 원본에서 그 한 곳만 바뀜 |

- 끊은 문자 8종: 이체 선택자 U+FE0F, U+E0100(BMP 밖), 결합 자소 연결자 U+034F, 한글 채움 문자 U+3164, 점자 빈칸 U+2800, 가운뎃점, 마침표, 소스 코드의 이어 붙이기 `" + "`.
- 스냅숏(되돌리기용 원본)은 두 판 모두 원래 바이트를 갖는다. 설계상 그렇다.

## 2. 복원·다시 쓰기와 문자 경계 (`exp/gateway28b.mjs`)

다섯 경우를 따로 확인했다. 모두 토큰 하나, 결과에 짝 없는 대리 문자 없음, `rebuildDocument`·`resolveToolArgs`가 원래 바이트 그대로였다.
- U+FE0F로 끊고 뒤에 결합 악센트를 붙인 키
- 이모지 ZWJ 묶음(👩‍💻)으로 끊은 비밀
- U+E0100과 한글 채움 문자로 끊은 비밀
- 한글과 마침표로 끊은 키
- 앞뒤에 이모지

**퍼징**: 무작위 글 4,000개, 끊는 문자 13종, 둘레에 이모지·결합 문자·한글을 두었다.
- 두 번 가려도 같음, 가린 글을 다시 가려도 같음
- 다시 쓰기 정확, 남은 글자 0, 결과에 짝 없는 대리 문자 0

**범위의 끝**: 범위의 두 끝은 늘 ASCII 글자·숫자다(`skeletonView`가 그 단위만 남긴다). 그래서 대리 문자 쌍은 범위 안에 통째로 들어가거나 밖에 남고, 쪼개지지 않는다.

### I-2 (정보) 키 바로 뒤의 결합 문자는 토큰 밖에 남는다

- 키 뒤에 U+0301이 붙어 있으면 가린 글은 `<토큰>` 다음에 U+0301이 온다. 결합 문자열이 토큰의 끝 `]`에 붙는다.
- 정확한 일치만 하는 main도 같다. 바이트는 정확히 돌아오므로 고칠 일은 아니다.

## 3. 과한 가림: 한 토큰의 범위

### L-1 (낮음) 한 토큰이 가리는 범위에 상한이 없다

**재현**
- 실제 CLI(`exp/e2e28b.mjs` L): 파일 맨 앞에 키의 앞 40자, 한글 5,000자 뒤에 나머지를 두었다.
  - 브랜치에서 모델이 받은 파일 내용은 **40자, 한글 4,667자 중 0자**다. 줄은 5줄에서 3줄이 되었다.
  - main은 5,113자를 모두 보였다(키도 그대로).
- 게이트웨이: 값의 두 반쪽 사이에 무엇을 두었는지별로, 브랜치에서 모델에게 남는 글자 수.

  | 사이에 둔 것 | 실제 형식 키 | `Summer2026Winter` | main(가리지 않음) |
  |---|---|---|---|
  | 한글 5,000자 | 4자 | 4자 | 다 남음 |
  | 이모지 2,000개 | 4자 | 4자 | 다 남음 |
  | 표 구분선 3,000자 | 4자 | 4자 | 다 남음 |
  | 줄바꿈 10,000개 | 4자 | 4자 | 다 남음 |

  - `Summer2026Winter`는 커밋이 "키 같은 값"으로 받아들인, 단어로 된 값이다.

**원인**
- `skeletonView`는 ASCII 글자·숫자 밖의 모든 것을 건너뛴다. 그리고 찾은 값의 첫 글자부터 끝 글자까지 원래 범위를 한 토큰으로 가린다.
- 그래서 조각 사이에 ASCII 글자·숫자가 하나도 없는 글은 길이와 상관없이 토큰 안에 든다. 해당하는 글: 한글·한자 문장, 이모지, 문장부호만의 줄, 빈 줄.
- 사이에 ASCII 숫자 하나만 있어도 끊긴다. 위쪽 행사 안내문은 "7월"의 숫자 때문에 가려지지 않았다.
- R-28의 구분 문자 단계(`ea1c15a`)도 공백·줄바꿈에 대해 같은 무상한이다(줄바꿈 10,000개). 다만 그때는 사이가 빈칸뿐이라 내용이 사라지지 않았다.

**영향**
- 기밀성은 안전한 쪽이다. 남는 키 글자는 0이다.
- 대신 모델이 그 사이의 내용을 보지 못한다. 줄들이 한 보호 줄로 합쳐져 고칠 수도 없다.
- 일어나려면 등록 값의 앞 조각이 어떤 ASCII 낱말의 끝에, 뒤 조각이 뒤의 어떤 ASCII 낱말의 처음에 있고, 그 사이에는 ASCII 글자·숫자가 없어야 한다.
  - 무작위 키는 실제로 그렇게 끊어 둔 때뿐이다.
  - 단어로 된 "키 같은 값"(커밋이 받아들인 대소문자·숫자 섞인 낱말)은 한글 문서에서 우연히 맞을 수 있다.
- 그래서 낮음으로 둔다.

**제안** (가림 담당 w3:p5). 후보를 실험으로 확인했다(`exp/gap-candidate.mjs`).
- 맞은 값 안에서 이웃한 두 글자 사이가 8단위(UTF-16)를 넘으면, 그곳에서 범위를 나눠 조각마다 따로 가린다.
- 한 토큰으로 남는 짧은 끊김(7단위 이하): R-25b의 문자들, `" + "`, 이모지 ZWJ 묶음, `한글.한글`, 줄바꿈과 `"  + "`
- 나뉘는 긴 끊김: 한글 5,000자, 이모지 2,000개. 이때 키 106자는 모두 가려지고 사이의 글은 보인다.
- 구분 문자 단계에도 같은 규칙을 두면, 줄바꿈이 많을 때 줄 구조도 남는다.

## 4. "키 같은 값" 조건

- 실제 형식 키는 모두 해당한다. 형식마다 10,000개를 만들어 확인했다.
  - 키 자신과 변형 형식 5종(Base64, base64url, URL 인코딩, hex 소문자·대문자, 형식마다 50,000개) 모두 빠짐 0이다.
  - Anthropic: `api03-`, `admin01-`, `oat01-`
  - OpenAI: `sk-`+`proj-`, `sk-`+`svcacct-`, `sk-`+`admin-`, 옛 형식

### I-1 (정보) 다른 제공자의 짧은 단일 대소문자 토큰은 "키 같은 값"이 아니다

| 값의 모양 | 키 같은 값인가 |
|---|---|
| AWS 액세스 키 id(20자, 대문자와 숫자) | 아님 |
| 소문자 hex 24자, 31자 | 아님 |
| 소문자 hex 32자 | 맞음 |
| GitHub 토큰 | 맞음 |
| 대소문자·숫자 16자 | 맞음 |

- `secretEnv`나 변수 파일로 등록한 이런 값이 구분 문자가 아닌 문자(가운뎃점, `" + "` 등)로 끊기면 가려지지 않는다. 구분 문자로 끊긴 것은 R-28 단계가 가린다.
- 단어로 된 값을 빼려는 커밋의 선택과 맞바꾼 것이라 정보로 둔다. 필요하면 "20자 이상, 숫자와 대문자만"을 더하는 것을 검토할 수 있다.

| 글 | 256 KiB | 1 MiB |

| 평문, 값 32개 | 4 / 18 | 14 / 74 |

- 크기에 비례하고 제곱으로 늘지 않는다.
- 이미 발급된 토큰이 많은 글의 재가림 비용(R-28 I-4)은 이번 변경과 관계가 없다.

## 6. 끊기지 않은 값

- 고정 난수원으로 브랜치와 main을 비교했다. 무작위 글 3,000개 모두 가린 글이 같았다.
- 글에는 정확한 값과 변형 형식(Base64, URL 인코딩, hex)이 섞였고, 둘레에 낱말·문장부호·한글·이모지·괄호·따옴표를 두었다.
