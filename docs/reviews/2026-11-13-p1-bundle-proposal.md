## 3. 묶음 A — 개인정보 자료

### 3.1 `query_table`과 표 스트리밍

**무엇을 하는 기능인가.**
`query_table`은 모델이 부르는 읽기 전용 도구다. 작업 공간의 표(CSV, TSV, JSON Lines)를 Codaryn이 로컬에서 읽고 집계해서, 집계 결과만 모델에 돌려준다. 모델은 행을 보지 않고 "지역별 금액 합계" 같은 수를 받는다.
- 쓰는 이유는 셋이다. 256 KiB를 넘는 표를 다룰 수 있다. 원자료 행이 모델로 가지 않는다. 모델이 직접 계산하지 않는다.
- 표 해석과 집계는 `data_checks`와 같은 순수 모듈 `src/tabular`를 쓴다. 큰 표를 위해 그 모듈을 조각 단위로 읽게(스트리밍) 바꾼다.

**설계가 이미 정한 것.**
- [정함] 읽기 전용이고, 집계 결과만 돌려준다(general-tasks 5.2, GT-D8 (b)).
- [정함] 큰 표를 위해 256 KiB 읽기 상한은 올리지 않고 이 도구로만 다룬다(GT-D11).
- [정함] `src/tabular`를 도구와 `data_checks`가 함께 쓴다. 그래서 검증기는 "보고한 수가 계산과 맞는가"만 확인하고, 계산 자체의 정확성은 `src/tabular` 유닛 시험이 맡는다. 이 한계를 검증 결과의 한계 목록에 적는다(5.2).
- [정함] 새 의존성은 없다. CSV는 직접 해석한다(11절).
- [사실] 표 형식, 수의 꼴, 연산 다섯은 이미 계약에 있다(`src/contracts/verify.ts` `TABLE_FORMATS`, `AGGREGATE_OPS`).
- [사실] 지금 `parseTable`은 표 전체를 글 하나로 받는다(`src/tabular/table.ts`). 스트리밍은 없다. `data_checks`의 상한은 16 MiB다(`MAX_DATA_TABLE_BYTES`).
- [사실] 도구 이름은 계약의 `WORKFLOW_TOOL_NAMES`에 더하면 된다(지금 `inspect_files`, `propose_plan`). 작업 종류 도구는 그 도구를 고른 실행에만 제시된다. 그래서 기존 실행의 모델 요청은 바뀌지 않는다.

**비워 둔 값.**
- [빈 값] 입력 상한("예: 64 MiB"), 그룹 최소 크기(13절), 연산·묶음·걸러내기의 범위, 돌려주는 묶음 수.

**권고 값과 근거.**
- **Q-1(사용자) 모델로 가도 되는 것**은 넷이다:
  1. 열 이름(머리 행). 가릴 값으로 등록한 것은 가린다.
  2. k행 이상이 함께 가진 묶음 키 값. 예: 지역 이름. 묶음 키는 칸 값이므로 사용자 확인이 필요하다.
  3. 묶음의 행 수.
  4. 집계 수.
  - 근거: DR-23은 "행"을 막는다. 열 이름과 큰 묶음의 키·수는 행이 아니다. 그러나 묶음 키가 칸 값이라는 점은 사용자가 알고 정해야 한다.
- **Q-2 연산:** 읽기 제외 표에서는 count, sum, mean만 받는다.
  - min과 max는 묶음이 아무리 커도 어떤 한 사람의 값 그 자체다(예: 최고 연봉).
  - 일반 표(읽기 제외 밖)는 `read_file`로도 읽히므로 다섯 다 받는다.
- **Q-3 묶음:** `groupBy`는 0~2열이다. 걸러내기는 P1에 두지 않는다.
  - 걸러내기는 조건을 좁혀 한 사람을 고르는 가장 쉬운 길이다(예: "나이=37 그리고 동=○○"의 count).
  - 묶음 2열이면 지역×성별 같은 흔한 교차표가 된다. 3열부터는 칸이 작아져 대부분 숨겨진다.
- **Q-4 k:** 기본 5다.
  - 통계 공개 제한에서 흔히 쓰는 문턱(3~10) 가운데 중간이다. 작은 표에서도 쓸모가 남는다.
  - 사용자 설정에서 2~1,000으로 바꿀 수 있다. task·정의·프로필은 올리기만 한다.
  - 읽기 제외 밖 표는 1이다(숨길 이유가 없다).
  - k 미만인 묶음은 키도 수도 주지 않는다. 숨긴 묶음의 **개수**만 준다(`suppressedGroups`). 숨긴 행 수는 주지 않는다. 전체 수에서 빼면 숨긴 묶음의 크기가 나오기 때문이다.
- **Q-5 상한:**
  - 표 64 MiB. 설계의 예시 값이다. 조각 단위로 읽으면 메모리는 묶음 수에만 든다.
  - 세는 묶음 10,000개. 넘으면 `too_many_groups` 오류다. 키가 거의 다 다른 열(이름, 번호)로 묶으면 여기에 걸린다. 그런 묶음은 어차피 k에 숨겨진다.
  - 한 번에 돌려주는 묶음 200개. `after`로 이어 읽는다(`inspect_files`와 같은 방식).
  - 한 번에 연산 8개.
  - 시간은 재지 않았다. 구현 단위에서 64 MiB 표 하나를 재고 PM이 조정한다.
- **Q-6 `describe`:** 열 이름, 데이터 행 수, 열마다 비어 있지 않은 칸 수와 수로 읽히는 칸 수를 준다.
  - 모델이 열을 모르면 질의를 짤 수 없다.
  - 읽기 제외 표에서 행 수가 k 미만이면 행 수와 칸 수를 숨긴다.
- **Q-7:** `data_checks`도 같은 스트리밍 코드로 바꾸고 상한을 64 MiB로 맞춘다. 같은 코드를 쓴다는 설계(5.2)를 지키려면 상한도 같아야 한다. 값은 시간을 잰 뒤 정한다.
- **Q-8 차감 공격:** 따로 질의 예산을 두지 않고 한계로 적는다.
  - "전체 합 − 보인 묶음 합"이나 묶음 조합을 바꿔 가며 묻기로 숨긴 묶음을 알아낼 수 있다.
  - 예산이 2 이상이면 이 공격은 그대로 된다. 예산은 지켜 준다는 착각만 준다.
  - 막으려면 차등 개인정보 보호(잡음)가 필요하다. 그것은 P1 범위 밖이다.
  - 그래서 보장은 "행을 보내지 않는다"이고, k는 실수로 작은 묶음이 드러나는 것을 줄이는 완화책이라고 적는다.
- **Q-9:** 수는 반올림하지 않는다. `data_checks`가 허용 오차로 비교하므로 같은 수가 필요하다. 반올림으로 얻는 보호는 Q-8의 차감 앞에서 작다.

**보안·개인정보에서 조심할 점.**
- **오류 결과가 칸 값을 실으면 안 된다.**
  - 지금 `TableProblem`은 코드와 행·줄 번호만 준다(좋다).
  - 그러나 JSON Lines를 해석할 때 Node의 `JSON.parse` 예외 메시지는 입력 조각을 담는다. 예외 메시지를 그대로 결과에 넣지 않는다는 것을 시험으로 지킨다.
- 수가 아닌 칸은 개수만 센다. 그 칸의 글은 주지 않는다.
- 묶음 키와 열 이름도 가림(등록 값)을 거친다. 모든 결과는 지금처럼 `privacy.mask`를 거쳐 기록되고 모델로 간다.
- 열 이름이 칸 값처럼 생긴 표가 있다(사람마다 열이 하나인 교차표). 열 이름은 Q-1에서 보낸다고 정하는 것이므로, 사용 문서에 이 경우를 적는다.
- 같은 표를 `read_file`로 읽을 수 있으면 보장이 없다. 그래서 읽기 제외(3.2)와 한 묶음이다.

**보장을 어떻게 시험하나("원자료 행은 모델로 가지 않는다").**
1. **카나리 표.**
   - 합성 표를 만든다. 개인 열(이름·연락처 자리)의 칸마다 그 행에만 있는 카나리 값을 넣는다. 실행 때 무작위 조각으로 만들고, 고정 값을 소스에 적지 않는다.
   - 묶음 열에는 6행, 5행, 4행이 함께 가진 키 A, B, C를 둔다. k=5의 경계다.
2. **모든 길을 부른다.** 대본 모델이 다음을 부른다.
   - 읽기 제외 경로에 `read_file`.
   - `search_files`: `text`에 카나리, `nameContains`.
   - 읽기 제외 경로에 `inspect_files`.
   - 읽기 제외 경로에 `write_file`.
   - `query_table`: 모든 연산 × 모든 열 × 열마다 `groupBy`.
   - `query_table`의 오류 길: 없는 열, 수가 아닌 열, 깨진 표(따옴표, JSON), 상한 넘는 표, 이어 읽기, 잘못된 인자.
3. **모델로 간 것을 모두 모은다.**
   - 대본 모델이 받은 `ModelRequest` 전체.
   - 모의 HTTP 서버가 받은 요청 본문(Anthropic과 OpenAI 둘 다, `[모의 API·실제 API 아님]`).
   - 함께 볼 것: 재수정 때 가는 검증 근거, journal, result.json, 진행 줄.
4. **단언.**
   - 한 행에만 있는 카나리는 어디에도 없다.
   - 키 C(4행)는 없다.
   - 키 A, B는 **있다**. 이것은 양성 대조다. 검사가 실제로 글을 보고 있다는 증거다.
   - 결과의 모든 묶음 개수는 5 이상이다.
5. **변이 시험.** 빌드한 `dist`만 고쳐 다음을 넣고, 각각 시험이 실패하는지 본다. 앱 계층 U-90·U-91이 한 방식이다.
   - k 검사 없앰.
   - 읽기 제외 판정 없앰.
   - 목록 거르기 없앰.
   - 근거 숨김 없앰.
   - 예외 메시지 전달.
6. **유닛 속성 시험.** 시드를 고정한 무작위 표 수백 개에서 `query_table` 결과의 모든 문자열이 (열 이름 ∪ k행 이상 키 ∪ 고정 낱말) 안에 있는지 본다.
7. **계약 시험.** 결과 형식에 자유 문자열 필드가 열 이름과 묶음 키 말고는 없는지 본다(형식 표로 고정).
- 카나리는 `[A-Za-z0-9]`와 한글로 만든다. JSON 이스케이프로 모양이 바뀌는 문자는 쓰지 않는다. 요청 본문은 해석한 뒤의 값으로도 찾는다.

**바뀌는 계약·고정 시험.**
- 계약(`src/contracts`):
  - `tool.ts`: `WORKFLOW_TOOL_NAMES`에 `query_table`, 인자·결과 형식, 상한 상수, 도구 정의(고정 설명 글), 도구 오류 코드 둘(`too_many_groups`, `table_too_large`. 또는 기존 `too_large` 재사용, PM).
  - `verify.ts`: `MAX_DATA_TABLE_BYTES`(Q-7).
  - k의 기본값과 범위 상수.
- 따라오는 것(형 검사가 깨지는 곳):
  - `src/engine/validate-args.ts`, `src/tools`의 작업 종류 도구 실행표: `WorkflowToolName`을 남김없이 나눠 처리한다.
  - 문구 카탈로그(새 도구 오류 코드, U-50의 `TOOL_FAILURE_HINTS` 표).
- 고정 시험:
  - **바뀌지 않아야 함:** `sp0-golden`·`sp0-expected`(Anthropic 어댑터. 기존 장면에는 새 도구가 없다), `g-legacy-interpretation`, 통합 고정 출력.
  - **바뀜:** `tool-definitions.test.ts`, `g-tool-contracts`의 목록, 카탈로그 시험. 새 문구 id가 생기면 `real-catalog`도 바뀔 수 있으므로 먼저 보고한다.

**어림 줄 수.**
- 계약 약 250.
- 표 스트리밍(파서·집계를 조각 단위로, 묶음 상한) 약 900. 코드 450, 시험 450.
- `query_table` 도구 약 800. 코드 350, 시험 450.

### 3.2 읽기 제외 경로(`unreadablePaths`)

**무엇을 하는 기능인가.**
사람이 정한 경로 아래의 파일을 모델이 읽거나 보지 못하게 한다. `read_file`과 `search_files`는 그 경로를 거부하거나 목록에서 빼고, `query_table`만 그 경로의 표를 집계한다. 지금의 `protectedPaths`는 쓰기만 막는다(privacy.md 23행 "설계만").

**설계가 이미 정한 것.**
- [정함] `read_file`·`search_files`는 거부하고 `query_table`만 집계한다(general-tasks 5.2).
- [정함] 이름은 계약 주석의 `unreadablePaths`다(`src/contracts/workflow.ts:19`).
- [사실] 정책 관문은 도구 설명자의 경로 필드마다 접근(`read`, `write`, `cwd`)을 보고 판정한다. 보호 경로는 글자 판정(`covers`)과 실경로 판정(`coversEffective`) 두 단계다(`src/policy/index.ts:177-212`, `src/policy/protected.ts`).
- [사실] **task 파일로 실행하면 task 파일의 정책이 설정 파일의 정책을 대신한다**(`src/cli/run.ts:686`, `givenPolicy = taskFile !== null ? parsed.policy : config?.policy`). 작업 종류 정의가 있을 때만 정의와 합친다(`mergeWorkflowPolicy`). 그래서 지금 방식이면 설정에 둔 읽기 제외가 task 파일 실행에서 빠진다.
- [사실] `search_files`는 디렉터리를 재귀로 훑고, `text`가 있으면 맞는 **줄의 글**을 돌려준다(`src/contracts/tool.ts:72-90`). 관문은 시작 경로 하나만 판정한다.
- [사실] `inspect_files`는 크기, 시각, 해시를 준다. 해시는 짧은 값을 추측해 맞혀 보는 데 쓰일 수 있다(R-1 L-6).

**비워 둔 값.**
- [빈 값] 형식, 어느 단계에서 오는지, 이름 숨김, 명령과의 관계, 검증기 근거.

**권고 값과 근거.**
- **R-1:** `protectedPaths`와 같은 형식 규칙과 같은 판정을 쓴다(`checkProtectedPaths`와 `compileProtectedPaths` 재사용). 사람이 한 가지 규칙만 배우면 된다. 링크로 우회하는 것도 같은 방식으로 막힌다.
- **R-2:** 설정·프로필·정의·task 모두 더할 수 있고, 어느 단계도 빼지 못한다(합집합).
  - **설정 파일의 읽기 제외는 task 파일 정책이 있어도 늘 합친다.** 지금의 "task 파일 정책이 설정을 대신한다" 규칙의 예외다.
  - 근거: 읽기 제외는 좁히기만 하므로 어디서 와도 안전하다. 사람이 설정에 둔 개인정보 폴더가 task 파일 하나로 빠지면 보장이 깨진다(M-9).
- **R-3:**
  - `read_file`은 거부한다(`unreadable_path`).
  - `search_files`는 시작 경로가 그 아래면 거부한다. 위면 그 아래 항목을 이름째 결과에서 뺀다(`truncated`처럼 "뺀 것이 있음" 표시만).
  - `inspect_files`도 같다.
  - `write_file`은 거부한다. 읽기 제외는 보호 경로를 겸한다. 입력 자료를 모델이 바꿀 이유가 없고, 덮어쓰기 오류(`conflict`)의 해시도 말하지 않게 된다.
  - 무결성 확인(`protectedPaths`와 같은 사후 탐지) 대상에 넣는다.
  - `query_table`의 설명자는 새 경로 접근 `aggregate`를 쓴다. 관문은 이 접근만 읽기 제외 아래에서 허용한다. 도구 이름으로 나누지 않는다(E5와 같은 원칙).
- **R-4 이름도 숨긴다.**
  - 사람마다 파일이 하나인 폴더는 파일 이름이 곧 개인정보다(예: 이름이 든 파일).
  - 표의 경로는 사람이 목표나 task에 적는다(목표는 원래 모델로 간다).
- **R-5 명령 금지.** 읽기 제외가 하나라도 있으면 명령 규칙도 `command` 검증기도 둘 수 없다(해석 단계 문제 `commands_not_allowed`와 새 문제 하나).
  - 명령 인자의 경로는 검사하지 않는다(general-tasks 2.3). 그래서 명령 하나로 읽기 제외가 무너진다.
  - `command` 검증기의 출력은 재수정 때 모델로 간다(privacy.md 5절).
- **R-6:** 원본이 읽기 제외 표인 `aggregate_match`는 근거에 다시 계산한 수를 넣지 않는다. "행 N, 열 X가 맞지 않음"만 적는다.
  - 지금 근거는 "비교한 두 수"를 담는다(`src/contracts/verify.ts` 주석).
  - 모델이 k 미만 묶음을 지어내 쓰면, 검증기가 그 묶음의 참값을 계산해 재수정 근거로 모델에 돌려준다. k를 우회하는 길이다.
- **R-7:** 설정에서 읽기 제외 항목을 빼거나 k를 낮추는 것은 넓히기다. GUI의 설정 변경 확인(U-107, `src/app/settings-change.ts:154` `wideningOf`)에 두 종류를 더한다.
- **R-8:** 새 거부 코드 `unreadable_path`(권한 `path`)를 둔다. `protected_path`와 나누어야 사람이 "쓰기 금지"와 "읽기 금지"를 구분한다. `REFUSAL_HINTS`와 두 언어 문구가 따라온다.

**보안·개인정보에서 조심할 점.**
- 판정은 실경로까지 본다. 작업 공간 안의 링크나 정션이 읽기 제외 아래를 가리키면 그 링크로 읽는 것도 막는다. 보호 경로의 `coversEffective`와 같다.
- `search_files`가 루트에서 시작하면 관문 판정을 통과한다. 그래서 거르기는 도구 실행기 안에서 해야 한다. 이것이 빠지면 `text` 검색 한 번으로 칸 값이 줄째 나간다. 카나리 시험이 반드시 이 길을 부른다.
- 읽기 제외 아래가 비어 있거나 없는 경로여도 오류로 막지 않는다. "없는 경로"가 오히려 정보가 되지 않게 판정을 같게 한다.
- 로컬(사람)에게 보이는 것은 막지 않는다. 예: GUI 작업 공간 트리, `changes`, journal. 막는 대상은 모델로 가는 것이다.

**바뀌는 계약·고정 시험.**
- `task.ts`: `PolicyConfig.unreadablePaths?`(`ConfirmablePolicyConfig`도 같다).
- `config.ts`: 설정과 프로필 정책.
- `workflow.ts`:
  - `mergeWorkflowPolicy`가 합집합을 만든다.
  - 새 `WORKFLOW_PROBLEMS` 하나(읽기 제외와 명령의 충돌).
- `policy.ts`: `unreadable_path`.
- `tool.ts`: `PathAccess`에 `aggregate`.
- 따라오는 것:
  - CLI의 task·설정 형식 검사, 설정 읽기 제외를 늘 합치는 곳(`src/cli/run.ts`), doctor의 정책 요약.
  - 문구, 앱 계층 설정 넓히기, cli-contract와 privacy.md.
- 고정 시험:
  - 바뀌지 않아야 함: 읽기 제외가 없는 실행 전부.
  - 바뀜: 거부 코드 목록 시험, 카탈로그 시험. doctor가 새 줄을 내면 doctor 고정 출력도 바뀌므로 보고를 먼저 한다.

**어림 줄 수.**
- 관문 판정(글자·실경로, `aggregate` 예외) 약 350.
- 도구의 목록 거르기(`search_files`, `inspect_files`) 약 350.
- 무결성 대상 약 50.

### 3.3 `analyze-private`

**무엇을 하는 기능인가.**
개인정보가 든 표를 분석하는 내장 작업 종류다. 원자료는 읽기 제외 경로에 두고, 모델은 `query_table`로 받은 집계만으로 결과 표와 보고서를 쓴다. 끝은 사람 확인이다. DR-23 아래에서 개인정보 자료를 다루는 유일한 정의가 된다.

**설계가 이미 정한 것.**
- [정함] 개인정보 자료는 `query_table`과 읽기 제외를 함께 쓰는 `analyze-private`로만 다룬다(GT-D8 (b), DR-23).
- [정함] 자료 분석은 사람 확인이 기본이다(GT-D7, DR-23).
- [사실] 내장 정의는 데이터 상수다(`src/workflows/index.ts`). id 목록은 계약의 `BUILTIN_WORKFLOW_IDS`다. 해석기는 상한(도구는 줄이기만, 명령 금지 등)을 지킨다.

**권고 값과 근거.**
- **P-1 정의:**
  - 도구: `read_file`, `search_files`, `query_table`, `write_file`. 읽기 도구를 빼지 않는 이유는 지시 문서나 결과 파일처럼 읽기 제외 밖의 파일은 읽어도 되기 때문이다. 읽기 제외 아래는 3.2가 막는다.
  - `allowCommands: false`(R-5와 같은 이유).
  - `completion: "human_review"`.
  - **해석 조건:** 실효 정책의 `unreadablePaths`가 비면 해석에서 거부한다(새 문제 `unreadable_paths_required`). 비어 있으면 "개인정보 모드"라는 이름이 거짓이 된다.
  - 지시문 초안: "The input tables are not readable. Use query_table for every number. Write only the result table and the report the goal names. Do not write values that identify a person."
- **P-2:** `analyze`에도 `query_table`을 준다. 큰 표를 다룰 수 있게 된다. k는 읽기 제외 표에만 적용하므로 일반 분석의 쓸모는 그대로다.
- **P-3 사람 확인 목록:** `analyze`의 둘에 "결과 표와 보고서에 한 사람을 알아볼 수 있는 값이 없다"를 더한다. 모델이 쓴 결과물은 로컬 파일이지만, 그 파일을 사람이 밖으로 보낼 수 있기 때문이다.
- **P-4 GUI:** 설정 화면의 읽기 제외 편집, 새 작업 화면의 `analyze-private` 안내와 선택은 다음 단위로 한다. CLI와 앱 계층이 먼저다.

**보안·개인정보에서 조심할 점.**
- 정의 하나로 끝나지 않는다. 설정의 읽기 제외가 늘 합쳐지는 규칙(R-2)과 명령 금지(R-5)가 없으면, task 파일 하나로 이 정의의 보장이 깨진다.
- 모델이 쓰는 결과 표는 읽기 제외 밖이어야 한다. 쓰기가 막히므로 저절로 그렇게 된다. 목표에 적는 출력 경로를 사용 문서 예시로 보인다.
- 재수정 근거(R-6)와 결과 화면의 근거가 같은 규칙을 따라야 한다.

**바뀌는 계약·고정 시험.**
- `workflow.ts`: `BUILTIN_WORKFLOW_IDS`에 `analyze-private`, 새 문제 코드.
- 따라오는 것:
  - `src/workflows` 정의, CLI 해석 문제의 안내 문구, `help`의 작업 종류 목록.
  - GUI의 작업 종류 목록(id 목록을 남김없이 다루는 곳이 있으면 깨진다).
- 고정 시험: 작업 종류 목록 시험(`g-workflows`), 도움말·카탈로그. GUI 시험은 GUI 단위에서 다룬다.

**어림 줄 수.**
- 정의와 해석 조건 약 200.
- CLI 연결(설정 읽기 제외 합치기, 명령·`command` 검증기 금지, 형식 검사, doctor 줄) 약 700.
- 검증기 근거(R-6) 약 150.
- 설정 넓히기(R-7) 약 250.

## 4. 묶음 B — `plan: "run"`과 `writablePaths`

**무엇을 하는 기능인가.**
모델이 먼저 "어느 파일을 어떻게 바꿀지"를 제안한다. 사람이 다이제스트로 승인하면, 새 실행이 그 계획을 지시로 받아 승인된 경로에만 쓴다. 지금의 `plan: "apply"`는 사람이 승인한 이동·폐기를 결정적 적용기가 그대로 실행하는 것이고, 모델은 적용에 관여하지 않는다. `run`은 큰 문서 개편이나 분석처럼 모델이 실제로 써야 하지만 범위를 먼저 확인하고 싶은 경우를 위한 것이다.

**설계가 이미 정한 것.**
- [정함] 의도(바꿀 파일, 개요)를 제안하고, 승인되면 새 실행이 계획을 지시로 받는다. 쓰기는 계획에 적힌 경로로만 한다(정책 `writablePaths`, general-tasks 6.1).
- [정함] 계획 승인은 실행 사이의 확인 하나다. 해시는 다이제스트 하나다(DR-1, GT-D4).
- [사실] `PLAN_MODES`는 `["none", "apply"]`다(`src/contracts/plan.ts:51`). 주석에 "P1 adds run"이 있다.

**비워 둔 값.**
- [빈 값] 승인된 계획과 실제 쓰기의 대응을 어디까지 강제할지. 경로만인지, 개요 대조까지인지(13절).
- [빈 값] 제안의 형식, 실행 입구, 상한.

**권고 값과 근거.**
- **B-1:** 새 작업 종류 도구 `propose_changes`를 둔다. `{ summary, files: [{ path, change: "create" | "modify" }] }` 꼴이고, 설명자는 `endsRun: "plan"`이다.
  - 지금의 `propose_plan`과 `plan.json`(이동·폐기)은 그대로 둔다. 적용기, 되돌리기, 인벤토리가 모두 그 꼴에 묶여 있다.
  - 저장은 같은 `plan.json`에 다른 `kind`로 한다. 다이제스트 규칙은 같다.
- **B-2:** 경로와 계획 때 있던 파일의 해시만 묶는다. 요약은 지시문으로만 쓰고 강제하지 않는다.
  - 경로는 기계로 강제할 수 있다. 개요 대조는 판정할 수 없다.
- **B-3:** `codaryn apply`(앱 계층 `applyPlan`)가 계획 종류로 나눈다.
  - 승인 경로(DR-1), 다이제스트, `applied.json`, 이벤트·취소 통로(DR-2)를 그대로 쓴다. 사람에게 승인하는 길은 하나다.
  - 결과는 모델 실행이므로 `EngineResult`다. `planRunId`와 다이제스트를 더하고 `run_started`에 남긴다.
- **B-4:** `writablePaths`는 일반 정책 필드로 둔다.
  - 설정·프로필·정의·task는 좁히기만 한다(교집합). 예: "이 프로필은 `out/`에만 쓴다".
  - 계획 실행은 승인된 목록과 교집합이다. 보호 경로와 읽기 제외는 그 위에서 여전히 막는다.
  - 판정은 읽기 제외와 같은 경로 집합 판정(글자, 실경로)을 쓴다. 그래서 A-3 뒤에 한다.
- **B-5:** 파일 100개까지 받는다. 파일만 받고 디렉터리 접두사는 받지 않는다. 사람이 승인 화면에서 목록을 읽을 수 있는 크기이고, 접두사 하나면 범위가 사실상 무한이 된다.
- **B-6:** 승인 뒤 계획 파일의 해시가 바뀌었거나 "create" 자리에 파일이 생겼으면, 모델을 시작하기 전에 `failed`/`plan_stale`로 끝낸다. apply의 사전 점검과 같은 원칙이고, 모델 토큰을 쓰기 전에 멈춘다.
- **B-7:** 계획 하나에 한 번만 실행한다(`applied.json`). 같은 승인으로 두 번 쓰지 않는다.
- **B-8:** `writablePaths`는 파일 도구만 막는다. 명령 규칙이 있으면 명령이 아무 데나 쓸 수 있다(인자 경로를 검사하지 않음). 그래서 사용 문서에 적고, `plan: "run"`과 명령 규칙이 함께 있으면 doctor가 경고한다. 코드 작업에서는 명령이 필요하므로 금지하지는 않는다.

**보안·개인정보에서 조심할 점.**
- 다이제스트 앞 12자 승인의 위협 모델은 apply와 같다. 상태 디렉터리에 쓸 수 있는 명령은 막지 못한다(R-1 I-3). 명령이 허용된 실행이라면 B-8의 경고로 이어진다.
- 실행 run의 지시문에 들어가는 요약은 모델 글이다. 가린 뒤 넣고, 고정 시스템 문구 뒤에 "승인된 계획" 표지와 함께 둔다(지시문 주입을 구분하기 위해서다).
- 읽기 제외와 함께 쓰면 계획의 경로가 읽기 제외 아래일 수 없다. 쓰기가 막히므로 제안 단계에서 거부한다.

**바뀌는 계약·고정 시험.**
- 계약:
  - `plan.ts`: `PLAN_MODES`에 `run`, `propose_changes`의 형식, 저장 `kind`, 상한.
  - `tool.ts`: 도구 이름·정의.
  - `task.ts`: `writablePaths`.
  - `engine.ts`: `EngineResult.planRunId?`. 이유 코드는 기존 `plan_stale`를 쓴다.
  - `journal.ts`: `run_started` 선택 필드.
- 따라오는 것:
  - `PlanMode`를 남김없이 나눠 처리하는 곳(엔진 E3, CLI `plan`·`apply`, 사람용 출력)이 깨진다. U-74·U-86처럼 계약 단위와 함께 따라오는 목록을 보고한다.
  - GUI 계획 화면.
- 고정 시험: `plan`·`apply` 출력 고정(새 종류에서만 다르다), 카탈로그, 계약 목록. 기존 apply 고정 출력은 바뀌지 않아야 한다.

**어림 줄 수와 단위.**
| 단위 | 내용 | 어림 줄 수 | 앞선 단위 |
| --- | --- | --- | --- |
| B-1 계약 | 위 계약 | 350 | 결정 B-1~B-8 |
| B-2 정책 `writablePaths` | 교집합, 판정 | 350 | B-1, A-3 |
| B-3 엔진·도구·저장 | `propose_changes`, 계획 저장, 실행 run의 낡음 점검과 지시, `applied.json` | 1,000 | B-1, B-2 |
| B-4 CLI·앱 | `apply` 나눔, `plan` 보기, 승인 화면 글, doctor 경고 | 800 | B-3 |
| B-5 문구·통합·문서 | 문구 100, 통합 400, 문서 200 | 700 | B-4 |
| (뒤) GUI | 계획 화면의 변경 목록 | 500 | B-4 |

## 5. 묶음 C — `markdown` 규칙

**무엇을 하는 기능인가.**
문서 작성 작업의 자동 검증이다. 결과 Markdown 문서에 정한 제목이 있는지(순서도 볼 수 있음), 상대 링크의 대상 파일이 작업 공간에 있는지를 본다. 지금은 `file_rules`의 존재·문자열 검사뿐이라 문서 구조를 확인할 수 없다.

**설계가 이미 정한 것.**
- [정함] 새 검증기 종류가 아니라 `file_rules`의 규칙 종류로 더한다. 링크는 작업 공간 안 상대 경로만 보고 외부 URL은 열지 않는다(네트워크 없음, general-tasks 5.1).
- [사실] `FileRule`은 `exists`, `absent`, `contains`, `not_contains` 넷이다(`src/contracts/verify.ts:23-27`).

**비워 둔 값.**
- [빈 값] 규칙의 형식, 제목 비교 방식, 링크 해석 범위, 크기 상한.

**권고 값과 근거.**
- **M-1:** 규칙 둘을 더한다.
  - `markdown_headings`: `{ path, headings: [{ text, level? }], order?: "any" | "in_order" }`. 기본은 `"any"`다.
  - `markdown_links`: `{ path }`. 문서 안의 상대 링크 대상이 모두 있어야 통과한다.
- **M-2:** 제목은 ATX(`#`)와 Setext(밑줄)를 둘 다 읽는다.
  - 앞뒤 공백과 닫는 `#`를 뺀 글자로 정확히 비교한다. 대소문자도 구분한다.
  - 사람이 적은 글과 같은지 보는 것이 가장 예측하기 쉽다. 느슨한 비교는 나중에 옵션으로 더할 수 있다.
- **M-3:** 링크.
  - 인라인 링크, 참조 링크, 이미지(`![]()`)를 본다.
  - 펜스 코드 블록과 인라인 코드 안은 건너뛴다.
  - 스킴이 있는 것(`http:`, `mailto:` 등)과 `#`만 있는 것은 건너뛴다.
  - 퍼센트 인코딩을 풀고, 문서 파일 기준 상대 경로로 해석한다.
  - 대상이 작업 공간 밖이거나 상태 디렉터리면 "밖"으로 실패한다. 밖의 존재는 확인하지 않는다(밖을 훑는 데 쓰이지 않게).
  - 앵커(`#절`)는 P1에서 보지 않는다. 제목을 앵커로 바꾸는 규칙(slug)이 렌더러마다 다르다.
- **M-4:** 파일 크기는 1 MiB까지다. 검증기는 모델로 내용을 보내지 않으므로 읽기 상한(256 KiB)보다 커도 된다. 넘으면 `inconclusive`다.
- **M-5:** 근거에는 빠진 제목과 대상 경로를 20개까지 적는다. 엔진이 가린 뒤 기록하고 재수정 때 보낸다(지금 검증 근거와 같다).

**보안·개인정보에서 조심할 점.**
- 네트워크를 쓰지 않는다. 링크 대상 존재 확인은 작업 공간 안만 한다.
- 링크 대상이 읽기 제외 아래면 존재만 확인하고 내용은 읽지 않는다. 존재 여부는 사람이 쓴 문서가 이미 말한 것이다.
- 근거의 경로는 등록 값이 가려진다(엔진의 기존 가림).

**바뀌는 계약·고정 시험.**
- 계약: `verify.ts`의 `FileRule`에 두 종류, 상한 상수.
- 따라오는 것: CLI의 task·설정 형식 검사(규칙 형식, na-core), `FileRule`을 남김없이 나눠 처리하는 검증기.
- 고정 시험: 기존 규칙의 결과는 바뀌지 않는다. 계약 목록 시험만 바뀐다.

**어림 줄 수와 단위.** 하나다(약 800): 계약 80, 검증기 550(코드 250, 시험 300), CLI 형식 검사 100, 문서 60. 다른 묶음과 겹치는 파일이 계약과 CLI 형식 검사뿐이므로 언제든 된다.

## 6. 전체 순서

```
결정(Q-1 사용자, 나머지 PM)
  └ A-1 계약
      ├ A-2 표 스트리밍 ─┐
      ├ A-3 읽기 제외 ───┼ A-5 query_table ─ A-6 CLI·정의 ─┐
      ├ A-4 문구          │                                  ├ A-8 카나리 통합 ─ A-9 문서 ─ GUI
      └ A-7 검증기·앱 ────┘(A-3 뒤)                          ┘
  A-3 뒤: B-1 → B-2 → B-3 → B-4 → B-5 → GUI
  언제든: C
```

- 묶음 A를 먼저 하는 이유: 사용자 결정 DR-23이 지금 막고 있는 작업 유형(개인정보 자료 분석)을 연다. B와 C는 지금 되는 일을 편하게 하는 것이다.
- B를 A-3 뒤에 두는 이유: `writablePaths`와 `unreadablePaths`는 같은 "경로 집합" 판정이다. 한 번 만들고 두 번 쓴다.

## 7. 이 제안이 확인하지 않은 것

- 시간을 재지 않았다. 64 MiB 표 해석·집계, `data_checks` 64 MiB, 묶음 10,000개의 메모리는 모두 구현 단위에서 잰다.
- 담당은 지금 배치를 가정했다. `src/tabular`·`src/verify`·`src/workflows`의 지금 담당은 확인하지 못했다.
- 도구 이름 `propose_changes`와 오류 코드 이름은 제안이다. 계약 단위에서 PM이 정한다.
- `real-catalog`가 무엇을 고정하는지는 열어 보지 않았다. 새 문구 id가 그 고정에 닿는지는 A-4에서 확인하고 보고한다.
- 차등 개인정보 보호(잡음)는 범위 밖으로 두었다(Q-8). 사용자가 "여러 질의로도 알아낼 수 없어야 한다"를 원하면 이 묶음의 설계가 바뀐다. Q-1을 물을 때 함께 묻기를 권한다.
