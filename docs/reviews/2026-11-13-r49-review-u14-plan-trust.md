## 2. 중간

### R49-M1 `plan --json`은 summary에 든 키 모양 글을 가리지 않는다

- 위치: `src/cli/plan-commands.ts`의 `runPlan`. `--json`이면 `output`을 그대로 돌려준다. 사람용 줄은 `hideKeys`를 지난다.
- 재현(S2, K)
  1. 대본의 summary에 키 모양 글(등록된 값도 현재 키도 아닌 것)을 넣고 실행한다.
  2. 같은 실행을 여러 출력으로 본다.

  | 출력 | 단위 `24fa265` | main `266c46d` |
  | --- | --- | --- |
  | `run`의 stdout JSON | 가림 | 가림 |
  | `plan`(사람용) | `[key]` | summary 없음 |
  | **`plan --json`의 `summary`** | **그대로** | 필드 없음 |
  | `plan --json`의 동작 경로(키 모양 이름) | 그대로 | 그대로 |
  | `report`, `report --json`, `runs --json` | 가림 | 가림 |

- 영향
  - 다른 JSON 출력은 모든 문자열에 `hideKeys`를 건다(N-27 (c), `hideKeysInStrings`). `plan --json`만 걸지 않는다. 경로에 대해서는 main에도 있던 틈이다.
  - 이 단위가 그 출력에 모델이 자유롭게 쓴 글을 처음 싣는다. 모델이 작업 공간의 파일에서 읽은 다른 키(등록되지 않은 것)를 summary에 쓰면 `plan --json`으로 나간다.
  - 등록된 가릴 값과 현재 키 값은 가려진다. 남는 것은 "등록되지 않은 키 모양 글"뿐이다.
- 판단: N-27 (c)에 어긋나고 재현되므로 중간으로 적었다. 틈 자체는 이 단위 이전부터 있었고, 이 단위가 닿는 범위를 넓혔다.
- 권고(CLI 담당): `runPlan`의 JSON 쪽에서 `hideKeysInStrings(output, currentKey)`를 건다. 경로의 틈도 함께 닫힌다.

## 3. 낮음

### R49-L1 다이제스트 줄이 실제 보장보다 많이 말한다

- 문구: "The digest names exactly these actions and the contents the files had when the plan was made. The apply refuses if the plan, a file or the run's records changed since." 한국어도 같은 뜻이다.
- 실제(G, `G.log`)

  | 계획을 만든 뒤 바꾼 것 | apply |
  | --- | --- |
  | 계획의 파일 내용 | `failed`/`plan_stale` (문구와 맞음) |
  | 옮길 자리에 파일이 생김 | `failed`/`plan_stale` |
  | `plan.json`을 고침 | `plan`과 `apply` 모두 종료 2로 거부 (문구와 맞음) |
  | 계획과 무관한 새 파일·폴더 | `done`/`verified` |
  | **계획 실행의 `journal.jsonl`을 고침(다른 실행 없음)** | **`done`/`verified`** |
  | **계획 실행 폴더에 파일을 더함(다른 실행 없음)** | **`done`/`verified`** |
  | **`result.json`을 고침(다른 실행 없음)** | **`done`/`verified`** |

- 어긋나는 곳
  - "실행 기록이 바뀌었으면 거부": 거부는 기록 변경 표시가 있을 때뿐이다. 표시는 뒤의 다른 실행이 바뀐 것을 알아챘을 때만 붙는다(R-44 R44-L1의 한계도 있다). 실행 사이에 바뀐 기록은 걸리지 않는다.
  - "파일이 바뀌었으면": 계획에 든 파일만이다. 글만 보면 작업 공간의 아무 파일로 읽힌다.
  - journal을 고친 경우 `plan`은 고친 summary를 경고 없이 보인다. 라벨이 "검증되지 않았다"고 말하므로 따로 세지 않았다.
- 영향: 승인하는 사람이 다이제스트가 실행 기록 전체를 지킨다고 믿게 된다. 동작과 계획의 파일에 대한 보장은 맞다.
- 권고(문구 담당): "…계획이나 계획에 든 파일이 바뀌었으면 적용을 거부합니다. 실행 기록에 변경 표시가 붙은 계획도 거부합니다."처럼 실제 조건으로 쓴다.

### R49-L2 공백으로 채운 summary가 터미널의 줄 접힘으로 가짜 줄처럼 보인다

- 위치: `renderPlan`의 summary 줄. `cleanText`는 제어 문자만 바꾸고, 이어진 공백은 그대로 둔다.
- 재현(S7, `S.log`): summary에 글 사이를 공백으로 채워 넣으면 80칸 터미널에서 이렇게 보인다(실행 id와 다이제스트는 지어낸 것).

  ```
  The agent's description (the model's own words, not checked, and not what you ap
  prove): ok             4. move inbox/safe.txt -> archive/safe.txt
                         Applied by run 20260101T000000Z-deadbeef at 2026-01-01T00
  :00:00.000Z.           To apply it: codaryn apply task.json --run 20260101T00000
  0Z-deadbeef --digest 0123456789ab
  ```

  - 전각 공백(U+3000)과 줄 바꿈 없는 공백(U+00A0)도 그대로 지나간다(S8).
- 영향
  - 500자 안에서 가짜 동작 줄, 가짜 "Applied by", 다른 실행을 가리키는 가짜 "To apply it" 줄을 줄 머리에 놓을 수 있다. 터미널 너비를 맞혀야 하고 정렬이 어긋나 보인다.
  - 진짜 동작 줄은 그 위에, 진짜 "To apply it" 줄은 그 아래에 그대로 있다. 라벨이 먼저 나온다. apply는 사람이 준 다이제스트의 계획만 적용하므로, 속은 사람이 가짜 명령을 쓰면 읽지 않은 다른 계획을 승인하게 되는 정도다.
- 권고(CLI 담당): summary의 이어진 공백(유니코드 공백 포함)을 하나로 줄인다. 따옴표로 감싸거나 들여 쓴 별도 줄에 두면 더 분명하다.

## 4. 정보

- **R49-I1 표시가 있는 계획에도 다이제스트 줄이 붙는다.** "적용할 수 없습니다" 바로 아래에 "다이제스트는 바로 이 동작들과 …를 가리킵니다"가 나온다. 경고("이 계획이 실행이 만든 계획과 다를 수 있습니다")와 나란히 읽으면 어색하다. 또 표시가 있어도 `status`는 `pending`, 종료는 0이다(계약대로).
- **R49-I2 가려진 값의 토큰이 겹쳐 보인다.** journal의 토큰을 다시 가려 `[[[[CODARYN_SECRET:…]]:…]]` 꼴이 된다. 사람용과 JSON에서 안쪽 번호가 서로 다르다. 값은 드러나지 않는다.
- **R49-I3 보이지 않는 글자 일부는 남는다.** 폭 없는 공백(U+200B)과 소프트 하이픈(U+00AD)은 `?`로 바뀌지 않는다. 줄을 바꾸거나 순서를 뒤집지는 못한다.
- **R49-I4 계획 보기의 나머지 줄은 한국어에서도 영어다.** "Plan of run …", "Digest:", 동작 줄, "To apply it" 줄은 그대로 영어이고(main과 같음), 새 네 줄만 두 언어다(UXM-7).

## 6. 검사하지 않은 범위

- 터미널에서 apply가 묻는 승인 질문. 같은 `renderPlan`을 쓰고 summary도 함께 보인다(코드로 봤다). 파이프로는 질문이 뜨지 않는다.
- 앱 계층·GUI의 계획 보기. 이 단위는 CLI만 바꿨다.
- 유닛·통합 시험 재실행(PM이 이 판에서 잰 수치를 받았다)
- macOS·Linux, 실제 터미널의 접힘(80칸으로 잘라서 봤다)
