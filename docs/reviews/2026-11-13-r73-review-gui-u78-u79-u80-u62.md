## U-78: 창 언어가 설정 파일의 language를 따른다 (`aa32f85`)

**변경:** 엔진 호스트의 `messages`가 앱 계층의 설정 읽기를 부른다(`gui/src/engine-host/host.ts:275`). `configLanguageOf`(`gui/src/engine-host/settings.ts:153`)는 ko와 en만 받는다. 그 값을 CLI와 같은 `selectMessageLanguage({ env: CODARYN_LANG, config, osLocale })`에 넘긴다(`gui/src/engine-host/main.ts:202-204`). 예외가 나면 config는 null이 되어 OS가 정한다.

**실험** (`.codaryn/r73/lang.mjs`, `LANG.log`): 합친 판의 실제 엔진 호스트를 조합마다 새로 띄워 `messages`를 불렀다. 같은 환경에서 CLI `run`·`runs`·`doctor`도 돌렸다.
- 조합: 설정 5가지(없음, ko, en, 틀린 값 fr, 깨진 JSON) × `CODARYN_LANG` 3가지(없음, en, ko) × OS 2가지(ko-KR, en-US)

| 확인 | 결과 |
|---|---|
| 순서 | 모든 조합에서 `CODARYN_LANG` > 설정 `language` > OS로 정해진다. 예: 설정 en·OS ko-KR → 창 en, 설정 ko·OS en-US → 창 ko, `CODARYN_LANG` en·설정 ko → 창 en |
| CLI와 비교 | `run`의 stderr 언어와 `doctor`의 "메시지 언어" 줄이 창과 같다. 이 기계의 Intl locale은 ko-KR이라 CLI 쪽은 OS ko 열과 비교했다 |
| 설정을 못 읽을 때 | 깨진 JSON과 틀린 값(fr)은 OS로 돌아간다(ko-KR → ko, en-US → en). 오류 없이 창이 뜬다. CLI도 언어는 OS로 정하고, `doctor`는 그 설정을 `[실패]`로 알린다 |
| 설정 파일 없음 | OS가 정한다 |

**정보**
- **I1** CLI `runs`는 설정의 `language`를 읽지 않는다. 설정 en, OS ko에서 창·`run`·`doctor`는 en인데 `runs`만 ko다(`LANG.log` "language en | CODARYN_LANG -" 줄). CLI 쪽에 원래 있던 어긋남이고 U-78 범위 밖이다. 창은 N-4 순서를 맞게 따른다.
- **I2** 설정 화면에서 바꾼 언어는 다시 시작해야 쓰인다. 설계 GU-6 줄에 "U-69 예정"으로 적혀 있고 U-78이 그 문장을 지키고 있다. `messages`를 부를 때마다 설정을 다시 읽으므로 U-69는 창이 `messages`를 다시 부르기만 하면 된다.

## U-80: GUI에서 고른 제공자의 출력 상한 쓰기 (`b13c215`)

**변경:**
- 설정 편집 `{ op: "outputCap", provider, value }`를 더했다(`gui/src/shared/settings-edit.ts:58-62`).
  - value는 null이거나 1 이상 `MAX_LIMIT`(1,000,000,000) 이하의 안전한 정수다.
  - provider는 `/^[a-z][a-z0-9_-]{0,31}$/`이고, 엔진 호스트가 계약의 제공자 표와 맞춰 본다(`gui/src/engine-host/host.ts:362`).
- 쓰는 곳은 `applySettingsEdit`(`settings-edit.ts:130-141`)가 정한다.
  - anthropic: `providers.anthropic`이 없으면 최상위, 있으면 그 안
  - 그 밖의 제공자: `providers.<이름>`
  - null이면 지운다.

**실험** (`.codaryn/r73/cap.mjs`·`CAP.log`, `cap2.mjs`·`CAP2.log`): 실제 엔진 호스트에 주 프로세스와 같은 순서로 보냈다. `proposeSettings {edit}` → 제안의 `next`·`baseDigest`로 `applySettings`. 먼저 `confirmWidening: false`로 쓰고, 넓힘이면 true로 한 번 더 썼다. 쓰기 전후의 파일을 필드 단위로 비교했다.

| 경우 | 넓힘 | 쓰임 | 바뀐 필드 |
|---|---|---|---|
| openai, 항목에 model만 있음 → 8000 | 없음 | 쓰임 | `providers.openai.maxOutputTokens` 하나 |
| `providers` 없음, openai → 4096 | 없음 | 쓰임 | `providers` 생김: `{"openai":{"maxOutputTokens":4096}}` |
| openai → 200000 | 없음 | 쓰임 | 그 필드 하나 |
| openai → 200001 | — | 제안 거부 `invalid_config` | 없음 |
| openai → 999,999,999 (화면 범위 안) | — | 제안 거부 `invalid_config` | 없음 |
| anthropic 최상위 1000 → 200000 | 없음 | 쓰임 | 최상위 `maxOutputTokens` 하나 |
| anthropic, `providers.anthropic` 있음 100 → 4096 | 없음 | 쓰임 | `providers.anthropic.maxOutputTokens` 하나 |
| anthropic, `providers`에 anthropic 없음 → 2048 | 없음 | 쓰임 | 최상위 `maxOutputTokens` 생김 |
| anthropic → null | 없음 | 쓰임 | 최상위 `maxOutputTokens` 지움 |
| 0, -1, 1.5, "100", 1,000,000,001, 제공자 nope, 키 하나 더 | — | `invalid_args` | 없음 |
| (비교) 제공자 바꾸기 | `provider_changed provider` | 확인 없이는 안 쓰임, 확인하면 쓰임 | `provider` |
| (비교) 한도 올리기 | `limit_raised limits.maxModelTurns` | 확인 없이는 안 쓰임, 확인하면 쓰임 | `limits.maxModelTurns` |

- **범위:** 마지막 문은 앱 계층의 계약 상한 `MAX_OUTPUT_TOKENS_LIMIT=200_000`(`src/contracts/config.ts:253`)이다. 200,001부터 모든 제공자에서 막힌다. 잘못된 값은 쓰이지 않는다.
- **넓힘:** 출력 상한을 바꿔도 넓힘이 아니라서 OS 확인 없이 쓴다. 설계(`docs/design/adapter-contract.md:542` "모델·출력 상한 변경은 넓히기가 아니다")와 `wideningOf`(`src/app/settings-change.ts:128`, LIMIT_FIELDS만 봄)대로다. 같은 통로에서 넓힘 판정과 확인 요구는 제대로 동작한다(비교 두 줄).
- **다른 필드:** 모든 경우에 목표 필드 하나만 바뀌었다. 확인한 필드는 schemaVersion, language, model, limits, policy, secretEnv, profiles, providers.openai.model이다.

**낮음**
- **L1 화면의 범위와 실제 상한이 다르고, 어긋난 값의 알림이 틀린 곳을 가리킨다.**
  - 입력란과 편집 검사의 상한은 `MAX_LIMIT` 1,000,000,000이다(`gui/src/renderer/settings/settings.ts:72`, `:240`, `:245`; `settings-edit.ts:44`, `:61`). 실제 상한은 200,000이다.
  - 200,001~1,000,000,000을 넣으면 제안이 `invalid_config`로 돌아온다. 화면은 "설정 파일의 형식이 맞지 않거나 파일이 없습니다. 설정 파일을 확인하세요."(`gui/src/renderer/i18n/ko.ts:204`)를 보인다. 파일은 멀쩡하고 값이 상한을 넘은 것이다.
  - 0이나 빈칸은 아무 알림 없이 무시된다(`settings.ts:245`의 `return`). 같은 화면의 한도 입력은 `warn("bad_number")`로 알린다(`settings.ts:139`).
  - 한도 입력도 1e9를 상한으로 쓰는 같은 꼴이지만, 출력 상한은 계약에 고정된 상한이 하나라 화면이 그대로 쓸 수 있다.
  - 제안: 출력 상한 입력의 `max`와 검사에 200,000을 쓰고(계약 값을 엔진 호스트가 설정 보기에 실어 주면 숫자가 한곳에 남는다), 범위 밖은 `bad_number`로 알린다.

**정보**
- **I1** 출력 상한 올리기(예: 1,000 → 200,000)는 요청당 비용 상한을 200배로 올리지만 OS 확인 없이 쓰인다. 설계가 정한 그대로다(위). 결함이 아니다. 비용 쪽으로 넓힘에 넣을지는 PM·Codex가 정할 일이라 질문으로만 남긴다(Q-1).
- **I2** `providers`에 그 제공자 항목이 없을 때 null 편집을 보내면 빈 항목이 생긴다. `providers: {"openai": {}}`로 파일을 쓴다(`CAP2.log` "openai entry absent: null"). 유효한 설정이고 다른 필드는 그대로다. 화면은 null을 보내지 않으니(`settings.ts:245`는 1 이상만 보냄) IPC로만 닿는다. 한도 편집은 빈 `limits`를 지우지만(`settings-edit.ts:148`) 출력 상한 편집은 빈 항목을 남긴다. 이 정도 차이다.

**중간**
- **M1 설정에 등록한 비밀(`secretEnv`)의 값이 클립보드로 갈 수 있다.**
  - 엔진 호스트의 `hideAllKeys`(`gui/src/engine-host/main.ts:193-200`)는 API 키 변수(`keyEnvs`)의 값만 가린다. `secretEnv`의 이름과 값은 읽지 않는다.
  - 실험(`.codaryn/r73/copy.mjs`, `COPY.log`): 설정 `secretEnv: ["R73_SECRET"]`이고 그 변수에 지어낸 값을 둔 호스트에서 `copyCheck`를 불렀다.

    | 넣은 글 | 결과 |
    |---|---|
    | 그 값이 든 경로 `notes/<값>.txt` | `clean true` |
    | 그 값만 | `clean true` |
    | (비교) 키 변수 값이 든 경로 | `clean false` |

  - 트리도 그런 이름을 가리지 않는다(`gui/src/engine-host/tree.ts:11-13`, 원래 있던 한계). 그래서 그 값이 이름에 든 파일에서 "경로 복사"를 누르면 값이 OS 클립보드에 그대로 올라간다. Windows 클립보드 기록과 기기 간 동기화를 켜 둔 사람은 값이 이 기계 밖으로 나간다.
  - 화면에 보이던 것이 앱 밖의 지속 저장소로 옮겨 가는 변화다. 설계와도 어긋난다.
    - 원칙 4 "가림본만 그린다 … 클립보드"(`docs/design/standalone-gui.md:77`)
    - 보안 시험 GS-4 "가짜 `secretEnv` 값으로 실행한다 → … 클립보드 … 에 없다"(`:642`)
  - 그런데 U-62의 설계 문장(`:586`)은 검사 범위를 "키 모양, 지금 설정된 모든 키 값"으로만 적었다. U-62는 그 문장대로 만들었고, 설계 안에서 두 문장이 서로 다르다.
  - 이름에 비밀 값이 든 파일은 흔하지 않다. 그래도 클릭 한 번으로 닿고, 명시된 수락 기준(GS-4)과 어긋나므로 중간으로 둔다.
  - 고치는 길: 엔진 호스트는 이미 `messages`와 설정 제안에서 앱 계층의 설정 읽기를 부른다(`host.ts:275`, `:363`). 거기서 `secretEnv` 이름을 얻어 `process.env`의 값을 `copyCheck` 가림에 더하면 GUI 안에서 닫힌다. 트리 표시는 앱 계층 함수가 필요하다는 기존 한계(A 목록)로 따로 남는다.

**낮음**
- **L1 `copyText`는 종류를 묻지 않아, 렌더러가 검사를 지나는 글이면 무엇이든 클립보드에 쓸 수 있다.**
  - 화면이 `copyText`로 복사하는 것은 실행 id(`RUN_ID` 꼴)와 다이제스트 앞 12자(16진수)뿐이다. 경로는 `copyPath`가 맡는다.
  - 그런데 주 프로세스는 한 줄, 1,000자 이하, 키 없음만 본다.
  - 손상된 렌더러는 `curl … | sh` 같은 명령 한 줄을 사람이 누르지 않아도 클립보드에 넣을 수 있다(붙여넣기 바꿔치기). 사용자 동작도 묻지 않는다.
  - 렌더러가 먼저 손상돼야 하고, 설계 표가 `copyText(text)`로 정했으므로(`standalone-gui.md:572`) 낮음으로 둔다.
  - 제안: `copy({ kind: "runId" | "digest12", value })`로 바꾸고 주 프로세스가 `RUN_ID`와 `/^[0-9a-f]{12}$/`로 확인한다. 실행 id는 `wasListed`로 더 좁힐 수 있다. 쓰는 곳이 둘뿐이라 작은 변경이다.

**정보**
- **I1** 렌더러 자신의 클립보드 쓰기(`navigator.clipboard.writeText`, `document.execCommand('copy')`)가 샌드박스 렌더러에서 막히는지는 시험하지 않았다. 권한 확인을 모두 거부하므로 `navigator.clipboard`는 막힐 것으로 보이지만, `execCommand('copy')`는 권한 처리기를 거치지 않을 수 있다. 막혀 있지 않다면 L1의 통로가 하나 더 있는 셈이다. 보안 시험 GS-4·GS-2와 함께 연기 시험에서 볼 것을 권한다.
- **I2** 연기 시험의 클립보드 기록기(`writeClipboard`)는 연기 하네스가 `startApp` 옵션으로만 넘긴다(`gui/tests/smoke/smoke.ts:151`, `app.ts:66-67`). 환경 변수나 명령줄로 켜는 길은 없다.
