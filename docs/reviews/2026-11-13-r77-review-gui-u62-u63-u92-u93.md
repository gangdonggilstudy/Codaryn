## U-62: 복사, 고친 판 (`90ca34c`)

**변경:**
- 주 프로세스의 `copyText` 처리기(`gui/src/main/ipc.ts`의 `IPC_CHANNELS.copyText`)가 `parseCopyArgs`(`gui/src/shared/ipc.ts`)로 거른다.
  - 받는 것: `{text}` 하나. 그 값이 실행 id 꼴(`/^[0-9]{8}T[0-9]{6}Z-[0-9a-f]{8}$/`)이거나 16진 소문자 12자(`/^[0-9a-f]{12}$/`)일 때만이다.
  - 그 밖은 `invalid_args`이고 클립보드에 아무것도 쓰지 않는다.
- `copyPath`와 엔진 호스트의 `copyCheck`는 없앴다. 두 꼴은 키나 등록 비밀을 담을 수 없으므로 엔진 호스트 검사가 필요 없다.

**좁힌 꼴 밖의 글:** 빌드된 `parseCopyArgs`를 직접 불렀다(`.codaryn/r77/parse.mjs`, `PARSE.log`). 받은 것은 실행 id와 12자 다이제스트 둘뿐이다. 아래 22가지는 모두 거부됐다.

| 종류 | 사례 |
|---|---|
| 다이제스트 꼴이 틀림 | 11자, 13자, 대문자, 64자 전체, 뒤 공백, 뒤 줄바꿈, 전각 숫자 |
| 실행 id 꼴이 틀림 | 뒤에 글자, 뒤 줄바꿈, 소문자 t/z, 대문자 16진, 날짜 자리의 글자 |
| 다른 글 | 경로 `sub/b.txt`, 빈 글, 아무 문장, 키 모양(쪼개 만든 합성 값) |
| 값의 형태 | 숫자, 배열, 키 하나 더, `text` 없음, 객체 아닌 문자열, null |

연기 시험의 `copyRefused`도 실제 창에서 같은 거부를 본다. 키 변수의 값 자체를 넣어도 `invalid_args`이고 written 0이다.

**`copyPath` 통로:**
- 원본 `gui/src`, `gui/scripts`, 설계 문서에 `copyPath`·`copyCheck`가 0회다.
- 빌드 결과(`gui/build/src`)에도 0회다. 나오는 곳은 시험 두 곳뿐이고, 둘 다 없음을 확인하는 줄이다(`u62-copy.test.js:27`, `smoke.js:369`).
- IPC 채널 표의 복사 채널은 `copyText` 하나다(`codaryn:app:copy`, preload와 shared 둘 다).
- 연기 시험에서 창의 `typeof window.codaryn.copyPath`는 `"undefined"`다. 고정한 창 함수 목록(`renderer` 검사)에도 `copyText`만 있다.
- 클립보드 읽기 통로는 여전히 없다.

**정보**
- **I1** `copyText`는 꼴만 보고, 그 실행 id나 다이제스트가 화면에 보였던 것인지는 보지 않는다. 두 꼴 모두 비밀이나 명령을 담을 수 없어 해는 없다. R-73 L1(임의 글을 클립보드에 쓰는 통로)은 닫혔다.
- **I2** R-73 I1의 남은 질문은 이번에도 시험하지 않았다. 렌더러 자신의 `document.execCommand('copy')`가 샌드박스 렌더러에서 막히는지다. 그것이 된다면 주 프로세스를 거치지 않는 쓰기 통로가 따로 있는 셈이다. GS-2·GS-4 보안 실행에서 볼 것을 다시 권한다.

## U-93: 출력 상한 입력의 범위와 알림 (`b6edc3d`)

**변경:**
- 화면 입력과 편집 검사의 상한이 `MAX_OUTPUT_CAP = 200_000`이다(`gui/src/renderer/settings/settings.ts`, `gui/src/shared/settings-edit.ts`). 계약의 `MAX_OUTPUT_TOKENS_LIMIT`과 같은지 유닛 시험이 대조한다.
- 범위 밖이나 빈칸은 `warn("bad_number")`로 알린다.
- null(빼기)은 빈 항목을 남기지 않는다. 항목이 비면 지우고, `providers`가 비어도 지운다.

| PM이 볼 것 | 편집 검사 (`PARSE.log`) | 실제 엔진 호스트 (`CAP.log`) | 화면 (유닛 시험 `u93-output-cap-range`) |
|---|---|---|---|
| 200001 | null | `invalid_args`, 파일 그대로 | `bad_number`, 제안 없음 |
| 0 | null | `invalid_args`, 파일 그대로 | `bad_number`, 제안 없음 |
| 빈칸 | `""`는 null | `invalid_args`, 파일 그대로 | `bad_number`, 제안 없음 |
| null | 받음(빼기) | 아래 | 화면은 null을 보내지 않음 |
| (경계) 200000 | 받음 | 쓰임, 그 필드 하나 | 제안됨 |

- null의 결과(실제 호스트):
  - 항목에 model만 있으면 바뀐 것이 없다(written false).
  - `providers`가 없으면 아무것도 만들지 않는다(written false). R-73 I2가 닫혔다.
  - 상한만 있던 openai 항목은 `providers`까지 지워진다.
  - anthropic 최상위는 그 필드만 지워진다.
  - 편집 검사 단계에서도 다른 필드, 다른 제공자, `providers.anthropic`의 model이 그대로임을 봤다(`PARSE.log` 8줄).
- -1, 1.5, `"4096"`(문자열), NaN, 1e9도 편집 검사가 거부한다.

**낮음**
- **L1 OpenAI의 아래쪽 한계(16)를 화면이 모른다. 1~15는 다시 "설정 파일의 형식이 맞지 않거나…"로 돌아온다.**
  - 계약의 제공자 표는 제공자마다 `minOutputTokens`를 둔다. anthropic은 1, openai는 16이다(facts C-10; `src/contracts/config.ts:457`, `:479`, `:489`).
  - U-93의 입력란(`min: "1"`)과 편집 검사(`cap >= 1`)는 모든 제공자에 1을 쓴다.
  - 실패 경우: 실제 엔진 호스트에서 openai 15는 제안이 `invalid_config`로 거부되고, 16은 쓰인다(`CAP.log`). 화면은 `error.invalid_config`의 "설정 파일의 형식이 맞지 않거나 파일이 없습니다. 설정 파일을 확인하세요."를 보인다. R-73 U-80 L1이 위쪽(200,001~)에서 지적한 것과 같은 어긋남이 아래쪽에 남았다.
  - 파일은 쓰이지 않으므로 해는 알림뿐이다.
  - 제안: 엔진 호스트가 설정 보기의 제공자 항목(`apiProviders`)에 `minOutputTokens`를 실어 주고, 입력란의 `min`과 `bad_number` 판정이 그것을 쓴다. 편집 검사도 제공자별 최소를 알면 같은 곳에서 거른다.

**정보**
- **I1** 설정 파일을 쓸 때 앱 계층이 키 순서를 다시 정한다. 예: `language`가 `secretEnv` 뒤로 간다(`CAP.log`). 값은 그대로다. U-93과 무관하다.
