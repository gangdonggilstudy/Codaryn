- 검토자: 검증 엔지니어 (w3:p4, ne-verify). 읽기 전용. 저장소 수정·커밋 없음.

## 먼저 알릴 것 두 가지

1. **U-103의 해시.**
   - 지시의 `1bf4dd4`는 U-64(`0457bba`)와 main(`c5325b0`)을 병합한 커밋이다. U-103의 변경(트리를 `listWorkspaceDir`로, `copyPath`)이 없다.
   - 그 변경은 10:52:40에 브랜치에 올라온 `8658416`("the file tree is the app layer's workspace list, and a plain entry's path can be copied by its id (U-103 …)")에 있다. reflog를 보면 `0457bba` → `1bf4dd4`(10:39) → `8658416`(10:52) 순서다.
   - **그래서 U-103은 `8658416`으로 검토했다.**
2. **지시한 U-65 `d336821`은 U-103과 한 판에 합쳐지지 않는다. 검토 도중 U-65가 U-103 위로 다시 올라왔다.**
   - U-103(`8658416`)과 U-65(`d336821`)가 다섯 파일에서 충돌한다. `gui/src/engine-host/tree.ts` 5블록(136줄), `gui/src/engine-host/main.ts` 2블록, `gui/src/main/workspaces.ts` 1블록, `docs/design/standalone-gui.md` 2블록, 그리고 `tree-view.ts`다.
   - 둘 다 U-64 위에서 트리를 따로 고쳤기 때문이다. 설계 표가 "U-103, U-65보다 먼저(PM)"로 정했으니, U-65가 U-103 위로 다시 올라가야 한다.
   - 충돌을 내 손으로 풀면 내 코드가 판에 들어가므로 풀지 않았다. 그래서 판 A(main+U-103)와 판 B(main+U-65 `d336821`)로 나눠 쟀다.
   - 정리하던 중 `unit/U-65-p5u-gui`가 **`50a79d5`**(10:58:01, 부모 `8658416`)로 움직인 것을 봤다. U-103 위로 다시 쓴 U-65다(`d336821`을 품지 않는다).
   - 그래서 셋을 합친 판 C(main + `50a79d5`)를 더 만들어 쟀다. U-65는 지시한 `d336821`과 다시 올린 `50a79d5`를 따로 판단했다(아래).

## U-103 (`8658416`)

**변경:**
- 엔진 호스트는 더 이상 디렉터리를 직접 읽지 않는다.
- 트리는 앱 계층 `listWorkspaceDir`(U-89)을 연 작업 공간과 설정 파일 기본값(프로필·작업 종류 없음)의 형태로 부르고, 결과를 필드마다 확인한다(`gui/src/engine-host/tree.ts`의 `treeValue`, `entryOf`).
  - 가린 항목은 `name: null`로 오고, `name !== null`이면 `host_error`다.
  - 가리지 않은 항목은 `name === shown`이어야 한다.
- 주 프로세스(`gui/src/main/workspaces.ts`)도 같은 조건을 다시 보고, 가리지 않은 `dir`·`file`에만 id를 준다.
- `copyPath(workspace, node)`(`gui/src/main/ipc.ts`)는 id를 경로로 풀고 `copyablePath`(`gui/src/shared/ipc.ts`)로 다시 본다. 보는 것은 `/` 조각, `.`·`..`·`\`·`:` 없음, 4096자 이하, 제어·줄·서식·방향·보이지 않는 글자 없음이다. 통과하면 클립보드에 쓴다.

**실험:** `.codaryn/r82/tree.mjs`, `TREE.log`.
- 판 A의 실제 엔진 호스트와 주 프로세스의 `Workspaces` 객체, `copyablePath`를 IPC 처리기처럼 이어 불렀다.
- 설정은 `secretEnv: ["R82_SECRET"]`이다. 호스트 환경에 그 값과 지어낸 `ANTHROPIC_API_KEY`를 두었다.

| 이름 | 엔진 호스트 → 주 프로세스 | 창 | id·열기·복사 |
|---|---|---|---|
| `plain.txt`, `sub/` | name = shown | 그대로 | id 있음. 복사 `plain.txt`, `sub` |
| `n-<등록 값>.txt` | `name: null`, shown `n-[[CODARYN_SECRET:…]].txt` | 가림 | id 없음 |
| `sec-<등록 값>/`(안에 `child.txt`) | `name: null`, 가림 | 가림 | id 없음. 펼칠 수 없음 |
| `k-<키 모양>.txt` | `name: null`, `k-[key].txt` | 가림 | id 없음 |
| `v-<지금 키 값>.txt` | `name: null`, `v-[key].txt` | 가림 | id 없음 |
| 보이지 않는 글자 넷: U+200B, U+202E(RTL), U+3164(한글 채움), U+00AD | `name: null`, 그 자리에 `?` | 가림 | id 없음 |
| `junc`(정션 → 작업 공간 밖) | kind `link` | "링크, 따라가지 않음" | id 없음. 엔진 호스트에 직접 `junc`를 대도 `refused` |
| `.codaryn` | kind `state` | "Codaryn 기록, 열지 않음" | id 없음. 직접 대도 `refused` |

- 엔진 호스트가 주 프로세스에 준 답 전체에서 등록 값, 키 모양, 키 값, 네 글자, 정션 너머의 파일 이름을 찾았다. **0건**이다. 주 프로세스는 가린 항목의 원래 이름을 갖지 않는다.
- 꾸민 id(`0`×32)는 `treeDir`에서 null이다.
- R-73 M1의 재현(등록 값이 든 파일 이름의 경로 복사)은 이제 막힌다. 그 항목에 id가 없다.
- 제어 문자(0x01–0x1F) 이름은 Windows가 만들지 못해 재지 못했다. 심볼릭 링크는 권한이 없어 만들지 못했다. 정션으로 링크를 봤고, 연기 시험의 `link-to-sub`도 "링크, 따라가지 않음"이다.

**낮음**
- **L1 트리를 나열한 뒤에 비밀로 등록한 값은, 그 전에 받은 id로 복사된다.**
  - id는 창을 닫거나 작업 공간을 잊을 때만 지운다(`TreeIds.clear`/`forget`). `copyPath`는 그때 푼 경로의 꼴만 다시 본다. 지금 등록된 값으로 다시 가리지는 않는다.
  - 재현(`TREE.log` 끝):
    1. `later-<값>.txt`를 나열한다. 그 값은 아직 등록되지 않았으므로 id가 있다.
    2. 설정의 `secretEnv`에 그 변수 이름을 더한다.
    3. 앞서 받은 id로 `copyPath`하면 "copies the name WITH the now-registered value"다.
    4. 새로 나열하면 같은 항목이 `later-[[CODARYN_SECRET:…]].txt`, masked다.
  - 설정 화면에서 가릴 값 이름을 더해도 트리는 다시 나열되지 않는다(U-65의 새로 고침 전까지). 그래서 창은 계속 그 이름을 보이고 복사도 된다.
  - R-73 M1과 같은 종류(등록 값이 클립보드로)다. 다만 등록 → 나열 순서에서는 막히고, 나열 → 등록 → 새로 고침 전 복사에서만 나므로 낮음이다.
  - 제안(둘 중 하나):
    - `copyPath`가 그 항목의 부모 디렉터리를 `listWorkspaceDir`로 한 번 더 받아, 그 이름이 지금도 가려지지 않았음을 확인한 뒤 쓴다.
    - 설정 변경(가릴 값 추가)이 쓰이면 주 프로세스가 그 작업 공간의 트리 id를 지우고, 창이 다시 나열한다.

**정보**
- **I1** 트리는 이름 붙인 설정 파일이 없을 때 `invalid_config`, 설정이 대는 `secretEnv` 변수가 없을 때 `secret_env_missing`으로 통째로 알린다(`TREE.log`).
  - 설계에 적은 동작이다(U-103 줄: "설정 파일을 읽을 수 없으면 … 트리도 그 코드로 알린다").
  - 기본 위치에 설정 파일이 아예 없는 처음 상태에서는 트리가 나열된다(`TREE-NOCONFIG.log`).
  - main의 임시 트리는 설정과 무관하게 나열했으니, 변수 하나가 없을 때 트리를 못 보는 것은 달라진 점이다.
- **I2** 가림은 간편 형식(설정 파일)의 등록 값과 지금 키 값으로 한다. task 파일의 `privacy.secretEnv`나 변수 파일만 등록하는 값(U-63 실행)은 트리 이름에서 가려지지 않는다. 설계에 "가림과 보호 표시는 프로필 없는 간편 실행의 것"이라 적혀 있다.
- **I3** 엔진 호스트에 가린 폴더의 실제 경로를 직접 대면 앱 계층이 나열한다(`sec-<값>`: listed 1). 주 프로세스는 그 이름을 모르므로 그 경로를 만들 수 없다. 창에서 닿는 길은 없다.

## U-64 (`0457bba`)

**변경:**
- 엔진 호스트가 끝나면 주 프로세스가 창에 `engineState`를 보내고, 창은 카드와 "엔진 다시 시작" 단추를 보인다.
- `restartEngine()`은 앞 호스트가 정말 끝났을 때만 새로 띄운다(`gui/src/main/app.ts`의 `restartEngine`, `launchHost`).
  - 돌고 있으면 `engine_running`, 띄우는 중이면 `engine_starting`, 앱을 끝내는 중이면 `app_closing`이다.
- 자동으로 다시 띄우지 않는다.

| PM이 볼 것 | 결과 |
|---|---|
| 다시 시작이 토큰·핸들·미리보기를 버리는가 | **버리지 않는다. 설계가 그렇게 정했다**(U-64 줄: "메인이 가진 토큰(미리보기·계획·제안)은 한 번만, 짧은 시간만 쓰이고 앱 계층이 다시 확인하므로 그대로 둔다"). 아래에서 종류마다 확인했다 |
| 다시 시작 중의 요청이 닫힌 쪽으로 가는가 | 가지 않는다(코드). 아래 |
| 도는 실행이 있을 때 | 호스트가 살아 있으면 다시 시작은 `engine_running`이다. 호스트가 죽으면 `runs.hostExited()`(`gui/src/main/runs.ts:112-120`)가 그 실행을 `adapter_host_exited`로 끝내고 진행 표시를 내린다. 그 뒤에야 다시 시작할 수 있다. 그 실행이 잡았던 작업 공간 잠금은 죽은 호스트 pid의 것이라 새 호스트가 거둘 수 있다(T-9) |

**다시 시작 중의 요청**
- `launchHost()`는 동기로 `hostState`를 새 `startHost(...)` 약속으로 바꾼다. 그 뒤에 오는 요청의 `deps.host()`는 새 호스트를 기다린다.
- 끝난 뒤 다시 시작 전의 요청은 `adapter_host_exited`다(연기 `whileEnded`).
- 끝난 호스트 객체에 대한 `call`은 엔진 클라이언트가 곧바로 `hostExited`로 돌려준다(`engine-client.ts:181-182`).
- 옛 호스트의 늦은 종료 알림이 새 `hostState`를 덮을 수 있는지 봤다. 없다. `exited = true`와 종료 리스너 호출이 같은 `exit` 처리기 안에서 동기로 일어나고(`engine-client.ts:160-164`), 다시 시작은 `exited`가 참일 때만 하기 때문이다.

**토큰 종류별 확인**: 다시 시작 뒤 쓰면 모두 앱 계층이 다시 본다(코드).

| 토큰 | 다시 확인하는 곳 |
|---|---|
| 계획 승인 | apply가 다이제스트와 사전 점검을 다시 한다 |
| 설정 제안 | `baseDigest` |
| 정리 미리보기 | 계획 다이제스트(`cleanup_plan_changed`) |
| 되돌리기 미리보기 | 파일마다 다시 확인 |
| DR-25 재시도 | 그 실행 id로만 |
| 모델 목록 항목 | 모델 id를 쓴다 |

엔진 호스트가 발급한 실행 토큰은 새 호스트가 모르므로 실패로 닫힌다.

**정보**
- **I1** 연기 시험(`engineRestart`)이 본 것: 카드, 끝난 동안의 호출 실패, 자동 재시작 없음, 단추로 새 호스트(pid 다름), 카드 숨김, 다시 시작 뒤 doctor ok, 두 번째 다시 시작 `engine_running`. 다음은 코드로만 확인했고 재지 않았다.
  - 띄우는 동안 들어온 요청
  - 실행 도중 호스트가 죽은 경우
  - 다시 시작 전의 토큰을 다시 시작 뒤에 쓴 경우
- **I2** 트리 id와 작업 공간 핸들도 다시 시작 뒤에 그대로다. 주 프로세스가 발급한 것이고 경로로만 풀리므로 호스트와 무관하다.
