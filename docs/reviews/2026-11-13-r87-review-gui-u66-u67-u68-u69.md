**변경:**

**실험:** `.codaryn/r87/probe.mjs`, `PROBE.log`. 실제 엔진 호스트의 `doctor { workspace }`(주 프로세스가 보내는 꼴)를 부르고, 앞뒤 작업 공간(상태 폴더 포함)을 항목·크기·sha256으로 비교했다.

| 경우 | `doctor`의 잠금 점검 | 작업 공간 |
|---|---|---|
| 상태 폴더 없음 | ok `doctor.lock.none` | 바뀌지 않음(`.codaryn`도 만들지 않음) |
| 살아 있는 다른 프로세스가 store `acquireLock`으로 잡은 잠금 | warn **`doctor.lock.held`** → 창이 새 작업을 끈다 | 바뀌지 않음 |
| 그 프로세스를 핸들로 끝낸 뒤(죽은 잠금) | ok `doctor.lock.stale` → 새 작업은 켜진 채(실행이 거둔다) | 바뀌지 않음. `doctor`는 죽은 잠금을 거두지 않고 그대로 둔다 |

- 이 창 자신의 실행이 잡은 잠금은 "다른 실행"으로 치지 않는다(`ownRunHere`).
- 막는 판정은 실행을 시작할 때 앱 계층이 다시 한다. 점검은 먼저 알릴 뿐이다.

  - 실패 경우: 다른 프로세스(예: CLI 실행)가 끝나도 실행 단추는 꺼진 채 남는다. 사람은 F5를 눌러야 한다는 것을 모른다.
  - 연기 시험도 잠금 파일을 지운 뒤 F5를 눌러서 다시 켰다(`smoke.ts`의 `pressF5`).
  - 제안: 문구에 "끝나면 F5로 다시 확인하세요"를 더하거나, 잠금이 보이는 동안 몇 초마다 점검을 다시 한다.

**정보**
- **I1** "task 파일 고르고 실행…" 단추는 잠금이 보여도 꺼지지 않는다(`applyLock`은 실행 단추만 다룬다). task 파일이 같은 작업 공간을 고르면 앱 계층이 `workspace_locked`로 막고, 다른 작업 공간을 고르면 상관없다. 해는 없다.

## 정정 (R-81)

R-81의 `kill-child.mjs`는 자식이 `await new Promise(() => {})`로 기다리게 했다. 이것은 Node의 이벤트 루프를 붙잡지 않는다. 그래서 그 자식은 부모가 핸들로 끝내기 전에, 시험 링크(또는 잠금)를 만든 직후 스스로 끝났을 것이다. "시험 링크를 만든 직후 프로세스가 끝나면 무엇이 남는가"라는 결과와 판단(R-81 L1)은 같다. 다만 "핸들로 끝냈다"는 서술은 "그 순간 끝났다"로 읽어야 한다.

이번에 같은 꼴로 처음 잰 잠금 결과는 거짓 경보였다(자식이 끝나 실제로 죽은 잠금이었음). 자식이 살아 있게 고쳐(`setInterval`) 다시 쟀고, 위 표는 고친 뒤의 것이다.
