# R-95 — U-124

## 판단: 병합해도 된다

권한 질문의 길(엔진 → 앱 계층 `RunObserver.confirm` → 엔진 호스트 → 메인 → OS 대화상자 → `answerQuestion`)에서 창(렌더러)이 답할 길은 없다. 답은 한 번만, 그 실행·그 질문에만 받는다. 답이 없는 모든 경우는 거부가 된다. 넓히기 쪽 두 변경과 연기 시험의 고정값 두 변경도 문제없다.

연기 시험은 다섯 번 중 한 번 실패했다(167/216). 실패한 곳은 U-124 의 질문 실행보다 앞 단계다. main 다섯 번은 모두 통과했지만, 이 횟수만으로는 U-124 탓인지 가를 수 없다. 담당이 처음 보고한 흔들림(첫 실행의 진행 목록 누락)은 main 에도 있는 경합 때문이고, 그 경합은 U-144 가 고친다. 아래 (6)에 적었다.

  - main 판에 150 ms 를 넣어도 같은 모양으로 멈췄다(위 수치의 지연 실험 표). 곧 U-124 가 만든 것이 아니다.
- 1회차의 "5j2 가 시작되지 않음"은 이 경합만으로는 설명되지 않는다. 바로 앞에 실행 시작이 없고(분석 실행 뒤 5j2 까지는 화면 이동·정리뿐), 분석 실행의 결과는 정상으로 보였다. 다만 5j2 실행이 모델에 묻기 전에 바로 끝났다면(잠금 등), 그 끝을 창이 버려 "실행 중"에 남는 같은 꼴이 된다. U-144 뒤에도 다시 나오면 `startsBlocked` 가 가려 줄 것이다.

결론: U-124 가 흔들림을 만든다는 증거는 없다. 담당이 본 증상은 main 의 결함이고 U-144 가 고친다.

## 정보

### I-1. Esc 와 대화상자 닫기는 "사람이 거부"(`by: user`)로 기록된다

- 설계 3.6 이 그렇게 정했고, 담당 시험도 그렇다. CLI 는 Enter·다른 글자가 사람 거부, 입력 끝(Ctrl+D)이 `dismissed`(default)다.
- GUI 에는 CLI 의 입력 끝에 해당하는 것이 없다. Esc 를 사람의 행동으로 보는 것은 맞다고 본다. 바꿀 것 없음.

### I-2. 제어·방향 글자는 묻지 않는 대신 `?` 로 바뀌어 보인다

- 설계 3.6 은 "메인이 꼴을 다시 본다: 제어·방향·보이지 않는 글자 없음. 아니면 묻지 않고 답이 없는 것으로 친다"라고 적는다.
- 실제로는 호스트의 `shown`(cleanText)이 먼저 LF·TAB·C1·방향 글자를 `?` 로 바꾸므로, 메인의 검사에 걸리는 것은 cleanText 가 남기는 폭 없는 글자 등뿐이다.
- CLI 질문도 cleanText 로 같게 보이므로 뜻은 같다. 사람이 보는 것은 바뀐 글자가 드러난 이름이다. 위험은 없다. 원하면 설계 문장에 "호스트가 먼저 `?` 로 바꾼다"를 더하면 된다.

### I-3. 연기 시험 1회차 실패(위 6)

- U-124 의 코드 길보다 앞 단계였고, main 에서는 다섯 번 모두 통과했다. 원인은 확정하지 못했다.
- U-144 의 연기 시험 정리 변경(마지막 정리의 EPERM 이 수를 지우지 않음)과 U-123 의 `startsBlocked` 가 다음 재현 때 원인을 남길 것이다.

# R-96 — U-144

## 판단: 병합해도 된다

창의 `RunModel`(`gui/src/renderer/run/run-model.ts`)이 "starting" 중에 온 진행 묶음과 끝을 두었다가, `started(runId)` 때 답이 말한 실행의 것만 온 순서대로 받는다. 늦춤 150 ms·400 ms 에서도 연기 시험이 모두 통과하고, 고치기 전 판은 같은 늦춤에서 멈춘다. 다른 실행의 것은 섞이지 않는다. 묶음 수에 상한이 있고, 넘치면 진행의 빠짐으로 알린다.

## 중점별 결론

### (1) 고침이 경합을 닫는가

**닫는다.**

- 지연 실험(위 수치): U-144 판은 150 ms, 400 ms 에서 216/216 이다. main 판(150 ms)과 U-124 판(400 ms)은 같은 늦춤에서 240초 한도에 걸린다.
- 탐침 `endBeforeAnswer`(진행 → 끝 → 답 순서):
  - 고치기 전: `running`, 항목 0, `canStart: false`. 창이 멈추고 새 실행도 시작할 수 없다.
  - 고친 뒤: `done`, 항목 `["a"]`, 해당 실행의 끝, `canStart: true`.
- 실행을 시작하는 창의 호출 네 곳이 모두 같은 모델을 지난다. 넷 다 `starting()`(적용은 `startingApply()`) 뒤에 `started()` 를 부른다.
  - 새 작업 `startRun`(`new-task.ts:125`), task 파일 `startTaskRun`(`new-task.ts:168`), 적용 `applyPlan`(`plan-screen.ts:179`), DR-21 동의 뒤 적용 `applyPlan(…, true)`(`run-screen.ts:86`).
  - 결과 화면의 "다시 실행"(`run-again`)은 새 작업 화면을 여는 단추라 첫째 길을 탄다.
  - 탐침 `applyStart` 로 적용 쪽도 확인했다(`done`, 항목 유지).
- 메인 쪽 순서(begin → gui-state → 답)는 그대로다. 받는 쪽에서 두는 방식이라, 답과 `send` 가 창에 닿는 순서에 기대지 않는다. task 파일·적용 경로처럼 await 없이 begin 하는 곳에서도 begin 이 이른 메시지를 답보다 먼저 보낼 수 있는데, 그것도 함께 닫힌다.

### (2) 다른 실행의 이벤트가 섞이지 않는가

**섞이지 않는다.**

- `started()` 는 `payload.runId === runId` 인 묶음만 받는다. 답 뒤에는 기존 검사(`payload.runId !== this.runId` 이면 버림)가 그대로다.
- 탐침 `otherRunMixed`: 답 앞뒤에 다른 실행의 묶음을 끼웠다. 항목은 `["a","b","c"]` 로 이 실행의 것뿐이다. 수(`turns 3, tools 1`)도 이 실행의 마지막 묶음 값이다.
- 끝도 같다. 다른 실행의 끝은 `started()` 에서 runId 가 맞지 않아 받지 않는다(담당 시험 2).
- 시작이 거부되거나(`failedToStart`) 새로 시작하면(`starting`) 둔 것을 잊는다. 탐침 `refusedThenStart`: 거부된 시작의 항목과 끝이 다음 시작에 넘어가지 않았다.
- 이 앞단에서 메인 `RunManager` 가 이미 활성 실행의 토큰만 창에 보낸다. 창이 다른 실행의 것을 받을 길은 지금 없다. 모델의 runId 검사는 그 위의 한 겹 더다.

### (3) 버퍼에 상한이 있는가

**있다.**

- 묶음 수: `MAX_EARLY_EVENTS` = 100. 넘치는 묶음은 버리고 `earlyLost` → `started()` 에서 `gap` 이 된다. 끝은 하나(`earlyDone`)만 둔다.
- 묶음 하나의 크기: 창의 `asRunEvents` 는 수를 세지 않는다. 메인의 `parseHostMessage` 가 묶음당 항목 2000개(`MAX_RUN_ITEMS`), 항목당 4000자(`MAX_RUN_ITEM_CHARS`)를 넘는 줄을 받지 않으므로, 그것이 상한이 된다.
- 받은 뒤에는 기존 상한 `MAX_KEPT_ITEMS` = 5000 으로 잘린다.
- 탐침 `bound`: 2000개짜리 묶음 101개 → 앞의 100개를 두고 101번째는 버림. 받은 뒤 항목은 마지막 5000개(`97:1000` ~ `99:1999`), `gap: true`.
- 메인 쪽 이른 보관도 그대로 상한이 있다(토큰 4개, 토큰마다 200개).

### 연기 시험 스크립트 변경

- 마지막 정리(생명 시험 뒤 `life-profile` 등 지우기)의 예외를 잡아 "left for the next run: …" 으로 이름을 대고 넘어간다.
- 검사가 아니라 정리다. 검사 수와 조건은 바뀌지 않았다. 이전에는 이 EPERM 이 결과 수를 내기 전에 스크립트를 끝냈다.
- 이번 일곱 번(다섯 차례와 늦춤 둘)에는 남긴 것이 없었다. 생명 시험 `hostEndsWhenMainKilled`·`hostEndsWithQuit` 도 모두 통과했다.

## 정보

### I-1. 둔 끝이 하나뿐이고, 다른 실행의 묶음이 넘쳐도 이 실행에 빠짐이 붙는다

- 탐침 `ownEndThenOtherEnd`: 이 실행의 끝 다음에 다른 실행의 끝이 오면, 뒤의 것이 앞의 것을 덮는다. 그러면 이 실행은 `running` 에 남는다.
- 탐침 `overflowByOtherRun`: 다른 실행의 묶음만 101개 와도 이 실행의 진행에 `gap: true` 가 붙는다.
- 둘 다 지금은 생길 수 없다. 메인이 활성 실행의 것만 보내고, 앞 실행의 끝은 새 시작보다 먼저 창에 닿기 때문이다(그래야 `canStart` 가 참이 된다).
- 모델만 따로 단단하게 하려면 끝을 runId 로 골라 두고, 넘침도 runId 별로 세면 된다. 지금 바꿀 필요는 없다.

### I-2. 상한은 묶음 수로 센다

- 최악의 경우는 메인의 꼴 검사 한도 그대로 100 × 2000 항목 × 4000자다. 이만큼을 `started()` 까지 잠시 들고 있다.
- 실제로는 엔진 호스트가 100 ms 마다 그 실행의 기록에서 나온 묶음 하나를 보내고, "starting" 은 gui-state 쓰기 동안뿐이라 아주 작다.
- 원하면 항목 수(예: `MAX_KEPT_ITEMS`)로 세면 받은 뒤의 상한과 같아진다. 지금 바꿀 필요는 없다.
