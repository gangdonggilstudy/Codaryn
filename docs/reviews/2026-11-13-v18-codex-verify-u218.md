## 승인과 권한 질문의 구분 및 시험 방법

공개 `createCodarynApp`으로 만든 앱의 `startRun`, `applyPlan`, `revert`를 직접 호출했다. 모델은 대본 제공자이며 제품 파일은 수정하지 않았다.

이 API에서 **계획 승인은 `ApplyPlanRequest.digest`로 전달**한다. 전체 계획 승인을 묻는 별도의 observer 함수는 없다. GUI 등 호출자가 사람의 계획 승인을 받은 뒤 `applyPlan`을 호출하는 계약이다. `ApplyObserver.confirm`은 이미 승인된 계획을 실행하는 중 **개별 명령 권한**을 묻는다. 따라서 유효한 다이제스트로 적용할 때 observer가 없다고 모든 파일 도구를 막는 계약은 아니다.

권한 질문 시험 8개에는 다음 제한이 있다.

- `scripted` 제공자는 task 파일에서만 사용할 수 있다(`src/cli/config.ts:74`). task 파일은 자체 policy가 필수이고, 그 명령 규칙에는 `confirm`을 넣을 수 없다(`src/cli/task.ts:329`). config의 질문 규칙을 task의 policy에 자동으로 합치지도 않는다.
- 따라서 이 8개만 공개 테스트 훅 `AppHooks.runApprovedPlan`에서 **실제 정책 게이트**에 `confirm: true`를 넣었다. `createWorkspace`, `createPolicyGate`, `runApprovedPlan`은 후보의 실제 구현이고, 계획 파일 목록과의 교집합도 그대로 전달했다.
- confirm 함수를 직접 호출하거나 엔진 결과를 만들어 돌려주지 않았다. 대본이 실제 `run_command`를 요청하고, 엔진이 질문을 만들며, 앱이 observer로 전달하는 길을 실행했다. 허용 사례에서는 실제 로컬 Node 명령이 합성 파일을 썼다.
- **설정 파서부터 질문까지 훅 없는 대본 모델 통합을 통과했다고 주장하지 않는다.** 나머지 독립 검사 15개는 엔진·정책 테스트 훅 없이 공개 앱을 호출했다.

## 취소 후 남는 것

독립 검사는 첫 파일의 `file_changed` 이벤트에서 취소했다. 한 파일의 바이트를 절반만 쓴 상태를 만든 것이 아니라, **계획의 두 파일 중 첫 파일만 적용된 상태**다.

| 취소 시점 | 결과 | 사용자 파일 | applied 기록 | done 뒤 잠금 | 같은 계획 재적용 |
| --- | --- | --- | --- | --- | --- |
| handle을 받은 직후 | cancelled/cancelled, 모델 0턴 | 변경 0 | 없음 | 없음 | 성공 |
| 첫 model_request 이벤트 | cancelled/cancelled, 기록상 모델 1턴 | 변경 0 | 있음 | 없음 | plan_already_applied |
| 첫 file_changed 이벤트 | cancelled/cancelled, 모델 1턴 | 첫 파일은 새 글 전체, 두 번째 파일 없음 | 있음 | 없음 | plan_already_applied |
| 명령 질문의 응답 대기 중 | cancelled/cancelled, 모델 1턴, 질문 signal.aborted=true | 명령 실행·파일 변경 0 | 있음 | 없음 | 소비된 상태 유지 |

- 위 4개 모두 `handle.done` 결과와 디스크 `result.json`이 정확히 같고, 저널의 마지막 `run_finished` 상태가 `cancelled`임을 추가 검사했다. `cancel-record-check.json` 참조.
- 첫 파일 적용 뒤 취소한 별도 사례에서 원본 스냅샷의 실제 바이트를 확인했다. 공개 `app.revert`는 `complete`였고 모든 사용자 파일이 실행 전 내용과 일치했다. 원래 계획의 applied 표시는 유지되고 잠금은 남지 않았다.
- 정상 취소 경로에서 `lockLeft`는 발생하지 않았다. 관련 기존 유닛 시험에서는 Windows의 다른 프로세스가 잠금 파일의 삭제를 잠시 막는 실제 조건을 만들어 `lockLeft: true` 및 후속 재시도 해제를 검증했으며 통과했다.

## 미실행과 한계

- 실제 API·외부 네트워크·키 파일 조회 없음. 독립 검사와 유닛 프로세스에는 네트워크 차단 preload를 사용했다. 자식 CLI·시험 프로세스에는 운영에 필요한 환경 변수만 넘겼다.
- GUI/Electron·GUI 승인 화면·실제 모델·전체 시험 묶음은 실행하지 않았다.
- 권한 질문 8개의 정책 주입 제한은 앞 절과 같다. 대본 모델과 설정 계약의 제한 때문에 설정 파서부터 이어지는 훅 없는 권한 질문 경로는 미검증이다.
- 승인된 `run_command`가 계획 목록 밖에 쓸 수 있는 B-8의 기존 한계를 새 차단 보장으로 바꾸어 평가하지 않았다. 목록 밖 쓰기 거부는 `write_file`에 대해 검증했다.
- 전원 종료·프로세스 강제 종료·모든 파일 쓰기 중간 시점의 취소를 망라하지 않았다. 검사한 취소는 공개 handle과 실제 관찰 이벤트를 통한 협조적 취소다.
- V-14에서 알려진 한계로 채택된 계획 기록의 작업 공간 간 복사는 이번에 새 결함으로 재집계하지 않았다.
- 확인 범위에서는 추가 수정 요청 사항이 없으며, 채택 판단은 PM 몫이다.
