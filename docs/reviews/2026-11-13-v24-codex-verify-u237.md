## M-1 — 설정·프로필에서 온 읽기 제외가 checkApply에서 빠진다

**중간, 4개 재현.** 실행 계획과 이동 계획 각각에서 설정·프로필 2개 출처가 영향을 받는다.

- 위치: `head/src/app/app.ts:935`, `head/src/app/changes-plan.ts:99`, `head/src/app/check-apply.ts:184`.
- `checkRunPlan`은 `probe.task.policy`와 writable 목록만 전달하고 합쳐진 `task.unreadablePaths`를 전달하지 않는다. 이동 계획의 사전 점검도 `createPolicyGate`에 합쳐진 읽기 제외를 주지 않는다.
- 재현: 읽기 제외가 없을 때 `private/secret.txt`의 수정 계획 또는 이동 계획을 만든다. 이후 config 또는 선택 프로필에 `unreadablePaths: ["private"]`를 추가한다. task policy에는 읽기 제외가 없다. 공개 `app.checkApply({settings, planRunId, digest})`를 호출한다.
- 실제: **`ok: true`, `problems: []`**. 새로 금지된 계획 파일을 문제없다고 답한다.
- 대조: 정의와 task에 읽기 제외를 더한 두 출처에서는 `[{index:0, problem:"denied"}]`로 답한다. 이들은 task.policy 쪽에 반영돼 우연히 같은 누락을 피한다.
- 이동 계획의 실제 `app.applyPlan`도 이어서 호출했다. 네 출처 모두 실제 적용은 **`plan_stale`**로 거부했다. 즉, config/profile의 **점검 결과와 실제 적용 판정이 서로 다르다**. 이 재현에서 금지된 이동이 실행된 것은 아니다.
- 원문: 최종 결과 폴더의 `config-check-run`, `profile-check-run`, `config-check-move`, `profile-check-move`; `findings-evidence.json`의 `moveChecks`.
- 재현 명령: `node probe.mjs "check"`.

권고: 점검 경로도 실행과 같은 합쳐진 읽기 제외를 받아 같은 관문을 구성해야 한다. 사전 점검의 `problems: []`를 승인 가능으로 해석하는 GUI가 잘못 안내하지 않도록 앱 함수 수준 회귀 시험을 추가한다.

## M-2 — 새로 읽기 제외한 파일의 변경 보기에서 이전 원문이 반환된다

**중간, 4개 출처 모두 재현.** 현재 읽기 제외가 앱 반환값의 변경 본문까지 막아야 한다는 V-24 검사 기준을 충족하지 못한다.

- 위치: `head/src/app/app.ts:425` / `:433`, `head/src/app/changes.ts:85` 이후 `readChanges` 경로.
- `changes()`는 현재 설정으로 secrets를 읽지만, `readChanges`에는 privacy gateway만 넘긴다. 현재 읽기 제외 목록이나 이를 판정할 관문을 넘기지 않는다.
- 재현: 제외가 없는 상태에서 표지가 든 `private/secret.txt`를 공개 대체 문장으로 수정하는 실행을 한다. 이후 config / profile / definition / task 중 한 곳에 private을 읽기 제외로 추가한다. 공개 `app.changes({settings, runId})`를 호출한다.
- 실제: 네 출처 모두 `ok: true`, `files[0].state: "as_run_left"`, `files[0].before`에 **이전 비공개 원문 표지**가 들어 있다. 새 대체 문장에는 표지가 없다.
- 이 표지는 제외를 추가하기 **전에 합법적으로 저장된 원본 스냅샷**에서 나온다. 이미 저장한 기록 전체를 삭제하라는 요구와는 구분한다. 문제는 현재 제외 설정을 적용해 달라는 변경 보기 호출에 원문을 다시 돌려준다는 점이다.
- 앱 반환값에서 관찰했다. 이 시험을 새 모델 요청으로의 누출이라고 주장하지 않는다. 제외를 처음부터 유지한 정상 실행의 이벤트·결과·변경 보기에서는 표지 누출이 없었다.
- 원문: 최종 폴더의 `*-changes` 사례, calls.json의 `changes-new-exclusion`, `findings-evidence.json`의 `changes`.
- 재현 명령: `node probe.mjs "changes after newly"`.

권고: 변경 보기에서 현재 제외 정책의 적용 범위를 명시하고, V-24 요구대로라면 제외된 파일의 before/after를 읽거나 반환하기 전에 차단한다. 사람이 보는 변경 본문을 모델의 읽기 제외와 별개로 허용하려는 제품 결정이라면, 이 관찰을 알려진 예외로 명시해야 한다.

## M-3 — 이 후보의 applyPlan은 실행 계획을 수행하지 못한다

**중간, 네 출처 모두 동일.** 이 항목 때문에 승인 실행 계획의 읽기 제외·query_table·이벤트 검사는 실행 단계에 진입하지 못했다.

- 위치: `head/src/app/app.ts:819`, `head/src/cli/plan-commands.ts:967`.
- 앱은 `runApply`에 이동용 engine/adapter/cancel 경로를 전달하지만, 실행 계획을 위한 `run` 환경을 전달하지 않는다. 공통 assembly에 approvedPlan 구성 요소가 생겨도 이 호출 경로가 연결되어 있지 않다.
- 재현: `plan: "run"` 작업 종류로 공개 docs 파일의 changes 계획을 `app.startRun`으로 만든다. 대본을 공개 파일 쓰기와 비공개 접근 시도로 바꾼 뒤 올바른 digest로 `app.applyPlan`을 호출한다.
- 실제: handle 없이 **`ok:false / internal_error`**, 메시지는 `this build cannot carry out a run plan here; nothing was sent or written`.
- 네 사례 모두 실행 폴더는 계획 생성용 **1개뿐**, applied 표시 없음, 공개 파일 변화 없음. 수행 중 읽기 제외가 잘 작동한다고 세지 않았다.
- 원문: 최종 폴더의 `config-carry`, `profile-carry`, `definition-carry`, `task-carry`; `findings-evidence.json`의 `carrying`.
- 재현 명령: `node probe.mjs "carried"`.

이는 V-18에서 확인했던 실행 계획 어댑터 경로가 이 지정 판에 없는 상태다. 올바른 통합 후보에서 해당 연결을 포함한 재검증이 필요하다.

## 미실행·판정 한계

- 실제 API·외부 네트워크·키 파일 조회·권한 상승 요청 없음. 네트워크 차단 preload를 사용했고 모든 자료는 합성이다.
- GUI/Electron, 전체 시험 묶음, 실제 모델은 실행하지 않았다.
- M-3 때문에 앱의 승인 실행 계획 내부에서의 읽기 제외·표 질의·취소·권한 질문·CLI 동등성은 **미검증**이다. startRun의 결과로 대신 통과시키지 않았다.
- 기준 커밋을 임의 병합해 시험하지 않았다. 이번 보고서는 eb72ba9 자체의 관찰이며 올바른 통합판의 결과가 아니다.
- PM에게 필요한 판단: 기준과 실행 계획 어댑터 연결을 포함한 후보를 지정하고, M-1 및 M-2의 적용 범위를 정해 재검증해야 한다.
