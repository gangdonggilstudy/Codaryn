주요 사례와 확인한 성질:

- ko/en × text/JSON의 미리보기·정상 삭제·잠금 해제 실패 안내가 동일했다. 미리보기 4사례는 쓰기 시도와 최종 변경 모두 0이다. `--dry-run`이라는 별도 옵션은 양쪽 모두 `invalid_arguments`로 거부한다. cleanup의 읽기 전용 방식은 `--confirm` 없는 미리보기다.
- 선택된 실행 기록만 지웠고 사용자 파일은 보존했다. 미복구/손상 기록은 별도 동의가 없으면 남고, 폐기 파일도 별도 동의가 없으면 남았다. 표식 없는 `cleanup-<hex>` 폴더는 보존하고 자기 표식이 있는 잔여 폴더는 제거했다. 근거: `src/store/cleanup.ts:373`, `:630`, `:667`, `:679`, `:711`.
- `.codaryn/runs`, 개별 run, discarded 폴더, run 내부의 정션과 run 안의 하드 링크를 구성했다. 삭제 대상 밖 합성 sentinel은 모두 보존됐다. run 내부 정션은 링크 자체만 제거됐다. `.codaryn` 정션의 메타데이터 쓰기는 M1로 분리했다. 일반 파일 심볼릭 링크 생성은 `EPERM`으로 불가능해 시험하지 못했다.
- 다른 살아 있는 프로세스의 점유 잠금은 `workspace_locked`, 최종 변경 0. 틀린 다이제스트와 점유 잠금을 겹치면 다이제스트 거부가 먼저이며 쓰기 시도 0이었다.
- 미리보기 뒤 기록을 추가하면 `cleanup_plan_changed`. 별도로 실제 lock 파일의 배타 link가 성공한 직후 기록을 추가했을 때도 잠금 아래 재계획으로 거부하고 삭제하지 않았다. 잠금은 해제됐다. 근거: `src/cli/cleanup.ts:241`, `src/store/cleanup.ts:625`, `:629`, `:630`.
- 실제 CLI에서 lock 제거에 지속 EBUSY/EPERM을 주입했다. 6회 시도 뒤 JSON에 `lockLeft: true`, 기존 삭제 결과와 상태/종료 코드는 유지됐다. 한 번만 EBUSY이면 재시도 성공, `lockLeft` 없음. 대상 CLI의 관측 전체 소요 시간 최대 약 1,200ms; 코드의 재시도 대기 합계는 775ms이며 시스템 실행 시간의 상한을 보증하지 않는다. 근거: `src/store/lock.ts:639`, `:648`; `src/store/cleanup.ts:765`.
- 같은 작업 공간에서 CLI와 앱의 summary·plan·다이제스트가 같았고, 복제한 작업 공간에서 결과 상태·outcome도 같았다. 손상 기록·보관함 동의·점유 잠금·해제 실패·잠금 아래 변경·정션·하드 링크를 포함했다. CLI와 앱의 기존 오류 문구 차이는 보존됐다.
