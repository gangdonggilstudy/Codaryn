## L-1 — applyChangesPlan이 이동 계획을 거부하지 않고 수행함

**위치:** head `src/cli/plan-commands.ts:255`, `:256`, `:349`; dispatch는 `src/app/apply-life.ts:250` 이하. old 기준은 base `src/cli/plan-commands.ts:590`~의 설명 및 `:605`의 helper, `:609`의 wrong-kind 검사다.

옛 helper는 먼저 저장된 계획을 읽고 **계획 kind가 changes가 아니면 task mode와 무관하게 거부**했다. 새 helper는 조건 없이 applyThroughApp을 호출한다. 그 안의 applyLife는 task mode가 apply이면 이동 계획을 수행하므로, 이전에 거부되던 직접 호출이 파일 이동·폐기를 할 수 있다.

### 정확한 재현과 효과

`R/v39-extra.mjs`는 각 버전에 대해 실제 CLI로 새 계획을 만들고, 해당 버전의 공개 export `applyChangesPlan(io, parsedArgs, prepared)`를 직접 부른다. 준비는 실제 parseApplyArgs와 prepareFor를 사용한다. 비교하려는 resolved task의 plan 필드만 run/apply/none으로 바꿔 2 kinds × 3 modes × 2 versions, **직접 호출 12회**를 수행했다. 다이제스트는 그 계획의 앞 12자이며 승인 없는 호출이 아니다.

핵심 재현: 저장 계획은 moves, resolved task.plan은 apply. 파일은 `inbox/a.txt = "alpha\n"`, `inbox/old.tmp = "old\n"`; 계획은 전자를 sorted/a.txt로 옮기고 후자를 discard한다.

old의 결과:

```json
{
  "code": "run_not_plan",
  "message": "that run made a plan of moves and discards (plan \"apply\"), but the task given to apply resolves to plan \"run\"; give the task the plan run used; nothing was run",
  "hint": "plan_kind_differs"
}
```

exitCode 2. applied.json 없음, 적용 실행 없음, 잠금 없음. 작업 파일 둘 모두 원본 그대로다. 문구는 실제 prepared task가 apply여도 옛 helper가 고정된 run 문구를 쓰는 것까지 포함한 실제 값이다.

head의 결과는 `kind: "apply", status: "done", reason: "verified", exitCode: 0`이다. 계획의 applied.json이 생기고 수행 실행 journal/result가 기록된다. `inbox/a.txt`는 없어지고 `sorted/a.txt = "alpha\n"`가 생긴다. `inbox/old.tmp`는 없어지고 `.codaryn/discarded/<applyRunId>/` 아래 파일로 보존된다. 종료 후 잠금은 없다. 즉 검사 문구만의 변화가 아니라 claim·파일 이동·폐기 효과의 확대다.

모든 직접 호출 결과:

| stored kind | prepared task.plan | old | head |
|---|---|---|---|
| changes | run | verified/0, summary.md 생성·claim | 같은 효과 |
| changes | apply | verified/0, summary.md 생성·claim | run_not_plan/2, 쓰기·claim 없음 |
| changes | none | verified/0, summary.md 생성·claim | run_not_plan/2, 쓰기·claim 없음 |
| moves | run | run_not_plan/2, 부작용 없음 | 같은 오류 문구·hint·부작용 없음 |
| moves | apply | run_not_plan/2, 부작용 없음 | **verified/0, 이동·폐기·claim** |
| moves | none | run_not_plan/2, 부작용 없음 | run_not_plan/2, 부작용 없음. 문구는 no plan mode로 바뀜 |

changes + apply의 새 오류 문구:

```text
that run made a plan of files to write (plan "run"), but the task given to apply resolves to plan "apply"; give the task the plan run used; nothing was moved
```

changes + none의 새 오류 문구:

```text
that run made a plan of files to write (plan "run"), but the task given to apply resolves to no plan mode; give the task the plan run used; nothing was moved or run
```

moves + none의 새 오류 문구:

```text
that run made a plan of moves and discards (plan "apply"), but the task given to apply resolves to no plan mode; give the task the plan run used; nothing was moved or run
```

이 세 새 오류의 hint는 모두 plan_kind_differs다. changes + apply/none은 문서상 task mode 전제를 벗어나므로 위 표에 별도 관찰로 남긴다. L-1의 실제 확대 사례는 moves + apply다.

### 문서 전제와 제품 호출자 전수 확인

old 설명은 `codaryn apply of a plan of kind "changes" (the task resolves to plan: "run")`라고 전제를 적고, 이 경로를 CLI 파서가 아직 연결하지 못하던 시기에 **시험을 위해 export**했다고 적는다(base plan-commands.ts:590, :602). 동시에 같은 설명은 **다른 kind를 run_not_plan으로, 묻거나 보내거나 쓰기 전에 거부**한다고 명시한다. 따라서 “run 계획이 전제니까 다른 kind 거부는 호환성 대상이 아니다”라고 단정해서는 안 된다. 새 주석도 `Compatibility entry point ... (plan A)`라고 한다(head :254).

제품 소스의 호출 관계를 src·gui/src·scripts 전체에서 검색한 결과:

| 버전 | 직접 제품 호출자 | 연결 |
|---|---|---|
| old | **한 곳:** `src/cli/plan-commands.ts:326` | runApply가 `mode === "run"`일 때만 applyChangesPlan을 호출한다. |
| head | **없음** | `runApply`는 :251에서 applyThroughApp을 바로 부른다. :255는 export 정의만 남는다. |

| 양쪽의 앱 진입 | `src/app/app.ts:946` | 공개 app.applyPlan이 runApply를 호출. helper 직접 호출 아님. GUI는 공개 앱 경로를 사용하며 helper 직접 참조 없음. |

`src/app/index.ts`는 이 helper를 공개 앱 export로 내보내지 않는다. 직접 시험 호출자는 `tests/unit/cli/g-u195-apply-run-plan.test.ts`이며 `u280-dist-old-paths.test.ts:76`은 export 이름의 존재를 보존한다. 이 존재 시험만으로 의미 보존까지 입증하지는 않는다. 저장소 밖 소비자의 존재는 확인하지 않았다.

따라서 이 확대는 현재 정상 CLI/app 호출에서 재현되는 승인 우회가 아니다. 그러나 export 호환 helper의 명시된 wrong-kind 거부가 바뀐 것은 실재한다. **PM 결정:** 직접 제품 호출자가 없어도 이행에서 이동·폐기로 조용히 넓히지 않는다. CLI helper의 옛 wrong-kind 오류·no claim·no side effects를 복원하고 앱 수명은 유지한다. codex-loop가 수정 중이며 검증자는 구현하지 않는다.
