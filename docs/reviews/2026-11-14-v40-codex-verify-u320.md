## L1 — 기존 경계: 이동 계획에서 취소 원천 생성 예외가 잠금 해제를 건너뜀

**낮음. 주입한 취소 원천/등록 예외에서 재현. 기준에도 같으며 일반 기본 CLI 신호 등록의 실제 실패는 재현하지 않았다.** PM에 별도 후속 사항으로 보고했고 C7b에서는 수정하지 않았다.

파일:줄:

- 기준 `src/cli/plan-commands.ts:430`에서 잠금 획득 후 `:432`에서 `io.cancelSignal(...)`을 부른다. 이 호출은 `:520`의 finally가 보호하는 try보다 앞이다. 해제는 `:523`이다.
- 대상 `src/app/apply-life.ts:353`에서 잠금 획득 후 `:355`에서 같은 취소 원천을 만든다. try는 `:360`에서 시작하며 `:427`의 finally/`:430` 해제에 닿기 전에 예외가 나간다.

재현 조건/방법:

1. 합성 scripted 모델로 정상 이동 계획을 만든다. 올바른 digest를 주어 승인 질문 경로를 건너뛴다. 외부 네트워크·키 없음.
2. runApply의 실제 store/엔진 구성은 유지하고 `cancelSignal` 경계에서 합성 등록 실패 예외를 던지게 한다(`edges.mjs`의 `cancel-create-throw`).
3. 기준·대상 모두 engine 호출 0, source 보존, destination 미생성, 등록 실패 예외 전파, **현재 살아 있는 검증 프로세스 소유 잠금 잔류**를 관찰한다. 생성 1회/반환된 취소 원천 없음/해제 호출 경로 미진입이다.
4. 증거 보존 후 검증기는 같은 소유자 runId로 자신의 잠금만 해제했다. 재현 폴더·evidence는 남겼다.

증거: `codex-sec-v40/edges-base/cancel-create-throw/evidence.json`, `edges-head/cancel-create-throw/evidence.json`. 두 semantic 결과는 같다. 실제 signal helper의 등록 예외 전파는 관련 U-296 시험도 확인하지만, 그 시험은 ordinary run이 assembly 전에 거부되는 경로이며 moves apply의 잠금 해제를 입증하지 않는다.

영향과 실제 기본 CLI 도달성:

- 임베딩 호출자가 취소 원천/신호 등록을 구현하다 실패하는 경우, 같은 프로세스가 살아 있는 동안 후속 작업이 잠금에 막힐 수 있다. 데이터 이동·동의 우회는 이 예외 전에 일어나지 않았다.
- 기본 CLI는 고정된 유효 신호 이름과 함수 handler를 process.on에 준다. task·모델·일반 인자로 이를 잘못된 신호/handler로 바꾸는 길은 찾지 못했다. Ctrl+C를 받는 것과 등록 함수가 예외를 던지는 것은 다르다.
- 실제 기본 on/off 연결로 createCancelSource 생성·dispose **100회**를 실행했고 예외와 listener 수 증가가 없었다. 실제 CLI의 취소 파일 경로도 정상 취소되고 잠금이 풀렸다. 따라서 **정상 기본 CLI 신호 등록에서 실제 발생한 결함으로 과장하지 않는다.** process.on 자체가 실패하는 비정상 환경/임베딩 조건의 예외 누락으로 기록한다. 단독 CLI 프로세스가 종료된 뒤에는 잔류 잠금이 stale로 판정될 수 있으므로 영구 잠금이라고 주장하지 않는다.

## 범위·미수행·인계

키 파일·실제 API·네트워크·권한 상승·소스 수정·커밋·push·worktree 추가는 수행하지 않았다. 실제 CLI 자식 환경에는 필요한 Windows 환경과 합성 등록값만 전달했다. 모든 파일·잠금·명령 재료는 자기 archive 사본 안의 합성 자료다. 고정 oracle 전체, 실제 TTY/Ctrl+C, GUI, 실제 비지원 볼륨, 모든 파일 시스템 실패/경쟁 일정은 검증하지 않았다.

PM 지시에 따라 L1은 기존 예외 경계로 별도 기록한다. M1 구현은 수행하지 않으며 U-321 구현 후 독립 검토를 기다린다. C7b 신규 회귀 판단은 확인한 범위에서 0건이고, 병합과 기존 L1의 후속 배정은 PM 판단이다.
