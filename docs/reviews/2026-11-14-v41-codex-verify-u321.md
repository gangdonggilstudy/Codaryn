## 오류·손잡이·교체 경계

독립 store 시험은 이름뿐인 helper 호출을 모의하지 않고 실제 NTFS 합성 파일을 만들고 fs 경계만 바꿨다. 대상 16개 최종 사례를 실행했다. 정상 경로와 일부 원래 결함·잔여 일정은 기준에서도 대조했다.

- open 실패: 열린 손잡이 없음, 기록 보존, 잠금 해제.
- open 뒤 fstat 실패: 확보한 손잡이 close 1회, 기록 보존, 잠금 해제.
- 로그 열기 직전 다른 inode의 hard link로 교체: 열린 파일의 신원/링크 수 검사에서 거부, 바깥 sentinel 보존, close 1회.
- 로그 open 뒤 경로를 다른 hard link로 교체: 이름과 손잡이 신원 대조에서 거부, 같은 보존/정리 결과.
- 삭제가 시작된 뒤 로그 경로를 바깥 sentinel의 hard link로 교체: 마지막 검사에서 append하지 않음. 이미 끝난 삭제 결과는 유지되고 바깥 sentinel은 그대로다. 결과를 롤백했다고 답하지 않는다.
- append에서 예외: 실제 삭제 결과 유지, close 1회, 잠금 해제. 원래 best-effort 로그 의미와 같다.
- close를 실제로 마친 뒤 합성 예외: 결과/잠금 해제가 가려지지 않음. **close 자체가 실패해 OS 손잡이가 열린 채 남는 모든 경우를 검증한 것은 아니다.** 구현은 close 거부를 삼키며 무조건 재시도하지 않는다.

소스는 열린 동일 FileHandle을 보존하고 `:829`에서 재검사한 뒤 `:830`에서 그 손잡이로 append한다. `:842`에서 정상·예외 경로의 close를 시도한다. 경로 문자열로 다시 appendFile하는 이전 방식으로 돌아가지 않았다. 이미 들어간 삭제·표식·보관함 규칙은 확대하지 않았다.

## R2 — 마지막 검사와 FileHandle append 사이에 hard link 추가

**기준/대상 모두 바깥 alias에 JSON 137바이트가 생김. 새로 생긴 회귀가 아니다.** 바깥의 기존 sentinel을 덮어쓴 시험은 아니며, 공격자를 흉내 낸 작업이 새 alias를 만든 뒤 cleanup의 append가 그 alias에서도 보이는 일정이다.

1. 정상 디렉터리와 선택된 기록을 만든다. 대상은 새 로그를 nlink 1인 파일로 열어 검증한다.
2. 대상의 최종 `log.check`가 완료된 직후 `handle.appendFile`이 실제 바이트를 쓰기 전에 멈춘다.
3. 열린 로그 inode에 대한 새 hard link `outside/linked-log`를 만든다.
4. 원래 append를 계속한다.

대상에서 같은 FileHandle을 사용하는 것은 경로 교체를 막는 데 도움이 되지만, 마지막 nlink 검사 뒤 새 alias가 생기는 것을 막지는 않는다. 선택된 기록 1개를 지우는 이 합성 fixture에서 JSON은 137바이트였고 outside/linked-log에서 그대로 읽혔다. 기준도 원래 경로 append 바로 전에 동일 alias를 추가하면 같은 137바이트(시각만 다름)가 기록됐다. 기존 outside/sentinel의 `ORIGINAL` 한 줄은 두 판 모두 보존됐다.

근거: 대상 `src/store/cleanup.ts:829`과 `:830` 사이. 기준 `:749`의 append 직전과 대조했다. 자료: `edges-base-residual/link-before-append`, `edges-head-final/link-before-append`.

R1/R2는 로컬 fs 호출 경계에서 결정적으로 멈춘 재현이다. 비협조적 로컬 프로세스가 할 수 있는 rename/junction/link 작업을 사용했지만, 무작위 경쟁의 발생률이나 일반 사용에서의 빈도를 측정한 것은 아니다. Codaryn 잠금은 이런 비협조적 변경자를 막지 않는다. 부모 핸들 기반 원자적 경계나 링크 생성 통제를 구현한 판이 아니며, 단순 반복 검사만으로 보편적인 race safety를 증명할 수 없다.

## 관련 시험과 건너뜀

대상 빌드에서 관련 7개 진입 파일을 실행했다. **44건 중 42 통과 / 실패 0 / 건너뜀 2 / todo 0, 3,136.547ms.**

건너뜀은 다음과 같다.

- 파일 심볼릭 링크 생성 EPERM. 하드 링크·디렉터리 정션은 실제로 구성해 시험했다.
- 로그 손잡이가 열린 뒤 부모 디렉터리 rename을 Windows가 거부함. 따라서 그 시험이 “부모 교체를 구현이 찾아 막았다”는 증거는 아니다. 시험은 열린 손잡이를 정리한 뒤 skip 처리했다. 독립 R1은 로그 open 이전의 가능한 교체를 사용했다.

새 교체 시험 중 before-open/after-open은 실제 교체가 성공한 후 거부됨을 확인했다. 이것을 건너뛴 parent-after-open 시험과 합쳐 전부 통과한 것으로 기록하지 않는다.

## 판단 범위와 다음 단계

분기 판에서 사전에 준비된 상태 정션·로그 하드 링크와 실제 시험한 open 전/후 교체를 거부했고, 거부 전 선택 기록을 보존했다. 정상 출력·삭제 범위와 기존 lock/digest 우선순위가 유지됐다. **지정된 한정 수정의 목적은 충족했으나 R1/R2 외부 쓰기까지 해결한 판은 아니다.** 이를 감수한 범위의 채택 여부는 PM 판단이다. 범위가 경쟁 완전 차단으로 바뀌면 이 보고를 승인 근거로 사용할 수 없다.

최종 통합 판이 오기 전 분기 증거를 먼저 제출한다. 실제 API·키 파일·외부 네트워크·권한 상승·제품 소스 수정·커밋·push·worktree 추가·전체 시험은 하지 않았다. 모든 바깥 대상도 자기 archive 작업 폴더 안의 합성 자료다. 최종 통합 판 및 Windows 외 OS/볼륨 검증은 미수행이다.
