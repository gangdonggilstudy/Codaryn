### seq별 boxed error와 겹치는 append

`src/app/app.ts:955`의 Map은 apply 호출 하나에만 속하고 **저장된 숫자 seq**를 키로 쓴다. `:957`에서 가린 record의 seq를 전달 전에 잡고, deliverApply의 첫 getter가 던진 값을 **`{ value }` 상자**로 저장한다. `:987`의 각 append는 자기 deps.journal.append가 돌려준 stored.seq로만 조회하고, `:991`에서 삭제한 뒤 원래 value를 재던진다.

따라서 저장값이 undefined/null이어도 Map 조회 결과는 상자 객체라서 “오류 없음”과 구분된다. 한 append가 다른 seq의 실패를 가져가는 공유 last-error 슬롯도 없다. 겹친 Promise의 완료 순서가 달라도 각 저장 seq에만 대응한다. 지워진 실패가 다음 append로 넘어가지 않는다.

`src/app/apply.ts:42`의 첫 getter는 기존에도 callback catch 밖이어서 append를 실패시킬 수 있었다. 두 번째 getter/함수 호출의 예외는 기존 try/catch가 삼킨다. 이행은 기존 경계를 보존한 것이며 관찰자 getter의 과거 동작을 새 결함으로 세지 않았다.

U323 새 시험 9개를 실행했다. 마지막 시험(`tests/unit/app/u323-apply-direct.test.ts:162`) 안의 **undefined/null/Error × hidden-first 여부 = 6조합**은 동시에 append한 세 항목에서 해당 Promise만 같은 reason identity로 rejected되고 다른 Promise는 fulfilled임을 확인한다. plan_item_started는 전달하지 않는 저장 전용 항목이며, 이 항목의 append가 다른 seq의 오류를 가져가지 않는다. 6조합은 57개 시험 수와 별도의 내부 반복 수다.

### 중복 가림 여부

새 journal wrapper(`src/app/app.ts:985`)는 오류를 재던지고 close를 전달할 뿐 **mask나 observer를 다시 붙이지 않는다**. moves의 앱 이벤트 재가림은 기존 applyLife의 observedApplyJournal(`src/app/apply-life.ts:224`) 한 곳이다. 옛 app의 applyJournalWithEvents 호출을 제거했다. changes는 observer 없는 appRunHooks가 journal을 그대로 넘기고 carryingEnvironment(`:549`, `:563`)가 한 번 관찰한다. appRunHooks.ended에는 observer가 없어 추가 notice도 재전달하지 않는다.

엔진의 자유 글 가림과 앱의 화면용 재가림은 원래 별개 층이다. 이번 검토는 **앱 이벤트 래퍼의 중복 부착이 없음**을 확인한 것이며 가림 호출 자체가 전체 엔진에서 한 번뿐이라는 주장이 아니다. 실제 event/journal 값·seq·field 순서와 notice가 기존 oracle과 일치했다. 별도 전역 mask 호출 계수기를 제품에 추가하지 않았다.
