# Codaryn 단계별 계획

현재 상태: **단계 1a 진행 중.** 단계 0은 완료했고 사용자의 연속 개발 지시에 따라 최소 CLI의 기반 작업에 착수한다. 코드·테스트의 검증 결과는 수행한 뒤 기록한다. 실제 API 검증(1b)은 미착수다.
일정과 비용은 정하지 않았다. 단계 전환과 후보 채택은 Codex가 판단한다. 이 계획의 설계 선택은 2026-11-12 Codex가 검토해 채택했다. 구조는 [architecture.md](architecture.md), 근거는 [decisions.md](decisions.md)를 따른다.

| 단계 | 내용 | 상태 |
| --- | --- | --- |
| 0 | 문서와 설계 | 완료 |
| 1 | 최소 CLI | 1a 오프라인 검증 완료(2026-11-12, 임시 PM 채택). 1b는 제공자 구현과 모의 API 검증까지, 실제 호출 미수행 |
| 2 | 코드 수정·검증 반복 | 미착수 |
| 3 | 자기 소스 후보 개발 | 미착수 |
| 4 | 범용 작업 확장 | 미착수 |
| 5 | GUI·IDE | 미착수 |

## 단계 0. 문서와 설계

- 입력: 사용자 확정 요구, 관리자 작업 지시.
- 산출물: docs 아래 설계·계획·결정·민감정보·테스트·페르소나·절차 문서.
- 완료 기준: 검토에서 확인한 문서 간 충돌을 해결했다. 확정·선택·미정이 구분되어 있다. 단계 1 범위와 유닛 테스트 우선순위를 정했다. Codex가 검토해 통합하고 완료를 기록했다.
- 검토 결과: 등록 비밀 우선 처리, 복원 권한과 미해결 토큰 거부, 치환 후 기록, 정상 교체와 파괴적 덮어쓰기 구분, 원문 스냅샷 접근 경로를 문서와 테스트 사례에 맞췄다. Claude 세 세션이 최종 지침을 읽고 역할·격리·커밋·테스트 원칙을 확인했다. 로컬 문서 링크와 코드 블록, Claude 귀속 설정을 확인했다.
- 미포함: 코드, 패키지 설치, API 호출, 외부 발송.

## 단계 1. 최소 CLI

단계 1은 도구 호출을 반복해 작업을 한 번 수행하고 검증 결과를 보고하는 데까지다. 검증이 실패하면 `failed`로 끝난다. 두 하위 상태를 따로 기록한다.

| 하위 상태 | 내용 | API 키·모델 설정 |
| --- | --- | --- |
| 1a 오프라인 검증 | 구현과 [유닛 테스트](unit-test-plan.md), 모의 모델 기반 자동 테스트 | 필요 없음 |
| 1b 실 API 검증 | 실제 Anthropic 호출로 같은 작업 실행 | 로컬 키와 명시적 모델 필요 |

- 입력: 통합된 단계 0 문서, 단계 시작 지시. 1b에만 로컬 API 키와 명시적 모델 설정(O-1 결정 후).
- 산출물:
  - 엔진, 모델 인터페이스와 모의 모델, Anthropic 어댑터, 도구 네 개(읽기, 목록/검색, 쓰기, 허용 목록 명령), 권한별 정책, 가림본 실행 기록, 잠금, 취소.
  - 검증기 두 종류(명령 종료 코드, 파일 존재·내용 규칙).
  - 치환 게이트의 자리와 좁은 규칙.
- 완료 기준 1a (키 없이 전부 실행 가능해야 한다):
  - 임시 디렉터리에서 작은 코드 수정 작업 하나와 문서 작성 작업 하나가 모의 모델과 같은 엔진으로 끝까지 실행된다.
  - 문서 작업 경로가 Git이나 테스트 러너 없이 동작한다.
  - 허용 루트 밖 경로, 허용 목록 밖 명령, 파괴적 동작이 거부되는 것을 테스트로 확인한다. 네트워크를 쓰는 도구가 없다는 것만 확인하며 네트워크 차단을 확인했다고 적지 않는다.
  - 도구 결과가 치환된 뒤에만 기록되는 것, 복원 허용 필드가 아닌 인자의 토큰이 복원되지 않는 것, 복원 뒤 실효 인자가 재검증되는 것을 테스트로 확인한다.
  - 읽은 뒤 바뀐 파일을 덮어쓰지 않는 것, 검증 실패 시 `failed`로 끝나는 것을 테스트로 확인한다.
  - 모델 설정이나 키가 없을 때 실제 호출 경로가 호출 없이 거부된다.
- 완료 기준 1b: 1a의 두 작업을 실제 API로 실행한 결과를 모의 테스트 결과와 구분해 기록한다. 수행하지 않았다면 "1b 미수행"으로 적고 단계 1 전체를 완료로 표시하지 않는다.
- 미포함: 검증 실패를 반영한 자동 재수정(단계 2), 대화형 세션, 병렬 도구, 웹 접근, MCP·확장, 자동 재개, 문맥 압축, 자기 수정.

## 단계 2. 코드 수정·검증 반복

단계 1과의 경계: 단계 1은 검증 결과를 보고하고 멈춘다. 단계 2는 실패 근거를 문맥에 넣어 다시 수정하는 반복을 더한다. 단계 1과 같이 오프라인 검증(모의 모델로 반복·한도·중단 논리 확인, 키 불필요)과 실 API 검증을 따로 기록한다.

- 입력: 단계 1 CLI(반복 논리의 오프라인 구현은 1a 완료로 시작할 수 있다), 실패하는 테스트가 있는 연습용 저장소(Codaryn 자신이 아님). 실 API 검증에만 키와 명시적 모델.
- 산출물:
  - 수정 → 테스트 → 실패 출력 반영 → 재수정 반복.
  - 반복·토큰·시간 한도와 한도 초과 보고.
  - 실행별 변경 집합과 되돌리기.
  - 테스트 출력 절단 규칙.
- 완료 기준:
  - 오프라인: 모의 모델로 실패 → 재수정 → 통과, 한도 초과 중단 경로가 각각 재현된다.
  - 실 API: 준비한 연습 과제 묶음에서 반복이 한도 안에 통과로 끝나거나, 실패 이유와 함께 멈춘다. 과제 수와 합격 기준은 testing.md에서 정한다.
  - 한도 초과, 취소, 테스트 명령 시간 초과가 각각 정해진 상태로 끝난다.
  - 모델이 테스트 파일이나 검증 설정을 고쳐 통과시키려는 경우를 보호 경로 정책으로 막는 것을 확인한다.
  - 보고서가 "지정한 테스트 통과"라고만 말한다.
- 미포함: 자기 소스 수정, 여러 저장소 동시 작업, 자동 커밋·push, PR 생성.

## 단계 3. 자기 소스 후보 개발

- 입력: 단계 2의 오프라인·실 API 검증을 모두 통과한 실행본(채택 커밋 고정), 후보용 worktree와 브랜치, 후보 허용 루트 밖의 보호된 검증기, 관리자가 정한 작은 과제.
- 산출물:
  - 실행본이 후보 worktree에서 자기 소스를 수정하는 절차.
  - 보호 대상 해시 확인.
  - 후보 보고서(변경 내용, 검증 결과, 한도 사용량, 검사하지 않은 범위).
- 완료 기준:
  - 실행본·검증기·정책 파일에 대한 도구 쓰기 시도가 거부된다. worktree는 OS 경계가 아니므로 이것을 격리 보장으로 적지 않는다.
  - 보호 대상이 바뀐 상태에서는 검증이 무효 처리된다.
  - 과제 하나 이상에서 후보가 만들어지고 보호된 검증을 거쳐 보고서가 나온다.
  - 채택 또는 반려는 Codex가 결정하고 기록한다. 자동 교체는 없다.
- 한도: 과제마다 재시도 횟수, 실행 시간, 토큰 상한을 설정으로 둔다. 값은 Codex가 과제별로 정한다. 한도 없이 실행하지 않는다. 초과 시 후보를 보존하고 멈춘다.
- 미포함: 무인 연속 자기 개선, 자동 병합, 검증기 자체의 자기 수정, 과제 자동 선정.

## 단계 4. 범용 작업 확장

- 입력: 안정된 엔진과 계약, 단계 1의 문서 작업에서 얻은 계약 수정 사항.
- 산출물:
  - 문서 작성, 파일 정리, 자료 분석 워크플로(각각의 도구 묶음과 검증기).
  - 실행 전 계획 확인.
  - 네트워크·파괴적 동작의 확인·기록 절차.
- 완료 기준:
  - 각 워크플로가 엔진 코드 변경 없이 등록만으로 추가된다. 엔진을 고쳐야 했다면 그 이유를 결정 기록에 남긴다.
  - 파일 정리는 계획 확인 없이는 이동·삭제하지 않는다.
  - 자동 검증이 없는 작업은 "검증 없음" 또는 사람 확인으로 끝난다.
- 미포함: 메일·메신저 발송 같은 외부 발송 도구(별도 결정 필요), 일정 실행, 다중 사용자.

## 단계 5. GUI·IDE

- 입력: 어댑터 경계가 지켜진 엔진, GUI 형태와 지원 OS 결정.
- 산출물: GUI 어댑터, VS Code 연동 어댑터.
- 완료 기준: 두 어댑터가 CLI와 같은 엔진·정책·기록을 쓴다. 어댑터에 작업 논리가 없다. 확인 질문과 취소가 CLI와 같은 의미로 동작한다.
- 미포함: 엔진 원격 실행, 계정·동기화 서비스.

## 앞당겨 고려하는 것

코딩 외 작업은 단계 4의 주제지만, 계약의 일반성은 일찍 확인해야 한다. 단계 1에 문서 작성 작업 하나를 넣고 단계 2에서도 유지한다. 이 작업의 목적은 기능 제공이 아니라 엔진에 Git·테스트 가정이 섞였는지 드러내는 것이다.

## 단계 전환 규칙

- 앞 단계의 완료 기준을 실행 결과로 확인한 뒤에만 다음 단계를 시작한다. 실행하지 않은 항목은 미완료다.
- 완료 기준을 바꿔야 하면 구현으로 우회하지 않고 Codex에 알린다.
- 테스트 통과는 채택의 필요 조건일 뿐이다. 변경 검토와 충돌 확인을 대체하지 않는다.
