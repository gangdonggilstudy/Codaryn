# 자기 개발 절차

Codaryn이 자기 소스를 고치는 절차의 설계와 현재 상태를 적는다. 설계 근거는 [architecture.md](architecture.md) 7절, [roadmap.md](roadmap.md) 단계 3, [단계 3 작업 지시](work-orders/phase-3-self-development.md)의 결정 U-1~U-8이다.

> 현재 상태(2026-11-12): 기구를 오프라인으로 만드는 중이다. **실제 Anthropic API로는 한 번도 실행하지 않았고, 실제 자기 개발도 하지 않았다.** roadmap 단계 3의 입력 조건(오프라인·실 API 검증을 모두 통과한 실행본)은 아직 충족되지 않았다. 아래에서 "설계"는 정한 방향, "현재"는 코드와 테스트로 확인한 동작이다.

## 1. 세 가지를 분리한다

| 역할 | 위치 | 바꾸는 주체 | 현재 집행 수단 |
| --- | --- | --- | --- |
| 실행본 | 채택 커밋에서 빌드한 CLI. 후보 밖 | PM(사람)이 채택 뒤 교체 | 준비 스크립트가 후보와 설정 위치를 설치 위치 밖으로 강제. 실행 시 거부(U-3)는 구현 중 |
| 후보 | `candidate/<이름>` 브랜치의 별도 worktree | 실행본이 작업으로 수정 | 파일 도구는 task의 `workspaceRoot` 안만 접근 |
| 보호된 검증기 | 후보 밖의 설정·task 파일, 검증기 명령, 후보 안의 보호 경로, `integrity.paths` | 사람만 | 보호 경로는 파일 도구 쓰기 거부. 명령에 의한 변경 탐지(U-1, U-2)는 구현 중 |

- 설계: 후보 코드가 자기 합격을 판정하지 않는다. 합격 판정은 사람이 정한 검증기로만 하고, 채택·병합·교체는 사람이 한다. 자동 교체는 없다.
- 현재: 엔진은 Git을 쓰지 않는다. 커밋, 병합, 교체를 하지 않으며 변경은 후보 디렉터리에 파일로 남는다.

## 2. 순서

1. **후보 준비(사람)**: `scripts/new-candidate.mjs`로 worktree, 브랜치, 설정·task 틀을 만든다(3절).
2. **설정 편집(사람)**: 설정 틀의 `model`, 한도, `policy`, `verifiers`, `integrity.paths`와 task 틀의 `goal`을 채운다. 후보에는 추적 파일만 있으므로 검증기에 의존성이 필요하면 사람이 후보에 설치한다(예: `npm ci`, 네트워크 사용).
3. **실행(사람이 시작, 실행본이 수행)**: 후보 밖의 실행본으로 task를 실행한다.

   ```powershell
   node <실행본>\dist\src\cli\main.js run --task <설정 디렉터리>\<이름>.task.json `
     --config <설정 디렉터리>\<이름>.config.json --vars-file <작업 공간 밖의 변수 파일>
   ```

   `--env-file`은 Codaryn 옵션이 아니다(Node가 먼저 읽는다). 키는 사용자 환경 변수나 `--vars-file`로만 준다.

4. **보고서**: 설계는 `codaryn report --workspace <후보> --run <runId>`(U-5, 구현 중)가 상태, 검증기 결과, 변경 목록, 사용량, 검사하지 않은 범위를 사람이 읽는 형태로 낸다. 현재는 stdout의 JSON 한 줄과 후보의 `.codaryn/runs/<runId>/result.json`, `journal.jsonl`을 읽는다.
5. **PM 검토(사람)**: 보고서, `git -C <후보> status`·`diff`, 보호 경로와 검증 설정의 변경 여부를 본다. 필요하면 보호된 검증을 사람이 다시 실행한다.
6. **병합(사람)**: 채택하면 PM이 후보 브랜치에 커밋하고 다른 작업 브랜치와 같은 검토를 거쳐 main에 병합한다. 실행본 교체는 병합한 커밋을 다시 빌드하는 것이다. 반려하면 후보를 지운다(`git worktree remove`, 브랜치 삭제).

## 3. 후보 준비 스크립트 (U-4, 현재: `claude/core-tools`에 구현, 병합 전)

```powershell
node scripts/new-candidate.mjs --repo <저장소> --name <이름> --out <후보 디렉터리> --state <설정 디렉터리> [--dry-run]
```

- **하는 일**:
  - `--repo`의 HEAD 커밋에서 `git worktree add -b candidate/<이름> -- <후보> <커밋>`을 실행한다. 커밋하지 않은 변경과 Git이 무시하는 파일(`.env` 등)은 후보에 없다.
  - 설정 디렉터리에 `<이름>.config.json`과 `<이름>.task.json`을 만든다. 설정 디렉터리가 없으면 만든다.
- **틀의 내용**: 그대로는 실행용이 아니다. 사람이 편집한다.
  - 공통: 모델 자리표시자 `<모델 ID>`, 출력 상한 4096. 한도는 턴 12, 도구 호출 24, 토큰 150000, 30분, `maxRepairAttempts` 2, `maxSameFailures` 2.
  - 정책: 허용 명령 없음, 빈 `integrity.paths`. 검증기는 기준 커밋에 `package.json`이 있으면 `npm test`(15분), 없으면 없다.
  - 보호 경로 제안: `tests`, `scripts`, `.github`, `package.json`, `tsconfig.json`, `.git`(후보의 Git 연결 파일), `.npmrc`(npm 실행 방식), `node_modules`(검증 도구). 기준 커밋 최상위의 검증·의존성 설정 파일(`tsconfig.*.json`, 잠금 파일, ESLint·Jest·Vitest·Mocha·c8·nyc 설정 등)도 넣는다.
  - task 틀: `workspaceRoot`는 후보의 절대 경로다. `limits`는 넣지 않아 설정 파일 값을 쓰며, 설정 파일 없이(`--config`도 `CODARYN_CONFIG`도 없이) 실행하면 한도가 없어 `invalid_task`로 멈춘다. 정책과 검증기는 설정 틀과 같다.
- **멈추는 경우(종료 코드 1, 아무것도 바꾸지 않음)**:
  - 후보 디렉터리가 이미 있다(빈 디렉터리 포함). 그 경로가 worktree로 등록되어 있다.
  - `candidate/<이름>`이나 충돌하는 ref(`candidate` 브랜치, 그 아래 ref)가 있다. 틀 파일이 이미 있다.
  - 후보가 저장소, 그 worktree, Git 디렉터리, CLI 설치 위치 안이다. CLI 설치 위치는 스크립트가 속한 패키지 루트다. 링크와 junction은 실제 경로로도 비교한다.
  - 설정 디렉터리가 후보, 저장소, 그 worktree, CLI 설치 위치 안이다.
  - `--repo`가 work tree의 최상위가 아니거나 커밋이 없다.
- **사용 오류(종료 코드 2)**: 이름은 영문 소문자·숫자·하이픈 1~40자이고 Windows 장치 이름(`con`, `nul` 등)은 안 된다. 모르는 옵션, 반복 옵션, 빠진 옵션도 사용 오류다.
- **`--dry-run`**: 모든 검사를 하고 실행할 Git 명령과 두 틀의 내용을 출력한다. 아무것도 만들지 않는다.
- **실패 시 정리**: `git worktree add`가 실패하면 이번에 만든 틀 파일과 설정 디렉터리를 지운다. Git은 이때 브랜치를 남긴다(Git 2.53에서 확인). 스크립트는 그 브랜치가 아직 기준 커밋을 가리킬 때만 지운다.
- **실행 방식**:
  - Git은 셸 없이 실행한다. 저장소 위치를 바꾸는 환경 변수(`GIT_DIR`, `GIT_WORK_TREE` 등)는 넘기지 않는다.
  - 키, `.env`, 비밀을 읽거나 만들지 않는다. 저장소의 Git 설정과 훅은 끄지 않는다.
- **확인 범위**:
  - 유닛 14건이 임시 디렉터리의 작은 Git 저장소로 실제 프로세스를 실행한다. 대상은 생성, 기존 대상 보존, 위치 거부, 사용 오류, 실패 정리다.
  - 생성된 두 틀은 CLI의 설정·task 검사를 통과한다. 단 `integrity`는 제외했다.
  - Windows, Git 2.53.0.windows.2, Node 26.13에서만 확인했다.
- **주의**: 현재 main의 CLI는 설정 파일의 `integrity` 필드를 모르는 필드로 보고 `invalid_config`로 멈춘다(확인함). 이 필드는 무결성 확인 계약(U-1, 구현 중)이 병합된 뒤에 쓸 수 있다.

## 4. 구현 상태

| 항목 | 상태 |
| --- | --- |
| 후보 준비 스크립트(U-4) | 구현, 병합 전 |
| 파일 도구의 접근 범위를 `workspaceRoot`로 제한 | 구현 |
| 보호 경로(`policy.protectedPaths`) 쓰기 거부 | 구현. 파일 도구만 막는다 |
| 검증 실패 뒤 재수정 반복(`maxRepairAttempts`) | 구현. 오프라인·모의 API로만 확인 |
| 보호 대상 무결성 확인과 `needs-input`/`protected_changed`(U-1, U-2) | 구현 중 |
| 실행본 설치 위치와 겹치는 작업 공간 거부(U-3) | 구현 중 |
| `codaryn report`(U-5) | 구현 중 |
| `doctor`, 도움말·버전, 진행 표시(U-6~U-8) | 구현 중 |
| 모의 모델로 하는 자기 개발 예행 | 구현 중 |
| 실제 API로 실행 | 하지 않음 |
| 실제 자기 개발 | 하지 않음 |
| OS 수준 격리 | 없음(범위 밖) |

## 5. 한계

- **worktree는 보안 경계가 아니다.** 변경을 나누는 수단일 뿐이다.
  - 후보에서 실행되는 명령과 검증기는 사용자 권한으로 돈다. 후보 밖의 파일과 네트워크에 접근할 수 있다.
  - 후보는 원래 저장소와 Git 객체와 ref를 공유한다.
  - 파일 도구의 쓰기 제한은 도구 정책으로만 집행된다.
- **검증기 명령은 후보 코드를 실행한다.** 검증기는 기본으로 후보 루트에서 실행된다.
  - 예를 들어 `npm test`는 후보의 `package.json` 스크립트, 테스트, 소스, 설치된 의존성을 실행한다. 후보 코드가 검증 결과에 영향을 줄 수 있다.
  - 보호 경로는 파일 도구의 쓰기만 막는다. 허용된 명령이나 검증기 자체가 바꾸는 것은 무결성 확인으로 사후 탐지하는 설계이며, 아직 구현 중이다.
  - 설계상 무결성 확인은 검증 직전과 직후의 해시를 비교한다. 그 사이에 바꿨다가 되돌린 것은 탐지 대상이 아니다.
- **무인 실행 금지.** 실제 API로 실행한 적이 없으므로 모델이 실제로 이 절차를 따르는지, 한도가 적당한지 모른다. 첫 실행은 사람이 지켜보는 작은 과제로 한다.
- **스크립트 검사는 실행 시점 기준이다.** 검사와 생성 사이에 다른 프로그램이 같은 경로나 브랜치를 만들 수 있다.
  - 틀 파일은 배타 생성으로 쓰므로 덮어쓰지 않는다. 이 경합 경로는 테스트하지 않았다.
- **보호 경로 제안은 출발점이다.** 저장소마다 검증에 쓰는 파일이 다르므로 사람이 목록을 고친다.
