## 1. 원칙

- [요구] 유닛 테스트도 구현 효율을 위해 설계해서 진행한다.
- [설계] 유닛 테스트는 그 계약의 구현보다 먼저 또는 같은 변경 단위에서 쓴다. P0 사례가 없는 기능은 완료로 보지 않는다.
- [설계] 결함을 고칠 때는 검토 보고서의 재현 입력으로 **실패하는 회귀 시험을 먼저** 추가하고, 고치기 전 코드에서 실패하는 것을 확인한 뒤 고친다. 기존 시험을 약하게 하거나 지우거나 건너뛰게 하지 않는다.
- [설계] 통과는 그 시험이 검사한 범위의 증거다. 보고에는 검사한 것과 검사하지 않은 것을 함께 적는다. 보안이나 정확성 전체의 보장을 주장하지 않는다.
- [설계] 실행하지 않은 시험과 API 호출을 성공으로 기록하지 않는다. 건너뛴 항목은 건너뛰었다고 적는다.
- [설계] 판정은 후보가 보고한 문장이 아니라 관찰 가능한 결과로 한다: 종료 코드, stdout JSON, 파일 바이트, journal.

## 2. 검증 층

[설계] 층을 섞지 않고 보고에서도 따로 적는다.

| 층 | 실제로 쓰는 것 | 대신 넣는 것 | 위치 | 상태 |
| --- | --- | --- | --- | --- |
| 유닛 | 대상 함수와 메모리 자료, 필요하면 임시 폴더의 실제 파일 | 시계, 난수, 전송(`fetch`), 실행기, 파일 계층 일부, 프로세스 생존 판정 | `tests/unit/<모듈>/` | 구현 |
| 엔진 대역 | 엔진과 계약 | 모델, 가림 게이트, 정책, 도구, 검증기, journal, 시계 대역(`tests/unit/engine/fakes.ts`) | `tests/unit/engine/` | 구현 |
| 프로세스 통합 | 빌드한 CLI(`dist/src/cli/main.js`) 실제 프로세스, 실제 파일 시스템, 실제 자식 프로세스 | 모델은 대본 제공자 | `tests/integration/` | 구현 |
| 모의 API | 위와 같음 + 127.0.0.1의 가짜 Messages API 서버 | 실제 API | `tests/integration/m01`~`m03`, `p05`, `s01` 등 | 구현. 시험 이름에 `[모의 API·실제 API 아님]` |
| 실제 API | Anthropic API | 없음 | `tests/live/anthropic-live.ts` | 작성됨, **미실행** |
| 자기 개발 예행 | 후보 준비 스크립트, 보호 경로, 무결성 확인, 대본 모델 | 실제 모델 | `tests/integration/k03` | 구현. 실제 자기 개발의 증거가 아니다 |

- 유닛, 통합, 모의 API는 API 키 없이 돈다. 통합의 자식 환경에는 허용된 변수만 넘기고, 키는 실제 키와 구별되는 가짜 값만 쓴다(`tests/support/cli.ts`의 `cliEnv`, `fakeApiKey`).
- 통합 시험은 제품 모듈을 import하지 않는다. 빌드한 CLI와 계약 타입·상수만 쓴다.
- 네트워크 가드(`tests/support/net-guard.ts`)
  - 통합 CLI 프로세스에 `--import`로 넣는다. 전역 `fetch`가 루프백 밖으로 나가면 막고 그 출처를 기록한다.
  - `node:http`·`node:https` 직접 사용은 막지 않는다.
- 완료를 주장할 때는 어느 층까지 실행했는지 적는다. "오프라인 검증 통과", "모의 API 통과", "실제 API 통과"는 서로 다른 주장이다.

| `npm run test:integration` | 빌드 뒤 `node --test "dist/tests/integration/**/*.test.js"` |
| `npm test` | 빌드 뒤 둘 다 |

  - 통합 26개 파일.
  - 도움 파일: `tests/support/` 10개(CLI 구동, 가짜 서버, 누출 검사, 네트워크 가드, 재수정 대본 등), `tests/fixtures/` 6개(실행 시점에 만드는 TypeScript 빌더).

  - 조건부 건너뜀
    - Windows 전용 사례(POSIX에서 건너뜀)
    - 링크·정션이나 8.3 이름을 만들 수 없는 환경
    - Git이 없을 때의 후보 스크립트 사례
- 지울 수도 건너뛰게 할 수도 없는 사례: 개인정보 회귀(`r01`), 잠금 회수(W-4).

## 4. 실제 API 검증 조건

- [요구] 실제 API 검증은 로컬 키, 명시한 모델, 한도가 준비된 뒤 사용자가 직접 실행한다. PM과 작업자는 실행하지 않는다.
- `tests/live/anthropic-live.ts`의 실행 조건과 상한 **구현(미실행)**
  - 세 조건(`CODARYN_LIVE`, `ANTHROPIC_API_KEY`, `CODARYN_MODEL`)이 모두 있을 때만 돈다. 아니면 건너뛴다.
  - 파일 이름이 `.test.ts`로 끝나지 않으므로 npm 스크립트에 들어가지 않는다.
  - 상한은 턴 4, 도구 4, 재시도 1, 출력 토큰 1,024, 총 토큰 30,000, 3분, HTTP 요청 8회다.
- 실행 전 확인
  - 키는 로컬 환경에만 있다. 출력과 기록에 없다.
  - 모델은 설정에 명시하고 결과에 기록한다.
  - 호출·토큰 상한을 넘으면 중단한다.
- 실제 응답은 실행마다 다르다. 판정은 관찰 가능한 결과로 한다.
- 실제 호출에서 확인할 항목: 503 분류, `retry-after` 형식, 빈 `tool_result`, thinking 블록, 시간 초과 뒤 재전송, `anthropic-version` 값, `anthropic-workspace-id` 필요 여부(decisions.md O-13).
- [미정] 사용할 모델, 비용 한도 값, 실행 주기.

## 5. 보호된 검증과 후보

[요구] 검증된 CLI가 별도 후보 worktree에서 자기 소스를 개발한다. [설계] 실행본, 후보, 보호된 검증 자료를 분리한다.

| 구분 | 위치 | 후보의 권한 | 용도 |
| --- | --- | --- | --- |
| 후보 기능 테스트 | 후보 worktree 안 | 추가·수정 가능 | 후보가 자신의 변경을 확인. 채택 근거로는 부족 |
| 보호된 검증 자료 | 작업 공간 안 `protectedPaths`, 작업 공간 밖 `integrity.paths` | 파일 도구로는 쓸 수 없음(R-5). 명령으로 바꾸면 무결성 확인이 탐지 | 채택 판정의 기준 |

**구현된 것**
- 보호 경로 쓰기 거부(R-5, T-13)
- 무결성 확인(U-1, U-2, W-1, W-2)
  - SHA-256 목록을 실행 시작, 검증 전, 검증 후, 끝에 비교한다.
  - 다르거나 확인할 수 없으면 `needs-input`/`protected_changed`다.
- 설치 위치 거부(U-3)
- 후보 틀의 `integrity.paths` 사전 기입(W-3)

**구현되지 않은 것**
- 단계 0의 "테스트 수 감소 탐지"(T1)는 없다. 보호 경로와 무결성 확인이 대신한다.
- 보호된 검증기를 후보 밖 프로세스가 실행하는 구조도 없다. 검증기는 실행본이 후보 작업 공간에서 실행한다.

무결성 확인은 실수와 단순한 변조를 찾는 사후 탐지다. 다음 이유로 악의적인 후보의 침해를 막는다고 표현하지 않는다.
- 같은 사용자 권한의 후보 코드는 검증 도중에만 바꿨다 되돌릴 수 있다.
- 후보 코드는 검증기 프로세스 안에서 판정을 바꿀 수 있다.
- OS 격리가 없다.

채택 보고에는 "검증 자료 무결성은 해시 확인 수준이며 OS 경계로 강제되지 않음"을 적는다.

## 7. 정보유출 검증

[설계] 가짜 비밀(카나리)을 심고 밖으로 나가는 내용 전체를 검사한다. **구현**(`tests/support/leak.ts`, `tests/fixtures/secrets.ts`)

- 심는 위치: 파일 내용, 파일 경로, 환경 변수, 명령 출력, 목표, 모델 출력, 검증기 출력.
- 검사 대상
  - 가짜 서버가 받은 요청 본문 전체와 헤더
  - journal, result.json, stdout, stderr
  - 검색 결과, 재수정 메시지, 되돌리기 출력
- 합격 조건
  - 원문과 정해진 변형, 디코드한 형태, 4자 조각이 0건이다.
  - 토큰은 남아 있다.
  - 키는 `x-api-key` 헤더에만 있다.
- 새 위치 복원 악용: 토큰을 복사, 새 파일, 명령 인자, 경로에 넣으면 거부되고 파일에 원문이 쓰이지 않는다(`a06`).
- 원위치 유지와 스냅샷
  - 보호 줄의 바이트가 그대로다.
  - 원문 스냅샷이 journal, 결과, 모델 요청, 검색 결과에 없다(`p02`).
- 범위의 한계
  - 등록한 카나리와 정해진 변형만 확인한다.
  - 최선 노력 탐지는 없으므로 탐지율을 보고하지 않는다.
  - 실제 API 단계에서도 카나리만 쓴다.

## 8. 작업 유형별 검증기

[요구] 범용 작업 에이전트다. [설계] 공통 엔진은 코드 테스트를 모든 작업의 전제로 삼지 않는다.

**구현된 검증기 종류**(main `f7b878a`)
- `command`: 종료 코드와 출력.
- `file_rules`: 파일 존재와 내용 규칙.
- `data_checks`: 표(CSV, TSV, JSON Lines)의 모양과 집계 대조(VF-04, 단계 4). 근거에는 열 이름, 행 번호, 비교한 두 수만 든다.
- `inventory`: 적용 실행마다 만든다(설정할 수 없음, VF-05). 계획 대상의 해시와 나머지의 경로·크기 목록을 대조하고 자체 상한을 둔다(DR-6).

| 작업 유형 | 검증기 예시 | 확인하지 못하는 것 | 상태 |
| --- | --- | --- | --- |
| 코드 수정 | 테스트 명령 | 테스트가 다루지 않는 동작 | 구현(`a01`, `p01`) |
| 문서 작성 | 필수 항목·형식(`file_rules`) | 서술의 타당성 | 구현(`a02`) |
| 자료 분석 | 스키마, 행 수, 합계 대조(`data_checks`)와 사람 확인(`awaiting_review`) | 방법의 적절성, 해석 | 구현(통합 `n07`, 유닛 `verify/g-data-checks.test.ts`) |
| 파일 정리 | 계획 확인 뒤 적용, 적용 뒤 `inventory` 대조 | 분류 의도 | 구현(통합 `n06`, 유닛 `verify/g-inventory.test.ts`) |

검증기가 없는 작업은 `needs-input`/`no_verifier`로 끝난다. 검증된 것으로 표시하지 않는다. 사람 확인으로 끝나는 작업(`awaiting_review`)도 `done`이 아니다.

## 9. 교차 검토와 병합 전 확인

- **교차 검토**
  - 구현자가 아닌 세션이 읽기 전용으로 한다.
  - 실험은 검토자 worktree의 `.codaryn/` 안에서만 한다. 빌드 사본(`git archive`, `tsc --outDir`)을 쓰고 실제 CLI로 재현한다.
  - 보고서는 `.codaryn/report-*.md`(Git 추적 제외)에 쓴다. 심각도, 파일:줄, 깨지는 입력과 결과, 재현 방법, 문제 없던 범위, 검사하지 않은 범위를 적는다.
  - PM이 원문을 `docs/reviews/`에 보관하고, 고칠 것은 작업 지시서에 결정 번호(S, T, V, W, X)로 정한다.
- **병합 전 확인**(PM)
  - `scripts/review-branch.mjs <브랜치> <소유 경로>...`가 PASS여야 한다. 검사 항목: 작성자, trailer 없음, 소유 범위, 충돌 없음, 공백, 비밀.
  - 내용을 검토한다.
  - main과 합친 트리에서 typecheck, 유닛, 통합을 모두 실행한다.
  - 시험은 review-branch가 돌리지 않으므로 따로 실행한다.
- **비밀 검사 훅**
  - 공용 `.git/hooks/pre-commit`이 `scripts/check-secrets.mjs --staged`와 같은 사본을 돌린다. 모든 worktree에 적용된다.

  - 출력은 파일·줄·규칙 이름뿐이다.
  - 훅은 Git이 추적하지 않는다. 새로 복제하면 다시 설치해야 한다. `--no-verify`는 금지다.
