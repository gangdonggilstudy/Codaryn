# 유닛 테스트 계획

담당 페르소나: 검증 엔지니어(주), 보안·개인정보 검토자(보조).

상태: 2026-11-12, main `349726a` 기준.
- 이 계획의 단계 1~3 사례는 대부분 시험으로 구현됐다(4.0절).
- 유닛 전체는 684건 중 683 통과, 0 실패, 1 건너뜀이다(실측). 실제 API 시험은 실행하지 않았다.
- 문서 기준
  - 모듈 이름과 단계: [아키텍처](architecture.md)와 [단계별 계획](roadmap.md)
  - 검증 층 구분: [테스트 전략](testing.md)
  - 치환과 복원 규칙: [민감정보 처리](privacy.md)
  - 기능별 시험 파일: [구현 위치표](design/implementation-map.md)

표기: **[요구]** 사용자 확정 요구, **[설계]** 관리자(Codex, 위임 기간에는 임시 PM)의 설계 선택, **[미정]** 결정하지 않은 항목.

## 1. 목적과 원칙

- [요구] 유닛 테스트도 구현 효율을 위해 설계해서 진행한다.
- [설계] 유닛 테스트는 해당 계약을 구현하기 전이나 구현과 같은 변경 단위에서 작성한다. 구현 뒤로 미루지 않는다.
- [설계] 대상은 위험 시나리오로 정한다. 커버리지 100%를 요구하지 않고, 수치를 채우려는 저위험 테스트를 만들지 않는다.
- [설계] 통과는 그 사례가 검사한 범위의 증거다. 보호된 검증기와 검증 보장 범위에 관한 규칙은 [테스트 전략](testing.md) §1, §4를 따른다.

## 2. 검증 층과 유닛 테스트의 한계

[설계] 다섯 층을 섞지 않는다. 이 문서는 첫 두 층만 다룬다.

| 층 | 실제로 쓰는 것 | 대신 넣는 것 | 키 |
| --- | --- | --- | --- |
| 순수 유닛 | 대상 함수와 메모리 안 자료 | 없음 또는 시계·난수 | 불필요 |
| 모의 adapter | 엔진과 모듈 연결 | 모델 응답, 명령 실행기, 시계 | 불필요 |
| 실제 프로세스 통합 | CLI 프로세스, 파일시스템, 자식 프로세스 | 모델 응답 | 불필요 |
| 실 API | Anthropic API | 없음 | 로컬 키와 명시 모델 |
| 외부 보호 검증 | 후보 밖의 고정 검증기 | 없음 | 불필요 |

유닛 테스트만으로는 다음을 입증하지 못하며 그렇게 보고하지 않는다.

- 실제 OS 격리와 네트워크 차단.
- 자식 프로세스의 실제 종료와 정리.
- 강제 종료나 전원 차단에서의 파일 원자성, 실제 심볼릭 링크 해석.
- 실제 모델의 응답 형태와 실제 API의 오류 동작.

이 항목들은 실제 프로세스 통합 또는 실 API 층에서 따로 검사한다.

## 3. 우선순위

| 등급 | 기준 | 규칙 |
| --- | --- | --- |
| P0 | 깨지면 비밀 유출, 사용자 자료 손실, 권한 이탈, 틀린 성공 보고로 이어지는 계약 | 해당 기능과 같은 변경에 포함한다. 없으면 그 기능을 완료로 보지 않는다. |
| P1 | 깨지면 잘못된 동작이지만 범위가 좁거나 다른 층에서 드러나는 계약 | 같은 단계 안에 추가한다. |

분기가 없는 전달 코드, 설정 상수, 자료형 정의는 유닛 테스트 대상에서 제외한다.

## 5. 대역과 결정성

- [설계] 대신 넣는 것은 외부 경계뿐이다: 모델, 시계, 난수, 명령 실행기, 전송 계층. 치환, 정책, 상태 기계 같은 내부 모듈은 실제 구현을 쓴다.
- [설계] 파일 동작은 가능하면 임시 디렉터리의 실제 파일로 검사한다. 오류 주입이 필요한 사례(WS-02)만 파일 계층을 대신 넣는다.
- [설계] 결정성은 고정 fixture, 가짜 비밀, 주입한 시계와 난수로 확보한다. 실제 비밀, 실제 시간, 네트워크에 의존하지 않는다.
- [설계] 가짜 비밀은 실제 키 형식과 구별되는 고정 값으로 두어 저장소 검사 도구가 실제 유출로 오인하지 않게 한다.
- 실제로 쓰는 대역(구현)
  - 엔진: `tests/unit/engine/fakes.ts`. 모델, 가림 게이트, 정책, 도구, 검증기, journal, 시계를 대신한다.
  - 도구: `tests/unit/tools/doubles.ts`. 가림 게이트, 작업 공간, 명령 실행기를 대신한다.
  - CLI 단계 3 시험: `tests/unit/cli/k-support.ts`. 대역이 아니라 임시 폴더, 대본 task, 실제 조립을 쓰는 준비 코드다.
  - Anthropic: 주입 `fetch`·`sleep`.
  - 잠금: 파일 계층(`fileSystem`)과 프로세스 생존 판정(`isProcessAlive`, W-4).
  - 무결성: 파일 계층(`buildIntegrityChecker`의 세 번째 인자)과 작은 상한.
- 시스템이 바꿀 수 있는 값에 기대지 않는다. 예: 끝난 프로세스의 pid는 재배정될 수 있으므로 "죽은 pid"는 주입한 판정으로 정한다(W-4).

## 6. 피할 것

- 구현 내부 절차를 그대로 따라 쓰는 테스트. 관찰 가능한 결과(반환값, 파일 바이트, 상태, 기록 내용)로 판정한다.
- 호출 횟수만 확인하는 테스트. "호출이 없다"는 판정은 유출·재실행 방지 사례에만 쓴다.
- 대상 대부분을 대신 넣는 거대한 대역.
- 위험이 낮은 코드에 대한 형식적 테스트.

## 7. 실패와 회귀

- [설계] 새로 발견한 결함은 먼저 재현하는 회귀 사례로 추가한 뒤 고친다.
- [설계] 테스트를 삭제, 건너뛰기, 기대값 완화로 통과시키지 않는다. 기대값을 바꿔야 하면 사유를 변경에 적고 관리자(Codex, 위임 기간에는 임시 PM) 검토를 받는다.
- [설계] 고치기 전 코드에서 회귀 사례가 실패하는지 확인한다. 주입 지점이 없어 그대로 확인할 수 없으면 고친 코드를 일부러 되돌리는 변이 확인으로 대신하고 보고에 적는다.
- [설계] 부하에서만 나는 간헐 실패는 지우거나 건너뛰게 하지 않는다. 먼저 원인(시험의 시간·환경 가정인지, 제품의 진행 보장인지)을 계측으로 가린 뒤 고친다(W-4).
- [설계] 실행 순서는 다음과 같다.
  1. 변경과 관련된 빠른 테스트.
  2. 필수 회귀(P0 전체와 해당 단계의 통합 테스트).
  3. 실 API 검증. 별도 한도 안에서, 명시적으로 켰을 때만 실행한다.

## 9. 경로와 러너(P-1로 확정)

- 러너는 Node 기본 `node:test`와 `node:assert`다. 시험은 TypeScript로 쓰고 빌드한 `dist/tests/`를 실행한다.
- 유닛은 `tests/unit/<모듈>/`, 통합은 `tests/integration/`, 실제 API는 `tests/live/`(npm 스크립트에서 제외)에 둔다.
- 공용 도움은 `tests/support/`, fixture는 `tests/fixtures/`(실행 시점에 만드는 TypeScript 빌더)에 둔다.
- 통합 시험은 제품 모듈을 import하지 않는다.
